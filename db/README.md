# Database: migrations, SQL tests, execution boundary

`migrations/` holds the schema (0001 core, 0002 RLS and grants, 0003 the draft's semantic issues for T-012 / D-028, 0004 the provisioning role for D-042, 0005 the IR stored as the canonical text its hash covers for D-040, 0006 the version's publish comment for D-041, 0007 a job's lifecycle for T-019 / ADR-024). 0005 stops on a database that already holds models: SQL cannot produce the canonical form from jsonb, so a development database is re-created. Until T-006 is accepted they are drafts that have only run on disposable `dt_test_*` databases; from then on a migration applied to any persistent environment is never edited — changes go into a new numbered file.

## Run

Use a fresh disposable PostgreSQL 16 database named `dt_test_*`, a provisioning administrator and no customer data:

```sh
export DATABASE_URL='postgresql://<test-admin>@<disposable-host>/dt_test_handoff'
DT_ALLOW_DB_TESTS=yes make db-test          # roles, up, tests, down, up, tests
GEMINUS_TEST_DATABASE_URL="$DATABASE_URL" make db-go-test   # Go repository tests on the migrated schema
# or both in one step (what CI runs):
DT_ALLOW_DB_TESTS=yes GEMINUS_TEST_DATABASE_URL="$DATABASE_URL" make integration-test
```

The runner refuses a non-`dt_test_*` database or an existing `twin` schema and creates no login passwords. Never point it at shared or production infrastructure; the down migrations are destructive.

### Provisioning a tenant (T-010, ADR-023)

Users and organizations are created by an operator, never through the API (D-008). Give provisioning a login of its own that may act as `twin_provisioner` and is nothing else (D-042). `twin_provisioner` can only read users and insert users, organizations, memberships and system audit events; RLS applies to it, and since RLS reads a scope the role sets itself, a trigger lets it add members and audit events only to the organization its own transaction created (`migrations/0004_provisioner.up.sql`). `cmd/provision-tenant` refuses a login that cannot `SET ROLE twin_provisioner`, one that is a member of `twin_owner`, `twin_api` or `twin_worker` (a superuser is a member of every role), and one with SUPERUSER, BYPASSRLS, CREATEROLE, CREATEDB or REPLICATION:

```sql
CREATE ROLE geminus_provisioner LOGIN NOINHERIT NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB IN ROLE twin_provisioner;  -- NOINHERIT: rights only after SET ROLE; set its password out of band
```

```sh
export GEMINUS_PROVISION_DATABASE_URL='postgresql://geminus_provisioner@<host>/<db>'
go run ./cmd/provision-tenant organization -name 'Acme' -owner-issuer 'https://<tenant>.auth0.com/' -owner-subject 'auth0|…'
go run ./cmd/provision-tenant user -issuer 'https://<tenant>.auth0.com/' -subject 'auth0|…'   # then an owner adds the user by ID
```

The SQL files are rendered from `db/tests/templates/` by `scripts/render_db_tests.py` (`make db-tests-render`; `make spec-check` fails if they are stale), which fills valid ULID test IDs and real RFC 8785 model hashes. Run them on databases with different default collations: CI's PostgreSQL image uses libc `en_US.utf8`; locally an ICU database works (`CREATE DATABASE dt_test_icu TEMPLATE template0 ENCODING 'UTF8' LOCALE_PROVIDER icu ICU_LOCALE 'en-US' LOCALE 'C.utf8'`). For diagnosis, `PGOPTIONS='-c dt.collect=on'` reports every failing case instead of stopping at the first.

## What this does not prove

Concurrent approval (T-013 covers models; proposals follow), API RBAC, artifact access and application schema validation remain separate. Tenant-bound deferred manifest checks must run before transaction-local context is cleared: one application transaction operates on one organization and never changes organization context mid-transaction (the test suites flush deferred checks before switching tenants).
