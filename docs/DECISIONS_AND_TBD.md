## Status and adoption method

`SOURCE` = explicitly decided by the report; `PROPOSED` = a candidate added to form an implementable contract; `TBD` = still undecided in the report.
The candidate details in OpenAPI, Schema and SQL are currently all `PROPOSED`. Parsers, fixtures, tests and spikes may be written first; before the listed gate, a human updates status / approved_by / approved_at in `planning/decisions.json`. A coding agent must not fill in the approver itself.
If documents conflict, first register the conflict and stop the affected changes; the original requirements must not be overridden automatically by "the most recently modified file". For compatibility checks of standard contracts see sources/SOURCE_MAP.md; external standards do not constitute new product requirements.

The cross-document contradictions and undefined behaviors inventoried by T-001 (2026-10-15) are listed in [CONTRACT_BLOCKERS.md](CONTRACT_BLOCKERS.md) (CB-01–CB-36); each item is marked with its corresponding D-entry or NEW; the mapping between tasks and decision gates is generated by `make spec-decisions` into `checks/decisions-check.json`.

## Engineering proposals that need confirmation

### D-001 — Identifiers and field naming

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: Contracts / Platform. Gate: before starting SDK generation or running migrations.**

Source gap (original report pp. 14–19, 24, 29–36): the report's API/IR uses mdl_/mv_/org_ prefixes, while the ER diagram says UUID; Proposal contains both base_model_version_id and base_version_id.

Candidate decision: this draft keeps opaque prefixed string IDs; SQL uses text. HTTP/Proposal standardize on base_version_id; two conflicting aliases must not be accepted. IR schema_version stays 0.1.

### D-002 — Proposal states and trust boundary

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: AI / Platform. Gate: before AI persistence.**

Source gap (original report pp. 23–26, 32–33): the report lists generating, ready, approved, rejected; the prompt requires needs_input, but the example Schema does not fully define it.

Candidate decision: separate the provider output from the server envelope. Add needs_input, invalid, failed, conflicted. The provider must not supply trusted IDs, validation or approval fields; the server binds all of them.

### D-003 — Interaction of publish, review and unpublished Drafts

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: Platform / Product. Gate: before the Version service.**

Source gap (original report pp. 18–19, 27, 31–33): the report requires immutable versions, optimistic concurrency and no silent rebase, but does not say what AI approval does when it meets a dirty draft.

Candidate decision: publish and approve lock the same model row. Approval takes effect only against the published base; a clean draft may be synced to the new version, a dirty draft is kept in full and marked out-of-date. Publishing a stale draft returns 409; reset requires explicit confirmation and If-Match.

### D-004 — Outcome of approving a Scenario Proposal

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: AI / Simulation. Gate: before Scenario development.**

Source gap (original report pp. 19, 23, 33–35, 51): the report says a Scenario is a patch on an immutable version and does not create a canonical ModelVersion; the Scenario Designer has no separate API/persistence contract.

Candidate decision: Proposal mode=edit or scenario. Approving an edit creates one ModelVersion; approving a scenario creates an immutable Scenario and must not add a ModelVersion. For a scenario, the user must start a run separately.

### D-005 — Undefined operational semantics of the DES

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: Simulation. Gate: before golden digests are created.**

Source gap (original report pp. 20–22, 34, 45–46): the report does not fix tick precision, the priority order of simultaneous events, the warmup cohort, bundle acquire, zero-time cycles, or the relationship between queue nodes and process waiting.

Candidate decision: adopt the candidate semantics in SIMULATION_SPEC.md: 1 ms ticks, stable event order, atomic resource bundles, explicit queues as the waiting place of the downstream process, rejection of zero-time cycles.

### D-006 — Hash, dataset freezing and RNG

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: Simulation / Platform. Gate: before version hashes go live.**

Source gap (original report pp. 15–22, 34–35): the report requires a hash, a seed and a deterministic digest; it does not fix the canonicalization, the PRNG, the empirical dataset revision or the engine numerical profile.

Candidate decision: the candidate is RFC 8785 JCS + SHA-256; the IR hash and the dataset manifest are stored separately. A run freezes the dataset content hashes. SIMULATION_SPEC fixes the seed derivation, SplitMix64, the numeric profile and the digest payload.

### D-007 — Initial engineering limits and defaults

**Status: APPROVED (2026-10-15, KCL1104). Responsible role: Platform / Simulation. Gate: before the Alpha / Beta configuration freeze.**

Source gap (original report pp. 7–8, 37, 50): the report gives graph/upload/replication/timeout targets marked TBD, and does not define the event cap, trace cap, lease or idempotency TTL.

Candidate decision: the original report's 500 nodes / 1,000 edges, 50 MB / 100k rows, 1,000 replications and 300 s timeout serve only as initial limit candidates. Also proposed: event budget=10M/run, active entities=100k, trace=100k/run, lease=30s, heartbeat=10s, idempotency TTL=24h; all need benchmarking/review.

Implementation note (T-023, 2026-10-19, awaiting independent review; does not change this decision's status): a run freezes the server's execution limits when it is enqueued (`internal/runs.DefaultLimits`: 300 s, 10M events, 100k active entities, 10k visits, 100k trace events); the client cannot set them. Budget across retries: the wall clock counts from the first start (`execution_deadline_at`); events are granted in batches through durable reservations (by default one tenth of max_events per batch), and the amount reserved by earlier attempts counts as used; for details see API_DATABASE §7 and SIMULATION_SPEC §8. The batch size is an implementation parameter, not part of this decision; it can be tuned after the benchmark (T-037).

### D-018 — LLM credential pool (two independent Anthropic organizations)

**Status: APPROVED (2026-10-15, KCL1104: chose failover). Responsible role: AI / Security. Gate: before the T-024 provider adapter implementation; before any live AI call.**

Source gap: H-001 specifies the Anthropic Claude API and provides two API keys that belong to separate, independent organizations, asking for rotation so that the credits on both sides are used. The original report and AI_SPEC assume only a single provider credential, and do not define multi-account selection, failover, data policy consistency or audit.

Candidate decision: ordered primary→secondary failover. Only 402 `billing_error` (credits used up) or 401/403 (key invalid/revoked) marks that credential as unavailable and switches; 429/529/5xx are retried only on the same credential with the SDK backoff, not across organizations, so as not to effectively combine the rate limits of the two organizations (whether this complies with Anthropic's terms needs human confirmation). A key appears only as a label in proposal/analysis/audit; the adapter injects the key explicitly and does not rely on `ANTHROPIC_API_KEY`; the retention/ZDR settings of the two organizations must match and be written into the data policy; keys are stored only in the secret manager.

T-024 implementation (2026-10-19, [ADR-027](adr/ADR-027-ai-provider-adapter.md) ACCEPTED (H-019); this resolution's status is unchanged): `internal/ai/provider/anthropic` tries `org-a` (`GEMINUS_ANTHROPIC_API_KEY_A`) and then `org-b` (`_B`) in order; 401/402/403 marks that credential as unavailable and moves to the next key (`failed_over_from` is recorded in metadata, and also on every later call that skips it); for 401/403 this lasts until the process restarts, for 402 the key rests 15 minutes and is then tried again (T-024 review, ADR-027); when both keys are unavailable it returns `credentials_exhausted`; 408/409/429/5xx (including 529) and connection errors are retried only by the SDK on the same key (`MaxRetries` of the budget). Keys are injected through config, and the adapter does not read environment variables; errors and metadata carry only the label. Tested only against a local httptest server; any live call still awaits owner approval of the model, quota and data policy (H-017), and the approved list in the config is empty. A 401/403 key is not re-probed (changing a key means restarting the process).

#### D-050 — Preventing and detecting deadlock and starvation

**Status: APPROVED (2026-10-20, KCL1104, H-018: 「全都照建議」 ("Follow all the recommendations")). Responsible role: Simulation. Gate: before T-046 phase 2; before T-047–T-050 implementation; the T-051 template must pass.**

Question: how are cyclic blocking and "a bundle that can never be assembled" (the review's two counterexamples: a bundle whose shift calendars do not overlap, and constant failures in opposite phase) prevented and detected with typed errors, and how far does the guarantee go?
