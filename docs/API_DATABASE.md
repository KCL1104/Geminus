## 1. Contract files and naming

`openapi/openapi.yaml`: OpenAPI 3.1.1, base `/v1`; it uses local external `$ref` pointing to `schemas/` and does not redefine the Model IR. `planning/api-operations.json` lists all operations with their SOURCE/PROPOSED origin. The added listing/scenario/membership/download/reset/analysis-read endpoints all have x-origin=PROPOSED, which marks that they are not in the original report's endpoint list (a source marker, not an approval status; D-012 is approved).

schemas/model-ir, proposal-output, proposal, scenario, simulation, analysis, canonical-event, ai-mapping, import, dataset-snapshot, http, common and json-patch each have a clear responsibility. The stored `ai_proposals.patch` maps to HTTP `changes`; model_versions.hash maps to API `hash` / run.model_hash; the serialization layer maps them explicitly. Public IDs use text; the conflict between the original ER diagram's UUIDs and the API prefixes is in D-001. base_version_id is the one name used; no ambiguous aliases are accepted.

## 2. Authentication / tenant context

Every `/v1` request: Authorization: Bearer OIDC JWT + X-Organization-ID. Only after the signature, issuer, audience, expiry, etc. are verified is the issuer/subject used to load the existing user identity and membership. The header only selects the tenant; it is not authorization. If the path contains an organization_id, it must equal the verified header scope.

The only exception is `GET /v1/me` (D-045, APPROVED, H-010; openapi marks it with `x-tenant-scope: user`, and `x-required-roles` is empty): any provisioned user can call it, and it **selects no organization**, so a request that carries `X-Organization-ID` (even empty) gets 400 `INVALID_REQUEST` (detail reason `X-Organization-ID`; the server never ignores this header, so the client never wrongly believes it selected an organization). The response is the user ID and the user's own memberships (`organization_id`, `organization_name`, `role`), ordered by organization name, then by the byte (code point) order of the organization ID (SQL uses `COLLATE "C"`, independent of the DB collation); at most 100 entries; beyond that it returns the first 100 with `truncated: true` (no silent truncation); with no membership it is an empty array; an unknown identity gets 403, and no user is created automatically (D-008). The response carries `Cache-Control: no-store` (every API response does), writes no audit (reads are not audited), and the log does not contain organization names. The UI uses it to select an organization and get the role; the role only shapes the interface; every other operation checks membership authorization in its own transaction each time, as usual. Implementation: `httpapi.Self`, `tenant.DB.RunSelf` (a read-only transaction that sets only `app.user_id`), `internal/tenant/me`, `internal/storage/memberships.OfUser`; for RLS see migration 0008 in §9.

APPROVED D-008: org/initial owner/user provisioning is a controlled bootstrap; no unauthenticated public provisioning endpoint is exposed; the provider and onboarding automation still need T-008/T-010. An Owner can manage the memberships of known existing user IDs; there is no site-wide user enumeration. When the last Owner is changed or deleted, per D-036 the same transaction first locks all owner memberships in user_id order with `SELECT … FROM twin.memberships WHERE organization_id=$1 AND role='owner' ORDER BY user_id FOR UPDATE`, then checks the count and rejects; the API has no UPDATE grant on organizations, so it does not lock the organization row (CB-13).

## 3. HTTP rules and errors

Responses use application/json; errors keep the original report's format: error.code/message/details[{path,reason}]/request_id; details may also carry optional code/severity (D-024). `error.code` is the closed list `common.schema.json#/$defs/ErrorCode`, and `x-http-status` gives each code its one status (D-025). Server-generated resource IDs are `<prefix>_<ULID>` (D-001, see TWIN_IR_SPEC §1). No error contains a stack trace, SQL, other tenants' names or provider credentials; the JSON Pointer shows the exact field. Normal requests carry the X-Request-ID correlation. T-035 (D-093, D-094 APPROVED, H-024): the request ID is issued by the server's outermost layer (`httpapi.AccessLog`) and returned as X-Request-ID by `httpapi.Handler` (the client's value is not read); the same ID appears in the response, the error envelope, the audit row and every log line of that request; each request gets one access log line (route pattern, status, duration, error code; no path, query, header or body).

| HTTP | Meaning |
|---|---|
| 201 | committed create / publish / approval effect |
| 202 | durably enqueued; does not mean the computation is done |
| 400 | malformed JSON, duplicate keys, wrong parameters |
| 401 / 403 | authentication failed / authenticated but role insufficient |
| 404 | does not exist or is not in the authorized tenant/parent; cross-tenant existence is not disclosed |
| 409 | MODEL_VERSION_CONFLICT, IDEMPOTENCY_KEY_CONFLICT, LIFECYCLE_CONFLICT, RESULT_NOT_READY, PROPOSAL_ALREADY_DECIDED (D-030) |
| 413 / 422 | size limit exceeded / schema, semantic, dataset or constraint invalid |
| 415 | Content-Type mismatch (UNSUPPORTED_MEDIA_TYPE) |
| 428 | missing If-Match (PRECONDITION_REQUIRED); a missing Idempotency-Key is 400 IDEMPOTENCY_KEY_REQUIRED |
| 429 / 503 | quota exceeded / provider or infrastructure unavailable |

The draft ETag has the fixed candidate format `"draft-revision-N"`. PATCH draft uses application/json-patch+json + If-Match; publish/reset also carry If-Match. The original report explicitly returns 409 for stale; this draft keeps that and does not switch to another status that is common in general HTTP.

Lists use items/next_cursor, limit 1–100; the cursor is bound to tenant, parent and sort/filter; another tenant's cursor cannot fetch out-of-scope data. The server chooses a stable created_at/id order and does not make authorization assumptions based on an unstable offset while rows are deleted or changed.

## 4. Model / proposal / scenario transactions

create: template valid → insert model, v1, draft revision1 → audit → commit. publish: expected_base + If-Match + model lock → candidate validate → insert version(parent=base,version=latest+1) → update latest/draft → audit → idempotency response → commit.

T-054 implementation (`internal/storage/datasets`, `internal/httpapi`, `internal/models`, `internal/runs`, `internal/proposals/approval`, `internal/scenarios`; supplement to D-069 (b), H-022 Q4; patchDraft and resetDraft are D-087 (H-023); review round 1 fixes L1–L3): **Classification**: the only infrastructure error of the dataset binding stage (`datasets.Resolve`) is storage failing to read a snapshot (Open, Read or Close fails, other than `datasets.ErrNotFound`); `Resolve` returns `*datasets.ReadError` for it (it records the dataset version; `errors.Is`/`errors.As` find the storage cause). Each route handles `Resolve`'s error at the call site with `datasets.Failure(ctx, err)`: when the request has already ended (cancelled or timed out), it returns the `errors.Join` of the context error and the original error, whatever storage returned (L2), and each route returns 503 (no details) as for any context error; otherwise it returns the error unchanged. Each route's only mapping is decided by `datasets.StorageFailure`: only a `ReadError` while the request is still live (not a context error) returns 503 `SERVICE_UNAVAILABLE`, produced by `httpapi.DatasetStorageFailed(message)`, with `details[0].code` `DATASET_STORAGE_FAILED`; `Resolve`'s other errors (the schema cannot compile, a snapshot that passed the schema cannot be decoded, a manifest that passed the shape checks cannot be sorted or hashed) are server errors and return 500 `INTERNAL_ERROR`, logged by httpapi at ERROR (L1); data problems such as a missing snapshot or a hash mismatch are still issues (422, or the draft's issues). **Reads covered**: **publishVersion** twice (the candidate check, and the check after the version INSERT for the clean draft that follows the new version); **patchDraft** once (the draft's issues after the patch, against the base's manifest, D-087); **resetDraft** once (the content of the latest version that the draft becomes, against that version's manifest, D-087); **approveProposal**'s revalidation and, for an edit, the read after the new version when `models.Service.Advance` brings the clean draft up to date (approveProposal's own binding stage, D-069 (b); both are the same `ReadError` with the same mapping); createManualScenario and createSimulation (§6) are the same. The model routes' message is `the dataset snapshots could not be read; nothing was changed (retry later)`, the same as approveProposal (createManualScenario: `nothing was saved`; createSimulation: `nothing was queued`). The cause is written only to the WARN log (`request_id`, organization, model or proposal, cause) and is never sent to the client. The failed transaction rolls back entirely: publish leaves no version, the model and draft are unchanged, there is no audit, and the Idempotency-Key stores no answer; patchDraft and resetDraft leave no new draft revision and no audit (neither uses an Idempotency-Key; the same If-Match can be resent); an approval leaves no version, the proposal is still ready and undecided, there is no `proposal.approve` audit, and the key stores no answer. So after storage recovers, the same request succeeds once. A base (or latest version) bound to a dataset while the model service has no dataset storage is still 503 (no details); currently `api.Handler` gives the model service no dataset storage (freezing datasets on import commit belongs to T-018), so for a base bound to a dataset the deployed API always returns this 503 first for publishVersion, patchDraft and resetDraft; the 503 for a read failure is verified by DB tests of the `models.Register` handler with dataset storage; approveProposal's draft sync uses the approval's own object storage, so a deployment does reach it. **Not covered** (recorded in D-087): object-storage read failures in the run trace download (downloadSimulationTrace; `internal/runs` reads the trace artifact) and in the import error report download (`internal/import/upload` reads the error report) are not snapshots and are still 500 (fail closed; no bytes are sent).

A proposal request returns 202 generating; after generating the content the worker only UPDATEs the proposal and cannot INSERT model_versions/scenarios. ready->approve is a human action in the API. First check role/key, then lock in the order model→draft→proposal; re-validate latest/base, patch, dataset manifest and risk; one transaction creates a version **or** a scenario. mode=scenario creates no version. The UI / generated client must use the discriminated approval response and must not always read new_version_id.

If the same proposal is already approved and the expected base matches the original proposal, the same effect may be returned; changing the Idempotency-Key must not create a second one. (D-030 (APPROVED, CB-12) sets a re-approval with a changed key to 409 `PROPOSAL_ALREADY_DECIDED`; only a replay with the same key and the same body returns the original 201. T-026 implements it per D-030.) When two different proposals compete for the same base, once one succeeds the other gets 409. A dirty draft is kept; an explicit reset needs confirm_discard=true + the latest ETag; there is no auto-rebase endpoint.

## 5. Import API and data retention

POST imports is a bounded multipart (kind, project_id, model_id, base_version_id, file) and accepts CSV events, JSON events and JSON model. profile/preview does not modify the Twin. CSV is UTF-8 (a BOM is handled); other encodings get a specific error, and the encoding is not guessed. A JSON event import is a canonical-event array; a JSON model must be a complete IR; after the server binds the model identity it produces a diff for review; server/tenant envelopes cannot be imported.

Mapper suggestions are async read-only suggestions; they do not overwrite a confirmed mapping. POST mapping carries expected_mapping_revision and confirmed=true, increments the revision and queues validation, and returns 202; only the worker of the same revision can publish the validation. VALIDATED means all rows are valid; invalid rows return AWAITING_MAPPING + an error report; only fatal parse/storage errors are FAILED. A JSON model with no field mapping still needs validation at revision=0.

T-016 implementation (`internal/import/upload`, `internal/import/profile`, `internal/import/report`, `internal/import/profiler`, `internal/storage/imports`, migration 0010; independent review round 1 CHANGES REQUESTED, fixed, awaiting re-review):
- **Upload (uploadImport)**: before reading the body, it confirms that object storage is configured and that the caller is an editor or owner (a client waiting for `100 Continue` that is rejected never sends the body). The four fields `project_id`, `model_id`, `base_version_id` and `kind` come once each, first, and `file` is the last part (any part after it is 400); an unknown part or a missing or malformed field is 422, with the JSON Pointer at the field (`/project_id`…`/file`); a duplicate field, a field sent as a file, and `Content-Transfer-Encoding` are 400. A project, model or version not in this organization is 404; ones that do not belong to each other are 422 (`/model_id`, `/base_version_id`). Only the last segment of the file name is kept (both `/` and `\` are separators): 1–255 characters, no control or format characters. Archives and executables are rejected by extension and by the first 512 bytes (415 `UNSUPPORTED_MEDIA_TYPE`, `details[0].code` `IMPORT_FORMAT_REJECTED`); an empty file is 422; everything else is streamed into object storage under the server-generated key `tenant/<org>/imports/<import>/upload` (D-035) while SHA-256 and size are computed; more than 50,000,000 bytes (D-007) is 413 and leaves no object, with or without `Content-Length` (when the declared length is already over, the body is not read). This route sets its own read deadline (default 5 minutes), replacing the server's 30-second ReadTimeout. The import (UPLOADED), the `import_profile` job (payload only `import_id`, `request_id`), the `import.upload` audit (kind, model, base version, size and SHA-256; no file name and no content) and the idempotency response commit in the same transaction before 202 is returned. The idempotency fingerprint is the four fields, the file name, and the file's SHA-256 and size; a retry with a used key only computes the hash and does not write the object again (the same file returns the original response, otherwise 409). A rejected request writes no row; the already-written object becomes an orphan only when a part follows file, when the request loses a race for the same key, or when the commit fails (D-044's maintenance is not implemented yet).
- **Profile (`import_profile` job, `internal/import/profiler`, linked only into cmd/worker)**: under the lease it marks the import PROFILING and reads the object outside the transaction; if the size or SHA-256 differs from the row it is FAILED (`UPLOAD_CORRUPT`), if the object is gone it is FAILED (`UPLOAD_MISSING`), and an object storage failure is the retryable `OBJECT_STORAGE_FAILED`; when the job's attempts run out or the job is cancelled, the import becomes FAILED in the same transaction, with the job's error (`follow_import_profile_job` in migration 0010, T-016 review M1); it streams the file once through `internal/import/profile`, and the result goes in the same transaction as the job's completion: AWAITING_MAPPING with profile, preview, `total_rows`, `invalid_rows` and the error report, or FAILED with the failure, plus an `import.profile` worker audit (counts and codes only). Rules: CSV is RFC 4180, comma-separated, strict quoting, and the first record is the header; UTF-8 (recorded as `utf-8-bom` when there is a BOM); invalid UTF-8, UTF-16 and NUL always fail, and the encoding is not guessed; column names are 1–256 characters, unique, at most 256 columns; a record whose field count differs from the header is an invalid row (counted in `invalid_rows`, listed in the error report, not counted in the column statistics; the preview shows the fields it has); JSON events are an array of objects whose columns are the top-level member names of each object, in order of first appearance; a JSON model is one object (rows 0, columns and preview both empty; its content is validated by T-017); in JSON, duplicate members, numbers beyond binary64, U+0000 and data after the value always fail; a file with only a header, or an empty array, fails (`IMPORT_EMPTY`). Limits: 100,000 rows (D-007), 256 columns and 256-character column names (D-043); a value of 32,768 characters, JSON nesting of 32 levels, a JSON model of 2 MiB (D-029's IR limit), and at most 1 MiB in written bytes for one CSV record (including the header) and for one JSON events row (including the whitespace and comma before it) are implementation parameters awaiting benchmark (T-037; CB-39(c)). Every limit is enforced while reading, and memory does not grow with the file (T-016 review H1): CSV is read by `internal/import/profile`'s own scanner (the same records, line numbers and errors as `encoding/csv`, compared by a fuzz test), which stops when a record exceeds 1 MiB, keeps for a row only the header's field count plus one field (the rest are only counted), and counts field length while reading; the JSON events decoder can read at most 1 MiB past the end of the previous row, so it holds at most one row; values already checked are not tracked again for member names when they are re-read. Measured with 20–50 MB malicious files, total allocation is 0.1–20 MiB (up to 6.7 GB before the fix). Type inference looks only at non-empty values (an empty string, JSON null and a missing member are empty): JSON number grammar (`007`, `+5`, ` 5` are strings), ASCII `true`/`false` (case-insensitive), RFC 3339 date-time with offset; integer and number merge into number, other differing types are mixed, and JSON objects and arrays are always mixed; length is counted in Unicode code points. The preview is the raw values of the first 100 rows: a string longer than 256 characters keeps 255 characters plus "…", and the whole preview is at most 1 MiB by its stored size in the database (the first row that does not fit, and every row after it, are left out); JSON numbers are kept as written, unless the database would print more than 400 characters, in which case the shortest binary64 form is stored. Every failure has a typed code and a JSON Pointer that treats the file as an array of rows (for a JSON model, the pointer in the document; at most 2,048 characters, cut at a `/` to an ancestor when too long, T-016 review L1); the message does not quote file content.
- **Read (getImport)**: viewer and above; in UPLOADED and PROFILING the profile is null and the preview is empty. When the profile job fails or is cancelled before the import leaves profiling, the import row itself is FAILED with the job's error (`JOB_CANCELLED` or `INTERNAL` when the job has no error); the API shows the row as stored and does not derive the status at read time (T-016 review M1). The `error` of FAILED is the contract's error envelope: `details[0]` carries the failure's own code and pointer, and `request_id` is the request of the step that failed (the upload, for profiling; after a mapping is saved, the save of the current revision, T-017); the provisional mapping of `error.code` is in CB-39.
- **Error report (downloadImportErrors)**: per D-044 no signed URL is issued (CB-38(b)): it authorizes in a transaction (viewer and above), confirms that the import has a report and that the key is under this import's own prefix, reads the object only after the transaction ends, and sends it as `text/csv; charset=utf-8` with `Content-Disposition: attachment; filename="<import>-errors.csv"` only if the size and SHA-256 both equal the row's; otherwise 500 and no bytes; no report is 404. The format is RFC 4180, CRLF, every cell quoted, UTF-8 with BOM, header `path,line,column,code,message,value`; a cell that (after stripping leading whitespace and quotes) starts with =, +, -, @ or their full-width forms, or that starts with tab, CR or LF, is prefixed with `'`; inside a cell, where the text after `,`, `;`, tab or a newline (after stripping whitespace and quotes) starts with these characters, a `'` is added after the separator, so a spreadsheet never runs a formula, whichever of these it splits cells on (TEST-029, T-016 review M2); at most 16 MiB, and what does not fit is counted in a last row `ERRORS_TRUNCATED`. The client sends only the import ID and cannot specify a key or URL.

- **Mapping (saveImportMapping)**: editor and above; needs an `Idempotency-Key` (CB-18; the fingerprint is the import ID and the body's canonical JSON; a replay still needs editor or above, and is 403 after a demotion). The body is `SaveMapping`: `expected_mapping_revision`, `mapping` (`import-mapping.schema.json`: each entry has only `source_column`, `target_field` and `transform`; the transform is decided by the target field), `confirmed: true` and the optional `confirmed_low_confidence`. In the same transaction it first locks the import's queued/running validation job, then the import (job first, as in the worker's Checkpoint/Finish), checks status and revision, and checks the mapping against the profile's column names with `mapping.Check` (D-070: the column name exists and appears at most once; each field other than metadata is filled by only one column; case_id/event_type/timestamp are required; at most 64 metadata columns; each entry's transform; the entries of a ready suggestion that need human confirmation (decided by the server from confidence < 0.80, a null target, or a flag) have been confirmed by a person; the stored suggestion is first validated against `ai-mapping.schema.json`, and a mismatch is 500 `MAPPING_SUGGESTION_INVALID`); on success `mapping_revision` increments, the status becomes VALIDATING, the previous validation and its results are cleared, an `import_validate` job for that revision is queued (payload: import_id, mapping_revision, request_id), jobs of other revisions that are still queued are cancelled, an `import.map` audit is written (counts only: revision, columns imported and skipped, metadata columns, confirmations, validations cancelled), and it returns 202 with the import. A stale or ahead revision is 409 `LIFECYCLE_CONFLICT` with `details[0].code` `MAPPING_REVISION_CONFLICT` (`/expected_mapping_revision`); UPLOADED/PROFILING is 409 `IMPORT_NOT_PROFILED`, FAILED/COMMITTED is 409 `IMPORT_FINAL`; a rejected mapping is 422 `REQUEST_VALIDATION_FAILED`, with one detail per issue (code and the JSON Pointer in the body); a JSON model is 422 `MAPPING_NOT_APPLICABLE` (`/mapping`, T-018). A rejected request writes no row.
- **Validation (`import_validate` job, `internal/import/validator`, linked only into cmd/worker)**: it reads the import under the lease and validates only while the import is still VALIDATING with the same revision as the job; it reads the upload outside the transaction (checking size and SHA-256), reads each row with `internal/import/profile`'s `Scan`, converts it to a canonical event with `mapping.Plan.Apply` (D-072's value and row rules), and decides only after reading everything: if there are invalid rows it writes an error report (`validation-errors-r<rev>-a<attempt>.csv`, T-016's format, with the value column blank); each event is finally validated against `canonical-event.schema.json` (a mismatch is an invalid row with `EVENT_NOT_CANONICAL`); when all rows are valid, it first confirms under the lease that the import is still VALIDATING with the same revision (otherwise it stops and writes no dataset, review round 1 L5), reads the upload again, and streams the canonical events in row order as a compact JSON array to `canonical-r<rev>-a<attempt>.json` (both files under `tenant/<org>/imports/<import>/`, at most 256 MiB). The result goes in the same transaction as the job's completion: while the import is still VALIDATING with the same revision it writes VALIDATED (`validation.valid=true`, the canonical preview, the dataset's key/SHA-256/size) or AWAITING_MAPPING (`validation.valid=false`, at most 100 issues, `invalid_rows`, report), or FAILED when the file is no longer the profiled one (`UPLOAD_CORRUPT`, `UPLOAD_MISSING`, `UPLOAD_CHANGED`); otherwise it writes nothing (stale-job fence, audit outcome `stale`). The `import.validate` worker audit has only counts and codes. An object storage failure is the retryable `OBJECT_STORAGE_FAILED`, and no object storage is the retryable `OBJECT_STORAGE_UNAVAILABLE`; when the attempts run out or the job is cancelled, the import becomes FAILED with it (0014's `follow_import_validate_job`).
- **Read (getImport)**: adds `canonical_preview` (the canonical events of the first 100 rows, null for invalid rows; empty while VALIDATING). The `error.request_id` of FAILED is the request of the step that failed: after a save, that revision's save; before one, the upload. `error.message` is changed to the neutral "the file could not be processed", because validation failures use the same envelope.

T-052 hackathon slice (D-059, D-072 (b) APPROVED; details D-118, PROPOSED; no migration, contract unchanged): **the pack's data-quality rules**. A check that returns an issue that cannot be recorded is a server error, and validation fails (fail closed); when the base version cannot be read, or its domain is not one the worker serves, the job fails with the non-retryable `INPUT_INVALID` and the import becomes FAILED with it. A validator with no Packs does only generic validation (T-017's behavior). ## 6. Runs / async states / SSE

POST simulations accepts only an immutable model_version_id + (exactly one of an inline scenario_patch or a scenario_id) + an explicit config. The baseline uses []. A saved scenario must match model_version_id; an inline patch is a person's explicit what-if request, still goes through the full validator, and provider tools must never be allowed to call this route directly. On enqueue, engine_version, hashes, datasets and execution_limits are frozen; 202 is returned only after the resource+job transaction has committed.

Run states: queued→running→completed/failed/cancelled; queued can go straight to cancelled; a retry after a transient failure can go running→queued, keeping the original inputs. The terminal completed/failed/cancelled cannot be updated again or go back to running. The progress revision increases monotonically; replication progress may restart on retry, and the UI does not treat an old attempt's progress as a completed result.

Cancelling a queued run cancels the job/run atomically; cancelling a running run sets cancellation_requested; the worker stops at a checkpoint and finalizes cancelled. Cancelling completed/failed returns 409; a repeated cancel of a cancelled run may return the same object. The result endpoint returns RESULT_NOT_READY for anything not completed; partial attempt output must not be used for analysis.

SSE `/events` carries progress snapshots, not the raw simulation trace. It uses authenticated fetch streaming, to avoid putting the token in the URL because the browser EventSource cannot set Authorization. id=run_id:progress_revision; Last-Event-ID is bound to the same run; a reconnect sends the latest snapshot; full-history replay is not guaranteed. Reconnects/periodic polls re-check the token/membership; revocation or expiry closes the stream. Sampled playback goes through a separate authorized trace artifact endpoint.

T-023 implementation (`internal/runs`, `internal/runs/runner`, `internal/storage/runs`, migration 0009):
- **Create (createSimulation)**: it first checks role (editor/owner) and the Idempotency-Key (D-011: the same key with the same body returns the original response; a different body is 409 `IDEMPOTENCY_KEY_CONFLICT`; the fingerprint is the canonical body), then freezes and enqueues in the same transaction: `model_version_id` must be an immutable version of this organization (the schema accepts only `mv_` IDs, so a model or draft ID is 422 `/model_version_id`; a missing version or another organization's is 404); `scenario_id` must exist and its base must be that version, otherwise 404/422 (`/scenario_id`), with no fallback to the baseline; both the inline patch and the saved scenario's patch go through the scenario patch policy and the full validator (`/scenario_patch/...`); the domain pack's errors, the dataset binding stage (hash, unit, zero-time) and the engine's own `Compile` also run before enqueue, so an enqueued run never fails in the worker on the same checks; the config's horizon/warmup are first converted to ticks (`/config/...`, 422 `REQUEST_VALIDATION_FAILED`). What is frozen: the version and its hash, the canonical patch, the effective model hash (confirming that the engine gets the same value when it recomputes it from the decoded IR), the config and config hash, the version's whole dataset manifest and the manifest hash (`run_datasets` and a deferred trigger), the engine version (`des-go-0.1.0`) and the server's execution limits (D-007; the client cannot set them). The run, the job (payload only `run_id` and `request_id`), the `simulation.create` audit (metadata only the version ID, replications, engine version and the hashes of the frozen input: model, effective model, config, dataset manifest; not the content of the patch or config; SECURITY §9) and the idempotency response commit in the same transaction before 202 `RunAccepted` is returned. When object storage is needed (the version is bound to a dataset, or `trace_level=sampled`) and the server has none configured, it returns 503 and does not enqueue. When the dataset binding stage cannot read a snapshot bound to the version from storage (`datasets.ReadError`), it returns 503 `SERVICE_UNAVAILABLE` with `details[0].code` `DATASET_STORAGE_FAILED` (the same as approveProposal and createManualScenario; supplement to D-069 (b), H-022 Q4, T-054), and the cause is written only to the log; other errors of the binding stage are server errors (500, ERROR log); when the request itself is cancelled or times out, or ends during a read failure, it is handled as any context error (503, no details; the T-054 paragraph of §4); none of run, job, `run_datasets`, audit and idempotency response is written, and the same request with the same key enqueues once after storage recovers.
- **Reads**: get, list (`/v1/models/{id}/simulations`, created_at/id order, the cursor bound to organization, model and list) and results (anything not completed is always 409 `RESULT_NOT_READY`; no partial results) all read with RLS under a viewer-or-above membership; another organization's run is always 404. A failed run's `error` is the job's failure converted to the contract's error envelope (`request_id` is the request that created the run); the mapping of run failure codes is in CB-38 (provisional, awaiting the owner).
- **Cancel (cancelSimulation)**: the body must be `{}` (`http.schema.json#/$defs/CancelSimulation`); the Idempotency-Key fingerprint includes the run ID (the same key on another run is 409). It locks the job first, then the run (the same order as the worker's finalize): a queued run and its job are cancelled together (the job through `jobs.CancelQueued`, the run following through 0009's trigger); a running run gets `cancellation_requested`, and at the next checkpoint (default every second) the worker stops the engine and ends the job and run as cancelled, storing no result; an already cancelled run is returned unchanged with 200 (no further audit); completed/failed return 409 `LIFECYCLE_CONFLICT`. Each cancel that has an effect writes one `simulation.cancel` audit (`effect`: `cancelled` or `cancellation_requested`). Cancel and complete are mutually exclusive: the worker's transaction that stores the result also locks the run first, and when it sees that cancellation was requested it ends as cancelled and stores no result.
- **Trace (downloadSimulationTrace)**: D-044 issues no signed URL, so the API first authorizes in a transaction (viewer-or-above membership, run completed, the result carries a trace, the object key is under this organization's `simulation-results`), reads the object only after the transaction ends, and streams back the `TraceArtifact` with `Content-Disposition: attachment` only if the size and SHA-256 both equal the result row's; a missing object or mismatched content is always 500, with no bytes sent (fail closed). A run with no trace is 404.
- **Compare (compareSimulations, T-029; D-088–D-090 APPROVED, H-024)**: the query is checked first (`baseline_run_id` and `scenario_run_id` once each, both run IDs, different from each other; otherwise 400 with `details[0].reason` the parameter name); then, in one read-only REPEATABLE READ transaction, it checks membership and role (any member), reads both runs (baseline first; a missing run or another organization's is 404, with the same response), looks at status only after both exist (not completed is 409 `RESULT_NOT_READY`), and reads both results; after the transaction ends it computes with `internal/results/compare`. The comparability conditions, statistics, deltas, missing values and warnings are in the T-029 paragraph of SIMULATION_SPEC §7; when the runs are not comparable it is still 200 (`comparable=false`, `incomparable_reasons`). A stored result that cannot be strictly decoded, that does not match the run's frozen input (ID, engine, seed, replications, manifest, model/effective model/config hash, window), or whose `metrics` do not match the contract, is 500 and is not compared (D-089 (b)). The response is in RFC 8785 form and identical every time for the same runs; no audit is written.
- **SSE (streamSimulationEvents)**: the first event is always the latest snapshot; after that, each poll (default 1 second) re-checks membership and role in a new REPEATABLE READ transaction and then reads the run (TEST-026); an event is sent only when the revision changed, and after 15 seconds of silence a `: keep-alive` comment is sent; removal of the member (or a role that can no longer read the run), token expiry, a terminal run, 10 minutes of connection, the client leaving, or a write timeout (10 seconds per write; after a write the deadline is extended past the next possible write, i.e. keep-alive + poll + 10 seconds, because an HTTP/2 stream is reset once its deadline passes even when no write is in progress, T-023 review I1) all end the stream; when the client reconnects, the ordinary request authorization applies (a rejection is an ordinary error response). A member demoted to viewer can still read the run, so the stream continues. Last-Event-ID accepts only this run's `<run ID>:<revision>`; anything else is 400.

## 7. Idempotency / crash recovery / fencing

Scope = organization_id + actor_id + operation/resource + key. request_hash includes the normalized parsed body, the URL resource and the concurrency headers; multipart uses the file content hash + metadata. Hashing only the body while ignoring If-Match/expected base is not allowed. The same key + the same fingerprint returns the original response; a different fingerprint returns 409. The permission check must still run before a replay; an old success response is not an access pass after revocation.

T-035 (D-091 APPROVED, H-024): when the worker loop records an attempt's failure (`jobs.Fail`) and when the reaper reclaims a lease (`jobs.ReapJobs`), `job.attempt_failed` is written in the same transaction (the job's resource as target, the payload's `request_id`, the code, whether it is requeued); if the event cannot be written, the failure is not recorded either. Every audit event is first checked against the `internal/audit` catalogue. Reserving the key happens in the same short transaction as the operation effect, audit and response; handling a duplicate reservation locks the same key. LLM/DES run outside the transaction. The initial TTL of 24h is a D-007 proposal; the versions/source_proposal unique and result.run_id unique constraints still guarantee that no canonical effect is duplicated after the TTL. Expired key cleanup is controlled maintenance; ordinary runtime gets no arbitrary DELETE.

Claim uses an organization filter + SKIP LOCKED + priority DESC/created_at/id. attempt increments, lease_token increments, and lease_expires_at is stored; the initial 30s lease / 10s heartbeat / max_attempts 3 are candidates. heartbeat/finalize both check organization, job_id, worker_id, lease_token, running and not expired; updating zero rows means ownership is lost, and an unscoped write must not be retried.

The result finalize transaction locks the job, then the run, and verifies a valid lease + no cancel flag; the unique result insert, run completed, job completed and audit commit together. An old worker whose lease expired can never overwrite a new result. The reaper handles expired leases tenant by tenant and verifies the retry budget first; the run's frozen input does not change. Non-transient validation/budget failures are not retried; the parameters of the bounded exponential backoff still need configuration. T-019's queue and worker loop follow [ADR-024](adr/ADR-024-job-queue-and-worker.md) (ACCEPTED, H-010: 30 s lease / 10 s heartbeat / 3 attempts, backoff starting at 5 s and doubling up to 5 min; queued cancels immediately; cancel and complete are mutually exclusive; migration 0007 makes terminal jobs unmodifiable); the run's finalize, cancel flag and budget belong to T-023.

APPROVED D-007: a logical run's wall/event budgets include retries rather than resetting on each retry. The worker uses durable budget reservations, bounded batch credit and an external cancellation governor; the engine only reads the granted budget/context and never reads the DB directly. The implementation must test that credit reserved but not used before a crash is consumed conservatively and cannot be overspent. This part is a required test of T-021/T-023 and is not claimed as done in this pack.

T-023 implementation (`internal/runs/runner`, `internal/storage/runs`, `engine.Credit`): the checkpoint at the start of an attempt locks the run, confirms that it is still queued, that no cancel is requested and that the engine version is the same, then marks the run running: on the first start it writes `started_at` and `execution_deadline_at = now() + wall_timeout_seconds` (never reset afterwards) and reserves the first batch of events (`event_budget_reserved += min(remaining, batch)`); when the remaining time is ≤0 or earlier attempts already reserved all events, the attempt fails with `WALL_TIMEOUT_EXCEEDED`/`EVENT_BUDGET_EXCEEDED` (not retried). The engine gets only `max_events − the amount reserved earlier` and the remaining wall time; when it uses up the granted credit it asks for the next batch through `Credit.Grant`, and the worker increases `event_budget_reserved` under the lease with a fence (the reserved amount must still be the value this attempt last wrote); on failure (lease lost, DB error) the worker stops the engine. So the amount reserved by earlier attempts always counts as used: a crash wastes at most the unused part of the last batch (conservative), and the events used by all attempts together never exceed max_events. The result finalize is `handler.Run.Finish`: one transaction locks the job (lease fence), locks the run, confirms there is no cancel request, inserts the result (0009's `check_simulation_result` requires the run to be running with no cancel requested, and engine version/seed/replications/the four hashes all equal to the frozen values), marks the run completed, writes the `simulation.complete` audit (worker identity; request_id is the request that created the run) and marks the job completed; once the lease is lost this transaction does not commit. The trace is first uploaded to this attempt's own key, and then the artifact ID, key, SHA-256 and size are written in the same finalize transaction (0009 requires all four together, the key under this run's prefix, and the result naming the same artifact). Progress is written at each checkpoint (the revision increments when it changes), and `cancellation_requested` is read back. Job retry, failure, the reaper and cancel all bring the run to the same state through 0009's `follow_simulation_job` trigger: on retry the run returns to queued with progress reset to zero (reservation and deadline unchanged); when failed, the run's `error` is the job's failure.

## 8. Relational model / constraints

| Tables | Responsibility / immutable boundary |
|---|---|
| users, organizations, memberships, projects | identity, scope, role; users is the special case of a global auth identity, the rest are tenant owned |
| models, model_drafts, model_versions | latest pointer, CAS draft (revision; `issues` stores the semantic issues at write time, D-028, migration 0003), immutable full IR; parent in the same org/model; service rules in ADR-022 (T-012) |
| datasets, dataset_versions, model_version_datasets | immutable object hash/unit/lineage; the version binding does not point to a mutable alias |
| imports, ai_proposals, scenarios | lifecycle, immutable review payload, scenario patch; source proposal unique effect |
| simulation_runs, run_datasets, simulation_results | frozen inputs, snapshot manifest, unique immutable result; mutable progress separated from input |
| ai_analyses | async analysis output + evidence; no model write authority |
| jobs, idempotency_keys, audit_events | scoped execution leases, dedupe, append-only audit |

Every tenant-owned table carries NOT NULL organization_id. Composite FKs guarantee that a child cannot point to a parent of a different tenant/project/model; a single UUID/text FK is not enough. Model version, scenario, dataset revision, binding, completed result and audit have immutable triggers + runtime grants; run input has a guard trigger. DB JSONB shape checks do not replace JSON Schema / the semantic validator.

The whole manifest is also stored in the frozen dataset_bindings JSON of model_versions / simulation_runs; deferred constraint triggers require the relational bindings to match it exactly at commit, so an immutable child cannot still change the manifest by a late INSERT. The API returns the frozen parent manifest and does not derive authority from an appendable child collection. event_budget_reserved and execution_deadline_at support a budget across retries; the deadline/first start cannot be reset, and the reservation cannot go backward.

Since T-006 the schema also enforces (verified by `db/tests/constraints.sql`): each kind of ID has its own domain (`twin.org_id`, `twin.mdl_id`…, `<prefix>_<ULID>`, D-001), so a column cannot hold another kind of ID; object keys are checked with `twin.object_key_ok` (a `starts_with` prefix; after the prefix only server-generated ASCII segments `[0-9A-Za-z_-][0-9A-Za-z._-]*` separated by a single `/` are allowed, so `..`, `.` segments, segments starting with `.`, empty segments and a trailing `/`, `%` encoding, backslashes, control characters, Unicode look-alike characters and format characters are rejected; ≤1024 characters = bytes; D-035/CB-14, tightened after the 2026-10-15 review); `logical_ref` is the `twin.logical_ref` domain (`^dataset:[a-z0-9_.-]+$`), and manifest comparison uses `ORDER BY logical_ref COLLATE "C"`, consistent with Go's byte order (D-034/CB-15); ai_proposals has `server_risk_level` and `provider_risk_claim`, and `risk_level` must equal the maximum of the two (D-027); immutable tables also have a BEFORE TRUNCATE guard (TRUNCATE does not go through row triggers or RLS).

Also enforced after the 2026-10-15 review (verified by `constraints.sql`/`roles.sql`, SQL mutation 19/19): (1) after a proposal leaves generating, its review payload (patch, risk, validation, expected_effects, questions, provider_metadata, etc.) can never change; an approved/rejected/conflicted/invalid/failed proposal row cannot change at all; decided_by/decided_at/new_version_id/scenario_id can be written only in the decision transition, decided_by must equal the transaction's `app.user_id`, decided_at is set by the DB to `now()`, and rejected must also have decided_by; an approved proposal's new_version_id (or scenario_id) must be the row whose `source_proposal_id` points back to this proposal. (2) The worker can update only generating proposals; it cannot change a COMMITTED import, nor an import's mapping, mapping_revision, dataset_version_id, proposal_id or identity columns; this is enforced by a trigger and holds even if the worker is mistakenly granted a wider UPDATE (such as `pg_write_all_data`) (D-037). (3) An audit event with actor_type='user' must equal `app.user_id`; the worker cannot write audit as a user (twin_owner provisioning is the exception). (4) Every twin function fixes `search_path = pg_catalog, pg_temp`, so same-named functions/operators in other schemas cannot shadow them.

## 10. Migration review / rollback gate

On disposable PostgreSQL, run up, schema smoke, runtime-role RLS tests, cross-tenant FK tests, immutable tests and up/down/up. A production migration needs independent review, a backup/restore rehearsal and a compatible deployment strategy; down deletes data or removes security and must not be used for automatic rollback. Users/org bootstrap and secrets go through deployment/provisioning, without example plaintext passwords.
