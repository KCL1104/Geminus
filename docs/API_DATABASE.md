# API / Database Contract

SOURCE：原報告 pp. 29–37、40–43。OpenAPI / SQL 完整化是 APPROVED D-001–D-004、D-006、D-008–D-015。**Migration 是需審查的草案，不是已在 PostgreSQL 執行過的結果。**

## 1. Contract files 與命名

`openapi/openapi.yaml`：OpenAPI 3.1.1，base `/v1`，使用 local external `$ref` 指向 `schemas/`，不重複定義 Model IR。`planning/api-operations.json` 列所有 operations 與 SOURCE/PROPOSED origin。新增的 listing/scenario/membership/download/reset/analysis-read endpoints 都有 x-origin=PROPOSED，標示它們不在原報告的 endpoint 清單內（來源標記，不是批准狀態；D-012 已批准）。

schemas/model-ir、proposal-output、proposal、scenario、simulation、analysis、canonical-event、ai-mapping、import、dataset-snapshot、http、common、json-patch 各有明确責任。stored `ai_proposals.patch` 對應 HTTP `changes`；model_versions.hash 對應 API `hash` / run.model_hash，序列化層顯式映射。public IDs 用 text；原 ER 圖 UUID 與 API 前綴的衝突見 D-001。base_version_id 統一命名，不另外接受含糊別名。

## 2. Authentication / tenant context

所有 `/v1` request：Authorization: Bearer OIDC JWT + X-Organization-ID。驗簽、issuer、audience、expiry 等完成後，才使用 issuer/subject 載入既有 user identity、membership。header 只選 tenant，不是授權。路徑中的 organization_id 若存在，必須等於已驗證 header scope。

唯一的例外是 `GET /v1/me`（D-045，APPROVED，H-010；openapi 以 `x-tenant-scope: user` 標示，`x-required-roles` 為空）：任何已 provisioning 的使用者都可呼叫，**不選 organization**，所以帶 `X-Organization-ID`（即使為空）回 400 `INVALID_REQUEST`（detail reason `X-Organization-ID`；server 從不忽略這個 header，client 不會誤以為選了 organization）。回應是 user ID 與自己的 membership（`organization_id`、`organization_name`、`role`），依 organization 名稱、再依 organization ID 的 byte（code point）順序排列（SQL 以 `COLLATE "C"`，與 DB 的 collation 無關）；至多 100 筆，超過時回前 100 筆並帶 `truncated: true`（不默默截斷）；沒有 membership 時為空陣列；未知 identity 回 403，不自動建立 user（D-008）。回應帶 `Cache-Control: no-store`（所有 API 回應都帶），不寫 audit（讀取不記 audit），log 不含 organization 名稱。UI 以此選 organization、取得 role；role 只決定介面，其他 operation 每次照常在自己的 transaction 中查 membership 授權。實作：`httpapi.Self`、`tenant.DB.RunSelf`（只設 `app.user_id` 的唯讀 transaction）、`internal/tenant/me`、`internal/storage/memberships.OfUser`，RLS 見 §9 的 migration 0008。

APPROVED D-008：org/initial owner/user provisioning 是受控 bootstrap，不暴露 unauthenticated public provisioning endpoint；provider 與 onboarding automation 仍需 T-008/T-010 完成。Owner 可管理已知既有 user ID 的 membership；不提供全站 user enumeration。改／刪最後一位 Owner 時，依 D-036 在同一 transaction 先以 user_id 順序 `SELECT … FROM twin.memberships WHERE organization_id=$1 AND role='owner' ORDER BY user_id FOR UPDATE` 鎖住全部 owner membership，再檢查人數後拒絕；API 沒有 organizations 的 UPDATE grant，所以不鎖 organization row（CB-13）。

## 3. HTTP 規則與錯誤

response 使用 application/json，error 保留原報告格式：error.code/message/details[{path,reason}]/request_id；details 另可帶選填 code/severity（D-024）。`error.code` 是封閉清單 `common.schema.json#/$defs/ErrorCode`，`x-http-status` 指定每個 code 唯一對應的 status（D-025）。伺服器產生的資源 ID 為 `<prefix>_<ULID>`（D-001，見 TWIN_IR_SPEC §1）。所有錯誤避免 stack trace、SQL、其他 tenant 名稱、provider credentials；JSON Pointer 顯示 exact field。正常 request 帶 X-Request-ID correlation。

| HTTP | 語義 |
|---|---|
| 201 | 已 committed 的 create / publish / approval effect |
| 202 | 已 durably enqueue；不代表計算完成 |
| 400 | malformed JSON、duplicate keys、錯誤參數 |
| 401 / 403 | authentication 失敗／已認證但 role 不足 |
| 404 | 不存在或不在 authorized tenant/parent；不揭露跨 tenant 存在性 |
| 409 | MODEL_VERSION_CONFLICT、IDEMPOTENCY_KEY_CONFLICT、LIFECYCLE_CONFLICT、RESULT_NOT_READY、PROPOSAL_ALREADY_DECIDED（D-030） |
| 413 / 422 | 大小超限／schema、semantic、dataset 或 constraint 無效 |
| 415 | Content-Type 不符（UNSUPPORTED_MEDIA_TYPE） |
| 428 | 缺 If-Match（PRECONDITION_REQUIRED）；缺 Idempotency-Key 為 400 IDEMPOTENCY_KEY_REQUIRED |
| 429 / 503 | quota exceeded／provider or infrastructure unavailable |

Draft ETag 固定候選格式 `"draft-revision-N"`。PATCH draft 使用 application/json-patch+json + If-Match；publish/reset 也帶 If-Match。原報告明確 stale 回 409，本草案保留，沒有換成一般 HTTP 常見的其他 status。

Lists 使用 items/next_cursor、limit 1–100，cursor 綁 tenant、parent、sort/filter；不能讓其他 tenant 的 cursor 取得 scope 外資料。服務端選穩定 created_at/id 排序，不在刪改中用不穩定 offset 做授權假設。

## 4. Model / proposal / scenario transactions

create：template valid →insert model、v1、draft revision1→audit→commit。publish：expected_base + If-Match + model lock→candidate validate→insert version(parent=base,version=latest+1)→update latest/draft→audit→idempotency response→commit。

proposal request 回 202 generating；worker 生成內容後只 UPDATE proposal，不能 INSERT model_versions/scenarios。ready->approve 是 API 中的人類 action。先驗 role/key，再按 model→draft→proposal lock order；重新驗 latest/base、patch、dataset manifest、risk；一次 transaction 建 version **或** scenario。mode=scenario 不建立 version。UI / generated client 必須使用 discriminated approval response，不能一律讀 new_version_id。

同一 proposal 已批准且 expected base 符合原 proposal 時，可回同一 effect；不可因換 Idempotency-Key 建第二份。（D-030（APPROVED，CB-12）把換了 key 的再批准定為 409 `PROPOSAL_ALREADY_DECIDED`；只有同一 key 與同一 body 的 replay 回原本的 201。T-026 依 D-030 實作。）兩個不同 proposals 競爭同一 base 時，一個成功後另一個回 409。dirty draft 保留；顯式 reset 須 confirm_discard=true +最新 ETag；沒有 auto-rebase endpoint。

T-026 實作（`internal/proposals/approval`、`internal/storage/proposals`、`internal/storage/scenarios`、migration 0013；D-067–D-069 PROPOSED）：
- **approveProposal**：body 為 `Approve`（`expected_base_version_id`、選填 `comment`）。順序：request 本身的檢查（path 400、media type 415、body 400／422、`Idempotency-Key` header 400，與其他 route 相同）→ role（editor／owner）→ Idempotency-Key（scope `approveProposal`；fingerprint 為 proposal ID 與 normalized parsed body（§7）：空 comment 即沒有，`{}` 與 `{"comment":""}` 相同；scope 不含 proposal，所以同 key 同 body 用在另一個 proposal 為 409 `IDEMPOTENCY_KEY_CONFLICT`；replay 的錯誤回答以這次 request 的 ID 為 `error.request_id`，其餘 byte 相同；D-069 (a)）→ proposal（不存在或其他 organization：404）→ `LockModel`、`LockDraft`、鎖 proposal → 狀態（approved／rejected／conflicted：409 `PROPOSAL_ALREADY_DECIDED`；generating／needs_input／invalid／failed：409 `LIFECYCLE_CONFLICT`）→ base 不是 latest：proposal 轉 conflicted、audit、回 409 `MODEL_VERSION_CONFLICT`（`/expected_base_version_id`），與狀態轉換一起 commit 並存為 key 的回應 → `expected_base_version_id` 不是 base：409（同 code 與 path），不寫入 → 再 review 一次與 dataset binding stage（422 `MODEL_VALIDATION_FAILED`；risk 不同 409 `LIFECYCLE_CONFLICT`；base 綁 dataset 而沒有 object storage 503；snapshot 讀不到 503，`details[0].code` 為 `DATASET_STORAGE_FAILED`；proposal 的 `dataset_bindings` 不是 base 的 manifest 為 500，不批准）→ effect → `Approve` 寫 status、`decided_by`、`new_version_id`／`scenario_id`、`decision_comment`（0001 設 `decided_at`）→ audit `proposal.approve` → idempotency response → commit，回 201 `Approval`。Edit 的 version：`version = base.version + 1`、`parent_version_id = base`、`source_proposal_id = proposal`、IR 為 base 套上 review 過的 changes（RFC 8785，D-040）、`dataset_bindings` 為 proposal 的（= base 的整份 manifest，D-062 (g)）、`comment` 為 request 的、`created_by` 為批准者；之後 `models.Service.Advance`（latest、model 名稱、clean draft 同步、dirty draft 保留）。Scenario：`scenarios` 一列（base、canonical changes、patch hash、名稱取自 summary，D-067、`source_proposal_id`），不建立 version、不入列 job。
- **rejectProposal**：body 為 `Reject`（選填 `comment`），scope `rejectProposal`，fingerprint 與 approveProposal 相同（proposal ID 與 normalized parsed body）；同樣先鎖 model row、draft，再鎖 proposal；ready 或 needs_input 轉 rejected，audit `proposal.reject`，回 200 與 getProposal 相同的 Proposal。
- **讀取**：approved、rejected、conflicted 的 Proposal 有 `decided_by`、`decided_at`，approved 與 rejected 有 comment 時有 `decision_comment`（D-068）。

## 5. Import API 與資料保留

POST imports 是 bounded multipart（kind、project_id、model_id、base_version_id、file），接受 CSV events、JSON events、JSON model。profile/preview 不修改 Twin。CSV UTF-8（可處理 BOM）；其他格式回具體錯誤，不自動猜編碼。JSON event import 為 canonical-event array；JSON model 必須完整 IR，server-bind model identity 後產生待審 diff，不能匯入 server/tenant envelope。

mapper suggestions 是 async read-only suggestion；不覆寫已確認 mapping。POST mapping 帶 expected_mapping_revision、confirmed=true，增加 revision 並排 validation，回 202；同 revision 的 worker 才能發布 validation。VALIDATED 意味所有 rows 合法；invalid rows 回 AWAITING_MAPPING + error report；fatal parse/storage 才 FAILED。JSON model 無欄位 mapping 時 revision=0 仍需 validation。

T-016 實作（`internal/import/upload`、`internal/import/profile`、`internal/import/report`、`internal/import/profiler`、`internal/storage/imports`、migration 0010；獨立 review 第 1 輪 CHANGES REQUESTED，已修正，待複審）：
- **上傳（uploadImport）**：讀 body 之前先確認 object storage 已設定、caller 是 editor 或 owner（等候 `100 Continue` 的 client 被拒時不會送出 body）。`project_id`、`model_id`、`base_version_id`、`kind` 四個欄位各一次、在前，`file` 是最後一個 part（之後再有 part 為 400）；未知 part、缺少或不合格的欄位為 422，JSON Pointer 指向欄位（`/project_id`…`/file`）；重複欄位、以檔案送出的欄位與 `Content-Transfer-Encoding` 為 400。Project、model、version 不在本 organization 為 404，彼此不相屬為 422（`/model_id`、`/base_version_id`）。檔名只保留最後一段（`/` 與 `\` 皆為分隔），1–255 字元，不含控制與格式字元。依副檔名與前 512 bytes 拒絕壓縮檔與執行檔（415 `UNSUPPORTED_MEDIA_TYPE`，`details[0].code` 為 `IMPORT_FORMAT_REJECTED`），空檔為 422；其餘以 server 產生的 key `tenant/<org>/imports/<import>/upload`（D-035）串流寫入 object storage，同時計算 SHA-256 與大小；超過 50,000,000 bytes（D-007）為 413 且不留下 object，`Content-Length` 有無皆然（宣告的長度已超過時不讀 body）。此 route 自設讀取期限（預設 5 分鐘），取代 server 的 30 秒 ReadTimeout。Import（UPLOADED）、`import_profile` job（payload 只有 `import_id`、`request_id`）、`import.upload` audit（kind、model、base version、大小與 SHA-256；不含檔名與內容）與 idempotency response 同一 transaction commit 後才回 202。Idempotency fingerprint 為四個欄位、檔名、檔案的 SHA-256 與大小；key 已用過的 retry 只計算 hash，不再寫入 object（同一檔案回原 response，否則 409）。被拒的 request 不寫任何 row；只有 file 之後還有 part、與同一 key 競爭落敗或 commit 失敗時，已寫入的 object 成為孤兒（D-044 的 maintenance 尚未實作）。
- **Profile（`import_profile` job，`internal/import/profiler`，只有 cmd/worker 連結）**：在 lease 下把 import 標為 PROFILING，在 transaction 外讀 object，大小或 SHA-256 與 row 不符時 FAILED（`UPLOAD_CORRUPT`），object 不見時 FAILED（`UPLOAD_MISSING`），object storage 失敗為可重試的 `OBJECT_STORAGE_FAILED`；job 的 attempt 用完或 job 被取消時，import 在同一 transaction 跟著變 FAILED，帶 job 的 error（migration 0010 的 `follow_import_profile_job`，T-016 review M1）；以 `internal/import/profile` 串流讀一次，結果與 job 的 completed 同一 transaction：AWAITING_MAPPING 帶 profile、preview、`total_rows`、`invalid_rows` 與 error report，或 FAILED 帶 failure，加上 `import.profile` worker audit（只有數量與 code）。規則：CSV 為 RFC 4180、逗號分隔、嚴格引號、第一筆 record 為 header；UTF-8（有 BOM 時記為 `utf-8-bom`），invalid UTF-8、UTF-16 與 NUL 一律失敗，不猜編碼；欄名 1–256 字元、不重複、至多 256 欄；欄位數與 header 不同的 record 是 invalid row（計入 `invalid_rows`、列入 error report、不計入欄位統計，preview 顯示它有的欄位）；JSON events 是 object 的陣列，欄位為各 object 頂層 member 名稱、依首次出現排序；JSON model 是一個 object（rows 0、columns 與 preview 皆空，內容由 T-017 驗證）；JSON 中重複的 member、超出 binary64 的數字、U+0000 與值之後的資料一律失敗；只有 header 或空陣列的檔案失敗（`IMPORT_EMPTY`）。上限：100,000 列（D-007）、256 欄與欄名 256 字元（D-043）；值 32,768 字元、JSON 巢狀 32 層、JSON model 2 MiB（D-029 的 IR 上限）、一筆 CSV record（含 header）與 JSON events 的一列（含前面的空白與逗號）以寫入的 bytes 計至多 1 MiB 為實作參數，待 benchmark（T-037；CB-39(c)）。所有上限都在讀取時強制，記憶體不隨檔案成長（T-016 review H1）：CSV 由 `internal/import/profile` 自己的掃描器讀取（與 `encoding/csv` 的 record、行號與錯誤相同，以 fuzz test 對照），record 超過 1 MiB 即停止，一列只保留 header 的欄位數再加一個欄位（其餘只計數），欄位長度邊讀邊計；JSON events 的 decoder 只能讀到上一列結尾之後 1 MiB，所以至多持有一列；已檢查過的值重讀時不再追蹤 member 名稱。以 20–50 MB 的惡意檔案量測，分配總量為 0.1–20 MiB（修正前最多 6.7 GB）。型別推斷只看非空值（空字串、JSON null 與缺少的 member 為空）：JSON 數字文法（`007`、`+5`、` 5` 為 string）、ASCII 的 `true`／`false`（不分大小寫）、帶 offset 的 RFC 3339 date-time；integer 與 number 合為 number，其餘不同型別為 mixed，JSON object 與 array 一律為 mixed；長度以 Unicode code point 計。Preview 為前 100 列的原始值：字串超過 256 字元時保留 255 字元加「…」，整個 preview 以資料庫儲存的大小計至多 1 MiB（第一個放不下的列與其後都不放）；JSON 數字照原文，除非資料庫會印出超過 400 字元，此時改存 binary64 的最短形式。每個 failure 都有 typed code、把檔案視為列陣列的 JSON Pointer（JSON model 為文件中的 pointer；至多 2,048 字元，過長時在 `/` 處截斷成祖先，T-016 review L1），訊息不引用檔案內容。
- **讀取（getImport）**：viewer 以上；UPLOADED 與 PROFILING 時 profile 為 null、preview 為空。Profile job 在 import 離開 profiling 之前 failed 或 cancelled 時，import 的 row 本身就是 FAILED，帶 job 的 error（job 沒有 error 時為 `JOB_CANCELLED` 或 `INTERNAL`）；API 照 row 顯示，不在讀取時推導（T-016 review M1）。FAILED 的 `error` 是契約的 error envelope：`details[0]` 帶 failure 自己的 code 與 pointer，`request_id` 為上傳的 request；`error.code` 的暫定對應見 CB-39。
- **Error report（downloadImportErrors）**：依 D-044 不發 signed URL（CB-38(b)）：在 transaction 中授權（viewer 以上）、確認 import 有 report 且 key 在本 import 自己的前綴之下，transaction 結束後才讀 object，大小與 SHA-256 都與 row 相同才以 `text/csv; charset=utf-8`、`Content-Disposition: attachment; filename="<import>-errors.csv"` 送出，否則 500 且不送任何 bytes；沒有 report 為 404。格式為 RFC 4180、CRLF、每個 cell 都加引號、UTF-8 加 BOM，header 為 `path,line,column,code,message,value`；每個 cell（去掉前導空白與引號後）以 =、+、-、@ 或其全形開頭，或以 tab、CR、LF 開頭者前面加 `'`；cell 內在 `,`、`;`、tab 或換行之後（去掉空白與引號後）以這些字元開頭者，在分隔字元之後加 `'`，試算表不論以何者切 cell 都不會執行公式（TEST-029，T-016 review M2）；至多 16 MiB，放不下的以最後一列 `ERRORS_TRUNCATED` 計數。Client 只送 import ID，不能指定 key 或 URL。

T-017 實作（`internal/import/mapping`、`internal/import/validation`、`internal/import/validator`、`internal/import/upload/mapping.go`、`internal/storage/imports/mapping.go`、migration 0014；D-070、D-071、D-072 PROPOSED；待獨立 review；DB 與 integration tests 在本分支 NOT RUN，見 checks/T-017_VALIDATION.md）：
- **Mapping（saveImportMapping）**：editor 以上；需要 `Idempotency-Key`（CB-18；fingerprint 為 import ID 與 body 的 canonical JSON，replay 仍需 editor 以上，demote 後為 403）。Body 為 `SaveMapping`：`expected_mapping_revision`、`mapping`（`import-mapping.schema.json`：每條只有 `source_column`、`target_field`、`transform`；transform 由 target field 決定）、`confirmed: true` 與 optional `confirmed_low_confidence`。在同一 transaction 中先鎖該 import 的 queued／running validation job、再鎖 import（job 在前，與 worker 的 Checkpoint／Finish 相同），檢查狀態與 revision，以 `mapping.Check` 對 profile 的欄名檢查（D-070：欄名存在且至多一次、metadata 以外的 field 只由一欄填入、case_id／event_type／timestamp 必有、至多 64 欄 metadata、每條的 transform、ready suggestion 的低信心條目已由人確認），通過後 `mapping_revision` 加 1、狀態 VALIDATING、清空上一次的 validation 與結果，排入該 revision 的 `import_validate` job（payload：import_id、mapping_revision、request_id），取消其他 revision 仍 queued 的 job，寫 `import.map` audit（只有數量：revision、匯入與略過的欄數、metadata 欄數、確認數、取消的 validation 數），回 202 與 import。Stale 或超前的 revision 為 409 `LIFECYCLE_CONFLICT`，`details[0].code` 為 `MAPPING_REVISION_CONFLICT`（`/expected_mapping_revision`）；UPLOADED／PROFILING 為 409 `IMPORT_NOT_PROFILED`，FAILED／COMMITTED 為 409 `IMPORT_FINAL`；mapping 被拒為 422 `REQUEST_VALIDATION_FAILED`，每個 issue 一個 detail（code 與 body 中的 JSON Pointer）；JSON model 為 422 `MAPPING_NOT_APPLICABLE`（`/mapping`，T-018）。被拒的 request 不寫任何 row。
- **Validation（`import_validate` job，`internal/import/validator`，只有 cmd/worker 連結）**：在 lease 下讀 import，只在它仍是 VALIDATING 且 revision 與 job 相同時才 validate；在 transaction 外讀 upload（核對大小與 SHA-256），以 `internal/import/profile` 的 `Scan` 讀每一列、`mapping.Plan.Apply` 轉成 canonical event（D-072 的值與列規則），全部讀完才決定：有不合法的列時寫 error report（`validation-errors-r<rev>-a<attempt>.csv`，T-016 的格式，value 欄空白）；全部合法時再讀一次 upload，把 canonical events 依列順序以 compact JSON array 串流寫入 `canonical-r<rev>-a<attempt>.json`（兩者都在 `tenant/<org>/imports/<import>/` 下，至多 256 MiB）。結果與 job 的 completed 同一 transaction：import 仍是 VALIDATING 且 revision 相同時寫 VALIDATED（`validation.valid=true`、canonical preview、dataset 的 key／SHA-256／大小）或 AWAITING_MAPPING（`validation.valid=false`、issues 至多 100、`invalid_rows`、report），檔案已不是 profile 的那份時 FAILED（`UPLOAD_CORRUPT`、`UPLOAD_MISSING`、`UPLOAD_CHANGED`）；否則什麼都不寫（stale-job fence，audit outcome `stale`）。`import.validate` worker audit 只有數量與 code。Object storage 失敗為可重試的 `OBJECT_STORAGE_FAILED`，沒有 object storage 為可重試的 `OBJECT_STORAGE_UNAVAILABLE`；attempt 用完或 job 被取消時 import 跟著 FAILED（0014 的 `follow_import_validate_job`）。
- **讀取（getImport）**：新增 `canonical_preview`（前 100 列的 canonical event，不合法的列為 null；VALIDATING 時為空）。FAILED 的 `error.request_id` 是失敗那一步的 request：存檔之後為該 revision 的 save，之前為 upload。`error.message` 改為中性的「the file could not be processed」，因為 validation 的失敗也用同一個 envelope。

APPROVED D-009 commit：驗 state/revision/base/current permission/valid rows→freeze dataset version→create generating proposal + inference job→標 COMMITTED→audit→202。report 中「import into model」在此解讀為交付審核 pipeline，不是直接 mutation。source JSON model identity/name/graph 差異都要展示；拒絕 proposal 後 dataset 已 commit 但 Twin hash 不變。

dataset model inference 可產生每 stage 的 empirical numeric snapshots，保留 parent_dataset_version_id 作 lineage。ready proposal 保存 candidate_dataset_bindings；批准時不得重新指向「最新 dataset」。原始 upload、error artifact 與推導樣本都為 tenant-private；retention TBD 不等於永久保留已獲同意。

## 6. Runs / async states / SSE

POST simulations 只接受 immutable model_version_id +（inline scenario_patch 或 scenario_id 二選一）+ explicit config。baseline 用 []。saved scenario 必須與 model_version_id 匹配；inline patch 是人類明確的 what-if request，仍完整 validator，不能允許 provider tool 直接呼叫此 route。enqueue 時 freeze engine_version、hashes、datasets、execution_limits；202 只在 resource+job transaction 已 commit 後回。

run states：queued→running→completed/failed/cancelled；queued 可直接 cancelled；暫時失敗 retry 可 running→queued，保留原 inputs。completed/failed/cancelled terminal 不可再更新或轉回 running。progress revision 單調增加；replication progress 可在 retry 時重新開始，UI 不把舊 attempt 進度當 completed 結果。

cancel queued 原子取消 job/run；cancel running 設 cancellation_requested；worker checkpoint 終止並 finalizes cancelled。completed/failed 取消回409，重複 cancelled 可回同一物件。result endpoint 對非 completed 回 RESULT_NOT_READY；partial attempt output 不得拿來分析。

SSE `/events` 是 progress snapshots，不是原始 simulation trace。使用 authenticated fetch streaming，避免 browser EventSource 無法設定 Authorization 而把 token 放 URL。id=run_id:progress_revision；Last-Event-ID 綁同 run；reconnect 送 latest snapshot，未保證全歷史 replay。重連／定期 poll 重新確認 token/membership，撤權或 expiry 關閉 stream。sampled playback 走獨立 authorized trace artifact endpoint。

T-023 實作（`internal/runs`、`internal/runs/runner`、`internal/storage/runs`、migration 0009）：
- **建立（createSimulation）**：先查 role（editor／owner）與 Idempotency-Key（D-011：同 key 同 body 回原 response，不同 body 409 `IDEMPOTENCY_KEY_CONFLICT`；fingerprint 為 canonical body），再於同一 transaction 凍結並入列：`model_version_id` 必須是本 organization 的 immutable version（schema 只接受 `mv_` ID，所以 model 或 draft 的 ID 為 422 `/model_version_id`；不存在或其他 organization 的 version 為 404）；`scenario_id` 必須存在且其 base 為該 version，否則 404／422（`/scenario_id`），不會退回 baseline；inline patch 與 saved scenario 的 patch 都經 scenario patch policy 與完整 validator（`/scenario_patch/...`），domain pack 的 error、dataset binding stage（hash、unit、zero-time）與 engine 自己的 `Compile` 也在入列前執行，所以入列的 run 不會因同樣的檢查在 worker 失敗；config 的 horizon／warmup 先換算 ticks（`/config/...`，422 `REQUEST_VALIDATION_FAILED`）。凍結的是 version 與其 hash、canonical patch、effective model hash（並確認 engine 以解碼後的 IR 重算會得到同一個值）、config 與 config hash、version 的整份 dataset manifest 與 manifest hash（`run_datasets` 與 deferred trigger）、engine version（`des-go-0.1.0`）與 server 的 execution limits（D-007；client 無法設定）。Run、job（payload 只有 `run_id` 與 `request_id`）、`simulation.create` audit（metadata 只有 version ID、replications、engine version 與凍結 input 的 hash：model、effective model、config、dataset manifest，不含 patch 或 config 的內容；SECURITY §9）與 idempotency response 同一 transaction commit 後才回 202 `RunAccepted`。需要 object storage（version 綁 dataset，或 `trace_level=sampled`）而 server 沒有設定時回 503，不入列。
- **讀取**：get、list（`/v1/models/{id}/simulations`，created_at／id 順序，cursor 綁 organization、model 與 list）、results（非 completed 一律 409 `RESULT_NOT_READY`，不回部分結果）都在 viewer 以上的 membership 下以 RLS 讀取；其他 organization 的 run 一律 404。Failed run 的 `error` 是 job 的 failure 換成 contract 的 error envelope（`request_id` 為建立 run 的 request）；run failure 的 code 對照見 CB-38（暫定，待 owner）。
- **取消（cancelSimulation）**：body 必須是 `{}`（`http.schema.json#/$defs/CancelSimulation`），Idempotency-Key 的 fingerprint 含 run ID（同一 key 用在另一個 run 為 409）。先鎖 job 再鎖 run（與 worker 的 finalize 同一順序）：queued 的 run 與 job 同時 cancelled（job 經 `jobs.CancelQueued`，run 由 0009 的 trigger 跟隨）；running 的 run 設 `cancellation_requested`，worker 在下一個 checkpoint（預設每秒）停止 engine 並以 cancelled 結束 job 與 run，不存結果；已 cancelled 的 run 原樣回 200（不再寫 audit）；completed／failed 回 409 `LIFECYCLE_CONFLICT`。每個有效果的取消寫一筆 `simulation.cancel` audit（`effect`：`cancelled` 或 `cancellation_requested`）。Cancel 與 complete 互斥：worker 存結果的 transaction 也先鎖 run，看到 cancellation 已請求就改為 cancelled、不存結果。
- **Trace（downloadSimulationTrace）**：D-044 不發 signed URL，所以 API 先在 transaction 中授權（viewer 以上的 membership、run completed、result 帶 trace、object key 在本 organization 的 `simulation-results` 之下），transaction 結束後才讀 object，大小與 SHA-256 都與 result row 相同才以 `Content-Disposition: attachment` 串流回 `TraceArtifact`；object 不見或內容不符一律 500，不送出任何 bytes（fail closed）。沒有 trace 的 run 為 404。
- **SSE（streamSimulationEvents）**：第一個事件一律是最新 snapshot；之後每次 poll（預設 1 秒）在新的 REPEATABLE READ transaction 中重新檢查 membership 與 role 再讀 run（TEST-026），revision 變了才送事件，靜默 15 秒送 `: keep-alive` comment；成員被移除（或 role 不再能讀 run）、token 到期、run 終態、連線 10 分鐘、client 離開或寫入逾時（每次寫入 10 秒；寫完後期限延到下一次可能的寫入之後，即 keep-alive＋poll＋10 秒，因為 HTTP/2 的 stream 在期限過了就被 reset，即使沒有寫入在進行，T-023 review I1）都結束 stream，client 重連時由一般的 request 授權（被拒時是一般的 error response）。降級為 viewer 仍可讀 run，所以 stream 繼續。Last-Event-ID 只接受本 run 的 `<run ID>:<revision>`，其他為 400。

## 7. Idempotency / crash recovery / fencing

Scope = organization_id + actor_id + operation/resource + key。request_hash 包含 normalized parsed body、URL resource、concurrency headers；multipart 用 file content hash+metadata。不可僅 hash body 而忽略 If-Match/expected base。相同 key+相同 fingerprint 回原 response；不同 fingerprint 回409。權限檢查在 replay 前仍必須執行；舊成功 response 不是撤權後的存取通行證。

reserve key 與 operation effect、audit、response 同一短 transaction；在處理 duplicate reservation 時鎖同一 key。LLM/DES 在 transaction 外。TTL 初始24h 是 D-007 提案；versions/source_proposal unique 與 result.run_id unique 仍保證 TTL 過後不重複 canonical effect。expired key cleanup 是受控 maintenance，不給一般 runtime arbitrary DELETE。

claim 用 organization filter + SKIP LOCKED + priority DESC/created_at/id。attempt 增加、lease_token 增加、lease_expires_at 保存；初始30s lease /10s heartbeat /max_attempts3 是候選。heartbeat/finalize 都核對 organization、job_id、worker_id、lease_token、running、not expired；更新零 rows 表示失去 ownership，不可重试 unscoped write。

result finalize transaction 鎖 job，再鎖 run，核實有效 lease +無 cancel flag；insert unique result、run completed、job completed、audit 同時 commit。lease expired 的舊 worker 永遠不能覆寫新結果。reaper 逐 tenant 處理 expired lease，先核實 retry budget；run frozen input 不變。non-transient validation/budget failure 不 retry；有限 exponential backoff 的參數仍需配置。T-019 的佇列與 worker 迴圈依 [ADR-024](adr/ADR-024-job-queue-and-worker.md)（ACCEPTED，H-010：30 s lease／10 s heartbeat／3 attempts、backoff 5 s 起倍增至多 5 min；queued 立即取消、cancel 與 complete 互斥；migration 0007 讓終態 job 不可改）；run 的 finalize、cancel flag 與 budget 屬 T-023。

APPROVED D-007：logical run 的 wall/event budgets 要包含 retries，而非每次重試重設。worker 使用 durable budget reservations、有限批次 credit 與外部 cancellation governor；engine 只讀授予的 budget/context，不直接讀 DB。實作時要測 crash 前已保留但未用完的 credit 可被保守消耗，不能超額。這一部分為 T-021/T-023 的必測項，不在本包聲稱已完成。

T-023 實作（`internal/runs/runner`、`internal/storage/runs`、`engine.Credit`）：attempt 開始的 checkpoint 鎖 run，確認仍為 queued、未請求取消、engine version 相同，再把 run 標為 running：第一次開始時寫入 `started_at` 與 `execution_deadline_at = now() + wall_timeout_seconds`（之後不重設），並保留第一批 events（`event_budget_reserved += min(剩餘, batch)`）；剩餘時間 ≤0 或之前的 attempt 已保留全部 events 時，attempt 以 `WALL_TIMEOUT_EXCEEDED`／`EVENT_BUDGET_EXCEEDED` 失敗（不重試）。Engine 只拿到 `max_events − 之前保留的量` 與剩下的 wall time；用完授予的 credit 時以 `Credit.Grant` 要求下一批，worker 在 lease 下以 fence（保留量必須仍是這個 attempt 上次寫的值）增加 `event_budget_reserved`，失敗（lease 失去、DB 錯誤）即停止 engine。所以之前 attempt 保留的量一律算作已用：crash 最多浪費最後一批中未用的部分（保守），全部 attempt 用掉的 events 不超過 max_events。結果 finalize 為 `handler.Run.Finish`：一個 transaction 鎖 job（lease fence）、鎖 run、確認沒有取消請求、insert result（0009 的 `check_simulation_result` 要求 run 為 running、未請求取消、engine version／seed／replications／四個 hash 都與凍結值相同）、run completed、`simulation.complete` audit（worker 身分，request_id 為建立 run 的 request）、job completed；lease 失去後這個 transaction 不會 commit。Trace 先上傳到這個 attempt 自己的 key，再在同一個 finalize transaction 中寫入 artifact ID、key、SHA-256 與大小（0009 要求四者同時存在、key 在本 run 的前綴之下、result 指名同一 artifact）。Progress 在每個 checkpoint 寫入（有變化時 revision 加一），並讀回 `cancellation_requested`。Job 的 retry、failure、reaper 與取消都經 0009 的 `follow_simulation_job` trigger 把 run 帶到同一狀態：retry 時 run 回到 queued、progress 歸零（保留量與 deadline 不變），failed 時 run 的 `error` 為 job 的 failure。

## 8. Relational model / constraints

| Tables | Responsibility / immutable boundary |
|---|---|
| users、organizations、memberships、projects | identity、scope、role；users 為 global auth identity 特例，其餘 tenant owned |
| models、model_drafts、model_versions | latest pointer、CAS draft（revision；`issues` 存寫入當時的語意 issues，D-028，migration 0003）、immutable full IR；parent 同 org/model；服務規則見 ADR-022（T-012） |
| datasets、dataset_versions、model_version_datasets | immutable object hash/unit/lineage；version binding 不指 mutable alias |
| imports、ai_proposals、scenarios | lifecycle、immutable review payload、scenario patch；source proposal unique effect |
| simulation_runs、run_datasets、simulation_results | frozen inputs、snapshot manifest、unique immutable result；mutable progress 與 input 分離 |
| ai_analyses | async analysis output + evidence；沒有 model write authority |
| jobs、idempotency_keys、audit_events | scoped execution leases、dedupe、append-only audit |

所有 tenant-owned table 帶 NOT NULL organization_id。composite FKs 保證 child 不能指不同 tenant/project/model 的 parent；單一 UUID/text FK 並不足夠。模型 version、scenario、dataset revision、binding、completed result、audit 有 immutable triggers + runtime grants；run input 有 guard trigger。DB JSONB shape checks 不取代 JSON Schema / semantic validator。

whole-manifest 另外存在 model_versions / simulation_runs 的 frozen dataset_bindings JSON；deferred constraint triggers 要求 relational bindings 在 commit 時完全一致，避免 immutable child 仍可被 late INSERT 改變 manifest。API 回傳 frozen parent manifest，不從可附加的 child collection 推導 authority。event_budget_reserved 與 execution_deadline_at 支援跨 retry budget；deadline/first start 不可重設，reservation 不可倒退。

T-006 起 schema 另強制（`db/tests/constraints.sql` 驗證）：每種 ID 有自己的 domain（`twin.org_id`、`twin.mdl_id`…，`<prefix>_<ULID>`，D-001），欄位不能放別種 ID；object key 以 `twin.object_key_ok` 檢查（`starts_with` 前綴；前綴之後只允許 server 產生的 ASCII 段 `[0-9A-Za-z_-][0-9A-Za-z._-]*`，以單一 `/` 分隔：因此拒 `..`、`.` 段、以 `.` 開頭的段、空段與結尾 `/`、`%` 編碼、反斜線、控制字元、Unicode 相似字元與格式字元；≤1024 字元＝bytes；D-035／CB-14，2026-10-15 review 收緊）；`logical_ref` 為 `twin.logical_ref` domain（`^dataset:[a-z0-9_.-]+$`），manifest 比對用 `ORDER BY logical_ref COLLATE "C"`，與 Go 的 byte 排序一致（D-034／CB-15）；ai_proposals 有 `server_risk_level`、`provider_risk_claim`，`risk_level` 必須等於兩者最大值（D-027）；immutable 表另有 BEFORE TRUNCATE guard（TRUNCATE 不經 row trigger 與 RLS）。

2026-10-15 review 後另強制（`constraints.sql`／`roles.sql` 驗證，SQL mutation 19/19）：(1) proposal 離開 generating 後，patch、risk、validation、expected_effects、questions、provider_metadata 等 review payload 一律不可改；approved／rejected／conflicted／invalid／failed 的 proposal 整列不可改；decided_by／decided_at／new_version_id／scenario_id 只能在決策 transition 寫入，decided_by 必須等於 transaction 的 `app.user_id`，decided_at 由 DB 設為 `now()`，rejected 也必須有 decided_by；approved 的 new_version_id（或 scenario_id）必須是 `source_proposal_id` 指回此 proposal 的那一筆。(2) worker 只能更新 generating 的 proposal；不能改 COMMITTED import，也不能改 import 的 mapping、mapping_revision、dataset_version_id、proposal_id 或身分欄位——由 trigger 強制，即使 worker 被誤授較大的 UPDATE（如 `pg_write_all_data`）也成立（D-037）。(3) actor_type='user' 的 audit event 必須等於 `app.user_id`，worker 不能以 user 身分寫 audit（twin_owner provisioning 例外）。(4) 所有 twin function 固定 `search_path = pg_catalog, pg_temp`，其他 schema 的同名函式／operator 不能 shadow。

T-024（migration 0011，接在 T-016 的 0010 之後，D-046 APPROVED）：`ai_proposals.id_pool` 是 proposal 建立時由 server 產生的 ID allocation pool（`common.schema.json#/$defs/IdAllocationPool`：node、flow、resource 各 16 個 `<kind>_<小寫 ULID>`，不重複）。欄位 NOT NULL；`twin.id_pool_ok(jsonb)`（IMMUTABLE STRICT，只授予 twin_api、twin_worker）的 CHECK 檢查 key 恰為三種、每種 16 個符合格式的字串、整個 pool 沒有重複；`protect_proposal_id_pool` trigger 拒絕任何 role（含 owner）修改它（55000），worker 本來就沒有該欄位的 UPDATE。已有 proposal 的資料庫拒絕套用 0011（要先清空 proposal；否則舊列沒有可回推的 pool）。`db/tests/proposals.sql` 驗證以上，`db/tests/pool_rows.sql` 驗證有資料時 0011 失敗且不留下半套改變。API 的 `Proposal` 不回傳 pool（CB-40(e)）。

T-025（migration 0012，接在 0011 之後，D-062 APPROVED，H-019）：`ai_proposals` 新增兩個建立後不可改的欄位：`output_locale`（en 或 zh-Hant，預設 en）與 `selected_entity_ids`（jsonb 字串陣列，至多 500 個）。新增 CHECK：只有 failed 帶 error；needs_input 有 questions，沒有 patch 與 risk；invalid 有 `validation.valid=false`，其他產生的內容都沒有（summary、assumptions、patch、patch_hash、expected_effects、questions、candidate_dataset_bindings、三個 risk 欄位、confidence）；failed 除 error 外沒有任何產生的內容，也沒有 provider_metadata（H-003 review L2）；provider_metadata 是 object。`protect_proposal_lifecycle` 的規則如下。

- 只有 API、worker 與 owner 能寫入。
- INSERT 只能是沒有任何產生內容、也沒有 decided_by／decided_at 的 generating（否則 55000）；API 的 created_by 必須等於 `app.user_id`（否則 42501）。
- ID、output_locale、selected_entity_ids、created_by、created_at 不可改。
- API 不能改 generating 的 proposal。
- generating → failed 只在這個 proposal 的 job 已 failed 或 cancelled 時允許（AFTER trigger 看得到 job 的新狀態；不再以 `pg_trigger_depth()` 判斷，H-003 review I1）。Job 一律以 queued 建立（0007），所以只有 `follow_proposal_job` 的那個 statement 會遇到這個情況。

Deferred constraint trigger `proposal_generated_with_its_job` 要求 generating → ready／needs_input／invalid 時，job 在 commit 前 completed。`follow_proposal_job`（jobs 的 AFTER UPDATE OF status）的規則：job completed 時 proposal 仍是 generating → 55000；job failed 或 cancelled 時 proposal 仍是 generating → proposal 轉為 failed，並帶 job 的 failure（預設 `JOB_CANCELLED` 或 `INTERNAL`），同時清空 generating 期間寫入的內容，讓 failed 的 CHECK 不會擋下 job 的結束。三個 function 都固定 `search_path`，並撤銷 PUBLIC 權限。測試在 `db/tests/proposal_jobs.sql`，`constraints.sql` 的 D-027 risk 組合改為由 worker 以 UPDATE 寫入。HTTP（`internal/proposals`）：stale base 回 409 `MODEL_VERSION_CONFLICT`，AI 關閉時回 503；failed 的 `error` 依 D-061 (c) 對應。

T-026（migration 0013，接在 0012 之後；D-068、D-069 PROPOSED）：`ai_proposals.decision_comment`（1–2000 字元，只在 approved 或 rejected，由決策寫入，之後隨 0001 不可改；worker 沒有它的 UPDATE 權限（column-level UPDATE grant 不含它），但以表級 SELECT 讀得到它）；conflicted 必須有 `decided_by` 與 `decided_at`（`ai_proposals_conflicted_decider`）；deferred constraint trigger `version_is_its_proposals_effect` 與 `scenario_is_its_proposals_effect`（function `twin.check_proposal_effect`，固定 `search_path`，撤銷 PUBLIC 權限）要求以 proposal 為來源的 version 或 scenario 在 commit 時是那個 approved proposal 自己的 effect：version 只屬於 edit proposal、`new_version_id` 指向它、parent 是 proposal 的 base、number 是 base 的加一（與 0001 的 unique `(organization_id, model_id, version)` 合起來，base 已不是 latest 的批准無法 commit）；scenario 只屬於 scenario proposal、`scenario_id` 指向它、base、patch、patch hash 都相同。沒有新表，所以 RLS、composite tenant FK 與 grant 都沿用 0002（API 對 ai_proposals 的表級 UPDATE 涵蓋新欄位）。`db/tests/proposal_decisions.sql` 驗證以上（API 與 schema owner）；`constraints.sql` 中已批准的 fixture 改放在它所接續的 base 上。
