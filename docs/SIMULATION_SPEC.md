# Native Go DES — Simulation Semantics & Engine Spec

SOURCE：原報告 pp. 19–22、33–35、44–46。**本文件的精確數學／排程細節來自 D-005 / D-006 / D-007 / D-010 / D-011（皆已批准；D-007 的數值為初始預設，待 T-037 benchmark），並非原報告已定義。** golden digest 由 engine 實作（T-020 起）產生後凍結。下面定義是一套可測的候選，不允許 agent 各自選擇互不相容的語義。

## 1. Execution model

Simulation 是 immutable ModelVersion + ordered Scenario Patch + frozen empirical manifest + RunConfig 的純執行。P0 engine 為 native Go discrete-event simulation；SimPy 僅 independent reference。每個 replication 單執行緒處理 event heap，replications 可在 bounded pool 平行；不得在同一 replication 用 goroutine scheduling 决定事件順序。

worker 在 engine 外負責授權、快照解析、dataset preload、job claim、timeout/cancellation、progress persistence、result atomic commit。engine 內無 network/DB/LLM、無任意 script。

H-016 的新 primitive（有限緩衝與阻塞、故障、班表、隨時間變化的投入、批次）提案見 [ADR-026](adr/ADR-026-line-flow-primitives.md) 與 D-047–D-057，2026-10-20 APPROVED（H-018）。T-046 phase 2 已把它們的 IR 成員、Result 成員與 trace 事件類型加入 contract（TWIN_IR_SPEC §2.1、本文件 §5、§9）。**有限緩衝與阻塞（queue `capacity`，D-049）自 des-go-0.2.0（T-047）起執行**，語義見 §3 的「有限緩衝與阻塞」一段；**resource 故障（`breakdowns`，D-051）與 lognormal、Weibull 分布（D-056）自 des-go-0.3.0（T-048）起執行**，語義見 §3 的「Resource 故障」一段與 §4；**班表（`calendars`、`calendar_id`、`shift_capacity`，D-052）與隨時間變化的投入（`arrival.schedule`，D-053）自 des-go-0.4.0（T-049）起執行**，語義見 §3 的「班表」一段與 §2 的「投入排程」一段；**批次 process（`batch`，D-054）與換線（`setups`，D-055）自 des-go-0.5.0（T-050）起執行**，語義見 §3 的「批次 process」與「換線」兩段（細節的解讀為 D-096、D-097，PROPOSED）；宣告式 metrics（D-058，T-051）在 T-051 實作之前，engine 不執行它們：Compile 對用到它們的模型回 `*engine.InputError`（PRIMITIVE_NOT_SUPPORTED，path 在 `/model` 之下；validator 已先拒絕，engine 另有自己的 kernel 支援清單，D-063 APPROVED，H-019），run 在入列時就是 422，不會被當作沒有這些成員而執行。沒有任何有限 buffer、故障、lognormal 或 Weibull 的模型，observation（含 seq）與 des-go-0.1.0 逐筆相同，Result 除 engine_version 外逐 byte 相同；有有限 buffer 而沒有故障、lognormal、Weibull 的模型與 des-go-0.2.0 逐筆相同；沒有班表與投入排程的模型與 des-go-0.3.0 逐筆相同，中性的班表（horizon 內每個 tick S＝C）與中性的投入排程（一段 rate 1/c 的 deterministic，c 使 1/c 與 τ 都精確，與 constant c 的 interarrival 同時刻）也是；沒有批次與換線的模型與 des-go-0.4.0 逐筆相同，中性的換線（只有一種 entity type、沒有 initial 或 initial 就是那一種）也是，批次沒有中性設定（D-047；T-046 phase 2 的 differential 見 checks/T-046_PHASE2_VALIDATION.md，T-047 的見 checks/T-047_VALIDATION.md，T-048 的見 checks/T-048_VALIDATION.md，T-049 的見 checks/T-049_VALIDATION.md，T-050 的見 checks/T-050_VALIDATION.md）。

## 2. Clock、event order、arrival

internal tick 固定 **1 millisecond**，int64；所有輸入換算成 tick 後做 overflow / safe bound 檢查。單位換算 second=1000、minute=60000、hour=3600000、day=86400000。非負 sample d 先換成 ms，再 round-half-up；sample>0 卻 round 為 0 時 clamp 到 1 tick，sample=0 保持 0。固定 engine numerical profile，不依不同語言的預設 rounding。實作為 `model.Ticks`（T-005）：一次 binary64 乘法後 `math.Round`（對非負值即 half up，且不像 `floor(x+0.5)` 有 0.49999999999999994 的進位誤差），超過 365 天回錯；config_hash、dataset binding 與 engine 共用此函式，修改即須換 engine_version。

heap key = (time_tick,event_priority,monotonic_sequence)。APPROVED priority（D-005、D-032）：SERVICE_COMPLETE=0，在同一事件內原子釋放資源後立即路由（進下一個 queue／delay／sink）；arrival、DELAY_COMPLETE 與其他 immediate state transitions=10，同樣立即路由；resource 狀態事件（FAILURE、REPAIR；CAPACITY_CHANGE（班表，T-049）；之後的批次 timeout，D-048）=15，在同 tick 的 arrival 之後、dispatch 之前，使 dispatch 看到該 tick 最後的 capacity（T-048）；internal resource dispatch=20，為該 tick 最後一步。route 不是獨立事件，entity 任何時刻恰處於一個狀態。release 在同 tick 的 dispatch 之前完成；sequence 在 replication 內 strictly increasing。Go map iteration、wall clock、worker scheduling 不得參與 tie-breaking。

source 第一個 arrival 在從 t=0 抽出的 interarrival 之後，而不是自動 t=0；其後每次 arrival 再排下一個。max_entities 若指定，限制該 source 的產生數；否則直到 horizon。多 source 的初始化按 node ID 排序，entity IDs 由 replication/source/local sequence 派生，不使用隨機 UUID。實作（`internal/simulation/engine`，T-020）：node、resource、flow 一律以 ID 的 bytes 排序後編號；ARRIVAL 事件依序 (1) 建立 entity、(2) 為同一 source 抽下一個 interarrival 並排程、(3) 交給 kernel 路由（T-021），此順序決定 sequence，因此決定同 tick 的先後（同 tick 同 priority 的事件依排程先後執行：多 source 只有第一輪依 source ID，之後依各自排程的時間點，例如 a 每 10、b 每 20 分鐘時，t=20 的 b 第 1 個先於 a 第 2 個）；entity ID 為 `r<replication index>/<source node ID>/<n>`（n 從 1 起；node ID 不含 `/`）；tick 晚於 horizon 的事件不排程（抽樣仍已消耗）；stream 依 (node, purpose) 首次使用時建立，彼此獨立，新增一個 source 不改變其他 source 的 arrival。

**投入排程（D-053；T-049，des-go-0.4.0；以下細節的解讀為 D-082，APPROVED，H-024）。** 有 `arrival.schedule` 的 source 不用 interarrival 分布。Rate 型（poisson、deterministic）：a₀＝0、aₖ＝aₖ₋₁＋Xₖ（deterministic 的 Xₖ＝1，不抽樣；poisson 的 Xₖ＝−ln(1−U)，從該 source 的 arrival stream 抽一次，U 先明確捨入再相減，避免 FMA），第 k 件在 tick(Λ⁻¹(aₖ)) 與上一件＋1 tick 中較大者（第一件的下限為 tick 0），a 保留未量化的值；Λ⁻¹ 依 D-053 的 numerical profile（P＝Λ(period) 依段順序累加、每個乘積先捨入；k＝⌈a/P⌉−1、r＝a−kP，修正一次使 r ∈ (0, P]；取第一個 rate > 0 且 cumEnd ≥ r 的段；τ＝k·period＋start＋(r−cumStart)/rate，clamp 到該段；以 sampler 的量化規則換成 tick，超過 365 天飽和、不處理）。晚於 horizon 的 arrival 不排程，抽樣已消耗。Table 型：period 與每列的 `at` 先各自以 `model.Ticks` 量化，第 k 個 period 的列在 k·period_ticks＋at_ticks；每列一個 ARRIVAL：先排下一列（這一列使 source 達到 max_entities 時不排），再依序建立這一列的 entity（列中達到 max_entities 即停，entity 編號連續），每建立一個就照現行路由；D-050 的檢查在整個事件之後一次。實作在 `internal/simulation/engine/release.go` 與 `replication.go`；`scripts/engine_reference.py` 逐運算移植 rate 的 profile，`engine-vectors.json` 的 `release_schedules`（27 個 Λ⁻¹ 步驟，含需要修正 r 的 P＝0.3、a＝502.5；4 個整段的 arrival run，共 4799 個 tick 與最後的 a 與 stream 狀態）逐 bit 固定；golden G-R1（a＝3 落在第一段的結束 3，不是 6）、G-R5（rate 在 tick 中改變、每件的量化）、G-R7（投入表、max_entities 在列中）、G-R8（投入表的 period 與 at 不是整數 tick：各自先量化，D-082 (b)；review round 1）、G-R9（rate 在上限，每 tick 一件，tick 嚴格遞增：ADR-026 原訂的 G-R5）手推，G-R3（common random numbers：一段 rate 加倍的 scenario 用同一組 draw）與 G-R4（中性）為測試。

所有 `event.time <= horizon` 都處理，包括 horizon 同 tick 產生的後續 immediate events；`>horizon` 不執行。horizon 不會自動 drain remaining work；在 horizon 仍未 completed 的 entity 是 censored，不能拿 horizon-arrival 當完整 lead time。zero-time cycles 在 compile 時拒絕（判定方式見 D-033：以分布可能的最小 tick 為準，empirical 於 dataset binding 階段判定），runtime 同時保留 visit/event caps。

## 3. Queue、resource、routing

process 可使用零個或多個 resource。requires bundle 採 all-or-nothing acquire；未湊齊不保留任何部分資源。FIFO request order 用 (queue_enter_tick,request_sequence)。dispatcher 按此序掃描：全部資源足夠、且沒有較早未授予且共享任一所需 resource 的 request，才可 grant；不共享 resource 的 request 可繼續進行。這是候選的 resource-wise FIFO，不是會阻塞所有獨立資源的 global head-of-line queue。

acquire→service_start→sample service duration→schedule complete；complete 原子釋放全部 units，再 route、觸發 dispatch。invariant：0≤in_use≤capacity；entity 同時最多在一個 queue/service/delay/sink 狀態；單一 entity 不會同時擁有兩次 service。

顯式 queue node 只把等待位置歸屬到接續 process；真正的 request buffer 不重複建立。沒有 queue node 時，queue 指標歸屬 process ID。顯式 queue 必須一個 outgoing process，process 至多一個顯式 queue upstream；其他 incoming direct route 仍進入相同 buffer，避免同 resource 出現兩份 metrics。

decision 依 flow ID 升序建立 cumulative probabilities，使用自己的 routing RNG。0% flow 永遠不被選；選第一個 U<cumulative 的 flow，最後一個作浮點容差兜底，但前提概率已通過 validator。非 decision 恰一條 p=1 route。failure/rework nodes 只產生對應 observation，再走明確 flow，不隱含 catch-all retry。

實作（`internal/simulation/engine/kernel.go`，T-021）：每個 resource 有一個 FIFO（依 (queue_enter_tick, request_sequence)）保存需要它的等待 request。依 resource-wise FIFO 規則，同一 resource 的 requests 彼此依序授予，因此只有「在自己每個 resource 的 FIFO 都排第一」的 request（candidate）可能被授予；dispatcher 依 sequence 檢查 candidates：bundle 每個 resource 都夠才授予（all-or-nothing），否則它留在最前面擋住共用這些 resources 的後來者，並標為 held，直到它的某個 resource 被釋放才再檢查（授予只會占用 units）；授予後下一個排到最前面的 request 若成為 candidate 就加入，順序與逐筆掃描完全相同（另以舊版逐筆掃描 kernel 做 differential 驗證）。每次 dispatch 只處理有變化的 candidates，成本不隨等待數增加（T-021 review 與複核）。一個依 FIFO 被擋住的 request 會擋住它 bundle 內所有 resources，即使其中某些 resource 有空（例：W1 要 R1（忙）、W2 要 R1+R2、W3 只要 R2：W3 等，R2 閒置）；這是已批准文字的直接結果。每次授予先回報 bundle 各 resource 新的 in-use，再開始 service、從該 process 的 service stream 抽樣，依授予順序。不需 resource 的 process 在該 tick 的 dispatch 開始服務。SERVICE_COMPLETE 先原子釋放全部 units，再在同一事件內路由；只要釋放了 resource 或有 request 進入 buffer，就確保該 tick 末有一次 dispatch；零時間 service 在 dispatch 之後同 tick 完成時會再排一次 dispatch（仍是 priority 20），等待者不會被擱置。visit 計數：source 為第 1 次，之後每進入一個 node 加 1，經過顯式 queue 時 queue 與其 process 各算一次；超過 max_entity_visits 回 `ErrEntityVisits`；系統內 entity 超過 max_active_entities 回 `ErrActiveEntities`；兩者都帶 entity、node／tick 並讓 run 失敗。sink 的 outcome=abandoned 記為未完成，但同樣離開系統；sink 未寫 outcome 時視為 completed（CB-22 的 sink 預設值）；entity 到達 sink 即釋放其紀錄，記憶體受 max_active_entities 限制。horizon 時仍在系統內的 entity 為 censored。kernel 以 `Observation` 回報事實（arrival、queue enter、service start／end、resource in-use、delay start／end、failure、rework、complete），依處理順序；指標彙整屬 T-022。以上實作解讀併入 D-038（2026-10-18 owner 批准）。

**有限緩衝與阻塞（D-049，blocking after service；T-047，des-go-0.2.0）。** 顯式 queue 的 `capacity` 限制它所命名的 process buffer 中等待、尚未授予的 entity 數（經 queue 或直接進入 process 都算；沒有 capacity 的 queue 與沒有 queue 的 process 仍為無限）。實作（`internal/simulation/engine/kernel.go`）：
- **先解析、後提交**：entity 離開 source（ARRIVAL）、process（SERVICE_COMPLETE）或 delay（DELAY_COMPLETE）時，路由先解析到它等待或離開的 node（decision 抽 routing、計 visit、記下經過的 failure／rework node），這一步不記 observation、不排事件；之後才提交。終點不是已滿的 buffer 時，observation 與 seq 和 des-go-0.1.0 完全相同（SERVICE_COMPLETE：釋放 bundle 的 ObsResource、ServiceEnd、priority 20 的 dispatch、路由 observation、進入 buffer／delay（delay 此時抽樣）／sink）。路由中途超過 `max_entity_visits` 時，錯誤前送出的 observation 也與 des-go-0.1.0 相同。
- **被擋**：終點是已滿的 buffer 時，entity 留在出發 node（ObsBlocked，Node＝出發 node、At＝路由到達的 queue 或 process）：process 保留整個 bundle（不釋放、不排 dispatch、不取 seq），source 形成 release backlog（投入時刻不變，lead time 從 arrival 起算），delay 不持有任何東西。被擋的 entity 依被擋的處理順序排在該 buffer 的 blocked FIFO；它不在任何 resource FIFO 中占位置，它持有的 unit 對任何 request 都不可用。同一 tick 兩個 entity 被同一 buffer 擋住時，依各自事件的處理順序（D-048；golden G-B3）。
- **解除**：只在 dispatch 內。授予使 buffer 少一件後（該次授予的 ObsResource、ServiceStart 與 service 抽樣之後），若有被擋的 entity，FIFO 最前面的一件立即移入：釋放出發 process 的整個 bundle（ObsResource；這些 resource 最前面的 held candidate 恢復為 candidate）、ObsUnblocked（Node＝出發 node）、以新的 request seq 排到 FIFO 最後（ObsQueueEnter，At＝路由當時到達的 node）。Dispatch 持續取 seq 最小的 candidate，直到沒有 candidate 放得下（fixpoint），連鎖在同一個 dispatch 內完成（golden G-B8）；dispatch 進行中的釋放與 enqueue 不再排 DISPATCH 事件。被擋 entity 的目標在解析時已固定，解除時不重抽、不再計 visit（G-B5）。
- **D-050 B1**：程式有有限 buffer 時，每個事件結束、且本 tick 沒有待執行的 dispatch 時（dispatch 結束時即屬此情形）檢查：有 blocked entity 或 held candidate，沒有服務中或 delay 中的 entity（其完成事件不論是否晚於 horizon 都算），且每個 held candidate 都放不下 → `engine.ErrDeadlock`（`*engine.DeadlockError`：偵測的 tick、最早被擋（依處理順序，不依被擋起的 tick 或 buffer 的 node 順序；golden G-D3）且仍被擋的 entity、其 node 與被擋起的 tick；沒有被擋的 entity 時為最早的 held request）。這是批准文字的**全域**定義：只要還有任何服務中或 delay 中的 entity 就不是 deadlock，所以循環旁若有一個一直在服務的不相關 process，循環上的 entity 會停到 horizon 而不報錯（只在 R1 被繞過時可能；D-064 (g)）。只在 dispatch 結束時檢查會漏掉「最後一個服務中的 entity 完成即被擋」而本 tick 沒有 dispatch 的情形（golden G-D2：7 分鐘），使 run 默默跑到 horizon；本 tick 有待執行的 dispatch 時延到它結束，所以不會誤報。沒有有限 buffer 的程式不檢查（D-047）。Valid 的模型因 R1 不會觸發（TWIN_IR_SPEC §4）。
- **驗證**：手推 golden（`testdata/simulation/blocking-goldens.json`，HAND_DERIVED_EXPECTATION_NOT_ENGINE_RUN）、只看 observation 的阻塞檢查器（`kernel_check_blocking_test.go`，含 R1 被繞過時每個 ErrDeadlock 都是真的全域循環等待、依全域定義沒有漏報）、凍結的 des-go-0.1.0 kernel（`frozen010_test.go`）對 50,000 個隨機模型的 differential 與中性 buffer（capacity ≥ max_active_entities）的 differential，以及 SimPy reference（`make simulation-reference-test`，§10）。

**Resource 故障（D-051，finish-first；T-048，des-go-0.3.0）。** 有 `breakdowns` 的 resource 的每個 unit u 有一個故障時鐘（alternating renewal）：TTF 由 (resource ID, `ttf/<u>`) stream、TTR 由 (resource ID, `ttr/<u>`) stream 抽樣（§4；首次使用時建立，所以多一個 unit 或另一個 resource 的時鐘不改變 unit u 的抽樣）。實作（`internal/simulation/engine/kernel.go`；以下細節的解讀為 D-074，APPROVED，H-022）：
- **t=0**：sources 依 ID 排第一個 arrival 之後，有故障的 resource 依 ID、unit 依 index 抽 TTF 並排 FAILURE（priority 15）；晚於 horizon 的 FAILURE／REPAIR 不排程、不取 sequence（抽樣已消耗），所以 TTF 為晚於 horizon 的 constant 時與沒有故障的模型逐筆相同（D-047 的中性設定）。
- **FAILURE(u)**：C − D − in_use > 0（有既不在使用中也未停機的 unit）時 unit 立即停機（D＋1，ObsResourceDown，At＝u、Value＝D），抽 TTR、排 REPAIR(u)；否則故障等待下一個變成可用的 unit（job 釋放的或修復好的；finish-first，服務中的 entity 做完才停；ObsBreakdownPending，Value＝等待中的故障數），依觸發順序排隊。
- **釋放**：bundle 釋放時，每個 resource 先回報新的 in_use（ObsResource），被釋放的 unit 依序給等待中的故障（每個 unit 一個，FIFO）：立即停機並抽 TTR、排 REPAIR，之後才喚醒該 resource FIFO 最前面的 held candidate（golden G-T4 的 tick 8 固定這個順序）。
- **REPAIR(u)**：D−1（ObsResourceUp），抽下一個 TTF、排 FAILURE(u)；修復好的 unit 與被釋放的 unit 一樣先給第一個等待中的故障（立即停機、抽 TTR、排 REPAIR；D-074 (a) 選項 B，T-048 review 第 1 輪 M1；golden G-F3、G-F3b、G-F9；先排 FAILURE(u) 再給等待中的故障的順序由 G-F9R10 固定），所以等待中的故障永遠不會與閒置的 unit 並存；沒有故障在等時 capacity 不經釋放而增加，所以喚醒該 resource FIFO 最前面的 held candidate，並在本 tick 末排 dispatch（若有喚醒）；把 unit 交給等待中故障的修復不喚醒、不排 dispatch（G-F10 的 sequence 與事件數）。TTR 為 0 的修復在同一 tick（priority 15，序號較後）執行，dispatch 之後才到時會再排一次 dispatch（G-T4）。
- **Dispatch**：candidate 的 bundle 只有在每個 resource 都滿足 in_use＋units ≤ C − D 時授予；放不下就 held，直到它的某個 resource 被釋放或修復。
- **D-050 B1**（有限 buffer 時）仍以全部 capacity C 判斷 release-bound：in_use＋units > C；放得下 C 但放不下 C − D 的 held candidate 是 capacity-bound，修復會讓它進入，不是循環等待（golden G-K1；把 `>` 改成 `>=` 的 mutant 必須被擋下）。
- **D-050 B2**（有故障時）：在每個 tick 的最後一個事件之後檢查（D-074 (c)）：held candidate 的 bundle 中沒有任何 unit 在使用中時，它在 B2 的狀態，since＝第一次在 tick 結束時處於這個狀態的 tick（tick 中被喚醒又 held 不重設）；TTRmax 為 bundle 中有故障的 resource 的 TTR 上界之最大值（constant 的值、triangular 的 max、empirical 的最大樣本；exponential、lognormal、Weibull 沒有上界，不檢查）；tick ≥ since＋TTRmax 時回 `engine.ErrStalled`（`*engine.StalledError`：tick、依 queue 順序最早的這種 request 的 entity、其 process、since 與 deadline）。在 tick 中間檢查會在修復稍後於同一 tick 讓它進入時誤報（golden G-S2）。Valid 的模型因 R3 不會觸發（TWIN_IR_SPEC §4）；golden G-S1 以繞過 validator 的 2-unit request 觸發。
- **驗證**：手推 golden（`testdata/simulation/breakdown-goldens.json`，HAND_DERIVED_EXPECTATION_NOT_ENGINE_RUN，每個 case 附推導）、只看 observation 的檢查器（`kernel_check_breakdown_test.go`：重建 in_use、D 與等待中的故障，檢查 finish-first、FIFO、constant 時鐘的時點、C − D 的 dispatch fixpoint、每個 ErrStalled 都在 B2 的狀態）、凍結的 des-go-0.2.0 kernel（`frozen020_test.go`）對 50,000 個隨機模型的 differential 與中性故障的 differential，以及 SimPy reference（§10）。故障與修復不是 entity 事件，不進 trace。

**班表（D-052，finish-first；T-049，des-go-0.4.0；以下細節的解讀為 D-081，APPROVED，H-024）。** 有 `calendar_id` 的 resource 的上班人數 S(t)：例外內 C（open）或 0（停工）；否則 t mod period 所在的 shift 的人數（label 的 `shift_capacity`，沒有 label 或沒有列出的 label 為 C），不在任何 shift 為 0；沒有 calendar 的 resource S＝C。S 由 `internal/model/calendar` 以整數 tick 計算（validator 的 R2、R4 與 kernel 共用，`model.Ticks` 量化）。實作（`internal/simulation/engine/kernel.go`）：
- **t=0**：sources 排第一個 arrival 之後，各 calendar（依 ID）排第一個 CAPACITY_CHANGE（priority 15），之後才是故障時鐘（D-048 的延伸；golden G-T5、G-D4C）；S(0) 由 Program 決定，不記 observation。
- **CAPACITY_CHANGE**：每個 calendar 同時只有一個待處理的，排在它的 resource 中任一個 S 下一次改變的 tick（晚於 horizon 的不排）；處理時先排同一 calendar 的下一個，再依 resource ID 設定 S，只對 S 改變的 resource 記 `ObsCapacity`（kind 16，Value＝新的 S；不進 trace）；S 增加的 resource 取消其 FIFO 最前面 held candidate 的 held（上班不經釋放就增加 capacity），有喚醒時在本 tick 末排 dispatch；S 減少不喚醒，服務中與被擋的 entity 照常完成（finish-first，超出的忙碌時間是 overtime）。S 在 horizon 內不變的 calendar（中性）不排事件、不取 sequence（golden G-C1、G-C2、G-C5、G-C7、G-C8、G-C9、G-K2；G-C9：下班時 held 在最前面的 request 不被喚醒、不排 dispatch）。
- **Dispatch**：candidate 的 bundle 只有在每個 resource 都滿足 in_use＋units ≤ min(S, C − D) 時授予。
- **故障時鐘只在上班時前進**（D-051 (ii)）：故障在 Θ(t) ≥ Θ(t_up)＋TTF 的最小 t，Θ(t) 為 [0, t) 中 S > 0 的 tick 數（含例外）；目標恰在一段上班的結束達到時，故障在該結束 tick（下班的 unit 算閒置，立即停機，G-T5）；搜尋到 horizon，之後的不排程；沒有 calendar 或永遠上班時為日曆時間（golden G-F6、G-C6、G-D5）。上班不滿足等待中的故障：故障只在 C − D − in_use＝0 時等待，S 的改變不釋放 unit（golden G-CF1）。
- **D-050 B1** 仍以全部 capacity C 判斷 release-bound，所以只被上班人數擋住的 held candidate 是 capacity-bound，上班會讓它進入（golden G-K2；把 `>` 改成 `>=` 的 mutant 必須被擋下）。
- **D-050 B2**：有故障或有 calendar 的程式在每個 tick 結束時檢查；request 進入狀態時算一次期限 next_fit(max(since, X_end)＋TTRmax)：沒有故障時 TTRmax＝0，X_end 為 bundle 各 calendar 最後一段例外的結束，next_fit 為從該 tick 起 bundle 的每個 resource 都有所需 units 上班的第一個 tick；horizon 前沒有時不檢查；`StalledError.Deadline` 為這個期限（golden G-D1 以繞過 R4 的模型觸發；G-D3C、G-D4C、G-D5 不可誤報）。

**批次 process（D-054；T-050，des-go-0.5.0；以下細節的解讀為 D-096，PROPOSED）。** 有 `batch` 的 process 的 buffer 依進入順序保存等待的 entity，它們沒有自己的 request（也不取 request sequence）；批次的 bundle 以批計。實作（`internal/simulation/engine/kernel.go`）：
- **就緒**：等待數 ≥ max_size，或 min_size < max_size 且等待數 ≥ min_size 且最老的已等 ≥ max_wait（等於上限的那個 tick 即就緒）。每次有 entity 進入 buffer、每次授予之後，以及 BATCH_TIMEOUT（priority 15）時檢查；就緒且沒有未授予的 batch request 時建立一個（取得 request sequence，進入它的 resource 的 FIFO）並在本 tick 末排 dispatch；沒有就緒的進入不排 dispatch（D-096 (e)）。
- **BATCH_TIMEOUT**：只在 min_size < max_size 時排程（min＝max 時 max_wait 不會讓批次開始，不排事件，D-096 (b)）：最老的未分批 entity 改變時（進入空的 buffer、授予後）排在它的進入時刻＋max_wait；已過期（進入時刻＋max_wait ≤ 現在）時不排，當場檢查；之前排的成為過時，到時忽略（D-096 (c)）。晚於 horizon 的不排程，但仍算待處理（見 B1）。
- **授予**：batch request 依 resource-wise FIFO 授予（bundle 的 ObsResource），取 min(等待數, max_size) 件（授予時刻的等待者，就緒後才進入的也算，D-096 (a)），依 FIFO：`ObsBatchStart`（kind 17，Value＝成員數，Batch＝本 process 的第 n 批，從 1 起）、各成員的 ServiceStart（Batch＝n）；從 (process, service) stream 抽一次，一個 SERVICE_COMPLETE；成員空出的位置讓同樣多個被擋的 entity 依序移入（D-049 的解除，D-096 (d)）；之後再檢查一次就緒，所以多個 unit 可在同一次 dispatch 各開一批。
- **完成**：先依 FIFO 解析每個成員的路由（routing draw 依成員順序；同一個有限 buffer 依序占位）。沒有成員被擋：bundle 釋放（ObsResource 一次）、排 dispatch，然後每個成員 ServiceEnd（Batch＝n）、路由的 observation、進入下一處；有成員被擋：不釋放，每個成員 ServiceEnd、路由的 observation，然後進入或 Blocked（Batch＝n），bundle 在最後一個被擋的成員移入時才釋放（只有那一次記 ObsResource）。路由的 visit 上限在第 j 個成員超過時，前面的成員已照上述提交，然後是第 j 個的 ServiceEnd 與錯誤（D-096 (f)）。
- **與故障、班表**：finish-first（整批做完）；批次 process 被擋時持有它的 bundle，是 D-050 的 holder（R1 照常檢查）。
- **D-050 B1 與 B2**（D-096 (g)；review 第 1 輪 M1、M2、L2 改寫）：還有待處理的 BATCH_TIMEOUT 時 B1 不判定 deadlock，過時的與晚於 horizon 的都算（ADR-026 D-050 B1：heap 中沒有 SERVICE_COMPLETE、DELAY_COMPLETE、BATCH_TIMEOUT，也沒有這些事件因晚於 horizon 被丟棄；G-BT19：循環旁一個不相關的批次，等待上限在 horizon 之後，run 跑到 horizon、不報錯；G-BT20：上限在 horizon 內，B1 等它與它開始的批次，之後報 ErrDeadlock。D-096 (g) 建議的 B 不計晚於 horizon 的逾時，修訂已批准的 ADR 文字，owner 批准之前不實作）。B1 與 B2 對 batch request 回報它的最老成員（授予時第一個被取的）。B2 的 since 與任何 request 相同，是第一次在 tick 結束時處於 B2 狀態的 tick（D-074 (c)），批次就緒時 bundle 還有 unit 在使用中的話晚於就緒的 tick（G-BT18）；B1 沒有被擋的 entity 時（`DeadlockError.Queued`）的 since 是 batch request 建立、即批次就緒的 tick（G-BT22；只在 validator 被繞過、所需 units 大於 capacity 時到得了）。
- **定義**：lead time 與 queue wait 照每件計，queue wait 從進入 buffer 到批次開始（含等待湊批）；utilization 是 chamber 的忙碌時間 ∫U／(C·T)（不是槽位）；批次統計見 §5。

## 4. RNG、seed derivation、determinism

候選 RNG = 本段明確定義的 SplitMix64，不使用 Go math/rand 的未固定預設 generator。所有 uint64 运算 mod 2^64：

```text
state += 0x9e3779b97f4a7c15
z = state
z = (z XOR (z >> 30)) * 0xbf58476d1ce4e5b9
z = (z XOR (z >> 27)) * 0x94d049bb133111eb
output = z XOR (z >> 31)
U = ((output >> 12) + 0.5) / 2^52       # strictly 0 < U < 1
```

replication_seed = first 8 bytes, little-endian, of SHA256(`dt-rep-v1\0` UTF-8 || uint64LE(base_seed) || uint32LE(replication_index))。index 從 0 起。stream seed = first 8 LE bytes of SHA256(`dt-stream-v1\0` || uint64LE(replication_seed) || uint32LE(len(node_id_bytes)) || node_id_bytes || uint32LE(len(purpose_bytes)) || purpose_bytes)。purpose = arrival/service/delay/routing；相互獨立。trace sampling 使用另一 purpose，不消耗以上 streams。Resource 故障（D-051，T-048）的 stream 以 resource ID 取代 node ID：unit u 的 TTF 為 purpose `ttf/<u>`、TTR 為 `ttr/<u>`（u 為十進位 unit index）；node 的 purpose 沒有 `/`，所以同 ID 的 node 與 resource 不共用 stream。

constant 不消耗 random draw。empirical 以 floor(U*N) 等權抽 samples；exponential = -mean*ln(1-U)；triangular 依標準 inverse CDF，min=mode=max 時視 constant；min/max 任一邊退化要避免除 0。所有 sample 再經同一 tick quantizer。T-020 補充：(a) exponential 樣本至少 1 tick（即使 mean 極小、乘積下溢為 0；D-033 視 exponential 恆 >0）；(b) 抽樣結果超過 365 天（只有 exponential 尾端可能）以 365 天＋1 tick 表示，必晚於任何 horizon，事件永不處理，tick 運算不會溢位；(c) triangular 用 `U < (mode-min)/(max-min)` 選分支；(d) decision 的 routes 只含 p>0 的 flow，依 flow ID 排序累加，浮點兜底因此不可能選到 0% flow；(e) triangular 的值在量化前 clamp 回 [min,max]（min=mode=1e-300、U=2^-53 時 max-sqrt(...) 恰為 0，會成為 D-033 禁止的零 interarrival；T-020 review）。以上 (a)–(e)、ARRIVAL 順序、entity ID 與下列 numerical profile 是 T-020 的實作語意，登記為 **D-038（2026-10-18 owner 批准，H-004；gate：T-023 對外提供結果前）**。

Lognormal 與 Weibull（D-056；T-048，des-go-0.3.0；範圍與數值細節為 D-075，APPROVED，H-022）：每個樣本一次 uniform。lognormal(mean, cv)：σ² = ln(1＋cv²)、μ = ln(mean) − σ²/2（compile 時算一次，乘積先捨入），x = exp(μ＋σ·Φ⁻¹(U))，Φ⁻¹ 為 AS241（Wichura 1988，PPND16，雙精度，48 個常數依 bit pattern 固定，`engine.ndtri`）。Weibull(shape, scale)：x = scale·exp(ln(−ln(1−U))/shape)。exp 不用平台的 `math.Exp`（amd64、arm64 等為 assembly，末位不同），改用固定的 `engine.exp`：Go `math.exp` 的 pure-Go 演算法（源自 FreeBSD e_exp.c），每個乘積以 `float64()` 捨入，結果以 `math.Ldexp` 縮放（精確，subnormal 時一次正確捨入）；結果為 normal number 時與真值的誤差小於 1 ulp（以 256-bit 的參考值抽測 300,000 個 [−710, 710] 的輸入，`TestExpAccuracy`；不是證明）。兩者與 exponential 一樣至少 1 tick（D-038 (a)）、超過 365 天時為 365 天＋1 tick（D-038 (b)）；compile 再檢查 0 < cv ≤ 10、0.1 ≤ shape ≤ 20（validator 的 DISTRIBUTION_INVALID，D-075）、mean／scale 換算後不超過 365 天（D-029、D-063 (c) 的 LIMIT_EXCEEDED）。在範圍內 |Φ⁻¹(U)| ≤ 8.21（U 的兩端 2⁻⁵³ 與 1−2⁻⁵³），σ ≤ √ln 101 ≈ 2.15，所以 exp 的引數 μ＋σz 至多 ln(mean)＋15.33（一個上界），不溢位；Weibull 的 shape 0.1 最多把 −ln(1−U) ≤ 36.8 放大為 36.8¹⁰ 倍 scale，超過 365 天即為上述的 365 天＋1 tick。`scripts/engine_reference.py` 逐運算移植 exp、AS241 與兩個 sampler；`engine-vectors.json` 加入 exp 與 ndtri 的常數、邊界與 10^6 個輸入的 SHA-256、lognormal 的 (μ, σ)、兩個 sampler 的 draw 向量與 digest、故障 stream 的向量與 priority 15 的事件順序，Go 必須逐 bit 相同；`make backend-numeric` 另要求各架構的組語中有 `engine.exp` 與 `engine.ndtri`。

Numerical profile（T-020 review 後）：ln 不用平台的 `math.Log`（amd64／s390x 為 assembly，其他 GOARCH 為 pure Go 且可能被編譯器融合為 FMA，末位不同），改用固定的 `engine.ln`：Go `math.log` 的 pure-Go 演算法（源自 FreeBSD e_log.c），每個乘積以明確 `float64()` 轉換捨入，Go 規格保證不融合，因此每步皆為一次 binary64 rounding；sqrt、round、floor、frexp 本身正確捨入或精確，可直接用。`scripts/engine_reference.py` 逐運算移植同一演算法；`testdata/simulation/engine-vectors.json` 保存 12-draw 向量、每個 sampler 10^5 次 draw 的 SHA-256（含量化前 binary64 值，因此公式或運算順序的任何改變都會被抓到，即使 tick 不變）、10^6 個 ln 輸入的 SHA-256、ln 常數 bit pattern 與邊界值、arrival 結束時的 stream state；Go 必須逐 bit 相同。`make backend-numeric`（`scripts/check_no_fma.sh`）檢查 engine 與結果統計程式在 amd64 v3、arm64、ppc64le、s390x、riscv64、loong64 的組語中沒有 fused multiply-add 也沒有呼叫平台 transcendental，並以 GOAMD64=v3（可融合 FMA）重跑數值測試。尚未在實體非 amd64 機器上執行測試（NOT RUN），因此跨架構的 byte-identical digest 仍不宣稱。算法、log/sqrt numerical profile 改變時必須換 engine_version，不把同一 human-readable semver 用於不同數值實作。

SOURCE invariant 仍為同 IR + engine version + run config + seed →同 aggregate digest；本草案另外固定 dataset manifest。Compile 不信任呼叫端：manifest 每個 binding 要通過 schema、依 logical_ref bytes 排序且不重複、涵蓋每個 empirical distribution，且 RunInput.Datasets 必須恰為 manifest 的 bindings（模型未用到的 binding 允許，與 datasets.Resolve 相同）。engine_version 要能唯一追到 container digest、source commit 與 numerical profile。跨架構的 byte-identical digest 未經測試不得宣稱；可部署同一受測 numerical profile 以維持承諾。

## 5. Warmup、metrics、統計 population

令 W=warmup tick，H=horizon tick，必須 0≤W<H≤365天（horizon cap 也是 D-005 候選）。觀測時間長度 T=H-W；邊界 events W≤t≤H 計入，time integral 取 [W,H]。warmup 前照常執行事件、維護資源與 queue，但 warmup 不重設系統狀態。

| 指標 | 候選定義 |
|---|---|
| throughput | 每個 replication 在 [W,H] 進入 completed sink 的 entity count；mean/p50/p95 跨 replications，不是每分鐘速率 |
| lead_time_minutes | arrival≥W 且 completion≤H 的完整 entity cohort；(completion-arrival)/60000；跨 replications pooled entity quantiles，另保留每 replication mean |
| queue wait | queue_enter≥W 且 service_start≤H 的完整 visit；包括零等待；重作每次 visit 都算一筆；不把未離隊 entity 當已知等待 |
| queue_length_mean | ∫queue_length(t)dt / T；從 W 的真實 queue state 積分 |
| utilization | ∫in_use(t)dt / (capacity*T)；含跨 W/H 的部分 service interval；跨 replications 算 mean |
| failure_count / rework_count | 在 [W,H] 執行 generic FAILURE/REWORK observation 的次數；不是 DORA failure rate |
| censored_entities | H 時仍 active 的 entities 數；呈現作截尾風險，不能納入 completed lead sample |

quantile 候選採線性插值 Type 7：排序 x，h=(n-1)*p；interpolate floor(h)/ceil(h)。mean 是該 population 的算術平均。禁止把「各 replication 的 p95 平均」稱為 pooled p95。

95% mean CI 採 independent replication mean 的 Student-t interval；n<2、replication 沒完整 cohort、沒有足夠 independent observations 時回 null + reason。對 lead time，CI 描述「replication mean 的平均」而非 pooled entity mean；UI 標示 estimand，不暗示 interval 對 p95 也有效。若要避免這個不同 estimand 混淆，可先令 pooled lead summary 的 CI=null，另在 additional_metrics 輸出 replication_mean_lead_time。**本草案採後者**：只有 population=replication 的 summary 可附此 CI。

產線流動的 Result 成員（D-058，T-046 phase 2 定名；只在模型用到對應功能時出現，所以沒有這些功能的 Result 與 digest 不變，D-047；**自 des-go-0.2.0（T-047）起產生有限 buffer 的三組**：模型有有限 buffer 時，每個 resource 都有 `resource_states[<resource>]` 的 `in_use_ticks`（∫U，與 utilization 同一積分）、`blocked_ticks`（∫K，被 blocked entity 持有的 unit）與 `scheduled_processing_ticks`（∫min(P, S)；沒有班表與換線時 S＝C、P＝U−K，即 `in_use_ticks − blocked_ticks`）；每個可能被擋的 node（source、process 或 delay，其路由可經 decision／failure／rework 到達有限 buffer）有 `blocking[<node>]`：視窗內開始的阻塞數、完整阻塞（開始 ≥ W、結束 ≤ H）的次數與總 tick、∫被擋 entity 數；每個有限 buffer 有 `buffers[<queue>].full_ticks`（等待數等於 capacity 的 tick 數）；實作在 `internal/results/metrics`，其他成員由 T-048–T-051 產生）：`metrics.domain`（DomainPack 的 model metrics，T-051：`des.Engine.ModelMetrics` 在 `DomainMetrics` 之後、digest 之前以 effective IR 的副本與 generic Result 呼叫 pack 的 `ComputeModelMetrics`（`domainpack.ModelMetricsProvider`），空的答案不寫此成員；電子產線 pack 的指標見 ELECTRONICS_LINE §5 與 §11，細節為 D-117，PROPOSED）；每個 replication 的 `replication_summaries[i].resource_states[<resource>]`（[W, H] 內的整數 tick 積分與次數：`in_use_ticks`、`scheduled_processing_ticks` 一律有；`blocked_ticks`（模型有有限 buffer）；`setup_ticks`、`setups_started`、`setups_completed`、`completed_setup_ticks`（setups）；`down_ticks`、`breakdowns_started`、`repairs_completed`、`completed_repair_ticks`（breakdowns）；`scheduled_ticks`、`scheduled_in_use_ticks`、`overtime_ticks`（calendar）；`available_ticks`、`idle_ticks`（breakdowns 或 calendar）；schema 以 `dependentRequired` 要求每組同時出現）、`blocking[<node>]`（`blocks_started`、`blocks_completed`、`completed_block_ticks`、`blocked_entity_ticks`）、`buffers[<queue>]`（`full_ticks`，D-049 的 buffer 滿比例）、`batches[<process>]`（`batches_started`、`members_started`）、`declared[<metric id>]`（宣告式指標的每個 replication 的值：system_wip 為數，flow_count／sink_count 為計數，period_throughput 為每期計數的陣列（至多 1000 期），不可用時為 null）；宣告式指標跨 replication 的 summary 在 `metrics.additional_metrics[<metric id>]`。各成員的定義與公式見 ELECTRONICS_LINE §5；由哪個任務產生見 TWIN_IR_SPEC §2.1。

有限 buffer 成員的計數細節（T-047；review 第 1 輪 I2 補寫，(e)(f) 是 D-064 的 (e)(f)，APPROVED，H-021）：`blocking` 的 key 是 source、process 與 delay 中，路由可經 decision、failure、rework node 到達有限 buffer 的 node；delay、sink 與無限 buffer 結束路由（所以 delay 之前的 source 不是 key，golden G-B12；經 failure node 的 process 是，G-B11）。阻塞在 [W, H] 內開始才計入 `blocks_started`（開始於 W 的也算，G-B4W）；完整阻塞是開始 ≥ W 且結束 ≤ H。同一 tick 中 arrival 與 DELAY_COMPLETE（priority 10）在 dispatch（priority 20）之前處理（D-048），所以到達時 buffer 已滿、在同一 tick 的 dispatch 中就解除的 entity，記為一次長度 0 的阻塞（blocked 與 unblocked 同 tick，G-B4 的 e3；D-064 (e)），UI 不應把它當成資料錯誤。被擋的 entity 在解除時才進入 buffer，queue wait 從解除起算，被擋的時間只算在出發 node 的 `blocking`（D-064 (f)）。`resource_states[].blocked_ticks` 以 unit 計：被擋的 entity 持有 bundle 中每個 resource 的全部 units（G-B10）。Run 因 B1 失敗時為不重試的 `SIMULATION_DEADLOCK`（API 顯示為 `MODEL_VALIDATION_FAILED`）；多個 replication 都 deadlock 時回報哪一個取決於 worker 的排程（§9 的 Engine 段），UI 只能說「某個 replication」，不能說「第一個」。

故障成員（T-048，des-go-0.3.0；細節為 D-074 (d)(e)，APPROVED，H-022）：每個有 `breakdowns` 的 resource 的 `resource_states` 有 `down_ticks`（∫D）、`breakdowns_started`（[W, H] 內開始的停機數，開始於 W 的也算，golden G-F1W10）、`repairs_completed` 與 `completed_repair_ticks`（完整修復：停機開始 ≥ W、修復 ≤ H，的次數與總 tick；TTR 為 0 的停機算一次開始、一次長度 0 的完整修復，golden G-T4）、`available_ticks`（∫A；沒有班表時 S＝C，A＝C − D，即 C·T − `down_ticks`）與 `idle_ticks`（∫max(0, A − U)；每個 tick U＋D ≤ C，所以等於 `available_ticks − in_use_ticks`）。沒有有限 buffer 時 `resource_states` 只列有故障的 resource（沒有 `blocked_ticks`；其他 resource 沒有任何功能適用，不列，golden G-F8）；有有限 buffer 時每個 resource 照舊都列，有故障的另加這一組。`resource_utilization` 不變（∫U／(C·T)，停機的 unit 不算在使用中）。Run 因 B2 失敗時為不重試的 `SIMULATION_STALLED`（API 顯示為 `MODEL_VALIDATION_FAILED`，`testdata/contracts/valid-run-failed-stalled.json`）。

班表成員（T-049，des-go-0.4.0；D-058，分母的標示為 D-084，APPROVED，H-024）：每個有 calendar 的 resource 的 `resource_states` 有 `scheduled_ticks`（∫S）、`scheduled_in_use_ticks`（∫min(U, S)）、`overtime_ticks`（∫max(U − S, 0)；兩者相加等於 `in_use_ticks`）、`available_ticks`（∫A，A＝min(S, C − D)）、`idle_ticks`（∫max(0, A − U)）與 `scheduled_processing_ticks`（∫min(P, S)，P＝U − K），以 U、S、D、K 同時的值積分（不能由各自的總和推得）。沒有有限 buffer 時 `resource_states` 列有故障或有 calendar 的 resource（golden G-C7：沒有被使用的 calendar resource 也列）。`utilization_mean` 與 `resource_utilization` 不變：分母仍是 C·T，含下班與停機的時間（D-052 (i)）；有班表的 resource 的 scheduled utilization 為 `scheduled_in_use_ticks`／`scheduled_ticks`，overtime 為 `overtime_ticks`，由 domain pack（ELECTRONICS_LINE §5，T-051）與 UI 計算並標示。

批次成員（T-050，des-go-0.5.0；D-058、D-096 (j)，PROPOSED）：每個批次 process 有 `batches[<process>]`（沒有批次開始也列，值為 0）：`batches_started`（[W, H] 內開始的批數）與 `members_started`（它們的成員數；平均批量＝members／batches，平均批量／max_size 由 domain pack 與 UI 計算）。批次本身不使 chamber 進入 `resource_states`（沒有有限 buffer、故障、班表或換線時不列）；有限 buffer 時一批的 bundle 在 `blocked_ticks` 只算一次，從第一個成員被擋到最後一個移入。

換線成員（T-050，des-go-0.5.0；D-058、D-097 (f)，PROPOSED）：每個有 setups 的 resource 的 `resource_states`（沒有有限 buffer 也列）有 `setup_ticks`（∫Z，Z 為換線中的 unit；跨 W、H 的換線依重疊計）、`setups_started`（[W, H] 內開始的換線數，0 tick 的也算）、`setups_completed` 與 `completed_setup_ticks`（完整換線：開始 ≥ W、結束 ≤ H，的次數與總 tick），以及 `scheduled_processing_ticks`＝∫min(P, S)，P＝U − K − Z（換線中的 unit 不是被擋的 unit；沒有班表時為 `in_use_ticks − blocked_ticks − setup_ticks`）。換線的結束沒有自己的 observation（在同一個 SERVICE_COMPLETE 的期間內），collector 以 min-heap 依 tick 處理，最後一個 observation 之後、H 之前結束的由 `Collector.Finish` 結束（G-SU9、G-SU12）；開始恰在 W 的換線算完整（G-SU11）。`utilization_mean` 與 `resource_utilization` 不變（U 含換線中的 unit）。

schema 中 `status=unavailable` 時 mean/p50/p95/CI 都是 null，reason 說明缺少什麼。沒有 completed entities 時 throughput=0 仍 available（有 replication count 樣本），lead time unavailable；缺 metric 不能回 0。

實作（`internal/results/metrics`，T-022；以下細節為 **D-039**，2026-10-18 owner 批准）：每個 replication 一個 `Collector`（engine Observer），依 replication_index 升序 `Build`；所有加總依固定順序，乘積明確捨入（與 D-038 同一 numerical profile，`make backend-numeric` 檢查）。schema 現在要求 unavailable 必有 reason，且只有 population=replication 可帶 CI（CB-23）；queue stats 同樣：unavailable 時 waits 為 null 且有 reason，available 時 waits 為數字且 sample_count≥1；resource 的 utilization_mean 為 null 時必有 reason（T-022 review）。available summary 的 reason 一律 null；n<2 時 CI 為 null，原因由 sample_count 表達（與 valid-result fixture 一致）。`additional_metrics.replication_mean_lead_time_minutes` 是各 replication cohort 平均的 summary，帶 CI；只要有一個 replication 沒有完整 cohort 就 unavailable（`REPLICATION_WITHOUT_COMPLETED_COHORT`，所有 replication 都沒有時為 `NO_COMPLETED_ENTITY_IN_WINDOW`），因為「replication means 的平均」此時沒有定義。queue wait 跨 replications pooled（每個 visit 一筆），沒有 visit 時該 queue unavailable（`NO_COMPLETED_QUEUE_VISIT_IN_WINDOW`）；queue_length_mean 與 utilization 是各 replication 時間積分的平均。reason codes 仍為暫定（CB-23）。IR 的 `metrics[]` 宣告尚未對應到 Result（CB-22 剩餘部分，T-029）。

## 6. DORA-oriented metrics 的 gating

本節適用 Software Delivery 範例 pack。P0 domain 自 H-016 起為電子組裝／測試線，其指標（FPY、站別 availability 等）與資料門檻由 T-046 定義（REQ-015；提案見 [ELECTRONICS_LINE.md](domains/ELECTRONICS_LINE.md) §5 與 D-058，APPROVED，H-018）；同一原則：未提供 mapping 一律 unavailable，不以 utilization 冒稱 OEE。

SOURCE 僅要求資料充足才計算；沒有提供完整 domain event taxonomy。APPROVED D-010：由 domain pack 保存明確 stage/event-to-milestone mapping 與 data-quality evidence，未提供 mapping 一律 unavailable。一般 source→sink lead time 不能自動當 Change Lead Time。

Change Lead Time 需要 change commit/deployed 關係與時間；Deployment Frequency 需要可辨識 production deployment 及觀測期間；Failed Deployment Recovery Time 需要 failure 與 recovery 配對；Change Failure Percentage 需要 deployment denominator 與 failure classification；Deployment Rework Rate 需要可辨識 rework deployment 與 denominator。公式、dedup/batching、calendar denominator 需在 DomainPack metric definition 明列並經 pilot 資料確認。P0 fixture 的 CI fail/rework 不足以冒稱 deployment failure/recovery。

## 7. Baseline / scenario comparison

比較前要求同 organization、model_version、engine numerical profile、dataset manifest、horizon、warmup、replications、seed；scenario_patch 不同是實驗變因。baseline patch 為 []。若條件不相同，回 comparable=false / reason，不以 inferential comparison 呈現；可保留並排 descriptive values。

absolute_delta=scenario-baseline；relative_delta=absolute_delta/baseline。baseline=0 時 relative_delta=null，reason=BASELINE_ZERO；任何一邊 unavailable 則相關 delta=null。API 提供實際計算值，AI 不重新發明。UI 的百分比為 relative_delta*100，不把 -0.11 當 -0.11%。source 中展示 -11% 等數字是示例，不是本包驗算結果。

matching seed/node streams 可用於 paired experiments，但 scenario topology 變更、不同 replication cohort 或不相容 config 時，不預設 paired CI 有效。P0 先只輸出已定義的 absolute/relative delta；paired difference CI 可在專門測試/評審後新增。

## 8. Execution budgets、progress、cancellation

初始候選：≤1000 replications；≤300s wall timeout/run；≤10M processed events/run（所有 replications 合計）；≤100k active entities/replication；≤10k node visits/entity；sampled trace≤100k events/run。warmup 事件同樣消耗 budget。API 不能接受使用者把上限調高；effective execution limits 在 enqueue 時保存。CPU/memory container limits 與 admission quotas 仍需獨立配置。

context checkpoint 至少每個 heap pop、每個 distribution 批量處理段、每次 replication、每個 artifact/aggregation batch。T-020 實作：每次 pop 先檢查 cancellation，再從整個 run 共用的 event budget 扣 1（含 warmup；平行 replications 以 atomic 計數，超過即 `ErrEventBudget`，run 失敗、不產生結果）；不變量被破壞回 `ErrInternal`，不會靜默略過。worker bounded polling 將 cancellation_requested 傳入 context。≤5s 是原報告待 benchmark 的目標，不是已測結果。timeout / event cap / active entity cap / cancellation 分別有 typed error；不要包裝為 completed。D-050 的 runtime backstop 另有兩個 typed error：`ErrDeadlock`（B1，循環等待；job failure code `SIMULATION_DEADLOCK`，T-047 實作：`internal/runs/runner` 記錄 `*engine.DeadlockError` 的 `Reason()`，不重試）與 `ErrStalled`（B2，bundle 永遠湊不齊；`SIMULATION_STALLED`，T-048 實作 TTR 的部分（§3）：runner 記錄 `*engine.StalledError` 的 `Reason()`，不重試；班表的部分屬 T-049），run failed、沒有部分結果；API 照 T-023 對 execution limit 的暫定對應以 `MODEL_VALIDATION_FAILED` 顯示，原 code 在 `details[0].code`（CB-38(a)；`simulation.schema.json` 的 `Run.error` 註解、`testdata/contracts/valid-run-failed-deadlock.json`、`valid-run-failed-stalled.json`）。

T-023 實作（`engine.Credit`、`des.Options`、`internal/runs/runner`）：event budget 改為分批授予的 credit。`engine.NewCreditBudget(limit, granted, credit)` 先授予 `granted` 個 events，用完時（在 mutex 下，同一時間只有一個 `Grant`，其他 replication 等它）呼叫 `Credit.Grant(ctx, granted)` 取得新的總授予量（必須大於舊值且不超過 limit，否則 `ErrInternal`）；已達 limit 時為 `ErrEventBudget`，Grant 的錯誤（含 context 取消、wall timeout）使 run 以該錯誤失敗，之後不再 Grant。每次 pop 的扣除照舊（先檢查 cancellation 再扣 1）；只有授予量改變，事件的處理順序、RNG 與結果不變：不同批次大小與 worker 數下 digest 相同（`des/credit_test.go`）。`des.Output.Events` 是實際用掉的 events。Worker 的 `Grant` 在 lease 下把 run 的 `event_budget_reserved` 由上次的值推進到新值才回傳，所以 engine 從不使用未保留的 events；batch 預設為 max_events 的十分之一（至少 1）。Retry 時 engine 的 limit 為 `max_events − 之前 attempt 保留的量`、wall timeout 為從第一次開始起剩下的時間（無條件進位到秒，且 attempt 另以絕對 deadline 結束）。Progress 由 worker 每秒寫入一次（engine 的 sink 只保留最新一筆）；同一個 checkpoint 讀回 `cancellation_requested`，已請求時以 `context.CancelCause` 停止 engine（engine 在下一個 pop 前看到），worker 以 cancelled 結束 job 與 run，不存結果。≤5 s 的取消目標在測試中實測（`TestCancelRunning`，見 checks/T-023_VALIDATION.md），不是 benchmark。

aggregate 依 replication_index 升序彙整；progress 不是 correctness input。所有 replications 完成後才可完成 run。重試使用原 frozen input；lease token 失效的 attempt 必須丟棄 finalize，不可覆蓋後來的成功結果。

## 9. Result digest / sampled trace

result_digest 的 payload（D-006 已批准，實作為 `hashing.Result`，T-005）：engine_version、metrics、replication_summaries、measurement_window、reproducibility（排除 result_digest 本身）；不含 run_id、status、created_at、wall duration、progress、worker ID、trace（含 object key）、LLM output。對此 payload 做 JCS + SHA-256；保留完整 numerical values，不因方便而捏造 round-trip equality；NaN／Infinity 無法序列化，回錯而非產生 digest。

## 10. 必備正確性案例

`testdata/simulation/` 提供**預期值 fixtures，不是已執行 Go engine 的成果**。首個案例：interarrival=10 min、service=5 min、capacity=1、100 entities、horizon=1010 min，第一個 arrival=10，最後 completion=1005；completed=100、wait=0、lead=5、utilization=500/1010。

congestion：interarrival=5、service=10、capacity=1、20 entities、horizon=205，完成 20、wait_i=5*i（i=0..19），wait mean=47.5、p95=90.25、utilization=200/205。原報告「queue grows」不能理解為每個 event 都單調；服務完成會降低 queue。候選驗收在 arrival 同 tick dispatch 完成後取樣，檢查 source active period 的 queue 趨勢。

還要測 100%/0% routing、same-tick release/arrival、bundle acquire、nonnegative capacity、zero-time cycle reject、empirical binding/hash mismatch、warmup cohort、horizon equality、censoring、worker retry determinism、cancel/finalize race。SimPy stochastic differential 比較 confidence/tolerance，不要求兩套 RNG byte-identical；tolerance 須先固定，不能看失敗結果再調到過。

有限緩衝與阻塞（T-047）的 SimPy reference：`make simulation-reference-test` 先以 `TestSimPyReferenceExport` 寫出 Go engine 對 reference cases 的每個 replication 結果，再由 `scripts/simpy_reference.py`（SimPy 4.1.2，只作獨立 reference，engine 不呼叫它）以 SimPy 自己的 resource 解讀同一個 IR：有限 buffer 是 capacity B 的「空位」resource，entity 在出發 process 完成後仍持有機台時 request 空位（沒有立即取得即為被擋），取得空位才釋放機台、再 request 下一站的機台、取得後歸還空位；source 的 entity 一到就 request 空位。確定性案例（G-B1、G-B1W、G-B2、G-B4、G-B4W、G-B7、G-B8、G-B9、G-B11、G-B12、G-B14）逐值比對手推的 service 開始、完成、每段阻塞與 Result 成員；G-B3（同 tick 的 tie-break，D-048）、G-B5（routing stream）、G-B10（units 2）與 G-D3 不比；G-B13 必須被腳本拒絕（見下）；G-D2 為示意（SimPy 不偵測 deadlock）。四個隨機案例（S1–S4，30 replications，Python 自己的 RNG）比對每個 replication 指標的平均，容差在 fixture 中預先固定：|Δ| ≤ 4·√(s²_go/n＋s²_simpy/n)＋0.5%·max(|平均|)。限制：腳本只接受每個需求都是 1 unit、每個 bundle 至多一個 resource 與其他 process 共用，且有共用 resource 的 bundle 中自己的每個 resource 的 capacity 都不小於共用的那個的模型；其他模型一律拒絕執行，fixture 中標為 refused 的 case（G-B13）每次都必須被拒絕。Bundle 逐一取得、取得後一起釋放：先取共用的，再依 capacity 由小到大（同 capacity 依 ID）取自己的。持有某個 resource 的 unit 的 entity 一定也持有排在它前面的每個 resource 的 unit，而每個 resource 的 capacity 不小於前一個，所以第一個取得之後，後面的一定有空 unit；整個 bundle 在第一個 resource（共用的，或沒有共用時最小的自己的）對它 FIFO 最前面的 request 有空 unit 時取得，正是 engine 的 all-or-nothing、resource-wise FIFO 授予的時刻。（T-047 review 第 1 輪 L1 更正：原文漏了 capacity 的條件；反例 G-B13：S（capacity 3）由 X、Y 共用，O（capacity 1）只屬 X，engine 依 resource-wise FIFO 在 11 才讓 Y 開始，逐一取得會讓 Y 在 3 就開始。第 2 輪 L1′ 更正：自己的 resource 原依 ID 取得，capacity 遞減時（G-B14：O1 capacity 2、O2 capacity 1）會先占住 O1 再等 O2，O1 的 in_use 為 29 分而 engine 為 20 分；改為依 capacity 由小到大。）

故障（T-048）的 SimPy reference：同一個 `make simulation-reference-test` 也讀 `testdata/simulation/breakdown-goldens.json`。腳本以 SimPy 自己的 primitive 解讀故障：有故障的 resource 是 `simpy.PriorityResource`，job 以 priority 0（彼此 FIFO）request；每個 unit 有一個交替 TTF、TTR 的故障時鐘 process：TTF 結束時若有既不在使用中也未停機的 unit（`len(users) < capacity`），以 priority −1 request（排在所有等待的 job 之前，SimPy 立即授予）並持有一個 TTR；否則故障依序等待下一個 job 釋放的 unit：job 把自己的 request 交給故障 process，而不是釋放（finish-first）。修復也一樣先把 unit 交給第一個等待中的故障，沒有故障在等時才釋放回 SimPy 的 queue、給等待中的 job（D-074 (a) 選項 B）。抽樣用 Python 的 `random`（expovariate、triangular、lognormvariate（σ² = ln(1＋cv²)、μ = ln(mean) − σ²/2）、weibullvariate），不用 engine 的 stream 或 sampler。確定性案例 G-F3、G-F3b、G-F7、G-F9、G-F9R10 逐值比對手推的 service 開始、完成、每段停機、等待中的故障與 Result 成員（含 `resource_states` 的故障組）；腳本只把等待時間為正的故障記為等待中的故障：等待 0 分鐘是同一時刻的故障與另一個事件（釋放或修復）的先後，SimPy 依排程先後、engine 依 D-048 處理，兩者都在同一時刻讓 unit 停機（G-F7 的 23、35 分；G-F9 的 30、45、60 分；G-F9R10 的 30、40、50、60 分），所以手推的等待中的故障也去掉等待 0 分鐘的再比對，停機本身逐筆比對；到 horizon 還在等的故障腳本不記，這樣的 case 不可比對而失敗。G-F1、G-F1W、G-F1W10、G-F2、G-T1、G-T2、G-T4（D-048 的同 tick 順序）、G-K1、G-S2（kernel 的 B1／B2）、G-D4、G-S1（SimPy 不偵測 deadlock 與 stall）、G-F10（兩個故障到 horizon 還在等）不比；G-F8 必須被腳本拒絕。四個隨機案例（B-S1–B-S4：exponential、Weibull 的 TTF、lognormal 的 TTR 與 service、三個 unit、有限 buffer 前的故障、兩個 process 共用的故障 resource；30 replications）以同一個預先固定的容差比對 completed、lead time、utilization、停機比例、available 與 idle 比例、開始的停機數，以及有限 buffer 的成員。限制（腳本在執行前檢查）：除了上一段的條件，有故障的 resource 必須是每個需要它的 bundle 中唯一的 resource（逐一取得時，等待其他 resource 期間持有的 unit 不能故障，engine 的 all-or-nothing 授予則讓閒置的 unit 可以故障，G-F8），分布只能是 constant、exponential、triangular、lognormal 或 Weibull（沒有 empirical）；其他模型一律拒絕。同 tick 的故障或修復與其他事件的順序是 kernel 的 D-048 順序，SimPy 不重現：有這種同 tick 的確定性案例標為不比；隨機案例的時間是連續的，在 SimPy 中這種同時發生的機率為 0，在 engine 的 1 ms tick 下也很少見，由容差涵蓋。

班表與投入排程（T-049）的 SimPy reference：同一個 `make simulation-reference-test` 也讀 `testdata/simulation/calendar-goldens.json`。有 calendar 的 resource 是 `simpy.PriorityResource`，下班的 unit 由 priority −0.5 的「blocker」request 持有（在故障的 −1 之後、job 的 0 之前）：腳本自己由 IR 計算 S(t)（不用 engine 的 calendar package），t=0 先以 blocker 擋住 C − S(0) 個 unit，S 減少時 request C − S 個 blocker（有空 unit 就立即取得，服務中的 job 先做完，即 overtime），S 增加時先取消還在等的 blocker、再釋放已取得的（unit 依 FIFO 給等待的 job）；calendar 的事件與有 calendar 的 resource 的故障時鐘、修復以 SimPy 的 URGENT priority 排程，在同時刻的 job 事件之前（對應 kernel 的 priority 15 先於 dispatch 20），彼此依排程先後；故障時鐘在上班時間上累積 TTF。投入表在 k·P＋A_j tick 依序投入（P 與 A_j 是 period 與該列的 at 各自量化後的 tick，D-082 (b) A，腳本自己由 IR 計算；review round 1 M1 之前誤以連續時間的 k·period＋at 投入）；deterministic 排程以 `fractions.Fraction` 精確計算 Λ⁻¹(k) 再依 D-053 量化（不用 engine 的浮點 profile）；poisson 以 Lewis–Shedler thinning（最大 rate 的齊次過程，每點以 λ(t)/λmax 保留，Python 的 random）產生。確定性案例 G-C1、G-C1W、G-C1W10、G-C2、G-C5、G-C6、G-C7、G-C8、G-C9、G-C10、G-F6、G-CF1、G-R1、G-R5、G-R7、G-R8、G-R9 逐值比對手推的 arrival、service 開始、完成、停機、等待中的故障、S 的每次改變與 Result 成員（含 `resource_states` 的班表組）；G-T5（故障恰在下班的 tick：腳本的 blocker 先取得下班的 unit，kernel 把它算作閒置）、G-K2（kernel 的 B1）、G-D1（SimPy 不偵測 stall）不比；G-C4、G-D4C（bundle 有兩個有 calendar 的 resource）、G-D3C（units 2）、G-D5（有故障的 resource 與夥伴同一 bundle）必須被腳本拒絕。四個隨機案例（C-S1–C-S4：兩班與停工的一天、每班 3／2／1 人與三段的 poisson 排程、有班表又會故障（Weibull TTF、lognormal TTR）且在有限 buffer 之後的站、deterministic 排程與投入表進入兩個不同班表的站；30 replications）以同一個預先固定的容差比對 completed、lead time、utilization、scheduled utilization、overtime／available／idle 比例、停機、阻塞的成員與每個排程段或投入列的件數。限制（腳本在執行前檢查）：有 calendar 的 resource 必須是每個需要它的 bundle 中唯一的 resource（逐一取得時，等待另一個 resource 期間持有的 unit 會在下班時被持有）；有 calendar 又會故障的 resource 的每班人數只能是 0 或 C（0 < S < C 時 blocker 持有的下班 unit 在 kernel 中是閒置的，故障可以取用，腳本的故障則會等待）；其他條件同上兩段。

批次與換線（T-050）的 SimPy reference：同一個 `make simulation-reference-test` 另以 `scripts/simpy_batch_reference.py`（SimPy 4.1.2）讀 `testdata/simulation/batch-goldens.json` 與 `setup-goldens.json`。站點由 D-054、D-055 的文字以 Python 寫成，跑在 SimPy 的 event queue 上：每個 event 以明確的 priority 排程（0 完成、1 arrival 與 delay 結束、2 故障、修復與等待上限、3 dispatch，同 priority 依排程先後），表達 D-048 的同一時刻順序；每個 resource 保存 unit 的狀態與設定、故障時鐘落在確定的 unit（D-097 (c)）；隨機抽樣用 Python 自己的 `random`。ADR-026 D-054 原訂的 SimPy 做法（`simpy.Store` 與向 chamber request 的 batcher process）沒有採用：Store 與 Resource 以 NORMAL priority 依建立先後授予，表達不了確定性案例依賴的 D-048 順序（偏差，記於 checks/T-050_VALIDATION.md）。確定性案例 G-BT1、G-BT2、G-BT3、G-BT6、G-BT7、G-BT8、G-BT10、G-BT11、G-BT14、G-BT15、G-BT21、G-SU1、G-SU2、G-SU3、G-SU6、G-SU7、G-SU8、G-SU11、G-SU12（後三個為 review 第 1 輪加入）逐值比對手推的 service 開始、完成、每批與其成員、每次換線與其 unit 和時間、停機、等待中的故障與 Result 成員；G-BT5（routing stream）、G-BT13、G-BT18（SimPy 不偵測 stall）、G-BT19、G-BT20、G-BT22（不偵測 deadlock）、G-SU5（stream identity）不比；G-BT4、G-BT12、G-BT17、G-SU10（有限 buffer）、G-BT9、G-SU9（班表）與 G-BT16（兩個 process 共用 resource）必須被腳本拒絕（批次與換線的 reference 沒有阻塞與班表；T-047、T-049 的 reference 沒有批次與換線，所以它們的組合只由手推 golden 與檢查器驗證）。八個隨機案例（BT-S1–BT-S4：一個或兩個 chamber、min／max／max_wait 的組合、三站的線、會故障的 chamber；SU-S1–SU-S4：一個與三個 unit、兩種與三種產品、initial 與 default、會故障的換線 resource、兩站都換線的線；30 replications）以同一個預先固定的容差比對 completed、lead time、utilization、開始的批數與成員數、換線比例與次數、停機比例。T-047–T-049 的 `scripts/simpy_reference.py` 拒絕有批次或換線的模型。
