# Native Go DES — Simulation Semantics & Engine Spec

SOURCE: original report pp. 19–22, 33–35, 44–46. **The exact math and scheduling details in this document come from D-005 / D-006 / D-007 / D-010 / D-011 (all approved; the D-007 values are initial defaults pending the T-037 benchmark); the original report does not define them.** Golden digests are produced by the engine implementation (from T-020 on) and then frozen. The definitions below are one testable candidate set; agents may not each choose mutually incompatible semantics.

## 1. Execution model

A simulation is a pure execution of an immutable ModelVersion + an ordered Scenario Patch + a frozen empirical manifest + a RunConfig. The P0 engine is a native Go discrete-event simulation; SimPy is only an independent reference. Each replication processes its event heap on a single thread; replications may run in parallel in a bounded pool. Goroutine scheduling must not decide event order within a replication.

Outside the engine, the worker handles authorization, snapshot resolution, dataset preload, job claim, timeout/cancellation, progress persistence and the atomic result commit. Inside the engine there is no network/DB/LLM and no arbitrary script.

The proposal for the new H-016 primitives (finite buffers and blocking, breakdowns, calendars, time-varying release, batches) is in [ADR-026](adr/ADR-026-line-flow-primitives.md) and D-047–D-057, APPROVED 2026-10-20 (H-018). T-046 phase 2 added their IR members, Result members and trace event types to the contract (TWIN_IR_SPEC §2.1; §5 and §9 of this document). **Finite buffers and blocking (queue `capacity`, D-049) run from des-go-0.2.0 (T-047)**; semantics are in the "Finite buffers and blocking" paragraph of §3. **Resource breakdowns (`breakdowns`, D-051) and the lognormal and Weibull distributions (D-056) run from des-go-0.3.0 (T-048)**; semantics are in the "Resource breakdowns" paragraph of §3 and in §4. **Calendars (`calendars`, `calendar_id`, `shift_capacity`, D-052) and time-varying release (`arrival.schedule`, D-053) run from des-go-0.4.0 (T-049)**; semantics are in the "Calendars" paragraph of §3 and the "Release schedules" paragraph of §2. **Batch processes (`batch`, D-054) and setups (`setups`, D-055) run from des-go-0.5.0 (T-050)**; semantics are in the "Batch processes" and "Setups" paragraphs of §3 (the detailed interpretations are D-096 and D-097, PROPOSED). Declarative metrics (D-058, T-051): until T-051 implements them, the engine does not execute them. Compile returns `*engine.InputError` for a model that uses them (PRIMITIVE_NOT_SUPPORTED, path under `/model`; the validator already rejects them first, and the engine keeps its own kernel support list, D-063 APPROVED, H-019), so such a run is a 422 at enqueue and is never executed as if those members were absent. For a model with no finite buffer, breakdown, lognormal or Weibull, the observations (seq included) are identical one by one to des-go-0.1.0, and the Result is byte-identical except for engine_version. A model with finite buffers but no breakdowns, lognormal or Weibull is identical one by one to des-go-0.2.0. A model with no calendar and no release schedule is identical one by one to des-go-0.3.0; so are a neutral calendar (S=C at every tick within the horizon) and a neutral release schedule (one deterministic segment with rate 1/c, where c makes 1/c and τ exact, at the same instants as a constant interarrival c). A model with no batch and no setup is identical one by one to des-go-0.4.0; so are neutral setups (only one entity type, and no initial or the initial is that type). Batches have no neutral configuration (D-047; the T-046 phase 2 differential is in checks/T-046_PHASE2_VALIDATION.md, T-047's in checks/T-047_VALIDATION.md, T-048's in checks/T-048_VALIDATION.md, T-049's in checks/T-049_VALIDATION.md, T-050's in checks/T-050_VALIDATION.md).

## 2. Clock, event order, arrival

The internal tick is fixed at **1 millisecond**, int64. Every input is converted to ticks and then checked for overflow / safe bounds. Unit conversion: second=1000, minute=60000, hour=3600000, day=86400000. A non-negative sample d is first converted to ms, then rounded half up; a sample>0 that rounds to 0 is clamped to 1 tick; sample=0 stays 0. The engine numerical profile is fixed and does not depend on any language's default rounding. The implementation is `model.Ticks` (T-005): one binary64 multiplication, then `math.Round` (for non-negative values this is half up, and it does not have the 0.49999999999999994 carry error of `floor(x+0.5)`); more than 365 days returns an error. config_hash, dataset binding and the engine share this function; changing it requires a new engine_version.

heap key = (time_tick,event_priority,monotonic_sequence). APPROVED priorities (D-005, D-032): SERVICE_COMPLETE=0, which atomically releases resources and then routes immediately within the same event (into the next queue/delay/sink); arrival, DELAY_COMPLETE and other immediate state transitions=10, also routed immediately; resource state events (FAILURE, REPAIR; CAPACITY_CHANGE (calendars, T-049); the later batch timeout, D-048)=15, after the same tick's arrivals and before dispatch, so that dispatch sees the tick's final capacity (T-048); internal resource dispatch=20, the last step of the tick. A route is not a separate event; an entity is in exactly one state at any time. Release completes before the same tick's dispatch; sequence is strictly increasing within a replication. Go map iteration, wall clock and worker scheduling must not take part in tie-breaking.

A source's first arrival comes after an interarrival drawn from t=0, not automatically at t=0; each arrival then schedules the next. max_entities, if given, limits how many entities the source produces; otherwise it produces until the horizon. Multiple sources are initialized in node ID order. Entity IDs are derived from replication/source/local sequence; no random UUIDs are used. Implementation (`internal/simulation/engine`, T-020): nodes, resources and flows are always numbered after sorting by the bytes of their IDs. An ARRIVAL event, in order, (1) creates the entity, (2) draws and schedules the next interarrival for the same source, (3) hands the entity to the kernel for routing (T-021). This order decides the sequence and therefore the order within a tick (events at the same tick and priority run in the order they were scheduled: with several sources only the first round follows source ID, after that each follows its own scheduled times; for example, with a every 10 and b every 20 minutes, b's 1st at t=20 comes before a's 2nd). The entity ID is `r<replication index>/<source node ID>/<n>` (n starts at 1; node IDs contain no `/`). Events whose tick is after the horizon are not scheduled (the draw is still consumed). Streams are created per (node, purpose) on first use and are independent of each other; adding a source does not change other sources' arrivals.

**Release schedules (D-053; T-049, des-go-0.4.0; the detailed interpretation below is D-082, APPROVED, H-024).** A source with `arrival.schedule` does not use an interarrival distribution. Rate type (poisson, deterministic): a₀=0, aₖ=aₖ₋₁+Xₖ (deterministic: Xₖ=1, no draw; poisson: Xₖ=−ln(1−U), drawn once from the source's arrival stream, with U rounded explicitly before the subtraction to avoid FMA). Item k arrives at the larger of tick(Λ⁻¹(aₖ)) and the previous item + 1 tick (the first item's lower bound is tick 0); a keeps its unquantized value. Λ⁻¹ follows the D-053 numerical profile (P=Λ(period) accumulated in segment order, each product rounded first; k=⌈a/P⌉−1, r=a−kP, corrected once so that r ∈ (0, P]; take the first segment with rate > 0 and cumEnd ≥ r; τ=k·period+start+(r−cumStart)/rate, clamped to that segment; converted to ticks with the sampler's quantization rule; beyond 365 days it saturates and is not processed). Arrivals after the horizon are not scheduled; the draw is already consumed. Table type: the period and each row's `at` are each quantized first with `model.Ticks`; the row in period k is at k·period_ticks+at_ticks. Each row is one ARRIVAL: it first schedules the next row (not when this row brings the source to max_entities), then creates this row's entities in order (stopping within the row when max_entities is reached; entity numbers are consecutive), routing each one under the current rules as it is created; the D-050 check runs once after the whole event. Implemented in `internal/simulation/engine/release.go` and `replication.go`. `scripts/engine_reference.py` ports the rate profile operation by operation, and `release_schedules` in `engine-vectors.json` (27 Λ⁻¹ steps, including P=0.3, a=502.5, which needs the r correction; 4 whole-segment arrival runs, 4799 ticks in total, plus the final a and stream state) fixes it bit for bit. Goldens G-R1 (a=3 falls on the end 3 of the first segment, not 6), G-R5 (rate changes within a tick; per-item quantization), G-R7 (release table, max_entities within a row), G-R8 (release table whose period and at are not whole ticks: each is quantized first, D-082 (b); review round 1) and G-R9 (rate at the cap, one item per tick, ticks strictly increasing: the G-R5 originally planned in ADR-026) are hand-derived; G-R3 (common random numbers: a scenario that doubles one segment's rate uses the same draws) and G-R4 (neutral) are tests.

Every event with `event.time <= horizon` is processed, including follow-on immediate events produced at the horizon tick; events at `>horizon` do not run. The horizon does not automatically drain remaining work. An entity not completed at the horizon is censored; horizon-arrival must not be used as a complete lead time. Zero-time cycles are rejected at compile time (D-033 defines the test: the smallest tick the distribution can produce; empirical distributions are decided at the dataset binding stage); the runtime also keeps visit/event caps.

## 3. Queue, resource, routing

A process may use zero or more resources. The requires bundle is acquired all-or-nothing; an incomplete bundle holds no partial resources. FIFO request order uses (queue_enter_tick,request_sequence). The dispatcher scans in this order: a request may be granted only if all its resources suffice and no earlier ungranted request shares any of its required resources; requests that share no resource may proceed. This is the candidate resource-wise FIFO, not a global head-of-line queue that would block all independent resources.

acquire→service_start→sample service duration→schedule complete; complete atomically releases all units, then routes and triggers dispatch. Invariants: 0≤in_use≤capacity; an entity is in at most one queue/service/delay/sink state at a time; one entity never holds two services at once.

An explicit queue node only attributes the waiting place to the following process; the real request buffer is not created twice. Without a queue node, queue metrics are attributed to the process ID. An explicit queue must have exactly one outgoing process, and a process has at most one explicit queue upstream; other incoming direct routes still enter the same buffer, so the same resource never has two sets of metrics.

A decision builds cumulative probabilities in ascending flow ID order and uses its own routing RNG. A 0% flow is never chosen; the first flow with U<cumulative is chosen, and the last one is the floating-point tolerance fallback, provided the probabilities have passed the validator. A non-decision node has exactly one p=1 route. failure/rework nodes only produce the corresponding observation and then follow an explicit flow; there is no implicit catch-all retry.

Implementation (`internal/simulation/engine/kernel.go`, T-021): each resource has a FIFO (by (queue_enter_tick, request_sequence)) holding the waiting requests that need it. Under the resource-wise FIFO rule, requests for the same resource are granted in order among themselves, so only a request that is "first in the FIFO of each of its resources" (a candidate) can be granted. The dispatcher checks candidates in sequence order: it grants only when every resource of the bundle suffices (all-or-nothing); otherwise the request stays at the front, blocking later requests that share these resources, and is marked held; it is checked again only when one of its resources is released (a grant only takes units). After a grant, the request that moves to the front is added if it becomes a candidate; the order is exactly the same as a one-by-one scan (verified by a differential against the old one-by-one-scan kernel). Each dispatch handles only the candidates that changed, so its cost does not grow with the number of waiting requests (T-021 review and re-check). A request held back by FIFO blocks all resources in its bundle, even if some of them are free (example: W1 needs R1 (busy), W2 needs R1+R2, W3 needs only R2: W3 waits and R2 stays idle); this follows directly from the approved text. Each grant first reports the new in-use of every resource in the bundle, then starts service and draws from the process's service stream, in grant order. A process that needs no resource starts service in that tick's dispatch. SERVICE_COMPLETE first atomically releases all units, then routes within the same event. Whenever a resource is released or a request enters a buffer, a dispatch is ensured at the end of that tick; when a zero-time service completes in the same tick after the dispatch, another dispatch is scheduled (still priority 20), so waiting requests are not left behind. Visit counting: the source is visit 1, each node entered after that adds 1, and passing an explicit queue counts once for the queue and once for its process. Exceeding max_entity_visits returns `ErrEntityVisits`; more than max_active_entities entities in the system returns `ErrActiveEntities`; both carry the entity and node/tick and fail the run. A sink with outcome=abandoned records the entity as not completed, but the entity still leaves the system; a sink with no outcome counts as completed (the CB-22 sink default). An entity's record is released when it reaches a sink; memory is bounded by max_active_entities. Entities still in the system at the horizon are censored. The kernel reports facts as `Observation`s (arrival, queue enter, service start/end, resource in-use, delay start/end, failure, rework, complete) in processing order; metric aggregation belongs to T-022. These implementation interpretations are folded into D-038 (approved by the owner 2026-10-18).

**Finite buffers and blocking (D-049, blocking after service; T-047, des-go-0.2.0).** An explicit queue's `capacity` limits the number of waiting, not yet granted entities in the buffer of the process it names (entering via the queue or directly into the process both count; a queue without capacity and a process without a queue remain unlimited). Implementation (`internal/simulation/engine/kernel.go`):
- **Resolve first, commit after**: when an entity leaves a source (ARRIVAL), a process (SERVICE_COMPLETE) or a delay (DELAY_COMPLETE), the route is first resolved to the node where it waits or leaves (decisions draw routing, visits are counted, the failure/rework nodes passed are noted); this step records no observation and schedules no event. Only then is it committed. When the destination is not a full buffer, the observations and seq are exactly those of des-go-0.1.0 (SERVICE_COMPLETE: the ObsResource of the released bundle, ServiceEnd, the priority-20 dispatch, the routing observations, entering the buffer/delay (the delay draws at this point)/sink). When `max_entity_visits` is exceeded mid-route, the observations emitted before the error are also the same as in des-go-0.1.0.
- **Blocked**: when the destination is a full buffer, the entity stays at its departure node (ObsBlocked, Node=departure node, At=the queue or process the route reached): a process keeps its whole bundle (no release, no dispatch scheduled, no seq taken), a source forms a release backlog (the release instant is unchanged; lead time counts from arrival), and a delay holds nothing. Blocked entities queue in the buffer's blocked FIFO in the order in which they were blocked; a blocked entity takes no place in any resource FIFO, and the units it holds are unavailable to every request. When two entities are blocked by the same buffer in the same tick, they follow the processing order of their own events (D-048; golden G-B3).
- **Unblocking**: only inside dispatch. After a grant leaves the buffer one item shorter (after that grant's ObsResource, ServiceStart and service draw), if there are blocked entities, the one at the front of the FIFO moves in at once: the departure process's whole bundle is released (ObsResource; the held candidates at the front of those resources become candidates again), ObsUnblocked (Node=departure node), and the entity joins the end of the FIFO with a new request seq (ObsQueueEnter, At=the node the route reached at the time). Dispatch keeps taking the candidate with the smallest seq until no candidate fits (fixpoint), so a chain completes within one dispatch (golden G-B8); releases and enqueues during a dispatch do not schedule further DISPATCH events. A blocked entity's target was fixed at resolution; unblocking does not redraw and does not count the visit again (G-B5).
- **D-050 B1**: when the program has a finite buffer, the check runs at the end of each event when no dispatch is pending in this tick (the end of a dispatch is such a case): there is a blocked entity or a held candidate, no entity is in service or in a delay (their completion events count whether or not they fall after the horizon), and no held candidate fits → `engine.ErrDeadlock` (`*engine.DeadlockError`: the detection tick; the earliest-blocked entity that is still blocked (by processing order, not by the tick it was blocked at or by the buffer's node order; golden G-D3), its node and the tick it was blocked at; when no entity is blocked, the earliest held request). This is the **global** definition of the approved text: as long as any entity is in service or in a delay there is no deadlock, so if an unrelated process next to the cycle is always serving, the entities on the cycle stay stuck until the horizon without an error (possible only when R1 is bypassed; D-064 (g)). Checking only at the end of a dispatch would miss the case where "the last entity in service is blocked on completion" and the tick has no dispatch (golden G-D2: 7 minutes), letting the run silently go on to the horizon; when a dispatch is pending in the tick, the check waits until the dispatch ends, so there are no false reports. Programs without finite buffers are not checked (D-047). Valid models never trigger it because of R1 (TWIN_IR_SPEC §4).
- **Validation**: hand-derived goldens (`testdata/simulation/blocking-goldens.json`, HAND_DERIVED_EXPECTATION_NOT_ENGINE_RUN); an observation-only blocking checker (`kernel_check_blocking_test.go`, including that, when R1 is bypassed, every ErrDeadlock is a real global circular wait and that none is missed under the global definition); a differential against the frozen des-go-0.1.0 kernel (`frozen010_test.go`) on 50,000 random models and a differential for neutral buffers (capacity ≥ max_active_entities); and the SimPy reference (`make simulation-reference-test`, §10).

**Resource breakdowns (D-051, finish-first; T-048, des-go-0.3.0).** Each unit u of a resource with `breakdowns` has a breakdown clock (alternating renewal): TTF is drawn from the (resource ID, `ttf/<u>`) stream and TTR from the (resource ID, `ttr/<u>`) stream (§4; created on first use, so an extra unit or another resource's clock does not change unit u's draws). Implementation (`internal/simulation/engine/kernel.go`; the detailed interpretation below is D-074, APPROVED, H-022):
- **t=0**: after the sources schedule their first arrivals in ID order, resources with breakdowns (in ID order, units in index order) draw TTF and schedule FAILURE (priority 15). A FAILURE/REPAIR after the horizon is not scheduled and takes no sequence (the draw is consumed), so with a constant TTF beyond the horizon the run is identical one by one to a model without breakdowns (the D-047 neutral configuration).
- **FAILURE(u)**: when C − D − in_use > 0 (some unit is neither in use nor down), a unit goes down at once (D+1, ObsResourceDown, At=u, Value=D), draws TTR and schedules REPAIR(u). Otherwise the breakdown waits for the next unit that becomes available (released by a job or repaired; finish-first: an entity in service finishes before the unit stops; ObsBreakdownPending, Value=number of pending breakdowns); pending breakdowns queue in trigger order.
- **Release**: when a bundle is released, each resource first reports its new in_use (ObsResource); the released units go in order to the pending breakdowns (one unit each, FIFO): each goes down at once, draws TTR and schedules REPAIR; only then is the held candidate at the front of that resource's FIFO woken (tick 8 of golden G-T4 fixes this order).
- **REPAIR(u)**: D−1 (ObsResourceUp), draw the next TTF, schedule FAILURE(u). Like a released unit, a repaired unit first goes to the first pending breakdown (it goes down at once, draws TTR, schedules REPAIR; D-074 (a) option B, T-048 review round 1 M1; goldens G-F3, G-F3b, G-F9; G-F9R10 fixes the order: schedule FAILURE(u) first, then serve the pending breakdown), so a pending breakdown never coexists with an idle unit. When no breakdown is pending, capacity grows without a release, so the held candidate at the front of that resource's FIFO is woken and a dispatch is scheduled at the end of the tick (if anything was woken); a repair that hands its unit to a pending breakdown wakes nothing and schedules no dispatch (the sequence and event count of G-F10). A repair with TTR 0 runs in the same tick (priority 15, later sequence number); if it comes after the dispatch, another dispatch is scheduled (G-T4).
- **Dispatch**: a candidate's bundle is granted only when every resource satisfies in_use+units ≤ C − D; if it does not fit, it is held until one of its resources is released or repaired.
- **D-050 B1** (with finite buffers) still uses the full capacity C to decide release-bound: in_use+units > C. A held candidate that fits C but not C − D is capacity-bound; a repair lets it in, and it is not a circular wait (golden G-K1; a mutant that changes `>` to `>=` must be caught).
- **D-050 B2** (with breakdowns): checked after the last event of each tick (D-074 (c)). A held candidate is in the B2 state when no unit of its bundle is in use; since = the first tick at whose end it is in this state (being woken and held again within a tick does not reset it). TTRmax is the largest TTR upper bound among the bundle's resources with breakdowns (the value of a constant, the max of a triangular, the largest sample of an empirical; exponential, lognormal and Weibull have no upper bound and are not checked). When tick ≥ since+TTRmax, `engine.ErrStalled` is returned (`*engine.StalledError`: the tick; the entity of the earliest such request in queue order, its process, since and deadline). Checking in the middle of a tick would report falsely when a repair later in the same tick lets the request in (golden G-S2). Valid models never trigger it because of R3 (TWIN_IR_SPEC §4); golden G-S1 triggers it with a 2-unit request that bypasses the validator.
- **Validation**: hand-derived goldens (`testdata/simulation/breakdown-goldens.json`, HAND_DERIVED_EXPECTATION_NOT_ENGINE_RUN, each case with its derivation); an observation-only checker (`kernel_check_breakdown_test.go`: rebuilds in_use, D and the pending breakdowns, and checks finish-first, FIFO, the instants of constant clocks, the C − D dispatch fixpoint, and that every ErrStalled is in the B2 state); a differential against the frozen des-go-0.2.0 kernel (`frozen020_test.go`) on 50,000 random models and a differential for neutral breakdowns; and the SimPy reference (§10). Breakdowns and repairs are not entity events and do not enter the trace.

**Calendars (D-052, finish-first; T-049, des-go-0.4.0; the detailed interpretation below is D-081, APPROVED, H-024).** The on-shift capacity S(t) of a resource with `calendar_id`: inside an exception, C (open) or 0 (closed); otherwise the capacity of the shift containing t mod period (the label's `shift_capacity`; C for no label or an unlisted label), and 0 outside every shift. A resource without a calendar has S=C. S is computed in integer ticks by `internal/model/calendar` (shared by the validator's R2 and R4 and by the kernel; quantized with `model.Ticks`). Implementation (`internal/simulation/engine/kernel.go`):
- **t=0**: after the sources schedule their first arrivals, each calendar (in ID order) schedules its first CAPACITY_CHANGE (priority 15), and only then the breakdown clocks (an extension of D-048; goldens G-T5, G-D4C). S(0) is set by the Program and records no observation.
- **CAPACITY_CHANGE**: each calendar has only one pending at a time, scheduled at the next tick at which S changes for any of its resources (none after the horizon). Processing first schedules the same calendar's next one, then sets S in resource ID order, recording `ObsCapacity` (kind 16, Value=the new S; not in the trace) only for resources whose S changed. A resource whose S increases clears the held flag of the held candidate at the front of its FIFO (a shift start adds capacity without a release), and if anything was woken, a dispatch is scheduled at the end of the tick. A decrease of S wakes nothing; entities in service and blocked entities finish as usual (finish-first; the busy time beyond the shift is overtime). A calendar whose S does not change within the horizon (neutral) schedules no events and takes no sequence (goldens G-C1, G-C2, G-C5, G-C7, G-C8, G-C9, G-K2; G-C9: at a shift end, the request held at the front is not woken and no dispatch is scheduled).
- **Dispatch**: a candidate's bundle is granted only when every resource satisfies in_use+units ≤ min(S, C − D).
- **Breakdown clocks advance only on shift** (D-051 (ii)): the breakdown happens at the smallest t with Θ(t) ≥ Θ(t_up)+TTF, where Θ(t) is the number of ticks in [0, t) with S > 0 (exceptions included). When the target is reached exactly at the end of an on-shift period, the breakdown happens at that end tick (an off-shift unit counts as idle and goes down at once, G-T5). The search runs to the horizon; later breakdowns are not scheduled. Without a calendar, or when always on shift, this is calendar time (goldens G-F6, G-C6, G-D5). A shift start does not serve pending breakdowns: a breakdown waits only when C − D − in_use=0, and a change of S releases no unit (golden G-CF1).
- **D-050 B1** still uses the full capacity C to decide release-bound, so a held candidate blocked only by the on-shift capacity is capacity-bound, and a shift start lets it in (golden G-K2; a mutant that changes `>` to `>=` must be caught).
- **D-050 B2**: programs with breakdowns or calendars check at the end of each tick. When a request enters the state, the deadline next_fit(max(since, X_end)+TTRmax) is computed once: without breakdowns TTRmax=0; X_end is the end of the last exception of the bundle's calendars; next_fit is the first tick from that tick on at which every resource of the bundle has the required units on shift; if there is none before the horizon, there is no check. `StalledError.Deadline` is this deadline (golden G-D1 triggers it with a model that bypasses R4; G-D3C, G-D4C and G-D5 must not report falsely).
- **Validation**: hand-derived goldens (`testdata/simulation/calendar-goldens.json`, 24 of them, HAND_DERIVED_EXPECTATION_NOT_ENGINE_RUN, each with its derivation); an observation-only checker (`kernel_check_calendar_test.go`: rebuilds S(t) and Θ from the IR alone, and checks grants against min(S, C − D), exactly one Capacity observation per change of S, the instants of constant clocks on shift time, the instants of release tables and deterministic schedules, and B2's since and deadline); a differential against the frozen des-go-0.3.0 kernel (`frozen030_test.go`) on 50,000 random models and differentials for neutral calendars and neutral schedules; the SimPy reference (§10); and the independent Python implementation planned in ADR-026 D-050 (`scripts/calendar_reference.py`, `make simulation-reference-test`): it computes R2, R3, R4, next_fit, X_end and TTRmax from the IR alone and compares them with Go's validator and compiler on 5,000 random models (review round 1 L2; R1 is not covered, see checks/T-049_VALIDATION.md).

**Batch processes (D-054; T-050, des-go-0.5.0; the detailed interpretation below is D-096, PROPOSED).** The buffer of a process with `batch` keeps the waiting entities in entry order; they have no request of their own (and take no request sequence); the batch's bundle is counted per batch. Implementation (`internal/simulation/engine/kernel.go`):
- **Ready**: waiting count ≥ max_size, or min_size < max_size and waiting count ≥ min_size and the oldest has waited ≥ max_wait (ready at the tick the wait equals the limit). Checked each time an entity enters the buffer, after each grant, and at BATCH_TIMEOUT (priority 15). When ready and there is no ungranted batch request, one is created (it takes a request sequence and enters its resources' FIFOs) and a dispatch is scheduled at the end of the tick; an entry that does not make the batch ready schedules no dispatch (D-096 (e)).
- **BATCH_TIMEOUT**: scheduled only when min_size < max_size (when min=max, max_wait never starts a batch and no event is scheduled, D-096 (b)). When the oldest unbatched entity changes (entry into an empty buffer, after a grant), it is scheduled at that entity's entry time+max_wait; if already expired (entry time+max_wait ≤ now), it is not scheduled and the check runs on the spot; the previously scheduled one becomes stale and is ignored when it fires (D-096 (c)). One after the horizon is not scheduled but still counts as pending (see B1).
- **Grant**: a batch request is granted under resource-wise FIFO (the bundle's ObsResource) and takes min(waiting count, max_size) items (those waiting at grant time, including ones that entered after it became ready, D-096 (a)), in FIFO order: `ObsBatchStart` (kind 17, Value=number of members, Batch=this process's n-th batch, from 1), then each member's ServiceStart (Batch=n); one draw from the (process, service) stream and one SERVICE_COMPLETE. The places the members free let the same number of blocked entities move in, in order (D-049 unblocking, D-096 (d)). Readiness is then checked again, so several units can each start a batch in the same dispatch.
- **Completion**: first each member's route is resolved in FIFO order (routing draws in member order; places in the same finite buffer are taken in order). If no member is blocked: the bundle is released (ObsResource once) and a dispatch is scheduled, then for each member ServiceEnd (Batch=n), the routing observations and entry into the next place. If a member is blocked: no release; for each member ServiceEnd and the routing observations, then entry or Blocked (Batch=n); the bundle is released only when the last blocked member moves in (ObsResource is recorded only that once). When the j-th member exceeds the routing visit limit, the earlier members have already been committed as above, followed by the j-th member's ServiceEnd and the error (D-096 (f)).
- **With breakdowns and calendars**: finish-first (the whole batch finishes); a blocked batch process holds its bundle and is a D-050 holder (R1 is checked as usual).
- **D-050 B1 and B2** (D-096 (g); rewritten in review round 1 M1, M2, L2): while a BATCH_TIMEOUT is still pending, B1 does not declare a deadlock; stale ones and ones after the horizon both count (ADR-026 D-050 B1: the heap has no SERVICE_COMPLETE, DELAY_COMPLETE or BATCH_TIMEOUT, and none of these events was dropped for falling after the horizon; G-BT19: an unrelated batch next to the cycle whose wait limit is after the horizon: the run goes to the horizon without an error; G-BT20: the limit is within the horizon: B1 waits for it and for the batch it starts, then reports ErrDeadlock. Option B recommended in D-096 (g) would not count timeouts after the horizon; it amends the approved ADR text and is not implemented before the owner approves it). For a batch request, B1 and B2 report its oldest member (the first one taken at grant). B2's since is the same as for any request: the first tick at whose end it is in the B2 state (D-074 (c)); if a unit of the bundle is still in use when the batch becomes ready, it is later than the ready tick (G-BT18). When B1 has no blocked entity (`DeadlockError.Queued`), since is the tick the batch request was created, that is, the tick the batch became ready (G-BT22; reachable only when the validator is bypassed and the required units exceed capacity).
- **Definitions**: lead time and queue wait are counted per item; queue wait runs from entering the buffer to the batch start (including waiting for the batch to fill); utilization is the chamber's busy time ∫U/(C·T) (not slots); batch statistics are in §5.
- **Validation**: hand-derived goldens (`testdata/simulation/batch-goldens.json`, 22 of them, HAND_DERIVED_EXPECTATION_NOT_ENGINE_RUN, each with its derivation; G-BT1–G-BT5 are G-T1–G-T5 of ADR-026 D-054, renamed because G-T was already used for the D-048 same-tick goldens; G-BT15 (max_wait 0: no timeout scheduled) and G-BT16 (the order of a stale timeout and two processes' requests in the same tick) were added after mutation run 1, G-BT17 (two members of the same batch blocked at once: the bundle counts only once in K) after run 2; review round 1 added G-BT18 (B2's since later than the ready tick), G-BT19, G-BT20 (BATCH_TIMEOUT after and before the horizon, and B1), G-BT21 (a batch process without resources: the batch end schedules no dispatch) and G-BT22 (B1's Queued since for a batch request), of which G-BT18–G-BT20 and G-BT22 bypass the validator); an observation-only checker (`kernel_check_batch_test.go`: rebuilds from the IR alone the buffer, the batch request and its FIFO position, BATCH_TIMEOUT and its staleness, and checks grants, members, completion, ticks without observations, and B1, B2); member routing draws computed from the stream itself (G-BT5) and one service draw per batch (`TestBatchServiceDrawsOncePerBatch`); visit limits at batch end charged to their own members (`TestBatchVisitsChargedToTheirMember`); a differential against the frozen des-go-0.4.0 kernel (`frozen040_test.go`) on random models without batches and setups (batches have no neutral configuration, D-047); and the SimPy reference (§10).

**Setups (D-055; T-050, des-go-0.5.0; the detailed interpretation below is D-097, PROPOSED).** A resource with `setups` keeps unit identity: each unit is in use, down or idle, and has the entity type it is set up for (`initial`; without it, not yet set up). The capacity rule is still a count (in_use+units ≤ min(S, C − D)). The product is the entity's `entity_type` (that of its source). Implementation (`internal/simulation/engine/kernel.go`):
- **Grant**: after the bundle's ObsResource, among units that are neither in use nor down, take the lowest-index one whose setup matches the product, otherwise the lowest-index one (D-097 (b): off-shift units are not identified separately). When the unit's setup differs from the product, a setup happens: take the transition for (current setup, product), the default if there is none, and 0 ticks if there is no default either (still one setup, D-097 (a)). With a distribution, draw once from (resource ID, `setup/<u>`) (created on first use; a constant does not draw), then draw service from (process, service) as usual; record `ObsSetup` (kind 18: Entity, Node=process, Resource, At=unit, Value=setup ticks), then ServiceStart; the unit is set to that product. A unit not yet set up takes its first item without a setup and records no observation.

## 4. RNG, seed derivation, determinism

Candidate RNG = SplitMix64 as defined explicitly in this section; Go math/rand's unpinned default generator is not used. All uint64 arithmetic is mod 2^64:

```text
state += 0x9e3779b97f4a7c15
z = state
z = (z XOR (z >> 30)) * 0xbf58476d1ce4e5b9
z = (z XOR (z >> 27)) * 0x94d049bb133111eb
output = z XOR (z >> 31)
U = ((output >> 12) + 0.5) / 2^52       # strictly 0 < U < 1
```

replication_seed = first 8 bytes, little-endian, of SHA256(`dt-rep-v1\0` UTF-8 || uint64LE(base_seed) || uint32LE(replication_index)). index starts at 0. stream seed = first 8 LE bytes of SHA256(`dt-stream-v1\0` || uint64LE(replication_seed) || uint32LE(len(node_id_bytes)) || node_id_bytes || uint32LE(len(purpose_bytes)) || purpose_bytes). purpose = arrival/service/delay/routing; the streams are independent of each other. Trace sampling uses another purpose and consumes none of these streams. Resource breakdown streams (D-051, T-048) use the resource ID in place of the node ID: unit u's TTF uses purpose `ttf/<u>` and its TTR `ttr/<u>` (u is the decimal unit index); node purposes contain no `/`, so a node and a resource with the same ID do not share a stream.

A constant consumes no random draw. empirical draws samples with equal weight by floor(U*N); exponential = -mean*ln(1-U); triangular uses the standard inverse CDF and is treated as a constant when min=mode=max; a degenerate side (min or max) must avoid division by 0. Every sample then goes through the same tick quantizer. T-020 additions: (a) an exponential sample is at least 1 tick (even when mean is tiny and the product underflows to 0; D-033 treats exponential as always >0); (b) a draw beyond 365 days (possible only in the exponential tail) is represented as 365 days + 1 tick, which is always after any horizon, so the event is never processed and tick arithmetic cannot overflow; (c) triangular picks its branch with `U < (mode-min)/(max-min)`; (d) a decision's routes contain only flows with p>0, accumulated in flow ID order, so the floating-point fallback can never pick a 0% flow; (e) a triangular value is clamped back to [min,max] before quantization (with min=mode=1e-300 and U=2^-53, max-sqrt(...) is exactly 0, which would be a zero interarrival, forbidden by D-033; T-020 review). The above (a)–(e), the ARRIVAL order, entity IDs and the numerical profile below are T-020's implementation semantics, recorded as **D-038 (approved by the owner 2026-10-18, H-004; gate: before T-023 serves results externally)**.

Lognormal and Weibull (D-056; T-048, des-go-0.3.0; ranges and numeric details are D-075, APPROVED, H-022): one uniform per sample. lognormal(mean, cv): σ² = ln(1+cv²), μ = ln(mean) − σ²/2 (computed once at compile, products rounded first), x = exp(μ+σ·Φ⁻¹(U)), where Φ⁻¹ is AS241 (Wichura 1988, PPND16, double precision, 48 constants fixed by bit pattern, `engine.ndtri`). Weibull(shape, scale): x = scale·exp(ln(−ln(1−U))/shape). exp does not use the platform `math.Exp` (assembly on amd64, arm64 and others, with different last bits) but the fixed `engine.exp`: the pure-Go algorithm of Go's `math.exp` (derived from FreeBSD e_exp.c), each product rounded with `float64()`, the result scaled with `math.Ldexp` (exact; one correct rounding for subnormals). When the result is a normal number, its error from the true value is under 1 ulp (spot-checked against 256-bit reference values on 300,000 inputs in [−710, 710], `TestExpAccuracy`; not a proof). Like exponential, both are at least 1 tick (D-038 (a)) and become 365 days + 1 tick beyond 365 days (D-038 (b)). Compile checks again that 0 < cv ≤ 10 and 0.1 ≤ shape ≤ 20 (the validator's DISTRIBUTION_INVALID, D-075), and that mean/scale, once converted, do not exceed 365 days (the LIMIT_EXCEEDED of D-029, D-063 (c)). Within these ranges |Φ⁻¹(U)| ≤ 8.21 (U at its ends 2⁻⁵³ and 1−2⁻⁵³) and σ ≤ √ln 101 ≈ 2.15, so the exp argument μ+σz is at most ln(mean)+15.33 (an upper bound) and does not overflow; Weibull's shape 0.1 magnifies −ln(1−U) ≤ 36.8 to at most 36.8¹⁰ times scale, and anything beyond 365 days becomes the 365 days + 1 tick above. `scripts/engine_reference.py` ports exp, AS241 and the two samplers operation by operation; `engine-vectors.json` adds the constants of exp and ndtri, boundaries and the SHA-256 of 10^6 inputs, the lognormal (μ, σ), the draw vectors and digests of both samplers, the breakdown stream vectors and the priority-15 event order; Go must match bit for bit. `make backend-numeric` also requires `engine.exp` and `engine.ndtri` to be present in the assembly of each architecture.

Numerical profile (after the T-020 review): ln does not use the platform `math.Log` (assembly on amd64/s390x; pure Go on other GOARCH values, where the compiler may fuse it into FMA, with different last bits) but the fixed `engine.ln`: the pure-Go algorithm of Go's `math.log` (derived from FreeBSD e_log.c), each product rounded with an explicit `float64()` conversion, which the Go spec guarantees is not fused, so every step is one binary64 rounding. sqrt, round, floor and frexp are themselves correctly rounded or exact and may be used directly. `scripts/engine_reference.py` ports the same algorithm operation by operation; `testdata/simulation/engine-vectors.json` holds the 12-draw vectors, the SHA-256 of 10^5 draws per sampler (including the binary64 values before quantization, so any change of formula or operation order is caught even when the ticks do not change), the SHA-256 of 10^6 ln inputs, the ln constant bit patterns and boundary values, and the stream state at the end of arrivals; Go must match bit for bit. `make backend-numeric` (`scripts/check_no_fma.sh`) checks that the engine and result-statistics code has no fused multiply-add and no call to a platform transcendental in the assembly for amd64 v3, arm64, ppc64le, s390x, riscv64 and loong64, and reruns the numeric tests with GOAMD64=v3 (FMA fusion possible). Tests have not been run on physical non-amd64 machines (NOT RUN), so a byte-identical digest across architectures is still not claimed. A change of algorithm or of the log/sqrt numerical profile requires a new engine_version; the same human-readable semver is never used for different numeric implementations.

The SOURCE invariant is still: same IR + engine version + run config + seed → same aggregate digest; this draft also fixes the dataset manifest. Compile does not trust the caller: every manifest binding must pass the schema, be sorted by logical_ref bytes without duplicates and cover every empirical distribution, and RunInput.Datasets must be exactly the manifest's bindings (bindings the model does not use are allowed, as in datasets.Resolve). engine_version must trace uniquely to a container digest, a source commit and a numerical profile. A byte-identical digest across architectures must not be claimed until tested; deploying the same tested numerical profile keeps the promise.

## 5. Warmup, metrics, statistical population

Let W=warmup tick and H=horizon tick; 0≤W<H≤365 days is required (the horizon cap is also a D-005 candidate). The observed length is T=H-W; boundary events W≤t≤H are counted, and time integrals are taken over [W,H]. Before warmup, events run and resources and queues are maintained as usual, but warmup does not reset the system state.

| Metric | Candidate definition |
|---|---|
| throughput | per replication, the count of entities entering a completed sink in [W,H]; mean/p50/p95 across replications; not a per-minute rate |
| lead_time_minutes | the complete entity cohort with arrival≥W and completion≤H; (completion-arrival)/60000; entity quantiles pooled across replications, with the per-replication mean also kept |
| queue wait | complete visits with queue_enter≥W and service_start≤H; zero waits included; every rework visit counts as one record; an entity still in the queue is not treated as a known wait |
| queue_length_mean | ∫queue_length(t)dt / T; integrated from the real queue state at W |
| utilization | ∫in_use(t)dt / (capacity*T); includes the parts of service intervals crossing W/H; mean across replications |
| failure_count / rework_count | the number of generic FAILURE/REWORK observations executed in [W,H]; not a DORA failure rate |
| censored_entities | the number of entities still active at H; shown as censoring risk; must not enter the completed lead sample |

Candidate quantile: linear interpolation Type 7: sort x, h=(n-1)*p; interpolate floor(h)/ceil(h). mean is the arithmetic mean of that population. Calling "the average of per-replication p95 values" a pooled p95 is forbidden.

The 95% mean CI is the Student-t interval of the independent replication means; with n<2, a replication without a complete cohort, or too few independent observations, it returns null + reason. For lead time, the CI describes "the mean of replication means", not the pooled entity mean; the UI labels the estimand and does not imply that the interval is also valid for p95. To avoid confusing these different estimands, the pooled lead summary may have CI=null, with replication_mean_lead_time output separately in additional_metrics. **This draft takes the latter**: only a summary with population=replication may carry this CI.

Counting details of the finite-buffer members (T-047; written in review round 1 I2; (e)(f) are D-064's (e)(f), APPROVED, H-021): the keys of `blocking` are the sources, processes and delays whose route can reach a finite buffer via decision, failure or rework nodes; delays, sinks and unlimited buffers end a route (so a source before a delay is not a key, golden G-B12; a process routed through a failure node is, G-B11). When not comparable, `comparable=false`, `incomparable_reasons` lists the reasons in the order above, every metric is `incomparable` (`RUNS_NOT_COMPARABLE`), and both sides' values are shown side by side with no delta. Every statistic in the two Results is compared (a summary's mean, p50, p95; a resource's utilization_mean; a queue's three waits and queue_length_mean); keys are the union, in a fixed order (run level, additional_metrics, dora, domain, resources, queues; keys in byte order), and the metric path is an RFC 6901 pointer (D-090). When either side is unavailable there is no delta (`BASELINE_UNAVAILABLE`, `SCENARIO_UNAVAILABLE`, `BOTH_UNAVAILABLE`); a metric that one run lacks is `MISSING_IN_BASELINE`/`MISSING_IN_SCENARIO`; a delta beyond ±1e15 is null with a reason; there is no -0; CIs do not enter the delta. Warnings: `SCENARIO_PATCH_EMPTY`, `SINGLE_REPLICATION`, `CENSORED_ENTITIES`, `METRICS_TRUNCATED` (more than 10000 records). The hand-derived golden is `testdata/contracts/valid-comparison.json` (derivation in that directory's README). The domain pack has no frozen version, so the pack's domain and DORA metrics are not part of the comparability conditions (D-088 (e)); with a negative baseline, relative follows the formula and the UI must display it with care (D-088 (f)).

## 8. Execution budgets, progress, cancellation

Initial candidates: ≤1000 replications; ≤300s wall timeout/run; ≤10M processed events/run (total over all replications); ≤100k active entities/replication; ≤10k node visits/entity; sampled trace≤100k events/run. Warmup events consume budget too. The API must not accept a user raising the limits; the effective execution limits are saved at enqueue. CPU/memory container limits and admission quotas still need separate configuration.

Context checkpoints at least at every heap pop, every distribution batch-processing segment, every replication, and every artifact/aggregation batch. T-020 implementation: every pop first checks cancellation, then deducts 1 from the event budget shared by the whole run (warmup included; parallel replications count atomically; exceeding it is `ErrEventBudget`, and the run fails without a result); a broken invariant returns `ErrInternal` and is never silently skipped. Worker bounded polling passes cancellation_requested into the context. ≤5s is the original report's target pending benchmark, not a measured result. Timeout / event cap / active entity cap / cancellation each have a typed error; do not wrap them as completed. The D-050 runtime backstop has two more typed errors: `ErrDeadlock` (B1, circular wait; job failure code `SIMULATION_DEADLOCK`, implemented in T-047: `internal/runs/runner` records the `Reason()` of `*engine.DeadlockError` and does not retry) and `ErrStalled` (B2, a bundle that can never be assembled; `SIMULATION_STALLED`; T-048 implemented the TTR part (§3): the runner records the `Reason()` of `*engine.StalledError` and does not retry; the calendar part belongs to T-049). The run fails with no partial result; following T-023's provisional mapping for execution limits, the API shows `MODEL_VALIDATION_FAILED`, with the original code in `details[0].code` (CB-38(a); the `Run.error` comment in `simulation.schema.json`, `testdata/contracts/valid-run-failed-deadlock.json`, `valid-run-failed-stalled.json`).

T-023 implementation (`engine.Credit`, `des.Options`, `internal/runs/runner`): the event budget becomes credit granted in batches. `engine.NewCreditBudget(limit, granted, credit)` first grants `granted` events; when they are used up (under a mutex: only one `Grant` at a time, other replications wait for it) it calls `Credit.Grant(ctx, granted)` to get the new total grant (which must be larger than the old one and not exceed limit, otherwise `ErrInternal`); at the limit it is `ErrEventBudget`. An error from Grant (including context cancellation and wall timeout) fails the run with that error, and no further Grant happens. The per-pop deduction is unchanged (check cancellation first, then deduct 1); only the granted amount changes, and the event processing order, RNG and results do not: the digest is the same across batch sizes and worker counts (`des/credit_test.go`). `des.Output.Events` is the number of events actually used. The worker's `Grant` advances the run's `event_budget_reserved` from its last value to the new one under the lease before returning, so the engine never uses unreserved events; the batch defaults to one tenth of max_events (at least 1). On retry the engine's limit is `max_events − amount reserved by earlier attempts` and the wall timeout is the time left since the first start (rounded up to whole seconds; the attempt also ends at an absolute deadline). The worker writes progress once per second (the engine's sink keeps only the latest record); the same checkpoint reads back `cancellation_requested`, and if cancellation was requested it stops the engine with `context.CancelCause` (the engine sees it before the next pop); the worker ends the job and the run as cancelled and saves no result. The ≤5 s cancellation target is measured in a test (`TestCancelRunning`, see checks/T-023_VALIDATION.md); it is not a benchmark.

Aggregation runs in ascending replication_index; progress is not a correctness input. A run can complete only after all replications complete. A retry uses the original frozen input; an attempt whose lease token is no longer valid must discard its finalize and must not overwrite a later successful result.

## 9. Result digest / sampled trace

The result_digest payload (D-006, approved; implemented as `hashing.Result`, T-005): engine_version, metrics, replication_summaries, measurement_window, reproducibility (excluding result_digest itself); it excludes run_id, status, created_at, wall duration, progress, worker ID, trace (including the object key) and LLM output. JCS + SHA-256 over this payload; full numerical values are kept, and round-trip equality is never faked for convenience; NaN/Infinity cannot be serialized and return an error instead of a digest.

trace_level must not change numerical results; it is still in config_hash, so changing trace_level can change the digest, but the metrics must be the same. The sampled trace selects entities by a stable entity hash; trace caps must not stop the simulation. A trace event has at least time_tick, sequence, type, entity_id and node_id, and may have resource_id; the order follows the same event order. The UI states that the trace is sampled and must not fill missing samples with an invented trajectory.

Implementation (`internal/simulation/trace`, `internal/simulation/des`, T-022; **D-039**, approved by the owner 2026-10-18): the trace records replication 0 only; an entity is selected when the first 8 bytes (little-endian) of SHA-256(`dt-trace-v1\0` || entity ID) are < 2^64/8 (rate 1/8), consuming no RNG stream (`scripts/engine_reference.py` has independent selection vectors). Recording stops at max_trace_events, after which `truncated=true` is set and the simulation runs to the end as usual. The artifact format is `simulation.schema.json#/$defs/TraceArtifact` (`geminus.trace.v1`). Events follow engine processing order (tick, event priority, sequence), so sequence may decrease within a tick; consumers keep the array order. The node of queue_enter is the node the entity actually entered: the queue when passing an explicit queue, the process when entering the process directly (even if the process has an explicit queue upstream; queue metrics are still attributed to the explicit queue per §3, T-022 review). With trace_level=none or max_trace_events=0 there is no artifact; with no events at all there is no artifact either, and Result.trace.available=false. artifact_id is filled in by the worker after upload (T-023). T-046 phase 2 added the ADR-026 event types to `geminus.trace.v1` (additive, the same approach D-047 takes for the IR; the format is unchanged): `blocked`, `unblocked` (D-049; node is the departure node where the entity is blocked, T-047), `setup_start` (D-055, with `resource_id`, T-050), and `batch_id` on batch members' `service_start`/`service_end` (`r<rep>/<process>/b<n>`, D-054, T-050); the schema allows `resource_id` only on `setup_start` and `batch_id` only on `service_start`/`service_end`. des-go-0.2.0 produces `blocked` and `unblocked` (T-047); des-go-0.5.0 produces `setup_start` (in the grant event, before that entity's service_start, with the same sequence) and the batch members' `batch_id` (T-050). Breakdowns and repairs are not entity events, and des-go-0.3.0 (T-048) does not write them to the trace; shift changes (T-049) and batch starts (`ObsBatchStart`, T-050) are not written either.

Engine (`des.Engine`): Compile → run the replications in a bounded pool (default GOMAXPROCS), sharing the event budget and wall timeout (the timeout covers the replication pool; Compile, Build and the digest are outside it; at the limits of 1000 replications and 10M events, Build takes a few hundred ms). Progress is sent by a separate goroutine in "keep only the latest record" fashion: never concurrent, counts never go backwards, the last record is always delivered (possibly after Run returns), and however slow the sink is, it does not affect the run's results or timing (T-022 review); after a sink panic no more progress is received and the run is unaffected. When the worker writes progress it must fence on run status/lease, because the last record may arrive after Run returns (T-023). A panic inside a replication or in `DomainMetrics` is treated as a bug and returns `ErrInternal` without terminating the process. The run completes only when all replications complete (a deadline or cancel arriving afterwards does not overturn a completed run). Any failing replication fails the whole run with a typed error (`ErrWallTimeout`, `engine.ErrEventBudget`, `ErrActiveEntities`, `ErrEntityVisits`, context errors, `*engine.InputError`, `*engine.DeadlockError` for finite buffers (`engine.ErrDeadlock`, T-047), `*engine.StalledError` for breakdowns (`engine.ErrStalled`, T-048)), with no partial result; when several replications fail at once, which limit is reported may vary, but the reported limit was really exceeded. The engine recomputes effective_model_hash from the IR it actually ran and rejects a mismatch with the frozen value; model_hash is the pinned version's value and is recorded as frozen. DORA is filled in before the digest by the program-injected `DomainMetrics` (DomainPack.ComputeMetrics), and `metrics.domain` next by the program-injected `ModelMetrics` (ModelMetricsProvider.ComputeModelMetrics, T-051) (a pack panic is also `ErrInternal`); the generic engine does not import any domain pack. engine_version is `des-go-0.5.0` (des-go-0.2.0 from T-047: finite buffers and blocking; des-go-0.3.0 from T-048: resource breakdowns, lognormal, Weibull; des-go-0.4.0 from T-049: calendars, release schedules; des-go-0.5.0 from T-050: batch processes, setups; under D-047 each kernel task bumps the minor version by one); a deployment may append a build identity. run_id is set by the worker. The des-go-0.1.0 digests of GOLDEN-001/002 are locked in `testdata/simulation/engine-golden-digests.json` (a regression lock on engine output, not an independent oracle; under D-047 they are not regenerated: the digest recomputed after switching the Result's engine_version back to `des-go-0.1.0` must equal the locked value). des-go-0.2.0 has its own `engine-golden-digests-0.2.0.json` (GOLDEN-001/002 and the finite-buffer goldens; des-go-0.3.0 likewise compares after switching engine_version back to `des-go-0.2.0`, without regenerating). des-go-0.3.0 has its own `engine-golden-digests-0.3.0.json` (the cases of the two earlier locks, the breakdown goldens and four random reference cases) and `kernel-observation-digests-0.3.0.json` (the observation sequences of the breakdown goldens and reference cases, At included). des-go-0.4.0 has its own `engine-golden-digests-0.4.0.json` and `kernel-observation-digests-0.4.0.json` (calendars and release schedules). des-go-0.5.0 has its own `engine-golden-digests-0.5.0.json` (the 23 batch and setup goldens that have a Result, and 8 random reference cases) and `kernel-observation-digests-0.5.0.json` (the observation sequences of 33 cases, with Batch added to the encoding). None of the old locks is regenerated; they all still hold.

## 10. Required correctness cases

`testdata/simulation/` provides **expected-value fixtures, not output of an executed Go engine**. First case: interarrival=10 min, service=5 min, capacity=1, 100 entities, horizon=1010 min; first arrival=10, last completion=1005; completed=100, wait=0, lead=5, utilization=500/1010.

Congestion: interarrival=5, service=10, capacity=1, 20 entities, horizon=205; 20 completed, wait_i=5*i (i=0..19), wait mean=47.5, p95=90.25, utilization=200/205. The original report's "queue grows" must not be read as monotonic at every event; service completions lower the queue. The candidate acceptance check samples after the dispatch in the arrival's tick completes and checks the queue trend over the source's active period.

Also test 100%/0% routing, same-tick release/arrival, bundle acquire, nonnegative capacity, zero-time cycle reject, empirical binding/hash mismatch, warmup cohort, horizon equality, censoring, worker retry determinism and the cancel/finalize race. The SimPy stochastic differential compares confidence/tolerance and does not require the two RNGs to be byte-identical; the tolerance must be fixed in advance, never tuned after seeing a failure until it passes.

SimPy reference for finite buffers and blocking (T-047): `make simulation-reference-test` first has `TestSimPyReferenceExport` write the Go engine's per-replication results for the reference cases; then `scripts/simpy_reference.py` (SimPy 4.1.2, an independent reference only; the engine never calls it) interprets the same IR with SimPy's own resources: a finite buffer is a "free slot" resource of capacity B; after its departure process completes, an entity still holding its machine requests a slot (not getting one at once means blocked); only on getting the slot does it release the machine, then request the next station's machine, and return the slot once it has that machine; a source's entity requests a slot as soon as it arrives. The deterministic cases (G-B1, G-B1W, G-B2, G-B4, G-B4W, G-B7, G-B8, G-B9, G-B11, G-B12, G-B14) are compared value by value with the hand-derived service starts, completions, each block period and the Result members; G-B3 (same-tick tie-break, D-048), G-B5 (routing stream), G-B10 (units 2) and G-D3 are not compared; G-B13 must be refused by the script (see below); G-D2 is illustrative (SimPy does not detect deadlocks). Four random cases (S1–S4, 30 replications, Python's own RNG) compare the mean of each per-replication metric, with a tolerance fixed in advance in the fixture: |Δ| ≤ 4·√(s²_go/n+s²_simpy/n)+0.5%·max(|mean|). Limits: the script accepts only models where every requirement is 1 unit, each bundle shares at most one resource with other processes, and in a bundle with a shared resource each of the bundle's own resources has a capacity no smaller than the shared one's; it refuses to run any other model, and a case marked refused in the fixture (G-B13) must be refused every time. A bundle is acquired one resource at a time and released all together: the shared one first, then its own resources in increasing capacity (ID order for equal capacity). An entity holding a unit of some resource always also holds a unit of every resource before it, and each resource's capacity is no smaller than the previous one's, so once the first is acquired the later ones always have a free unit; the whole bundle is acquired when the first resource (the shared one, or the smallest own one when nothing is shared) has a free unit for the request at the front of its FIFO, which is exactly when the engine's all-or-nothing, resource-wise FIFO grant happens. (Correction in T-047 review round 1 L1: the original text missed the capacity condition; counterexample G-B13: S (capacity 3) is shared by X and Y, O (capacity 1) belongs only to X; under resource-wise FIFO the engine lets Y start only at 11, while one-at-a-time acquisition would let Y start at 3. Correction in round 2 L1′: own resources were originally acquired in ID order; with decreasing capacity (G-B14: O1 capacity 2, O2 capacity 1) the script would occupy O1 first and then wait for O2, giving O1 an in_use of 29 minutes against the engine's 20; changed to increasing capacity.)

SimPy reference for breakdowns (T-048): the same `make simulation-reference-test` also reads `testdata/simulation/breakdown-goldens.json`. The script interprets breakdowns with SimPy's own primitives: a resource with breakdowns is a `simpy.PriorityResource`, and jobs request it with priority 0 (FIFO among themselves). Each unit has a breakdown clock process alternating TTF and TTR: when a TTF ends, if some unit is neither in use nor down (`len(users) < capacity`), the clock requests with priority −1 (ahead of all waiting jobs, so SimPy grants it at once) and holds the unit for one TTR; otherwise the breakdown waits, in order, for the next unit a job releases: the job hands its own request to the breakdown process instead of releasing it (finish-first). A repair likewise hands its unit to the first pending breakdown first, and releases it back to SimPy's queue for waiting jobs only when no breakdown is pending (D-074 (a) option B). Sampling uses Python's `random` (expovariate, triangular, lognormvariate (σ² = ln(1+cv²), μ = ln(mean) − σ²/2), weibullvariate), not the engine's streams or samplers. The deterministic cases G-F3, G-F3b, G-F7, G-F9, G-F9R10 are compared value by value with the hand-derived service starts, completions, each downtime, the pending breakdowns and the Result members (including the breakdown group of `resource_states`). The script records as pending only breakdowns with a positive wait: a 0-minute wait is just the order of a breakdown and another event (a release or repair) at the same instant, which SimPy handles in scheduling order and the engine under D-048; both take the unit down at the same instant (minutes 23 and 35 of G-F7; 30, 45 and 60 of G-F9; 30, 40, 50 and 60 of G-F9R10), so the 0-minute waits are also removed from the hand-derived pending breakdowns before comparing, while the downtimes themselves are compared one by one. The script does not record breakdowns still pending at the horizon; such a case is not comparable and fails. G-F1, G-F1W, G-F1W10, G-F2, G-T1, G-T2, G-T4 (D-048 same-tick order), G-K1, G-S2 (the kernel's B1/B2), G-D4, G-S1 (SimPy detects neither deadlocks nor stalls) and G-F10 (two breakdowns still pending at the horizon) are not compared; G-F8 must be refused by the script. Four random cases (B-S1–B-S4: exponential and Weibull TTF, lognormal TTR and service, three units, breakdowns before a finite buffer, a breakdown resource shared by two processes; 30 replications) compare completed, lead time, utilization, down share, available and idle shares, downtimes started, and the finite-buffer members, with the same tolerance fixed in advance. Limits (checked by the script before running): besides the conditions of the previous paragraph, a resource with breakdowns must be the only resource in every bundle that needs it (with one-at-a-time acquisition, a unit held while waiting for another resource cannot break down, while the engine's all-or-nothing grant lets an idle unit break down, G-F8), and distributions may only be constant, exponential, triangular, lognormal or Weibull (no empirical); every other model is refused. The order of a same-tick breakdown or repair relative to other events is the kernel's D-048 order, which SimPy does not reproduce: deterministic cases with such same-tick events are marked not compared; random cases have continuous times, where such coincidences have probability 0 in SimPy and are rare under the engine's 1 ms tick, and the tolerance covers them.

SimPy reference for calendars and release schedules (T-049): the same `make simulation-reference-test` also reads `testdata/simulation/calendar-goldens.json`. A resource with a calendar is a `simpy.PriorityResource`, and off-shift units are held by "blocker" requests with priority −0.5 (after the breakdowns' −1, before the jobs' 0): the script computes S(t) itself from the IR (not with the engine's calendar package); at t=0 blockers first block C − S(0) units; when S decreases it requests C − S blockers (taken at once if a unit is free; a job in service finishes first, which is overtime); when S increases it first cancels blockers still waiting, then releases the acquired ones (units go to waiting jobs in FIFO order). Calendar events and the breakdown clocks and repairs of resources with calendars are scheduled with SimPy's URGENT priority, ahead of job events at the same instant (matching the kernel's priority 15 before dispatch 20), and among themselves in scheduling order; breakdown clocks accumulate TTF over on-shift time. A release table releases in order at tick k·P+A_j (P and A_j are the period and that row's at, each quantized to ticks, D-082 (b) A, computed by the script itself from the IR; before review round 1 M1 it wrongly released at continuous time k·period+at). A deterministic schedule computes Λ⁻¹(k) exactly with `fractions.Fraction` and then quantizes under D-053 (not with the engine's floating-point profile); poisson is generated by Lewis–Shedler thinning (a homogeneous process at the maximum rate, each point kept with probability λ(t)/λmax, Python's random). The deterministic cases G-C1, G-C1W, G-C1W10, G-C2, G-C5, G-C6, G-C7, G-C8, G-C9, G-C10, G-F6, G-CF1, G-R1, G-R5, G-R7, G-R8, G-R9 are compared value by value with the hand-derived arrivals, service starts, completions, downtimes, pending breakdowns, every change of S and the Result members (including the calendar group of `resource_states`); G-T5 (a breakdown exactly at the shift-end tick: the script's blocker takes the off-shift unit first, while the kernel counts it as idle), G-K2 (the kernel's B1) and G-D1 (SimPy does not detect stalls) are not compared; G-C4, G-D4C (a bundle with two resources that have calendars), G-D3C (units 2) and G-D5 (a resource with breakdowns in the same bundle as its partner) must be refused by the script. Four random cases (C-S1–C-S4: two shifts and a closed day; 3/2/1 people per shift with a three-segment poisson schedule; a station with a calendar that also breaks down (Weibull TTF, lognormal TTR) after a finite buffer; a deterministic schedule and a release table feeding two stations with different calendars; 30 replications) compare completed, lead time, utilization, scheduled utilization, overtime/available/idle shares, downtimes, blocking members and the item counts of each schedule segment or release row, with the same tolerance fixed in advance. Limits (checked by the script before running): a resource with a calendar must be the only resource in every bundle that needs it (with one-at-a-time acquisition, a unit held while waiting for another resource would be held across a shift end); a resource with a calendar that also breaks down may only have 0 or C people per shift (with 0 < S < C, the off-shift units held by blockers are idle in the kernel and a breakdown can take them, while the script's breakdown would wait); the other conditions are as in the two previous paragraphs.

SimPy reference for batches and setups (T-050): the same `make simulation-reference-test` also runs `scripts/simpy_batch_reference.py` (SimPy 4.1.2), which reads `testdata/simulation/batch-goldens.json` and `setup-goldens.json`.
