# Twin IR / Model Contract

SOURCE: original report pp. 5–6, 14–20, 24–25, 31–35. The full closed-object schema, hash, dataset binding and patch allowlist involve D-001 / D-005 / D-006 / D-014 / D-017 (all approved). This document is still a P0 draft contract. It has not been frozen as a production contract.

## 1. The single canonical representation

`schemas/model-ir.schema.json` is the source of truth for IR v0.1 and uses JSON Schema Draft 2020-12. The IR keeps the original report's arrays: entity_types, nodes, flows, resources, constraints, metrics. They must not be turned into dictionaries for UI or patch convenience. IDs express identity; an array index is not a stable identity. T-046 phase 2 adds an optional root-level `calendars` array (D-052, §2.1).

schema_version, model_id, domain, name, time_unit and views are root-level fields. metadata and domain_attributes are untrusted data containers, not code or expressions. Closed objects reject unknown fields. metadata is the exception, but it is still subject to depth/size limits and redaction. The original report's "minimal IR" has empty nodes/flows. It only illustrates the shape and is not an executable model; an executable model must pass the semantic validation below.

APPROVED D-001 (2026-10-15): server-generated resource IDs are `<prefix>_<ULID>`. The ULID is 26 uppercase Crockford base32 characters (first character 0–7). The schema enforces this with `common.schema.json#/$defs/<Type>ID`; in SQL it is text. User-defined IR entity IDs (node / resource / flow / entity_type, etc.) are not subject to this and still use `$defs/ID`. The IR's model_id is assigned by the server; import / patch cannot change tenant or resource identity.

A worker is its `WORKER_ID`; system is `provision-tenant`.

## 2. Node, flow, resource catalog

| Type | Required configuration | P0 behavior |
|---|---|---|
| source | entity_type, arrival.distribution | draws the first interarrival from t=0, then generates entities; the optional max_entities is D-005's proposal for tests / finite sources |
| queue | id/type | explicitly shows the FIFO wait of the downstream process; not an extra second service or a duplicated wait timer |
| process | service_time.distribution, requires[] | acquires all resource units at once and releases all of them after service completes |
| decision | id/type | outgoing probability routing; no script predicate |
| delay | delay_time.distribution | a wait that holds no resource; delay_time is a field added by D-005 / D-014 |
| sink | optional outcome=completed/abandoned | ends the entity; abandoned does not count toward completed throughput |
| failure | optional reason | records a generic failure event, then continues on the given flow; does not represent a real deployment failure |
| rework | id/type | records a generic rework event, then continues on the given flow; implies no jump target |

Every flow has id/from/to/routing={type:probability,probability}. A decision can have several outgoing flows whose probabilities sum to 1. Every other non-sink node has exactly one flow with probability=1. A sink has no outgoing flow. A queue feeds exactly one process; this is a candidate P0 restriction and does not quietly add calendar/priority/preemption.

A resource's type keeps human / machine / generic; capacity is a positive integer; queue_discipline=fifo. The optional role gives domain catalog semantics. The example pack's Software Delivery catalog contains developer, reviewer, ci_runner, test_environment, deployment_slot, generic_resource (machine-read by `TestResourceCatalogMatchesSpec` in `internal/domainpack/softwaredelivery/pack_test.go`, which needs this exact form: Software Delivery catalog 包含 developer、reviewer、ci_runner、test_environment、deployment_slot、generic_resource；). The electronics line catalog is defined by T-046 (H-016; see [ELECTRONICS_LINE.md](domains/ELECTRONICS_LINE.md) §3, APPROVED, H-018). The production and logistics catalog (H-045) is in [PRODUCTION_LOGISTICS.md](domains/PRODUCTION_LOGISTICS.md) §2. The kernel does not decide behavior from role strings.

Each requires entry is {resource_id,units}. A process cannot list the same resource twice; units≤capacity. capacity=0, negative values, non-integers and unknown resources are always invalid; an infinite wait does not replace validation.

## 3. Distributions / units

P0 has only constant(value), exponential(mean), triangular(min,mode,max), empirical(samples_ref). lognormal, calendar-dependent and mixtures are P1 (lognormal and Weibull were moved up to P0 by D-056: APPROVED, H-018, implemented in T-048; the schema accepts `lognormal(mean, cv)` and `weibull(shape, scale)` since T-046 phase 2, and rejected them with PRIMITIVE_NOT_SUPPORTED before T-048, §2.1). Since T-048 (des-go-0.3.0) both can be used in any distribution position (arrival, service, delay and resource breakdowns). The semantic validator also checks that the lognormal mean decodes to > 0 with 0 < cv ≤ 10, and that the Weibull scale decodes to > 0 with 0.1 ≤ shape ≤ 20 (DISTRIBUTION_INVALID, D-075 APPROVED, H-022). mean and scale are time parameters; above 365 days after conversion per D-029 they are LIMIT_EXCEEDED (D-063 (c)). cv and shape have no unit. Samples of both are at least 1 tick (as for exponential; D-033 treats them as always > 0). The sampling formulas are in SIMULATION_SPEC §4.

The schema checks types and non-negative values. The semantic validator also checks min≤mode≤max, finite numbers, that empirical is parseable and non-empty, and that the unit is convertible. interarrival must be strictly positive. Zero service/delay may exist, but a reachable zero-time cycle cannot run. Time conversion and rounding are fixed by SIMULATION_SPEC.

APPROVED D-017: in P0 a day is a continuous 24 hours. Under these semantics the report's example mean=16 min means 90 arrivals/day. It must not be read as 30/day or as implying an 8-hour work calendar. The full template fixture uses a synthetic mean=48 min to show 30/day. The other new Test/Deploy parameters are also marked synthetic and must not be taken as customer facts.

## 4. Semantic validation order

Before execution and data changes, validate in this order: JSON parse (reject duplicate keys / NaN / Infinity)→JSON Schema→primitive support (T-046 phase 2, D-063 APPROVED, H-019)→limits→ID uniqueness→references→graph rules→distribution/domain semantics→bundle feasibility (D-050's R2–R4; R3 since T-048, R2 and R4 belong to T-049)→constraint checks→dataset bindings→scenario/patch policy→risk classification. Invalid returns an issue code, a JSON Pointer path, and severity/message.

| DUPLICATE_ID | duplicate ID in the same catalog; the candidate profile requires that nodes/resources do not share IDs, to avoid an ambiguous selectedEntityId |
| UNKNOWN_REFERENCE | a flow endpoint, entity_type, resource, metric, constraint or view position points to an ID that does not exist |

APPROVED D-023 (implemented in `internal/model/validate`, T-004): all issues of a stage are collected; if a stage has an error, the next stage does not run. Issues are sorted by JSON Pointer, then by code, message, severity. Within tokens, only the RFC 6901 array index form (`0` or a digit string not starting with 0) compares numerically (any length, no overflow) and sorts before other tokens; the rest compare byte by byte. The order is therefore total and independent of discovery order. T-004's implementation interpretation (a separate decision can be raised if owner confirmation is needed): (1) every node that some source reaches via p>0 flows but that cannot reach a sink returns NO_REACHABLE_SINK, not only the source itself; (2) a flow that points to a source returns ROUTING_INVALID, because a source does not receive entities; (3) metrics / constraints only check that the reference exists, not the type of the referenced node. D-033: zero time is judged by the smallest tick the distribution can produce (constant=0, triangular min=0; an exponential is valid only if its mean decodes to >0, and the engine gives exponential samples at least 1 tick; empirical is judged in the dataset binding stage).

Primitive support stage (T-046 phase 2, implemented in `internal/model/validate/primitives.go`; D-063 APPROVED, H-019): `validate.Uses` lists, in D-023 path order, the location of each line-flow member in the model (the table in §2.1; distribution types count in any distribution position, including breakdowns and setups in resources). `validate.Checked` is the set of primitives whose rules this build implements (currently `finite_buffer` (T-047), `breakdowns`, `lognormal`, `weibull` (T-048), `calendars`, `release_schedule` (T-049) and `batch`, `setups` (T-050)). Each use that is not implemented returns one PRIMITIVE_NOT_SUPPORTED error. This stage comes after schema and before limits; when it has errors, no later stage runs, so the existing stages only ever see models they can check completely. The engine's Compile has its own kernel support list (`engine.kernelExecutes`, currently the same eight). It also returns PRIMITIVE_NOT_SUPPORTED for members the validator accepts but the kernel does not execute yet (path under `/model`). Each of T-047–T-051 adds its primitive to both lists only after it adds, in the same task, the rules, the kernel, the engine_version and the D-057 risk rules.

An unreachable dormant node can be a warning; an active path without a reachable sink is an error. A valid graph can still have heavy rework, so runtime budgets must exist. The source does not explicitly require IDs to be globally unique across catalogs; the node/resource uniqueness above is a candidate restriction of D-014.

## 5. Version, hash and empirical freezing

SOURCE: Draft is mutable; ModelVersion is immutable and keeps its parent; a run stores model_version_id, model_hash, patch, engine, seed, replications, config.

APPROVED D-006: `model_hash = sha256(JCS(IR))`, keeping the original array order. JCS means RFC 8785; the default output of Python sort_keys / Go json.Marshal must not pass for it. Duplicate JSON keys, invalid Unicode and non-finite numbers are rejected. Numbers use the interoperable IEEE-754 profile; seed is limited to 0..2^53-1. The model hash includes views/metadata. It is a hash of the complete version content, not a pure simulation semantic hash.

An empirical logical ref (e.g. dataset:review_duration) is not a mutable remote URL. Every published version carries an immutable DatasetBinding manifest: logical_ref, dataset_version_id, content_hash, unit, sample_count. It is fully frozen before the version is approved. A run copies the same manifest, and the worker checks the hash of the actual object bytes before it preloads samples. New data that arrives later can only produce a new dataset version / model version; it cannot change a submitted run.

`effective_model_hash = sha256(JCS(apply(base.IR,scenario_patch)))`. dataset_manifest_hash applies JCS/SHA-256 to the manifest sorted by logical_ref. config_hash applies JCS/SHA-256 to the complete public config. execution_limits and the engine profile are also fixed in the run input, so a retry cannot change the settings.

JSON Schema only checks the `sha256:` format; it cannot check that the content really matches. Hash consistency is a product test of T-005/T-021, not something this pack's schema validation guarantees.

### 5.1 Hash definitions (D-006, D-019, D-034; implemented in `internal/model/hashing`, T-005)

Every hash is written as `sha256:` + 64 lowercase hex characters. Except for content_hash, all are SHA-256(JCS(payload)). JCS uses `github.com/gowebpki/jcs` (ADR-014). It is also cross-checked against the RFC 8785 examples, V8 `JSON.stringify` number vectors and the independent Python `rfc8785` implementation (`testdata/hashing/`, `make spec-hashes`).

| Hash | Payload |
|---|---|
| model_hash | the complete IR document |
| effective_model_hash | the candidate of `internal/model/patch.Apply` (the base IR with the scenario patch applied); for the baseline `[]` it equals model_hash |
| patch_hash | the JSON Patch array; `[]` also has a hash (= SHA-256 of `[]`); a non-array is rejected |
| config_hash | `{horizon_ticks, warmup_ticks, replications, seed, trace_level}`; durations are first quantized with `model.Ticks`, so `120 hour` and `5 day` have the same hash |
| dataset_manifest_hash | the DatasetBinding array sorted by the UTF-8 bytes of logical_ref (SQL: `COLLATE "C"`); binding the same logical_ref twice is rejected; without empirical it is the hash of `[]` |
| result_digest | the Result's engine_version, metrics, replication_summaries, measurement_window, reproducibility (without result_digest); excludes run_id, status, trace |
| content_hash | SHA-256 of the stored object's **raw bytes**, not parsed and not canonicalized; a snapshot does not contain its own hash |

Input rules: reject duplicate members (including ones that are equal after unescaping), invalid UTF-8, lone surrogates, numbers outside binary64 (such as `1e400`) and multiple top-level values. The input is also parsed once more, independently, with `encoding/json/jsontext`, so the check does not rely only on jcs's parser. Numbers compare by binary64 value per RFC 8785: documents that differ only beyond binary64 precision (`9007199254740993` and `9007199254740992`, `0.30000000000000001` and `0.3`) have the same hash. The schema limits fields that need exact integers (seed, counts) to 2^53−1. T-005 once also rejected integer literals above 2^53−1. Fuzzing found that this made Canonical reject its own output (`1e17` is output as `100000000000000000`, and so is a patch candidate that Go re-marshals), so the check was removed. Error messages carry only a byte offset and do not quote input content (a metadata member name can be customer data).

### 5.2 Dataset binding stage (implemented in `internal/storage/datasets`, T-005)

`datasets.Resolve`, in order: (1) every binding passes the schema (including D-034 `^dataset:[a-z0-9_.-]+$`), logical_refs must not repeat, and every empirical `samples_ref` in the IR must have a binding (distributions of nodes and of resources; the latter are breakdowns, T-048; path `/ir/resources/<i>/breakdowns/<time_to_failure｜time_to_repair>/distribution/samples_ref`); (2) the object is fetched through the tenant-scoped `Store`, **content_hash is compared before parsing**, then organization, dataset_version_id, logical_ref, unit, sample_count and each sample's 365-day limit are checked; (3) D-033 is rerun with the actual samples: an empirical with any sample that quantizes to 0 ticks counts as zero time; a source interarrival or a resource time_to_failure that can be 0 returns DISTRIBUTION_INVALID (the latter D-051, T-048), and a zero-time cycle returns ZERO_TIME_CYCLE (`validate.Bindings`). The engine's Compile does the same checks on the manifest and datasets, also covering resource distributions (path under `/model/resources/...`). Each stage stops on error (D-023).

Issue paths point into the ModelVersion-shaped document: `/ir/...` for the IR, `/dataset_bindings/<index given by the caller>/...` for the manifest. A dataset version that is not found and one that belongs to another organization return the same message. Until the object is confirmed to be a frozen snapshot of this organization, messages do not contain its size or hash. `Store.Open` returns an `io.ReadCloser`, and Resolve reads at most MaxSnapshotBytes+1 bytes. Limitation: if a Store implementation is not scoped correctly, someone who knows another tenant's dataset version ULID can still infer that the ID exists from the difference between "hash mismatch" and "not found" (not its content or hash). The Store's tenant scope remains the main line of defense. Every issue is built with `model.NewIssue`, so message / path always match the ValidationIssue schema (valid UTF-8, ≤2000 / 2048 characters). Bindings the model does not use are still validated and frozen (a run reuses the version manifest, and a scenario may have removed the empirical distribution). Store I/O errors and context cancellation are returned as errors; they are not turned into issues and never become a false success. The Postgres / object storage Store implementations belong to T-006 / T-012.

## 6. JSON Patch profile / approval scope

SOURCE: RFC 6902, application/json-patch+json, array-index patch examples. APPROVED D-014: P0 accepts only add/remove/replace/test. move/copy, an empty-string root path, an invalid `~` escape and an overly deep pointer are all rejected. An RFC 6901 pointer is decoded only once. Authorization does not use string startsWith checks; it must compare decoded tokens.

A manual draft patch can operate on name, nodes, flows, resources, entity_types, constraints, metrics, views, metadata. It cannot change schema_version/model_id/domain/time_unit or any server envelope identity. Changing time_unit needs an explicit migration; P0 does not implicitly reinterpret existing durations.

The AI edit allowlist is smaller than the manual one: name, nodes, flows, resources, entity_types, constraints, metrics; views/metadata/identity are forbidden. An AI scenario covers only existing resources/*/capacity, nodes/*/arrival/distribution, nodes/*/service_time/distribution, nodes/*/delay_time/distribution, flows/*/routing/probability. It cannot add or remove topology or create a dataset binding. A whole-object replace still validates the full candidate IR field by field; child fields are not skipped because the parent path is allowed.

Every patch is applied in order on a copy and committed only if it succeeds as a whole; any failed op/test produces no partial mutation. An array index has meaning only against the pinned immutable base; the diff shows logical entity IDs. APPROVED D-020 (implemented in `internal/model/patch`): before modifying, replacing or removing an existing element of nodes / flows / resources / entity_types / metrics / constraints, the same patch must first `test` that element's identifying field (constraints have no id and are identified by `node_id`, a T-004 interpretation). An insert or removal in between invalidates the earlier test. A whole catalog array (such as `replace /resources`, `remove /entity_types`, or `add` on an existing member) is always rejected while it still has elements (PATCH_TEST_REQUIRED), because it changes every existing element without an id test. It can only create a catalog that does not exist or is empty (the fail-closed interpretation after the 2026-10-15 review). Append (`/-`) and inserting new elements need no test. test is not limited by the allowlist, does not count as a business mutation, and cannot replace the expected base. The allowlist does prefix matching on decoded tokens. Scenario mode (D-021, the same for manual and AI: createManualScenario for manual scenarios, the inline patch of createSimulation and the review of AI scenarios all use `patch.Scenario`, and T-028 compares the manual and AI results with `TestTheAIScenarioModeTakesTheSameRules`) allows only the five parameter paths listed above and D-057's line parameter paths (next paragraph). AI edit also allows removing `/views/2d/positions/{id}` of a node that the same patch removes (D-022), and after the patch is applied no node with the same id may remain (if a node is removed and added back with the same id, its coordinates must be kept). A scenario patch must not introduce a `samples_ref` that the base model has not bound ("cannot create a dataset binding"; reusing an existing ref in another distribution is allowed). A patch document larger than 2 MiB returns LIMIT_EXCEEDED before parsing. Patch error codes: PATCH_SCHEMA_INVALID, PATCH_PATH_INVALID, PATCH_PATH_FORBIDDEN, PATCH_TEST_REQUIRED, PATCH_TARGET_MISSING, PATCH_TEST_FAILED; their paths point into the patch document (such as `/3/path`). Removing a node/resource must repair references at the same time; otherwise it is invalid.

APPROVED D-057 (implemented in `internal/model/patch` by T-046 phase 2): the manual and AI edit allowlists add the root-level `calendars`. `calendars` follows D-020 like the other catalogs (`test /calendars/<i>/id` before changing an element; no whole replace while it has elements). The scenario allowlist also adds `nodes/*/capacity` (replace, add, remove: finite↔infinite), and the following paths, which accept only `replace`: `resources/*/breakdowns/time_to_failure/distribution`, `resources/*/breakdowns/time_to_repair/distribution`, `nodes/*/arrival/schedule/segments/*/rate`, `nodes/*/arrival/schedule/releases/*/quantity`, `nodes/*/batch/min_size`, `max_size`, `max_wait`, `resources/*/setups/transitions/*/distribution`, `resources/*/setups/default`, `resources/*/calendar_id` (the candidate must point to an existing calendar), `resources/*/shift_capacity/<label>`, `calendars/*/shifts`, `calendars/*/exceptions`. Any distribution that may be changed can be replaced with lognormal / Weibull. Adding or removing breakdowns, setups, calendars, schedule, batch, transition, segment, release and `shift_capacity` keys (labels), and changing a period, a segment start, a release time or a calendar name, are all PATCH_PATH_FORBIDDEN and must go through draft→publish. `replace calendars/*/shifts` can move, add or remove shifts ("add a shift"), and can also add, remove or rename shift labels (D-063 (b) option B, chosen by the owner as recommended, H-019; T-049 relaxed `afterApply` before lifting the calendars gate, `TestScenarioMayChangeShiftLabels`). If a label referenced by `shift_capacity` is removed or renamed, the candidate's `shift_capacity` references a label that the calendar does not have; candidate validation returns `CALENDAR_INVALID` (path `/resources/<r>/shift_capacity/<label>`, D-052; `TestScenarioDropsAReferencedLabel`), and the scenario cannot be created. Unreferenced labels do not affect the kernel (unlisted labels use the full capacity). shifts and exceptions accept only `replace`, so adding a label to a shift or removing one is a replace of that shift or of the whole shifts, not an add or remove beneath it. Before T-049 (phase 2's interim interpretation), each calendar's set of shift labels had to stay the same. The candidate is fully validated as before, so before a gate is lifted these scenarios all return PRIMITIVE_NOT_SUPPORTED. "Cannot create a dataset binding" also covers distributions in resources. D-057's server risk (shrinking or adding a finite buffer, or any breakdown / setup / calendar / release / batch parameter: at least medium; enlarging a buffer or changing it back to infinite: low) is added to `internal/ai/review` in the task that lifts the matching gate. Until then the candidate is already rejected by the gate and no risk is computed. T-047 added the queue `capacity` rule (`review.ServerRisk`: the capacity of the same queue in base and candidate becomes smaller, or changes from infinite to finite: at least medium; larger or back to infinite: low); a scenario that causes BLOCKING_CYCLE is invalid at candidate validation. T-048 added the breakdowns rule (breakdowns of the same resource added or removed (edit), or any difference in the time_to_failure / time_to_repair distribution (compared by value, either direction): at least medium; changing only arrival, service, delay distributions (including lognormal, Weibull) stays low); a candidate where R3 fails is invalid; the numbers a proposal's expected effects may cite also include breakdowns and the lognormal and Weibull parameters. T-049 added the calendar and release schedule rules (`review.ServerRisk`: a calendar added or removed, or any difference in period, shifts (including labels) or exceptions (except the name); a resource's `calendar_id` changed or removed, or a different `shift_capacity`; a source's release schedule added, removed, or with any different member (rate, quantity, period, segment, release), in either direction: all at least medium); a candidate where R2 or R4 fails is invalid (CALENDAR_INVALID, STALL_RISK); the numbers expected effects may cite also include calendar times, the headcount on shift and the schedule's rate and quantity. An AI proposal cannot add a calendar: the ID allocation pool does not issue calendar IDs, and a calendar in the candidate that the base does not have is always `ID_POOL_VIOLATION` (D-083, APPROVED, H-024; T-046 review I3). T-050 added the batch and setup rules (`review.ServerRisk`: a process's batch added, removed, or any difference in min_size, max_size, max_wait; a resource's setups added, removed, or a different initial, default or any transition (including added and removed ones); in either direction at least medium); candidates with BATCH_INVALID, SETUP_INVALID or UNKNOWN_REFERENCE are invalid; the numbers expected effects may cite also include batch sizes, the wait limit and setup times. The AI's scenario rules (`aicontext.modeRules`, prompts/scenario `scenario-0.7.0`; T-050 review round 1 added the 365-day limit of max_wait; T-050 was `scenario-0.6.0`, T-049 `scenario-0.5.0`) list the parameters of buffers, breakdowns, calendars (`calendar_id`, `shift_capacity/<label>`, shifts, exceptions), release schedules (segment rate, release quantity), batches (min_size, max_size, max_wait) and setups (setups' default, transitions/*/distribution), state that they can only be replaced, and give the parameter ranges of lognormal and Weibull.

## 7. View / canonical event schema

2D positions go in views.2d.positions[node_id]; 3D layout_mode=derived_from_2d. views must not contain another copy of nodes/flows. When positions are missing, DomainPack.DefaultViews generates them. Selection and playback use the same ID.

canonical-event.schema.json keeps case_id/event_type/timestamp required, stage recommended, and the rest optional. timestamp is RFC3339. Across time zones, normalize before sorting; never guess times without a time zone. When duration_ms disagrees with the timestamp-derived duration, a data-quality issue is produced; domain inference must state the chosen policy explicitly. Low-confidence CSV mappings and dataset inference never change the canonical Twin directly.

APPROVED D-059 (T-046 phase 2): adds optional `end_timestamp` (RFC 3339), `shift` (≤ 64 characters) and `product` (≤ 128 characters, maps to an entity type; required in multi-product logs). `end_timestamp` ≥ `timestamp`, agreement with `duration_ms`, and the presence of `product` in multi-product logs are data-quality rules (T-017 / T-052), not schema. In downtime records, `case_id` is the equipment ID. T-017 (D-070 (a), PROPOSED) has added these three fields to the mapping's target fields: `import-mapping.schema.json#/$defs/TargetField`, shared by manual mapping and `ai-mapping.schema.json`, and checked against `internal/ai/aicontext.TargetFields` by a test. T-017's validation checks that `end_timestamp` is not earlier than `timestamp` and that the difference from `duration_ms` is less than 1 ms (D-072 (b)); rows that fail are currently invalid rows. The previous paragraph calls a duration mismatch a data-quality issue; the difference between the two is listed as an option of D-072 (b) for the owner to decide (review round 1, I2). Requiring `product` in multi-product logs still belongs to T-052. T-052 hackathon slice (D-118, PROPOSED): requiring `product` in multi-product logs, and the pack's event_type, stage, outcome and product vocabulary, are checked by the pack's optional `domainpack.EventRulesProvider` against the base version the import is bound to. They are warnings of import validation (D-072 (b)), and the import stays VALIDATED; see ELECTRONICS_LINE §12.

## 8. Compatibility and extension

An unknown schema_version is rejected, not quietly parsed on a best-effort basis. New v0.1 fields / new nodes or constraints need updates to the schema, fixtures, Go/TS contract tests and the version migration strategy. A future DomainPack can use the existing generic primitives and domain attributes. A new core primitive needs its own ADR and must not bypass the contract with an arbitrary script. The finite buffers and blocking, resource breakdowns, calendars, time-varying release and batches that H-016 (ADR-025) needs are of this kind. T-046 proposed the ADR and decisions (2026-10-20 APPROVED, H-018); until they are implemented, the P0 restrictions in the table above (FIFO, no calendar/priority/preemption added) still apply. Proposal: [ADR-026](adr/ADR-026-line-flow-primitives.md) and D-047–D-057 (the IR's optional new fields and the compatibility strategy are in D-047); the domain specification is [ELECTRONICS_LINE.md](domains/ELECTRONICS_LINE.md); 2026-10-20 APPROVED (H-018). T-046 phase 2 has completed the schema change (§2.1): per D-047 A, schema_version stays `0.1`, all new members are optional, and closed objects make old readers that do not recognize them fail closed; "an unknown schema_version is rejected" is unchanged. schema_version therefore does not tell which features a model uses; the IR content does (`validate.Uses`).

Addendum (D-010): a flow that simply returns to the previous node does not automatically count as domain rework. It counts only with an identifiable rework node or an approved DomainPack mapping. The generic kernel must not hard-code semantics from string names such as f_retry.
