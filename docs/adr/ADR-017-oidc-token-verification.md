# ADR-017 — Provider-agnostic OIDC access-token verification (T-008)

Status: ACCEPTED (chosen by the T-008 agent; the owner KCL1104 agreed on 2026-10-18, H-004). Date: 2026-10-15; amended on 2026-10-18 after the T-008 independent review (see the end). The original report lists the auth provider as TBD (DECISIONS_AND_TBD.md "Auth provider: managed OIDC"); this ADR **does not choose a provider**. It only fixes how the API verifies an access token issued by any OIDC provider. For the provider and the browser session see [ADR-018](ADR-018-browser-session-and-oidc-provider.md).

## Decision

- `internal/auth.OIDCVerifier` verifies the Bearer access token. The provider's issuer, audience and JWKS URL come only from the deployment settings (`AUTH_OIDC_ISSUER`, `AUTH_OIDC_AUDIENCE`, `AUTH_OIDC_JWKS_URL`, the optional `AUTH_OIDC_ALGORITHMS` and `AUTH_OIDC_REQUIRE_AT_JWT`). The issuer and the JWKS URL are each ≤2048 bytes. There is no discovery, and no endpoint is taken from the token (SECURITY §3 "provider endpoints only from the deployment allowlist").
- Library: `github.com/go-jose/go-jose/v4` v4.1.5 (Apache-2.0, released 2026-09-03, depends only on the Go standard library) parses compact JWS and JWK and verifies signatures. v4.1.6 was released the day before today; under AGENTS.md a version younger than two weeks is not used. The header and claims checks are done by this repository's code, not by the library's defaults.
- Token: only compact JWS is accepted, containing only base64url characters and `.` (Go's decoder skips CR/LF even in strict mode). Each of the three segments must be a unique base64url encoding (strict: non-zero surplus bits are rejected). `alg` must be on the allowlist (default RS256, ES256; the deployment may add the 384/512 variants of RS/PS/ES and EdDSA; `none` and HMAC are always rejected) and must match the key's `alg` and type. `kid` is required. `jku`, `x5u`, `jwk`, `x5c`, `x5t`, `x5t#S256`, `crit`, `b64`, `zip` and `enc` are always rejected. `typ`, if present, must be `JWT` or `at+jwt`; with `AUTH_OIDC_REQUIRE_AT_JWT=true` it must be `at+jwt` (RFC 9068; turn it on when the provider supports it, so that an ID token cannot be used as an access token). Duplicate members in the header or the payload are rejected. The token is at most 8 KiB.
- Claims: `iss` is identical to the setting; `aud` (a string or an array) contains the configured audience; `exp` is required; `nbf` and `iat` are checked if present; the allowed clock skew is 30 seconds by default (at most 5 minutes); `sub` is required, ≤255 bytes, printable characters only (control, format characters such as U+202E, separator and private-use characters are rejected). The audience must be the API's own identifier and must never equal any client_id; otherwise the `aud` of an ID token could match.
- JWKS: https, no redirects followed, a fetch timeout of 10 seconds by default (`FetchTimeout`, ≤1 minute), at most 256 KiB (read through a size-limited reader). Only keys that are public, have `use` of `sig` or no `use`, have a `kid`, have an `alg` on the allowlist, and are RSA ≥2048 bits, P-256/384/521 or Ed25519 are kept. When a `kid` is duplicated, neither key is used. Keys that cannot be parsed are skipped. The first fetch happens on first use. **Stale-while-revalidate**: cached keys are always used immediately; after the JWKS has been used for 1 hour (KeyMaxAge) it is refreshed in the background; when the refresh fails, the keys already fetched are used for at most 24 more hours (KeyMaxStale). Only an unknown `kid` waits for a refresh, and only until the request context ends; when the previous fetch failed it waits at most 1 second (the provider is most likely still unreachable, and the connection must not use up the whole FetchTimeout). At most one fetch runs at a time (single-flight), and two fetches are at least 1 minute apart (MinRefreshInterval); when no key is usable this becomes 5 seconds, so that a cold start can recover. The intervals must satisfy 1 second ≤ MinRefreshInterval ≤ KeyMaxAge ≤ KeyMaxStale, MinRefreshInterval ≤24 hours, and KeyMaxStale ≤7 days. A fetch runs in its own goroutine and context; a panic becomes an error; when a fetch does not end normally (for example the transport calls `runtime.Goexit`), the refresh state is reset too. The configured `Now` must be monotonic (default `time.Now`): when the clock goes backwards, the refresh is postponed until the clock catches up. When no key can be fetched, the verifier returns `ErrKeysUnavailable` (the API answers 503, without `WWW-Authenticate`); the error keeps the cause (status, parse error, timeout) but not the URL. Other failures return `ErrInvalidToken` (401 UNAUTHENTICATED). `WWW-Authenticate` (RFC 6750 §3): with no Bearer credentials (none sent, or another scheme) it carries no error code; multiple headers, no token after `Bearer`, or a token in the URL give `error="invalid_request"`; everything else gives `error="invalid_token"`. Errors carry only a reason code, never the token or claims. The error string of `ReasonKeys` contains the transport cause (for example `dial tcp …: connection refused`, internal host names) and is for the log only; T-013's error writer must not return `err.Error()` to the client.
- Transport: only a single `Authorization: Bearer` header is read. In the URL query, any `access_token`/`id_token` in any letter case, escaping or `;`-separated form, and any parameter name that cannot be decoded, are rejected. Cookies are not read (the BFF of ADR-018 turns the browser session into a Bearer token). `auth.Middleware` answers through an injected error writer and does not define a second error format (T-013 provides the envelope).
- Users: `tenant.ResolveUser` looks up `twin.users` in a read-only transaction with the RLS identity settings (`app.oidc_issuer`, `app.oidc_subject`, transaction-local), and confirms that the transaction really is read-only. An issuer/subject that is empty, too long, not UTF-8 or contains NUL returns `ErrInvalidIdentity`; no matching user returns `ErrUnknownUser` (the API answers 403). A user is **not** created automatically from the token (D-008: controlled provisioning). Role and membership always come from the DB (`tenant.Run`).
- Test tokens are issued only by `internal/auth/authtest` (a test-only provider with a TLS JWKS that can produce malicious tokens). `scripts/check-architecture` forbids any production package from linking it, so there is no test verifier that could be turned on in production.

## Consequences

- When a provider is chosen, only four variables need to be set. The provider must issue JWT-format access tokens (opaque tokens and introspection are outside this ADR and need a separate ADR).
- A key that the provider removes (revokes) is still accepted until the background refresh after 1 hour (KeyMaxAge) completes (stale-while-revalidate: requests during the refresh use the cache); if the provider is unreachable at the same time, for at most 24 hours. When faster revocation is needed, adjust these two values or add introspection.
- Open: rate limiting and alerting for verification failures (T-035/T-036). The provider (Auth0) and the browser session (BFF) were decided by ADR-018.

## 2026-10-18 amendment (T-008 independent review)

The review confirmed that holding the lock during a refresh made every request wait up to 10 seconds for a hung provider (even when the key was cached). The design was therefore changed to the stale-while-revalidate and single-flight described above. The amendment also added strict base64, the URL query scan, error causes, the RFC 6750 error codes, `FetchTimeout`, `AUTH_OIDC_REQUIRE_AT_JWT`, the interval and length limits, format characters, and the input and read-only checks of ResolveUser. The direction of the decision did not change; for details and tests see checks/T-008_VALIDATION.md.
