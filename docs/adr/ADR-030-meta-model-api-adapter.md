# ADR-030 — Meta Model API adapter (Muse Spark, SAM 3.1) and the photo path's settings (T-055)

Status: **PROPOSED** (2026-10-26, proposed and implemented by the T-055 agent; the agent approved nothing; awaiting independent review and the owner's/coordinator's decision). Basis: H-029 (APPROVED; the owner chose the Meta Model API, Standard mode, and sending only synthetic data and demo images), H-031, H-033 (APPROVED; T-055 resumed: natural-language proposals use Muse Spark, photo recognition uses SAM 3.1 + Muse Spark, Claude is a switchable fallback), ADR-027 (ACCEPTED), T-053's D-110–D-115 (PROPOSED), D-116 (APPROVED), AGENTS.md §2. The detailed choices are listed as D-121, D-122, D-123 (PROPOSED, `docs/DECISIONS_AND_TBD.md`); of these, the part of D-121 (b) for requests with images was decided by the owner in H-037 (count_tokens plus 10%), implemented by the review round 1 fixes of 2026-10-26 (`checks/T-055_VALIDATION.md` "Review round 1 fixes"). **This ADR approves no live call and ran none**: every test runs only against a local `httptest` server and fakes; live smoke, live eval, token count and model listing are all NOT RUN.

## Context

H-033 asks for a second live provider on T-053's provider boundary (`provider.Client`, `Billable`, `Meter`, the spend ledger, the switch): the Meta Model API's Muse Spark (proposals) and SAM 3.1 (machines and conveyors in photos), and for T-056's photo path to choose its provider by setting (Meta by default, Claude as fallback), with the API unchanged. The official documentation (under https://dev.meta.ai/docs/: models, protocols/messages, api-reference/messages, structured-output, image-understanding, reasoning, pricing-rate-limits, error-handling, authentication, protocols/responses, api-reference/responses, sam/overview, sam/segmenting, sam/reading-segmentation, and under https://dev.meta.ai/legal/: Terms of Service, Data Commitments, Model Designation Policy; all retrieved 2026-10-26, the texts and their sha256 recorded in `checks/T-055_VALIDATION.md`) states:

- The Messages endpoint is Anthropic-compatible ("Base URL | https://api.meta.ai", "Endpoints | POST /v1/messages", "Auth | Bearer token"); it does not support `stop_sequences`, `top_k`, `container` or `inference_geo`, and unknown top-level fields return 400; `thinking: {type: "disabled"}` returns 400; the adapter is stateless, with storage off.
- Standard mode is determined by the model ID (`muse-spark-1.3` is Standard, `muse-spark-1.3-contributor` is Contributor); the Terms also say "the system may route you to a Contributor Model".
- Prices (Standard, per million tokens): cached input USD 0.15, input USD 1.25, output USD 4.25; SAM "Image segmentation | $2.50 per 1,000 images".
- The structured output schema has explicit limits (nesting 10 levels, 5,000 properties, 120,000 characters, enum 1,000 values, etc.).
- Images: at most 50 MB each and at most 50 per request; the cost varies with resolution (about 1280px adds 1,300–1,500 tokens); there is no per-image token cap.
- SAM 3.1: one request takes one concept (a short noun phrase) and one medium; the answer is a text grammar (`<|box;id=…;x1=…;…|>` and mask records); `metadata.include_confidence` returns confidences; `store` defaults to true.

Meta has no Go SDK.

### Muse Spark (proposals)

- **Request**: `POST https://api.meta.ai/v1/messages` (a constant; only tests can change it), `Authorization: Bearer <key>`, redirects not followed, at most 8 MiB of the answer read. The body has only `model`, `max_tokens`, `system` (one text block), one user message (first the base64 image blocks, then the prompt's text), and `output_config.format` (`json_schema`, T-053's projection). No tools, thinking, sampling, metadata, `stop_sequences`, `top_k`, `container`, `inference_geo`, `cache_control`, `service_tier` or stream. The reasoning effort is the model's default (documentation: "When you omit the parameter, the model still reasons at a model-determined level"; reasoning tokens count toward output and `max_tokens`).
- **Projection and limits**: before sending, `SchemaViolations` checks the projected schema (nesting of 10 levels counted per nested subschema, 5,000 properties, 120,000 characters, enum 1,000 / large enum 250 values 15,000 characters, 200,000 expanded nodes, recursion; it also rejects an empty schema, an object without `additionalProperties: false`, and unknown keywords); over a limit, nothing is sent. The tests check the schema each prompt role actually sends (proposal-output 2,623 bytes, 7 levels; analysis 6 levels; mapping 5 levels).
- **Answer**: a strict JSON document, `type` `message`, `role` `assistant`, usage not negative; `model` must equal the request's model, otherwise `invalid_output` (the Standard mode guarantee: a Contributor answer is not accepted, and its usage is settled all the same); `end_turn` takes the text block (`thinking`/`redacted_thinking` are discarded unread), `max_tokens` is `output_truncated`, `refusal` is `refused`, any other stop reason or content block is `invalid_output`; open values are decoded fail-closed with `structured.Decode`, and then go through the full schema and server review as usual.
- **Errors and retries** (D-121): one key (label `meta`), no failover. 401/403 disable the key until the process restarts, 402 rests 15 minutes, both `credentials_exhausted`; 429 is retried with backoff (500 ms doubling, jitter ≤ 500 ms, cap 8 s; waiting at least as long as Retry-After asks; when Retry-After is over 60 s, no retry, and the call ends with that status's code (review round 1 L2: the documentation's "wait at least that long"); never past the call's deadline), `rate_limited`; 504 is not retried (documentation: "Do not simply retry"); other 5xx are retried, `unavailable`; other 4xx are `request_rejected`. Errors record only the HTTP status and the error types the documentation lists (the Anthropic envelope of Messages and the OpenAI envelope of the other endpoints, 8 types in all); anything else is `other`; no message, key or URL is recorded.
- **Metering**: reservation = (1 + retries) × (input × 1.25 + `max_tokens` × 4.25), **without** Anthropic's 1.1× geo factor (`spend.GeoPriced` is only `claude-opus-5-5`). The input for `Quote`: for a text request, the bytes of the prompt and the projected schema plus 4096 (D-111 (a)), without calling the provider. For a request with images (Meta has no per-image token cap): **H-037** (the owner's answer to review round 1 M1, option C of D-121 (b)) counts first with `POST /v1/messages/count_tokens` (the same body as Messages but without `max_tokens`, under the same connection rules: the key only in the Bearer header, no redirects, the 8 MiB answer cap, the call's deadline, the same attempts and retries, the closed list of error types) and reserves ⌈count × 1.1⌉, at most the context window; when the count fails or its answer is not plausible (not an integer from 1 to 1,048,576, or the wrong shape), the whole call fails with a typed code, with no reservation and no Messages call (it never reserves a smaller number). The count is not billed (the documentation gives it no price, the count endpoint "does not … record generation usage", and billing follows usage). The original context window cap (the old rule of D-121 (b)): per attempt 1,048,576 × 1,250 + 8,192 × 4,250 = 1,345,536,000 nano-USD (about USD 1.35); with the default 3 attempts, 4,036,608,000 nano-USD in all (about **USD 4.04** per photo proposal; D-121 (b). Review round 1 M1: the text originally gave only the about USD 1.35 per attempt and not the reservation of one photo proposal, and the "about 7 times" in Consequences was wrong; see below). Attempts that may already be billed: a dropped connection, an attempt timeout, a body that cannot be read to the end, **every 5xx** (the documentation does not say error statuses are not billed), and a 2xx that cannot be read (settled at least at the whole reservation). The prices are fixed in `internal/ai/spend` (source https://dev.meta.ai/docs/pricing-rate-limits, retrieved 2026-10-26); cache writes use the input price (the documentation lists no separate write price).
- **Images**: `provider.NewImage` accepts only PNG, JPEG and WebP (the signature must match the declared type), at most 5 MiB, at most 8000 px per side, at most 4 per prompt, checked before the request; `Prompt.Seal` copies the data and counts each image's media type, sha256 and dimensions into the prompt hash (the hash of a text-only prompt is unchanged). `provider.Client` passes a prompt with images only to a backend that is `ImageInput` and `AcceptsImages()`, otherwise `invalid_request`; the Meta backend accepts them only when the approved data policy lists images (H-029 does, H-018 does not).

### SAM 3.1 (segmentation for the photo path, used by T-056)

- `provider.Segmenter`: `Segment(ctx, SegmentRequest{OrganizationID, Role, Attribution, Image, Concepts}) (Segmentation, error)`; one request per concept (documentation: one concept per request). `SegmentClient` checks the request (organization, role, image, at most 8 concepts, each a lowercase noun phrase within 64 bytes `^[a-z0-9]+(?:[ -][a-z0-9]+)*$`, attribution required when metered) and the answer (the frame equals the image's dimensions (or rotated 90°), at most 100 per concept, no repeated object ID, boxes inside the frame, confidence in 0..1, matching concept); otherwise `invalid_output` (issue path `/concepts/<i>/…`). Concurrency, timeout and retries share the budget with proposals.
- Backend: `POST /v1/responses`, `store: false`, `stream: false`, `metadata: {include_confidence: "true", mask_encoding: "one_bit"}`, one user message (`input_text` is the concept, `input_image` a data URL). The answer must be `object: response`, `status: completed`, the same model, and only `output_text`; the text is parsed strictly by the documentation's grammar (the box's and the mask's confidences must be equal; the mask is only checked for shape, not decoded, and discarded; an empty string is zero results).
- Metering: each concept reserves (1 + retries) × 2,500,000 nano-USD per image; with an answer, it settles at max(1, `usage.images_processed`) images; each attempt that may be billed but has no answer counts one image, an answer that cannot be read at least the whole reservation, a refusal 0.

### Approval record (`internal/config/aiapproval`, D-122)

- `Record` gains `SegmentationModel`; `Gap` is split by provider: anthropic's rules are unchanged (and also require `SegmentationModel` to be empty); meta requires credential `["meta"]`, a model that is a Standard Muse Spark of the Model Designation Policy (1.1/1.2/1.3), a segmentation model that is the Standard `sam-3.1` (only when the data policy lists images), a data policy of synthetic data, demo images and text the user types, roles `modeler` and `scenario`, a monthly budget > 0, and retention `meta_standard_services` (owner, date, basis). No confirmation of a Console spend limit is required (Meta has no corresponding setting the owner has confirmed; the in-code ledger is the cap).
- H-029's record: provider `meta`, model `muse-spark-1.3`, segmentation `sam-3.1`, USD 100/month (H-029 carries over T-053's cap; the interpretation is in D-122), approver KCL1104, 2026-10-26, source "H-029 (1), amended by H-033".
- `Approval` gains `Provider()`, `SegmentationModel()` and `AllowsImages()`; `anthropic.New` now rejects an approval that is not anthropic's, and `meta.New`/`NewSegmenter` reject one that is not meta's.

### Settings (`internal/config.LoadAI`) and assembly

- `AI_PROVIDER=meta`: the same switch rules as anthropic, plus the approval must belong to that provider (otherwise `provider_mismatch`); the key is read only from `GEMINUS_MUSE_API_KEY` (the name the owner chose), only after the switch is on and every other condition holds; it must have no whitespace or control characters and match the documentation's `LLM_<numeric ID>_<secret>`; `MODEL_API_KEY` (the conventional name in Meta's documentation) and Anthropic's keys are never read.
- The photo path (D-123): when `AI_VISION_PROVIDER` is unset, it follows `AI_PROVIDER`; `disabled` turns it off; `fake` only in development/test; another live provider needs `AI_VISION_POLICY_APPROVAL`, `AI_VISION_MODEL` (the same rules), its own key and the same switch. When the approved data policy has no images (H-018), the photo path stays off (`images_not_approved`), and proposals are not affected. The two paths share one ledger; the monthly cap is the smallest budget among the live approvals.
- `cmd/worker`: `aiClient` builds the metered client of Claude or Muse Spark by provider; at startup, `photoPath` builds the photo path's judge (`provider.Client`) and segmenter (`provider.SegmentClient`), placed in the handler's `deps.photo` for T-056's handler; the log records provider, model and typed codes (`LIVE_AI_ON`, `PHOTO_PATH_ON`, `SWITCH_OFF`, `IMAGES_NOT_APPROVED`…), never the key. `cmd/api`'s availability treats meta the same as anthropic. `cmd/ai-eval-live` builds the adapter by `AI_PROVIDER`; the report records the provider and the source of that model's prices.
- Redaction: the credential patterns of `aicontext` and `observability` gain `LLM_<digits>_<secret>`.

## Consequences

- The two live adapters share the projection, decoding, metering, ledger, switch and review; either one can only be called through a metered client, and each accepts only its own provider's approval.
- The photo path's provider is a setting, not part of the API; T-056 depends only on `provider.Segmenter`, `provider.Client` and `provider.Image`.
- The reservation of a call with images (corrected in review round 1 M1; defaults `MaxRetries` 2, `MaxOutputTokens` 8192, and D-110's caps: a deployment daily cap of USD 10, an organization daily cap of USD 5):
  - **Old rule (context window)**: each photo proposal reserves 4,036,608,000 nano-USD (about USD 4.04), not the "about 7 times under the USD 10 daily cap" originally written: under the deployment daily cap, at most **2** at once; the real limit is the **organization daily cap**: it holds only **1**, and only when that organization's committed total for the day is ≤ about USD 0.96 (the conditional UPDATE in `aispend.go`), so once the judge account and the owner, both in the demo organization, have spent about USD 1 on text proposals that day, every photo proposal is `AI_QUOTA_EXCEEDED`.
  - **New rule (H-037, count_tokens plus 10%)**: reservation = 3 × (⌈1.1 × count⌉ × 1,250 + 8,192 × 4,250) nano-USD; the output part is fixed at 104,448,000 nano-USD (about USD 0.10). Example: count 3,000 → 116,823,000 (about USD 0.12). A demo-sized photo proposal (the size of the demo prompt and the 1200×520 demo image, with the count estimated pessimistically at 40,147 tokens: one token per byte of text plus 4096, and 15,000 tokens for the image = ten times the documentation's about 1,500 for ~1280px) → 270,055,500 (about **USD 0.27**); plus the whole reservation for SAM's 8 concepts (USD 0.06), the organization daily cap holds **15** of them (`TestADemoPhotoProposalFitsTheOrganizationCap`). The actual count is known only live (NOT RUN).
  - Settlement follows actual usage; when settlement exceeds the reservation, it is still marked `spend_over_reservation` (H-037: when live billing exceeds the reservation, report to the owner).
- Possible overestimates: every 5xx is treated as possibly billed. Possible underestimates: billing items outside the documentation (for example, the documentation states that the steering context Meta injects is not billed).
- The API still cannot tell whether live AI is on without reading a key (T-053 I5 is not handled in this ADR); the deployed API stays at `AI_PROVIDER=disabled`. (A later follow-up handled it: the API decides from four settings that are not secrets, without reading a key, and the deployed API and worker carry the same settings; see the last item of the ADR-027 addendum, the coordinator's decision.)

## Alternatives

- **The OpenAI-compatible Chat Completions or Responses endpoint for Muse Spark**: feasible, but Messages has the same request/answer shapes and error handling as T-053, so the projection and tests can be shared; SAM can only use Responses.
- **A community SDK**: there is no official Go SDK; adding a dependency needs ADR-011's review, and the standard library is enough.
- **Estimating image tokens with `count_tokens`**: originally listed as a question for the owner/coordinator; the owner has chosen it (H-037), and the review round 1 fixes implemented it (see "Metering"). The two ways to handle a failed count: (i) fail the call with a typed code, reserving and sending nothing (**adopted**); (ii) reserve the whole context window and send anyway. Why not (ii): under the organization daily cap of USD 5, a USD 4.04 reservation is mostly refused (`AI_QUOTA_EXCEEDED`, and the user sees a quota problem rather than a count problem), which is exactly what H-037 wants to avoid; a failed count (401/402/403, 429, 5xx, 400) mostly signals that the Messages call would fail too, and sending anyway only uses up attempts that may be billed; an implausible count means the provider behaves differently from its documentation, so per AGENTS.md it returns unavailable rather than guessing; the count is not billed, so a failure costs nothing, and retryable codes are handled by the job's retries.
- **Estimating image tokens by formula** (option B of D-121 (b)): the documentation has no formula ("Fixed per-image or prompt-overhead estimates are not portable across deployments"), so it could undercount; not adopted.
- **Treating 5xx as not billed**: a smaller reservation, but the documentation does not say so; the safe side is chosen.

## Addendum (2026-10-27): the output cap of requests with images

2026-10-27 (after T-056 live): the `max_tokens` of a request with images becomes `provider.ImageMaxOutputTokens` = 32,000 (text proposals keep the budget's 8,192). Basis: dev.meta.ai/docs/reasoning "Reasoning tokens count toward your output-token budget"; the photo judge used up all 8,192 and was truncated twice live (runs 01M5XJ8Q4RJCQBESJZWZPG4BPJ, 01M5XJCVYRB05MV25ZJ5R6Q8V7, with the same result at 30 boxes and at 10 boxes). The reservation follows automatically: with the demo's live count (6,661), the judge's reservation per photo proposal is about USD 0.44, about 10 times under the organization daily cap of USD 5; `usage.output_tokens_details.thinking_tokens` is recorded in `provider.Usage.ThinkingTokens` and in the photo smoke report. `output_config.effort` (the documentation lists low–max) is not sent for now, until the live thinking_tokens data are in. After review round 1: (i) this cap is not affected by the deployment's `AI_MAX_OUTPUT_TOKENS` (spending is still bound by D-110's daily caps); (ii) the attempt timeout and the whole call's timeout of a request with images are scaled by the same ratio (32,000 ÷ the budget's `max_tokens`), at most `BudgetCaps.Timeout` 300 s (the default 90 s/120 s both become 300 s): at the live speed (about 24 s for 8,192 tokens), 32,000 takes about 94 s, over the default 90 s; the worker's lease is renewed by heartbeat and does not limit the call's length; (iii) when the provider does not report `thinking_tokens`, it is recorded as null (not 0).
