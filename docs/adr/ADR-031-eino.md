## Context

H-058 and H-059 ask for the AI roles (proposal generation in edit, scenario, research and photo modes; the analyst; H-057's repair attempt; H-056's investigations, which H-060 and H-061 make an Eino ADK agent in the worker) to run on Eino, while every reviewed safety step stays as it is: the context and redaction, spend metering, the Standard-mode check, strict decoding, the server's review, the photo rules, the grounding checks and no-store. So Eino must reach a model only through the app's own metered client (`provider.LLMProvider`, the `*provider.Client` of ADR-027), never through a provider SDK of its own, and the engine and the domain packs must never depend on it. This slice (E0) pins the module and adds the rules; no package imports Eino yet, and no product behaviour changes.

### Why not eino-ext

`github.com/cloudwego/eino-ext` holds Eino's provider components (OpenAI, Claude, Gemini, Ark and others), retrievers, callbacks to hosted tracers and tools. Its model components call a provider with their own SDKs and HTTP clients, so a call through one would bypass the metered client: no spend reservation or settlement, no Standard-mode check, no approved-model check, no strict decoding of the answer, no output size limit and no no-store guarantee, and it would need a provider key outside the worker's configuration. The design (§6.3) instead builds one ChatModel, `internal/aigraph/einomodel.Metered`, over `provider.LLMProvider`. So eino-ext is not added, and the rules `no-eino-ext` and `no-eino-ext-in-tests` refuse it in production code and in tests (a test import would put it in `go.mod`). `github.com/eino-contrib/jsonschema`, which Eino itself links, is a schema library, not part of eino-ext.

### JSON: sonic's compat path

Eino uses `github.com/bytedance/sonic` for its JSON. sonic v1.15.0's native path (a JIT that writes generated machine code into executable memory through `sonic/loader`, plus SIMD assembly) is built only for `(amd64 && go1.17 && !go1.27) || (arm64 && go1.20 && !go1.27)`; with `go 1.27.0` in `go.mod` and toolchain go1.27.3, every platform builds its compat path instead, which is `encoding/json` (`sonic.APIKind == sonic.UseStdJSON`), with no JIT and no executable memory. The coordinator chose this path. The alternative, a sonic release that supports go1.27 natively (the design names v1.15.4), was not taken: it would map executable memory in the worker (and, under H-056's first placement, the API).

- **Enforced.** `json-without-jit` forbids, in every package, sonic's loader, JIT, JIT decoder, x86 encoder and native assembly, golang-asm and base64x. Minimal version selection would move sonic to a native release if any module required one, and no import would change; this rule (and `aigraph-has-no-storage`'s package-by-package sonic list) then fails. A sonic upgrade is a reviewed change to this ADR.
- **The stderr line (a reviewed exception to D-093 (a) and D-094).** On the compat path an `init` function of `github.com/bytedance/sonic/ast` writes one line to the process's stderr, before `main` runs:

  ```text
  WARNING: sonic/ast only supports (go1.17~1.26 and amd64 CPU) or (go1.20~1.26 and arm64 CPU), but your environment is not suitable and will fallback to encoding/json
  ```

  It is not a JSON line (D-093 (a)) and does not pass `internal/observability`'s filter (D-094), because it is printed with `fmt.Fprintf(os.Stderr, …)` by a dependency. It is constant text and carries no data, no ID, no prompt and no answer. It will appear once at the start of every process that links Eino: the worker (`cmd/worker`) from the first H-059 slice on, and the live eval (`cmd/ai-eval-live`). It never appears in the API process: H-061 (approved in H-063) places no Eino there, and `no-eino-in-the-api` refuses any path by which `cmd/api` could link it. This ADR proposes it as the one exception; `TestSonicRunsItsCompatPath` builds a program that links the seven Eino packages and checks that stdout reports the compat path and that stderr is exactly this line, so a second line (sonic's `decoder` or `encoder` packages each print their own when linked), a changed one or none (the native path) fails. The `cmd` tests capture the writer `run` is given, not `os.Stderr`, so they are unchanged. Log collectors that parse every stderr line as JSON will see one unparsable line per process start.

### The adapter contract (recorded in E0; built in E1, see below)

Per the design §6.3, with H-060's change: `einomodel.Metered` implements Eino's `model.ToolCallingChatModel` over `provider.LLMProvider` (one instance over the text client, one over the vision client). `Generate` takes exactly a system and a user message equal to the sealed prompt's texts (a tripwire refuses anything else), dispatches to `GenerateModelProposal` or `AnalyzeSimulation` so `Client.call` runs unchanged (verify, attribution, image and research gating, approved model, prompt size, per-organization slot, quote, reserve, settle, returned model, output size, strict decoding, output hash, no-store), returns the canonical answer with usage and the typed result, and unwraps errors to `*provider.Error`. Eino's retry and failover configurations, `effort` and thinking options and ChatTemplates are never used; callbacks carry no message content. Tool calling (H-060) is not `Metered`'s: H-061 keeps `Metered` refusing tools and adds `einomodel.Planner`, a tool-calling ChatModel over a separate investigator `provider.Client` on the same spend ledger, used only by the investigator agent in the worker (its slice A6).

### As built in E1 (PROPOSED; [checks/E1_VALIDATION.md](../../checks/E1_VALIDATION.md))

`internal/aigraph/einomodel.Metered` is a `model.ToolCallingChatModel` over `provider.LLMProvider`, as the paragraph above says, with one difference from its last sentence, recorded for the coordinator and the owner: the slice's task asked for tool calling in the adapter itself (H-060's change), so a call is one of three kinds carried by the user message (`Extra["geminus.call"]`): a proposal and an explanation, which refuse any tool, tool choice or extra message exactly as H-061 asks of `Metered` (their requests are byte for byte as before: request goldens of both adapters), and a **tool turn** (`Call.Turn`), which goes to a new client method `provider.Client.Turn` over an optional backend interface `provider.ToolTurner` (H-061 §9's name; `Complete` is never handed tools and keeps refusing every `tool_use`). `Client.Turn` runs through the same `Client.call` (verify, attribution, approved model, prompt bytes with the tools and transcript counted, the organization's slot, quote, reserve, settle, returned model, no-store) and checks each call strictly (an offered tool, an ID of a token's shape, one strict JSON object of at most 16 KiB valid under the tool's closed input schema, at most 4 calls). H-061's investigator policy (`Client.PlanTurn`: the investigator role, exactly one `tool_use`, one attempt, the note's sanitizing, `tool_choice` any) is A5's and can be a policy over `Client.Turn`; A6's `Planner` can be `Metered` over the investigator client, or a type over it. If H-061's split is wanted literally, the `Call.Turn` path moves to a `Planner` type unchanged. The Meta adapter sends tool turns only for roles its approval names tool calls for, and no recorded approval names any, so no live call can make one until A5; the Claude adapter refuses them (`tools_unsupported`).

### As built in E2 (PROPOSED; [checks/E2_VALIDATION.md](../../checks/E2_VALIDATION.md))

The analyst is the first role on a graph: `internal/aigraph/analysis` is a `compose.Graph` in DAG mode (`decode → compare → build_context → generate → ground`, design §6.4), compiled once in `analyzer.New` and run by `analyzer.analyze`, which keeps its signature and maps the graph's typed errors (`*analysis.Error`, one `Kind` per failure) to the job's failures and log lines as before (pinned by goldens written before the change). The comparison is injected by the handler (`comparisons.Input`, `compare.Compare`); the call's log line is the handler's, told of each call through `Config.Called`; nothing in the graph logs, stores or reads storage. The call goes through `einomodel.Metered` over the metered client. Every failure ends the graph as a node error rather than as data (the design's `Answer{Message, Err}` is for the proposal graph, whose failures can be outcomes; every failure of an analysis ends its job). No callback handler is attached. A node's panic is carried out of Eino and raised again in the caller's goroutine as an `analysis.Panic`: its own value and the stack where the node panicked, taken as the node's panic was recovered (Eino's recovery unwinds the frames that panicked). The worker records that value and that stack (`handler.Reraised`, E2 review round 1), so it still records INTERNAL, does not retry it and logs where the panic happened (Eino alone would turn it into a retried error whose text holds the stack). `cmd/worker` now links Eino: it writes H-064's one stderr line at start (`cmd/worker` `TestTheWorkerWritesOneLineThatIsNotJSON`); `cmd/api` does not.

### As built in E3 (PROPOSED; [checks/E3_VALIDATION.md](../../checks/E3_VALIDATION.md))

The proposal role graph (built in parallel with E2's): `internal/aigraph/proposal`, the design's §6.4 proposal graph, `compose.NewGraph` compiled once in DAG mode (`AllPredecessor`) with eleven Lambda nodes and no ChatModel node (the call sits in the `generate` Lambda, as §6.3 says, so the client's errors stay data the next node classifies): `decode_base`, `build_context`, `preload`, `verify`, `generate`, `classify`, `review`, `bind`, and H-057's repair as an unrolled branch, `repair_context` (`repair.Plan`), `generate_2`, `review_2` (`repair.Settle`). H-057 merged into the old generator before this slice, so the slice absorbs it (the design's §16 and E4's "port it with its tests unchanged"): every H-057 test passes unchanged. The model's callbacks run under their own `RunInfo` (`model`, `GeminusMetered`, ChatModel), no callback is attached in production, every step runs under the attempt's own context and sees a cancellation itself (Eino runs on a context that never ends, so it never stops a run between two nodes, and a stopped attempt ends as it did before the graph), and a node's panic is raised again on the caller's goroutine as a `proposal.Panic` with the value and the stack where it was raised, which the worker records in its place (`handler.Reraised`; never Eino's panic error, whose text holds the value and a stack). `Metered`'s `CallError` gains `Prior`, the answer the client hands back with a refused proposal, for the repair. `internal/proposals/generator` and `internal/aievals` (the live text eval) run the graph, so **`cmd/worker` and `cmd/ai-eval-live` now link Eino** (23 packages each by `go list -deps`; `cmd/api`, `cmd/migrate` and `cmd/provision-tenant` none), and the sonic line of H-064 appears once at their start.

### As built in E5: the photo graph (PROPOSED; [checks/E5_VALIDATION.md](../../checks/E5_VALIDATION.md))

`internal/aigraph/photo` is the photo role graph (design §6.4, photo; built in parallel with E2 and E3). It is a `compose.Graph` in DAG mode, compiled once, with the nodes gate, segment, check_segments, build_context, generate, classify, review, repair_context, generate_2 and settle. Both vision calls go through `einomodel.Metered`, and the repair is one unrolled branch with no cycle. It differs from the design's text in three ways, each recorded for review:
- **No `internal/ai/photostep`.** The graph takes the steps as an interface (`photo.Steps`), and `internal/ai/photopipeline` keeps the reviewed step code and its public API. Reason: with the design's layout (the graph importing the steps, which import `aicontext`), E0's probe "the context builder links the photo graph" becomes an import cycle and fails to load (`import cycle not allowed in test`, checked with a temporary import).
- **The graph runs on `context.WithoutCancel` of the caller's context.** Each node hands its step a context with Eino's values over the caller's and the caller's deadline, cancellation and cause. Reason: Eino checks its context before every step and ends the run with its own error, so a cancellation would no longer reach the steps the way the pipeline met it (the client's cancelled call, its log line and settlement, the repair refused once the attempt is stopping). Seven of the parity test's cancellation cases change without this, and every pre-E5 test still passes.
- **A panic in a step stays a panic, with the same value**, not turned into a typed error. Reason: Eino makes it an error whose text holds the stack, and the worker would then retry the job (`jobs.Failure` is not set) where it treats a handler panic as a bug and never retries it. No step runs inside Eino: each node hands its body to `Run`, which runs it on the caller's goroutine while Eino's run waits on a goroutine of its own. So the panic is never recovered on the way, and the stack the worker logs shows the step that raised it, as before E5 (review round 1; a first version recovered it in the node and raised it again in `Run`, which started the logged stack at `Run`).

`einomodel.CallError` gains `Prior`: the answer the client handed back with an `invalid_output` error, which H-057's repair follows. The adapter's own callbacks get the error without it. `internal/ai/repair` gains `Prepare` and `Settle` (E3 made the same split in parallel, as `Plan` and `Settle`; E6's merge kept `Plan`, and `Settle` sets the record's call and tells `answered`, as E5's did); `Once` is `Plan`, the client's call and `Settle`, so the photo graph makes the second call through `Metered` under the same rules.

### As built in E6: the seal (PROPOSED; [checks/E6_VALIDATION.md](../../checks/E6_VALIDATION.md))

E6 builds on E2, E3 with E4, and E5, which were built in parallel and merged in that order. Their two parallel answers to the same question are made one: `handler.Reraised` (E2: `PanicStack() string`, and a Reraised with no value or no stack is recorded as any other value; E3 had `[]byte` and recorded one with no stack by its first value: E2's kept, `proposal.Panic.PanicStack` returns a string) and the repair's steps (E3's `Plan` and E5's `Prepare` were the same body: `Plan` kept; E5's `Settle`, which sets the record's call and tells `answered`, kept, and the proposal graph passes no `answered`, its `generate_2` having told the hook). Two tests of those slices changed for it, never in what they hold beyond the merged contract: E3's worker fixture (renamed, the stack a string, its "no stack" row expecting E2's verdict) and the two steps tests' calls (E3's pass `nil` for `answered`, E5's call `Plan`); see [checks/E6_VALIDATION.md](../../checks/E6_VALIDATION.md).

The seal is design §6.6's go/ast source test, `internal/aigraph/seal_test.go`, over every `.go` file of every package `go list ./...` reports (build constraints ignored, so every platform's files): in non-test code only `internal/aigraph/einomodel` and `internal/ai/provider` (those directories exactly, not the adapters beneath) name a client's model method, `GenerateModelProposal`, `AnalyzeSimulation`, `ProposeImportMapping` (`provider.LLMProvider`'s role methods) or `Turn` (`provider.Client.Turn`, H-060; E5's package check named it too), any selector, so a method value or expression counts; the one exception is `repair.Once`'s own second call, and no non-test code uses `repair.Once` (under any import name, by a dot import, or from `internal/ai/repair`'s own code). Nowhere, tests included, does `WithCheckPointStore`, `CheckPointStore`, `AppendGlobalHandlers`, `InitCallbackHandlers`, `ModelRetryConfig` or `ModelFailoverConfig` appear (H-061 §5.3 adds the last two to the design's four). It reads names, not types: a field of another type called `Turn` would be refused too (none exists), and a call made by reflection would not be seen. The merge of H-061 A5 and A6 with E6 adds A5's planner turn, `PlanTurn` (`provider.Client.PlanTurn`, the investigator role's only path to a model), to those methods: only `einomodel.Planner` names it, and the investigator eval (`internal/aievals`, behind `make ai-eval` and `cmd/ai-eval-live -suite investigator`) runs the worker's ADK agent over `Planner` instead of a planner loop of its own, with its four fake reports byte-identical; no exception is added.

`repair.Once` is kept, not deleted as a leftover: no production code calls it after E3 and E5 (the proposal and photo graphs run `Plan`, their own call through `Metered`, and `Settle`), but H-057's own tests (`internal/ai/repair`), E4's reference (`internal/aigraph/proposal`'s `repair_test.go`) and E5's parity test hold the graphs to it, and the task keeps every existing test unchanged. No other leftover of the old orchestration was found (a scan for functions and methods that no non-test code names found only `Once`). The panic guards of the analysis and proposal graphs stay their own (they differ in what `String` prints, and both are pinned by their tests): sharing them, as E2 proposed, is left PROPOSED.

E6 review round 1 ([checks/E6_VALIDATION.md](../../checks/E6_VALIDATION.md) §10): **the analysis graph runs on `context.WithoutCancel` too**, as the proposal graph does since E3's review round 1 and the photo graph since E5. E2 had Eino run it on the attempt's context, so an attempt that stopped between two nodes ended with Eino's cancellation (the worker's `WORKER_STOPPED`, retried) where the handler's steps had ended with their own failure (not retried: the worker records a handler's failure even while it stops), and an answer that came before the stop was not checked; E2's finding 5 had accepted that as the same outcome, which it is not. Now each node's step runs under the attempt's context (`attempt`: the node's values over the attempt's, with its cancellation, cause and deadline), so every step meets the stop itself, as before the graph (characterized on `88c9191`). **The seal refuses every checkpoint entry point** of Eino v0.9.21, not only `WithCheckPointStore` and `CheckPointStore`: the ADK turn loop takes a store as `TurnLoopConfig.Store` with `CheckpointID`, so `TurnLoopConfig`, `NewTurnLoop` and `CheckpointID` are refused (the turn loop as a whole: `Store` is too common a name; H-061's investigator runs on `adk.NewRunner`), and so are `CheckPointDeleter`, `WithCheckPointID` (compose's and adk's), `WithWriteToCheckPointID`, `ResumeWithParams` and `MigrateCheckpointState`. None of them appears in the module.

## Consequences

- No binary links Eino after E0: `go.mod` lists it and its closure as `// indirect`, and **`go mod tidy` would remove them** until the first package imports Eino (E1). Do not run `go mod tidy` in between; if it is run, the Eino probes of `scripts/check-architecture` fail to load (they import Eino through an overlay), so the removal cannot pass unnoticed. **E1:** `internal/aigraph/einomodel` imports Eino, so `github.com/cloudwego/eino` and `github.com/eino-contrib/jsonschema` (imported by its tests) are direct requirements; `go mod tidy -diff` now changes nothing in `go.mod` but those two lines (it would add checksums of dependencies' test modules to `go.sum`, not applied). Still no binary links Eino: nothing under `cmd/` imports `internal/aigraph` until E2. **E2:** the analysis job handler runs `internal/aigraph/analysis`, so `cmd/worker` links Eino v0.9.21 and sonic v1.15.0 (`go version -m bin/worker`); `cmd/api`, `cmd/ai-eval-live`, `cmd/migrate` and `cmd/provision-tenant` link none of Eino's modules; `go.mod` is unchanged (`go mod tidy -diff` changes only `go.sum`, as in E1). **E3:** the proposal graph is linked by `cmd/worker` (through `internal/proposals/generator`) and `cmd/ai-eval-live` (through `internal/aievals`); `cmd/api` still links none (`no-eino-in-the-api`). No module was added or changed: `go.mod` and `go.sum` are as E1 left them. **E5:** `cmd/worker` and `cmd/ai-eval-live` link Eino through the photo pipeline's graph (23 Eino packages each, `go list -deps`), so their processes print H-064's one sonic line at start; `cmd/api`, `cmd/migrate` and `cmd/provision-tenant` link none. `go.mod` is unchanged.
- `go mod download` in the Dockerfiles' build stage fetches the new modules (including the five that no platform links); the runtime images do not change.
- **NOT RUN**: `govulncheck` (v1.9.0, the version CI pins) on the repository with Eino added. CI runs it on every push; source-mode scanning reports only code that is reachable, and no package reaches Eino yet, so the first slice that links Eino (E1) must run it and record the result. E1 did not: no `govulncheck` binary is installed and the slice had no network but the module proxy, so it is still **NOT RUN** (CI's run on push is the first). The design reports that a scratch probe that linked Eino was scanned with 0 affecting vulnerabilities; this slice did not repeat that. **E2** (the first slice whose binary links Eino) ran it: govulncheck v1.9.0 (built from the module cache; DB updated 2026-10-27), source mode on `./...`: "Your code is affected by 0 vulnerabilities", and 2 in a required module the code does not call, `golang.org/x/net` v0.60.0 (GO-2026-6866, GO-2026-6860, fixed in v0.62.0), which OpenTelemetry's gRPC exporter brings, not Eino. E3 (built in parallel with E2, on a tree without E2's graph) did not run one (no binary installed): **NOT RUN** for the proposal graph's own code until a later slice scans the merged tree. E5 (in parallel) did not run it either (no binary installed): **NOT RUN**.
- Upgrading Eino, sonic or any module above follows ADR-011's two-week rule, updates this ADR, the lists in `scripts/check-architecture/rules.go` (`einoClosure`, `einoBrings`, `sonicJIT`) and [THIRD_PARTY_NOTICES](../THIRD_PARTY_NOTICES.md), and reruns `make architecture-check` (the matrix test `TestEinoAgreedPlacementsConform` shows a new module or a new I/O edge).
- AGENTS.md §7 keeps "an autonomous multi-agent framework" out of P0. The design uses compose graphs and one ADK `ChatModelAgent` (H-060), not Eino's multi-agent packages (`adk/prebuilt/deep`, `planexecute`, `supervisor`, `flow/agent/multiagent`). Nothing refuses them yet: `go list` resolves `supervisor`, `planexecute` and `multiagent/host` with the current `go.sum` (only `deep` needs a module it lacks, doublestar). A rule refusing them is PROPOSED, not added.
- If the owner withdraws H-058/H-059, remove the `go.mod` lines, these rules and this ADR; nothing else depends on them.

## Alternatives

- **eino-ext's model components** (rejected above): they bypass the metered client.
- **sonic's native path** (a release supporting go1.27): no stderr line, faster JSON, but executable memory written at run time in the worker; not taken (the coordinator's choice).
- **Wait for v0.9.22**: under two weeks old until 2026-11-02, nothing needed from it.
- **No Eino** (H-056's first answer): superseded by H-058.
