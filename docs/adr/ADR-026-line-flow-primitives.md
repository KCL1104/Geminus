## Context

**How the current kernel (`internal/simulation/engine`, des-go-0.1.0, D-005/D-032/D-038 approved) works**; every proposal in this ADR takes it as the baseline:

- The event heap is totally ordered by (tick, priority, seq); there are only three priorities: SERVICE_COMPLETE=0, ARRIVAL/DELAY_COMPLETE=10, DISPATCH=20. `schedule` drops events later than the horizon outright, without taking a seq. A route is not an event: SERVICE_COMPLETE first releases the whole bundle atomically and records ServiceEnd, then, within the same event, follows decision/failure/rework to the next buffer, delay or sink; ARRIVAL, in order, creates the entity, schedules the next arrival, and routes.
- Each process has one unbounded request buffer (an explicit queue node is only its name); each resource has one FIFO; only a request that is first in the FIFO of every one of its resources is a candidate; dispatch takes candidates by seq and grants only when the whole bundle fits (all-or-nothing), otherwise it marks the request held and checks it again only when one of its resources is released (D-038 (k)(m)).
- Resource units are anonymous: the kernel has only an `inUse` count and does not know which unit serves which entity; capacity is fixed for the whole run.
- RNG streams are created on first use by (node ID, purpose) (purpose: arrival, service, delay, routing; trace uses a separate one); seeds are derived by SHA-256 and are mutually independent.
- The kernel reports Observations (kind, tick, seq, entity, node, resource, value) one by one; `testdata/simulation/kernel-observation-digests.json` locks the observation sequence; `engine-golden-digests.json` locks the result_digest of GOLDEN-001/002, whose payload contains engine_version, metrics, replication_summaries, measurement_window, reproducibility.

**Why new primitives are needed.** A research draft (not committed, not validated, used only as input) holds that factory engineers treat finite buffers and blocking, machine breakdowns, shift calendars and batching as basic features, and reject the results outright without them; changeovers are also common in high-mix SMT. None of these can be composed from the existing primitives: a resource is released at the end of each process, so it cannot hold a "downstream free slot" across steps; capacity does not vary over time; routing has no memory; a source has only fixed-distribution interarrivals. Working around this with scripts or a domain pack violates AGENTS §2, §7 and ADR-010.

**Constraints.** The kernel stays pure Go, with single-threaded replications, bounded events and no arbitrary scripts (REQ-011, REQ-024); the generic kernel does not read domain attributes; every new feature must leave **models that do not use it bit-for-bit identical to the current kernel**, with golden vectors and an independent SimPy reference (TEST-034).

## Decision (proposal)

Add the following generic primitives, all as optional IR fields; when a field is absent, the semantics are exactly the current ones. The field names were settled in the T-046 phase 2 schema change (table below; the full shape is in TWIN_IR_SPEC §2.1, the Result and trace members in SIMULATION_SPEC §5, §9); schema_version stays `0.1`. Until T-047–T-051 implement them, the validator and the engine reject any model that uses one of them with `PRIMITIVE_NOT_SUPPORTED` (D-063 APPROVED, H-019).

### D-047 Compatibility contract and differential method

**Questions.** How do new primitives enter the IR, the Result and engine_version so that models that do not use them stay bit-for-bit identical to the current kernel? How is that proved?

**Options.**
- A: add optional fields to the IR, schema_version stays `0.1`, an absent field = current semantics; new Result members appear only when the model uses the corresponding feature (or declares it in IR `metrics[]`, D-058); each task that changes the kernel bumps engine_version by one minor. Consequences: the bytes, model_hash and results of existing ModelVersions are unchanged, so no migration or upgrade flow is needed; the closed-object schema keeps old readers that do not recognize the new fields failing closed; schema_version no longer says "which features are used"; one has to look at the IR content.
- B: a new schema_version `0.2` (a superset of 0.1); 0.1 documents forbid the new fields, plus an explicit upgrade operation (it creates a new draft and the hash changes). Consequences: strict version semantics; one more upgrade API and UI flow, and templates, AI and the patch allowlist must handle both versions at once.
- C: always add the new statistics to every Result. Consequences: the result_digest of every existing model changes, which violates REQ-024's "identical when unused"; not adopted.

**Recommendation: A.** The IR is still a P0 draft (the opening of TWIN_IR_SPEC) with no production data yet, and A is the smallest change; if the owner wants strict version semantics, switch to B; the other decisions are not affected.

**Details.**
- Go types never output absent new fields (pointer or `omitzero`); existing fixtures re-encoded give the same model_hash (contract test).
- New events count toward `max_events`; blocked entities and entities in the release backlog count toward `max_active_entities`; new runtime failures have typed errors (`ErrDeadlock`, `ErrStalled`, D-050).
- New observation kinds continue the existing numbering, without renumbering (the observation digest encoding includes the kind's numeric value). New features record observations only for actual transitions: the initial capacity at t=0 and the initial "up" state are not recorded (Capacity and ResourceUp appear only on change); the Program gives the initial values to the Collector.
- The existing lock files (`kernel-observation-digests.json`, `engine-golden-digests.json`) are **not regenerated**.

**Determinism and digests.** engine_version is in the digest payload, so a version bump changes the digest string; for models **without any new field**, the criterion for "bit-for-bit identical" is therefore: the observation sequence (including seq) is identical, and the digest computed after setting the Result's engine_version back to `des-go-0.1.0` equals the locked value. A model that uses a new field (even with a neutral setting) gets new Result members, so its digest necessarily differs; only the observation sequence and the existing Result members are compared (see step 2 below). The new version gets locks of its own.

**Differential (every one of T-047–T-050 must do it).**
1. Freeze the des-go-0.1.0 kernel and replication as a test-only copy (the same approach as keeping the old kernel in the T-021 re-check); run models without new fields from the random model generator of `kernel_check_test.go` (bundles, explicit queues, zero-time service, decision loops, failure/rework); the observation sequences must be identical record by record; the number of models is fixed in the implementation task (the T-021 re-check used about 50,000).
2. Compare models with a "neutral setting" against models without the setting: the observation sequence (including seq) is identical record by record, and every existing Result member (metrics' throughput, lead time, the existing fields of resources, queues, failure/rework count, the existing fields of replication_summaries, measurement_window) is identical value by value; the new members a feature brings are not compared, nor is the whole digest. A neutral setting must not produce any new observation (including Capacity or ResourceUp at t=0). Neutral settings: buffer capacity ≥ `max_active_entities` (cannot block); a breakdown TTF that is constant and later than the horizon (the event is not scheduled and takes no seq); a calendar with only one shift covering the whole period (capacity unchanged, no events scheduled); a single-segment deterministic release schedule whose rate and period are exactly representable and whose 1/rate is an integer number of ticks (for example 0.5 items per minute, period 60 minute), at the same times as a constant interarrival of the same value (neither draws from the RNG); a single product and setups without `initial` (never changes over, D-055). Batching has no neutral setting (a batch request gets its FIFO position at a different time, D-054) and is not listed.
3. GOLDEN-001/002 and the existing des and metrics tests (none of their models has new fields) run as before on the new kernel and are compared against the locked digests by the "without any new field" criterion above.

**SimPy.** Not applicable; the reference for this item is the frozen old kernel.

### D-048 Same-tick order of the new events

**Questions.** Where in a tick do breakdowns, repairs, shift capacity changes, batch timeouts and unblocking go?

**Options.**
- A: add priority 15 (the resource-state kind: FAILURE, REPAIR, CAPACITY_CHANGE, BATCH_TIMEOUT), after arrival/delay (10) and before dispatch (20), by seq within the same priority; unblocking is not an event and happens inside dispatch, right after the grant that frees a slot (D-049). Consequences: that tick's dispatch sees the tick's final capacity; a unit released at priority 0 can be taken by a breakdown in the same tick; the relative order of the existing three priorities is unchanged.
- B: priority 5 (after service complete, before arrival). Consequences: the dispatch result is the same as A (dispatch is still at 20); only the observation order differs; no extra benefit.
- C: priority 25 (after dispatch). Consequences: capacity that has been repaired or come on shift must wait for the next dispatch, so each time one more dispatch must be scheduled and the event count grows; arrivals in the same tick do not see the new capacity.

**Recommendation: A.** Reason: capacity changes take effect before grants, no extra dispatch is needed, and the order of existing events does not change.

**Details.** Initialization order at t=0 (review L3): (1) each source's first arrival (node ID order, as now); (2) each calendar's first CAPACITY_CHANGE (scheduled only if S changes; calendar ID order; one event per calendar, D-052); (3) for each resource with breakdowns (resource ID order), each unit's first failure (unit index order; a scheduled clock computes its time from the calendar, D-051). A batch timeout is scheduled only after an entity enters the buffer. Priority-15 events in the same tick go by seq, that is, in the order they were scheduled. If a priority-15 event for the current tick is scheduled while a dispatch is in progress (for example a 0-tick repair), it runs after that dispatch and, if needed, schedules another priority-20 dispatch (an extension of D-038 (j); the tick does not go backwards).

**Determinism and digests.** The total order is unchanged; models without new features never have priority-15 events, and their seq is the same as now.

**Golden vectors.** (1) At t, priority 0 releases a unit, a breakdown (15) in the same tick takes it, and the waiting request is not granted at t; (2) an arrival (10) and a repair (15) in the same tick: dispatch (20) grants that arrival at t; (3) an arrival and a shift start in the same tick: granted at t; (4) a 0-tick repair arrives after dispatch: one more dispatch in the same tick.

**SimPy.** SimPy orders simultaneous events by scheduling order (some internal events are URGENT); no attempt is made to reproduce this kernel's tie-break. Same-tick semantics are fixed by hand-computed goldens; SimPy comparisons use only deterministic cases without simultaneous ties, or random cases with tolerances fixed in advance.

### D-049 Finite buffers and blocking

**Questions.** (1) Where capacity is defined and what it counts; (2) blocking after service (BAS) or blocking before service (BBS); (3) how a blocked entity holds resources; (4) the interaction with resource-wise FIFO and all-or-nothing bundles; (5) what happens when a source or a delay is blocked.

**Options.**
- A (BAS): an explicit queue node gets `capacity` (1–100000), which counts only waiting, not-yet-granted entities; absent = unbounded; when an entity's route reaches a full buffer, the entity stays at the node it departs from and becomes blocked: a process keeps its whole bundle, a source forms a release backlog, a delay occupies no resources; when the buffer has a free slot, blocked entities move in in FIFO order. Consequences: matches the line's "a finished board stays on the machine until the next station has room"; no reservation mechanism is needed; the sampling time of the routing stream does not change.
- B (BBS): service starts only when the downstream buffer has a free slot (or reserves one). Consequences: a grant must reserve a downstream slot across processes, and the interaction with all-or-nothing bundles and resource-wise FIFO is complex; probabilistic routing through a decision does not know before service where it goes, so routing must be drawn early or every possible downstream reserved, which changes the sampling time of the routing stream; unsuited to lines with test-failure branches.
- C: model it as a "downstream slot resource" (add the downstream buffer slot to the process's requires). Consequences: the current kernel releases all resources at the end of each process, so a slot cannot be held across processes; it needs a more general new primitive, "hold a resource across steps" (not scheduled for P0, see Consequences).

**Recommendation: A.** Reason: BAS is the common assumption on lines and easy for engineers to understand; it adds a check only at the "enter buffer" step, and the routing sampling time, resource-wise FIFO and the bundle rules are all unchanged; when nothing is blocked, it is exactly the same as now.

**Semantics (A).**
- **Capacity and "full"**: capacity belongs to the process's request buffer (D-005: an explicit queue is only its name), and counts whether an entity enters through the queue node or directly into the process; occupancy = the number of waiting, not-yet-granted entities (excluding those in service). Only an explicit queue node can declare capacity; a process without an explicit queue stays unbounded. Capacity 0 (a direct handoff with no buffer) is deferred: it needs "granted on entry", which changes the rule "grants happen only in dispatch".
- **Route resolved first**: the decision/failure/rework segment is resolved in the departure event as now (routing drawn at the same moment, failure/rework observations recorded, visits counted); only the last step, "enter buffer", checks capacity. A blocked entity's target is fixed and is not redrawn on unblocking.
- **SERVICE_COMPLETE**: resolve the target first. Resolution only draws the decision's routing and counts visits; it schedules no event and records no observation; the commit that follows keeps the current steps and order. When the entity will not be blocked, this is exactly the same as now (ObsResource for releasing the bundle → ServiceEnd → needDispatch → routing observations → enter buffer/schedule delay (the delay is still sampled at this point)/sink), so seq is the same too; when it will be blocked, it records ServiceEnd, the routing observations and Blocked, the bundle stays in use, and needDispatch is **not** called (no release and no enqueue; no seq taken). When ARRIVAL is blocked, it records Arrival, then Blocked (release backlog); when DELAY_COMPLETE is blocked, it records DelayEnd, then Blocked.
- **A limit hit mid-route (review L3)**: if resolution exceeds `max_entity_visits` (or another limit), first emit, in the current order, the observations that would already be recorded (the released ObsResource, ServiceEnd, and the routing observations before the failing node), then return `ErrEntityVisits`; these are exactly the observations the current kernel emits before the error (the differential relies on this order).
- **Unblocking**: only a grant makes an entity leave a buffer, so unblocking happens only in dispatch. After each grant that reduces P's buffer by one, if P has blocked entities, the first one in blocked FIFO order (the order in which they became blocked) moves in: atomically release the whole bundle of its departure process (ObsResource; the held candidate at the head of those resources' FIFOs is no longer held, as with SERVICE_COMPLETE), record Unblocked, and append it to the end of P's FIFO with a new request seq (ObsQueueEnter, At = queue node). Dispatch keeps taking the smallest-seq candidate until no candidate fits (fixpoint); chains (downstream grant → unblock → upstream release → upstream grant → unblock again) all complete within the same dispatch. Releases and enqueues during dispatch do **not** schedule another DISPATCH event (the current `enqueue` calls needDispatch; while a dispatch is in progress, a pending dispatch is treated as already present; no seq taken). A released unit first satisfies waiting breakdowns (D-051); only the rest can be granted.
- **Invariant**: P has a blocked entity ⇒ P's occupancy = capacity (at event boundaries); a newly arriving entity that meets a full buffer always queues behind the existing blocked entities.
- **With FIFO and bundles**: a blocked entity holds no place in P's resource FIFOs; the units it holds are unavailable to any request (including its own departure process's); P's grants are still all-or-nothing, and D-038 (m)'s "blocked by the FIFO" rule applies as before.
- **Source**: release times do not change because of blocking (the arrival stream runs as usual), and the entity waits at the source; lead time starts at arrival, so it includes backlog time; the backlog has statistics of its own.
- **Statistics** (appear only when the model has a finite buffer; T-046 phase 2 named them per replication `blocking[<node>]` (`blocks_started`, `blocks_completed`, `completed_block_ticks`, `blocked_entity_ticks`), `resource_states[<resource>].blocked_ticks` and `buffers[<queue>].full_ticks`, SIMULATION_SPEC §5): for each node that can be blocked, the number of blocks, the mean duration of complete blocks (W ≤ start, end ≤ H), and the time-average number of blocked entities; for each resource, the fraction of unit time held by blocked entities ∫K(t)dt/(C·T); for each finite buffer, the fraction of time it is full. The existing `utilization_mean` definition is unchanged (∫in_use/(C·T), including blocked units).

**Determinism and digests.** The new Blocked and Unblocked observations appear only in models with finite buffers; "resolve first, release after" changes only internal steps, and when nothing is blocked the observation order is the same as now.

**Golden vectors.**
- G-B1 two stations in series (constant): interarrival 1 min, A service 1 min (1 unit, unbounded buffer), queue before B capacity 1, B service 3 min (1 unit). B's completion times are 5, 8, 11, … (2+3k); A's blocked intervals are [4,5], [6,8], [9,11], …; each unblock and A's next grant are in the same tick.
- G-B2 the same model with an unbounded buffer before B: A is never blocked, and B's queue grows linearly (contrast with G-B1).
- G-B3 two upstream processes blocked by the same buffer in the same tick: unblocked in event-processing order.
- G-B4 source backlog: interarrival 1, queue capacity 1, service 2: the backlog grows by one item every 2 minutes; item k completes at 1+2k, lead time 1+k.
- G-B5 blocked after a decision: the number of routing-stream draws equals the number of decisions resolved; no further draw on unblocking.
- G-B6 neutral: capacity ≥ max_active_entities is identical record by record to an unbounded buffer (D-047).
- G-B7 the blocked entity's bundle includes a resource shared with another process (not forming a D-050 cycle): while the entity is blocked, that unit is unavailable to others.

**SimPy.** A machine is `simpy.Resource(capacity)`; a finite buffer is a "free slot" `simpy.Resource(capacity=B)`: the entity acquires A, runs timeout(service), requests a free slot of B **while still holding A** (blocking), releases A once it has the slot, requests B's machine, and releases the slot once it has the machine. The source creates entities on schedule, and each first requests a slot. Deterministic cases without simultaneous ties are compared value by value; random cases compare throughput, blocking fraction and buffer-full fraction with tolerances fixed in advance.

### D-050 Preventing and detecting deadlock and stall (deadlock/starvation)

**Questions.** When finite buffers, shared resources, shift calendars, breakdowns, batching and changeovers combine, a request may wait forever: (1) circular blocking (retest loops, shared resources); (2) a bundle's resources never all available at once. The review pointed out two counterexamples: with calendars R1 [0,480), R2 [480,1440) (period 1440) and process X needing R1+R2, X is never granted, upstream is blocked permanently once `q_X` fills, and X's request, blocking the FIFO, makes the other requests that use R1/R2 wait forever too (D-038 (m)); with capacity 2, TTF = TTR = 10 (constant) and X needing 2 units, the two failure clocks end up 10 apart, each time one unit is repaired the other's failure is processed before dispatch, and there are never 2 free units. The original proposal's runtime backstop required "no event in the heap that can release a unit", but periodic CAPACITY_CHANGE and REPAIR events are always there, so with calendars or breakdowns it never fires. How can this be prevented statically, how can the runtime detect it with typed errors, and how far does the guarantee reach?

**Options.**
- A: static rules R1–R4, all errors, plus runtime B1 (circular wait, exact) and B2 (bundle never assembled, a definite deadline). Consequences: every valid model lies within the range that provably never stalls permanently; B2 is only a backstop for gaps in the implementation or the rules; the runtime needs no state recording. The cost is that R4 rejects common forms such as "a machine that can fail has no calendar, its operator has one"; users must, as the error message says, give the machine the operator's calendar (the machine runs only while the operator is there anyway); when one failing machine is used by two operators whose shifts do not overlap, R4 cannot be satisfied and the machine must be split into two resources.
- A′: R1–R3 errors, R4 a warning; for bundles with a warning, B2 additionally detects fixed-phase permanent lockout with a state signature (the previous version's B2b). Consequences: accepts more models; but models with a warning are detected only when TTF and TTR are fixed, and other lockouts are not detected; signatures must be recorded and compared only after all exception days have ended (exception days are not periodic, review N6 (a)); signature memory must be capped by a per-replication total and counted toward the run's limits, and when a digest is stored, it must be confirmed by full state or by re-simulation before it is reported (review N7); implementation and validation costs are clearly higher; D-051's `clock` field comes back with it, and R4's warning must also add back the condition "has a calendar but uses a calendar-time clock"; otherwise a bundle without a warning can still fail while its partner is off shift, and the no-false-report argument no longer holds (review round 4 L2).
- B: runtime detection only (general wait-for analysis plus periodicity checks). Consequences: in periodic models with random breakdowns there is no general way to decide "will it recover later"; errors appear partway through a run, depending on the seed.
- C: no detection; rely on the horizon and limits. Consequences: violates TEST-034; not adopted.

**Recommendation: A (R4 an error).** Reason: most errors are pointed out with a JSON Pointer before running, independent of the seed, and come with a concrete fix; the guarantee covers every valid model; the runtime has only two backstops without false reports and no state-recording cost. If the owner wants to accept more forms, switch to A′, at the cost above. This also answers the "warning or error" question.

**Static rules (validator; R1 in the graph rules stage, R2–R4 after distribution/domain semantics; all errors).**
- **R1 `BLOCKING_CYCLE`**: holder = a process that needs at least one resource (including batch processes); sources, delays and processes without resources hold nothing when blocked. When A is a holder and A's way out (along p>0 flows, through decision/failure/rework, possibly through one more queue node) can reach P's finite buffer, there is a blocking edge A→P; processes that need the same resource are merged into one shared component (union-find, in ID order); the blocking edges are projected onto the components, and the model is rejected if there is a cycle (including component(A) = component(P)). Path is `/nodes/<i>/capacity` of each finite queue on the cycle; the message lists, in ID order, the nodes on the cycle and the shared resources that caused the merge, and states the fix: make at least one buffer on the cycle unbounded, or make the blocked process not share a resource with the process that blocks it.
- **R2 `CALENDAR_INVALID` (a bundle's available time)**: the least common multiple L of the periods of all calendars in the model ≤ 365 days; each process (including batch processes) has at least one tick in [0, L) at which every resource r of its bundle has S_r(t) ≥ its units (without a calendar S_r≡C_r; for per-shift capacity see D-052). Only the periodic part is considered; exception days are not counted. Path is `/nodes/<i>/requires`. The first counterexample is rejected.
- **R3 `RESOURCE_REQUIREMENT_INVALID` (bundle shape of failing resources)**: for a request on a resource with breakdowns, units must be 1; a bundle has at most one resource with breakdowns. The second counterexample and "two resources failing in anti-phase in the same bundle" are rejected. Cost: a step that needs two failing machines at once must be modelled as one resource representing the whole set (the set fails together).
- **R4 `STALL_RISK` (working time of a failing resource and its partners)**: when a bundle has a failing resource R, then at every tick at which R is on shift (S_R ≥ 1), every other resource Q of the bundle must have S_Q ≥ its units. Only the periodic part is considered; exception days are not counted (exception days are handled by X_end below). Path is `/nodes/<i>/requires`; the message names R and the insufficient Q, and suggests "give R a calendar contained in Q's working time (for example the operator's calendar)". D-051's failure clocks always advance only while S > 0, so there is no separate clock condition.

**Notation.** For a bundle, define fit(t): every resource r of the bundle has S_r(t) ≥ units_r (calendars only, including per-shift capacity and exception days; downtime and use are ignored). next_fit(t) = the smallest t′ ≥ t with fit(t′). X_end(q) = the end tick of the last exception among all calendars of q's bundle (0 when there are no exceptions; all exceptions lie within 365 days). Calendars are deterministic, so next_fit can be computed in integer ticks by merging each calendar's change points (the periodic part and the finitely many exceptions); R2 guarantees that every window of length L after the last exception contains a fit tick, so next_fit always exists and its computation is bounded.

**Guarantee (premise: service, delay, repair and changeover times are finite; TTF is at least 1 tick, D-051).** For every valid model (passing R1–R4), with an unlimited horizon, every waiting request is eventually granted, every blocked entity eventually moves, and B1 and B2 never fire. Proof sketch:
1. Processes that need the same resource belong to the same shared component, so the requests ahead of a request in any FIFO all belong to the same component. Hence in every component with waiting requests, the request with the smallest seq is first in the FIFO of each of its resources and is necessarily a candidate; by D-038 (m), later requests that share its resources cannot be granted first, so released or repaired units are all kept for it.
2. A unit in a candidate's bundle can only be: in service (released within finite time, or becoming blocked under BAS), held by a blocked entity, down (finite repair), or off shift.
3. A unit held by a blocked entity (at A) belongs to A's component, and A is waiting for P's buffer; this is a blocking edge between components. R1 makes the component graph acyclic, so the induction can proceed in reverse topological order of the component graph (starting from the components with no outgoing blocking edges).
4. Base case of the induction: when no unit of a component is held long-term by a blocked entity (it has no outgoing blocking edge, or every downstream component already satisfies the induction hypothesis), then for its smallest-seq candidate q, the units of q's bundle that are in service are released within finite time, after which only down or off-shift capacity is missing. Without a failing resource, q is granted at next_fit(now) (that tick's CAPACITY_CHANGE triggers a dispatch). With a failing resource R (R3: exactly one, units = 1), consider only the time after X_end(q): after it, the calendars have only their periodic part, and R4 makes "R on shift" imply fit; every down unit is repaired within TTR; R's clock advances only while R is on shift, so a repaired unit is still available at the next tick at which R comes on shift (it cannot fail while off shift, nor at the tick it has just come on shift, since no working time has accumulated yet), and that tick is also a fit tick, so q is granted. Before X_end, a partner may be off work on an exception day while R is still on shift, and a unit may fail (review N6 (b)); this only delays, never permanently.
5. Induction step: every request of the downstream components is eventually granted → their buffers repeatedly get free slots → the blocked entities of this component eventually move in in FIFO order and release their bundles → back to step 4, this component's smallest-seq candidate is eventually granted; after it leaves, the next smallest is again a candidate, so every request of this component is eventually granted.
6. Other features: a batch request exists only once the batch is ready, and waiting to fill a batch before that is not a stall (there is no request); a changeover only lengthens service, and the choice of unit does not affect "whether it fits" (a count); a release schedule only adds arrivals; finish-first overtime and waiting breakdowns both fall under "in use, released within finite time".
7. Deadline: when q enters, at t_q, the state "no unit of the bundle is in use", it is granted at the latest at deadline(q) = next_fit(max(t_q, X_end(q)) + TTRmax(q)), where TTRmax(q) is the largest possible value of the TTR distribution of q's failing resource (0 without a failing resource; exponential, lognormal and Weibull are unbounded, and then there is no deadline). Reason: the units already down at max(t_q, X_end) are all repaired within TTRmax after it, and by step 4 stay available until the next fit tick; if no unit was down at that time, q would already have been granted before next_fit(max(t_q, X_end)).

**Not guaranteed (stated explicitly).**
- When the TTR distribution is unbounded, the wait eventually ends (with probability 1) but has no deadline, and B2 does not check it.
- R1 is conservative: when the finite buffers in a loop are large enough to hold every entity that could be in the loop, the model in fact never deadlocks, yet it is still rejected; R4 also rejects some forms that would in fact never lock (for example when the failure distributions are not fixed).
- A stall means only a permanent wait; a wait not yet over at the horizon is censoring, not an error.

**Runtime backstop.** Both backstops read only counts and the deterministic calendars, do not affect the event order or the RNG, and keep no state record; when one fires, the run fails with no partial result (SIMULATION_SPEC §8). They are checked at the end of each dispatch; repairs, shift starts and a batch becoming ready all trigger a dispatch. By the guarantee above, neither fires for a valid model; they occur only when there is a gap in the rules or the implementation, and neither fails a run that would later make progress.
- **B1 `ErrDeadlock` (circular wait, exact)**: there is a blocked entity or a held candidate; the heap has no SERVICE_COMPLETE, DELAY_COMPLETE or BATCH_TIMEOUT, and none of these events was dropped for being later than the horizon; and every held candidate is release-bound (some r in its bundle has inUse_r + units > C_r, so neither a repair nor a shift start can make it fit) → return `ErrDeadlock` (job failure code tentatively `SIMULATION_DEADLOCK`), with the ID, node and tick of the earliest blocked entity (or, if there is none, of the earliest candidate). No false reports: no work in progress can release a unit, and capacity events cannot help a release-bound candidate.
- **B2 `ErrStalled` (bundle never assembled, a definite deadline)**: no resource in held candidate q's bundle has a unit in use. This state can end only by q being granted (other requests cannot take those units first), so it is counted from the tick t_q at which it was entered; if at the end of a dispatch q is still in this state and now ≥ deadline(q) → `ErrStalled` (tentatively `SIMULATION_STALLED`), with q's entity ID, process, t_q and deadline. Not checked when TTRmax is unbounded.

**Determinism and digests.** Validator output is sorted per D-023; the runtime checks do not change events or sampling; a failed run has no result digest.

**Golden vectors.**
- Invalid: (1) a process returns through a decision to its own finite queue; (2) two finite buffers form a loop; (3) A and P share a resource and A can be blocked by P's finite buffer (rejected even without a flow cycle); (4) the first counterexample → `CALENDAR_INVALID` at X's `/requires`; (5) periods of 300 days and 7 days (least common multiple > 365 days) → `CALENDAR_INVALID`; (6) the second counterexample (units = 2 on a failing resource) → `RESOURCE_REQUIREMENT_INVALID`; (7) two failing resources in the same bundle → the same; (8) a machine (no calendar, with breakdowns) + an operator (with a calendar) in the same bundle → `STALL_RISK`, and the message suggests giving the machine the operator's calendar; valid after the fix. Valid: the template.

### D-051 Resource breakdowns (MTBF/MTTR)

**Questions.** (1) Whether the failure clock runs on calendar time, scheduled time or busy time; (2) the entity in service at a failure: preempt-resume, preempt-restart or finish-first; (3) resources with several units; (4) RNG stream naming, so that existing streams do not change; (5) the definition of availability.

**Options (the entity in service).**
- A: one independent alternating renewal process per unit; at a failure, if a unit is not in use (including off-shift units), it goes down immediately; when all units are in use, finish-first: the next unit released goes down (several pending failures in FIFO order of failure time), and the repair time counts from the moment it goes down; the work item in service completes as usual. Consequences: the kernel's anonymous units are enough; no unit identity and no cancelling of scheduled events is needed; the downtime of each failure = TTR, and the capacity loss is the same as with preempt-resume, only that one work item finishes earlier; for long services (burn-in, rack tests) it underestimates the impact of interruptions.
- B: preempt-resume (interrupt, then finish the remaining time after the repair). Consequences: needs unit identity (which work item was interrupted), cancelling and rescheduling SERVICE_COMPLETE (the heap needs lazy deletion), and a rule on whether the bundle's other resources are kept or released during the interruption; many interactions with blocking, shift calendars and batches; belongs to the PRD's P1 preemption.
- C: preempt-restart (redo or scrap after the interruption). Consequences: as B, plus redrawing the service (RNG consumption changes) or scrap routing; belongs to the PRD's P1 preemption.

**Options (the failure clock, T-046 review M1).**
- (i) Calendar time: counted from the repair, regardless of busy or idle, on or off shift. Consequences: simplest; but machines fail while running, and in downtime records the calendar interval "from repair to the next failure" includes nights and weekends; with `two_shift_weekdays` (∫S/T = 80/168), the model's failure rate during shifts is only about 48% of the data's, while failures off shift take an idle unit and cause no loss, which systematically underestimates downtime during shifts.
- (ii) Scheduled time: the clock advances only while the resource is on shift (S(t) > 0). Per resource, no unit identity needed; because the calendar is deterministic, the failure time can be computed directly when the TTF is drawn: t_fail = min{t : Θ(t) ≥ Θ(t_up) + TTF}, where Θ(t) is the number of ticks in [0, t) with S > 0 (integer arithmetic, no pausing or cancelling of events). Consequences: the failure rate during shifts matches an MTBF "estimated on shift time"; when shifts have different staffing (D-052), the clock advances whenever S > 0, which is an approximation.
- (iii) Busy time: advances only while a unit is in service. Consequences: closest to wear-out failures, but needs the identity and accumulated busy time of every unit; not scheduled for P0 (see Consequences).

**Recommendation: A, with the clock always (ii) scheduled (calendar time for a resource without a calendar); no field to choose.** Reason: A has the smallest implementation and is compatible with anonymous units; (ii) corrects the systematic underestimate of (i) under shift calendars and needs no unit identity; D-050 recommends R4 as an error, and using (i) with a calendar would make failures happen while the partner is off shift, which is exactly the case R4 excludes, so (i) does not need to be an option. If the owner adopts D-050's A′ instead (R4 as a warning), add back an optional `clock: "scheduled" | "calendar"`. TTF must be estimated on the same clock: with scheduled, it is "the on-shift time between a repair and the next failure" ([ELECTRONICS_LINE §6](../domains/ELECTRONICS_LINE.md)).

**Semantics (A + (ii)).**
- IR: the resource's `breakdowns: {time_to_failure: {distribution}, time_to_repair: {distribution}}`; TTF accumulates on the resource's on-shift time (S > 0), and is calendar time when there is no `calendar_id`. The smallest possible tick of TTF must be > 0 (the same as D-033's rule for interarrival, to avoid a storm of same-tick events), otherwise `DISTRIBUTION_INVALID`; TTR ≥ 0, counted in calendar time (a repair can span off-shift time); empirical through dataset binding (D-006). D-050 R3: request units = 1 for a resource with breakdowns, and a bundle has at most one resource with breakdowns.
- Each unit u (0..capacity−1) is up at t=0, and its first TTF is drawn at t=0; failure → when it goes down, TTR is drawn and REPAIR is scheduled; at REPAIR, down decreases by one, the next TTF is drawn, the failure time is computed on the clock and FAILURE is scheduled. With the scheduled clock, failures happen only during on-shift time; when the target is reached exactly at the end of an on-shift segment, the failure time is that segment's end tick. When the drawn TTF saturates at 365 days + 1 tick (D-038 (b)), or the target on-shift time cannot be reached before the horizon, the FAILURE event is not scheduled (the same as events after the horizon, no seq taken); the search for t_fail moves along the calendar's change points and stops at the horizon, so it never searches without bound (review N4).
- The grant condition becomes `inUse + units ≤ min(S(t), C − down)` (S is the calendar capacity, C when there is no calendar, D-052). Pending failures are satisfied first at each unit release (the released unit goes down directly), and only the rest become available; REPAIR, like the start of a shift, cancels the held state of that resource's first candidate and schedules a dispatch.
- **Stream**: (resource ID, `ttf/<u>`) and (resource ID, `ttr/<u>`), u being the decimal unit index; the validator already requires node and resource IDs to be unique (DUPLICATE_ID), and the purposes are new strings, so existing streams are unaffected. Adding one to capacity only adds the streams of unit C; the draw sequences of units 0..C−1 do not change (common random numbers at the stream level). The clock does not affect the draws, only how a drawn TTF is converted into a time.
- **Statistics** (only for resources with breakdowns; their place in the Result is in D-058): the number of downtimes that start in the window, the down fraction ∫D/(C·T), the mean of complete repair times, availability = ∫min(S, C−D)dt / ∫S dt (unavailable when ∫S=0). Time spent pending (not yet down) does not count as downtime. An equipment breakdown and the generic `failure` node (a test failure) are different things; `failure_count` still counts only failure nodes (D-010).

**Determinism and digests.** The new events (FAILURE, REPAIR, priority 15) and the ResourceDown/ResourceUp observations appear only in models with breakdowns; no ResourceUp is recorded at t=0 (only actual transitions are recorded, D-047). Θ is computed entirely in integer ticks.

**Golden vectors.**
- G-F1 failure while idle: 1 unit, interarrival 2, service 1, TTF 10, TTR 3 (constant, no calendar): the arrival at t=10 enters the buffer first, the failure (15) takes the unit down until 13, a grant at 13, the next failure at 23.
- G-F2 failure during service (finish-first): interarrival 3, service 2, TTF 10, TTR 3: at 10 the unit is busy (9–11) and the failure waits; the release at 11 takes it down until 14; the entity that arrived at 12 starts at 14; the next failure is at 24, when the unit is idle, and the entity that arrives at 24 waits until 27.
- G-F3 2 units, one pending failure, two releases: the first unit released goes down, the second becomes available.
- G-F4 a capacity +1 scenario: the TTF/TTR draw sequences of units 0..C−1 are the same as the baseline's (compare the stream output, not the times).
- G-F5 neutral: a constant TTF later than the horizon is identical, record by record, to no breakdowns.
- G-F6 clock: calendar period 10 minutes, shift [0,6), TTF 8, TTR 1 (constant). Scheduled: on-shift time accumulates 6 in [0,6) and another 2 in [10,12), failure at 12, repaired at 13, then accumulates 8 again (3 in [13,16) and 5 in [20,25)), failure at 25. Compared with the calendar clock, which is not adopted: failure at 8 (off shift, takes an idle unit, no loss), repaired at 9, fails again at 17.
- `engine-vectors.json` adds Python reference values for the first k TTF/TTR of each unit.

**SimPy.** Uses `simpy.PriorityResource`: one failure process per unit, which after `timeout(TTF)` requests a unit at a higher priority than work items (non-preemptive), and once it has one, holds it for TTR and then releases it. The semantics of a non-preemptive priority are exactly "take an idle unit, otherwise take the next unit released"; equal priorities are ordered by request time, which matches the FIFO of pending failures. Scheduled clock: the failure process's timeout accumulates only during shifts (paused and resumed by the calendar process's events); compared within a stochastic tolerance.

### D-052 Shift calendar

**Questions.** (1) Calendars are expressed in ticks in the IR and use no time zone; (2) the entity in service at a shift change; (3) the denominator of utilization; (4) whether different staffing per shift and exceptions such as holidays are included (H-017's direction is to keep as many features as possible; whether to include them is for the owner to decide).

**Options (representation).**
- A: a root-level `calendars[]` (`id`, `period`, `shifts`: the [start, end) on-shift intervals within the period, optionally with a `label`, expressed in the model's time_unit); a resource refers to one with `calendar_id`; on shift S(t) = capacity, off shift 0. Consequences: several stations share one calendar, and there are common "scheduled hours of the line" to use as the UPH denominator.
- A+: A plus two optional fields: the resource's `shift_capacity` (label → 0..capacity, to express 2 people on the day shift and 1 on the night shift) and the calendar's `exceptions` ([{start, end, open}], expressed in absolute model time from t=0, with no dates or time zones; open=false is a shutdown, such as a holiday; open=true is overtime, S=capacity). Consequences: staffing per shift and holidays can both be expressed, still only as another way to write S(t), and the kernel does not change; the validator and D-050's R2 have to handle two more cases.
- B: each resource's own periodic capacity table ([{at, capacity}]). Consequences: can express different staffing per shift; repeated for every resource; no common line calendar, so UPH per scheduled hour needs a separately specified denominator.
- C: calendars with absolute dates and time zones. Consequences: needs time zones, DST and date functions, which violates "expressed in ticks, no wall clock" (T-049 scope); not adopted (exception days are expressed in A+'s absolute model time).

**Recommendation: A+.** Reason: several stations sharing one calendar is the norm on a line, and it gives "scheduled hours" a clear denominator; following H-017's direction, the agent recommends including both: staffing per shift and holidays cost little (both only change S(t)). H-017 approves no decision.

**Semantics (A+).**
- t=0 corresponds to offset 0 of the period (model local time; no time zone, no DST). Period ≤ 365 days; at least one shift, sorted by start, not overlapping, 0 ≤ start < end ≤ period (a night shift across midnight is split into two segments); quantized with `model.Ticks`, and still strictly increasing after quantization; at most 100 segments. A `shift_capacity` label must exist in that calendar, and its value is an integer 0..capacity; labels not listed and shifts without a label use capacity. `exceptions` are sorted by start, not overlapping, 0 ≤ start < end ≤ 365 days, at most 100 segments; within an exception S=0 (open=false) or capacity (open=true). Violations return `CALENDAR_INVALID`; an unknown `calendar_id` returns `UNKNOWN_REFERENCE`; D-050's R2 also checks each bundle's available time (exceptions not counted). A resource without a `calendar_id` is available all day (D-017: no implicit calendar).
- **Events**: each calendar schedules a CAPACITY_CHANGE (priority 15) at the times its S pattern changes; one calendar has at most one pending change event at a time. On processing, all resources that refer to it are updated in resource ID order, and a Capacity observation is recorded only for resources whose S actually changes; a resource whose capacity increases cancels the held state of its first candidate and schedules a dispatch. The initial S at t=0 is set by the Program, and no observation is recorded (D-047).
- **Shift change options**: (a) finish-first: entities in service and blocked entities complete or wait as usual, and busy time beyond the shift is recorded as overtime; (b) preempt-resume: the same mechanism as D-051 B, belongs to the PRD's P1 preemption; (c) do not start what cannot finish: needs the service length before the grant and changes when draws happen; not scheduled for P0 (see Consequences). **Recommendation (a).**
- **Denominator options**: (i) the original `utilization_mean` (∫inUse/(C·T)) stays unchanged, and resources with a calendar also get `scheduled_utilization` = ∫min(inUse, S)dt/∫S dt and overtime = ∫max(inUse−S, 0)dt; (ii) resources with a calendar use ∫S as the denominator of `utilization_mean`: the same field would mean different things for different resources, and existing users would misread it; (iii) only C·T: a station fully loaded on a single shift shows about 33%, and engineers will think it is wrong. **Recommendation (i).**
- With breakdowns: the failure clock pauses while S=0 (including shutdown exceptions, D-051); grant condition `inUse + units ≤ min(S, C−down)`.

**Determinism and digests.** CAPACITY_CHANGE uses no RNG; only resources that refer to a calendar have new events and Capacity observations.

**Golden vectors.** G-C1: 1 unit, period 10 min, shift [0,6), interarrival 2, service 3: services 2–5, 5–8 (off shift at 6, 2 minutes of overtime); the entity that arrives at 6 starts when the shift begins at 10 (10–13), the one that arrives at 8 starts at 13; scheduled utilization in the first period 4/6. G-C2: shift start and arrival in the same tick, granted in that tick. G-C3: neutral (one shift covering the whole period) is identical, record by record, to no calendar. G-C4: the two resources of a bundle have different but overlapping calendars; granted only when both are on shift. G-C5: capacity 2, `day` shift 2, `night` shift 1: at most 1 item in service at a time on the night shift; at the shift change, the 2nd item already in service is finished (overtime). G-C6: an exception with open=false means no grants in that segment, and the failure time of the scheduled clock is postponed by the same length. G-C7: two resources refer to the same calendar: one CAPACITY_CHANGE, Capacity observations in resource ID order.

**SimPy.** One calendar process per resource: when capacity drops from c1 to c2, it requests c1−c2 units at the highest priority (non-preemptive) and holds them until capacity rises again; when it rises, it releases the units it has taken and cancels the requests not yet granted. Finish-first is the same as in this proposal; exception days and per-shift capacity are different timetables of the same process. When used together with breakdowns, only a stochastic-tolerance comparison is done.

### D-053 Time-varying release (release schedule)

**Questions.** How is a release rate that varies by time period expressed? How does it relate to common random numbers? Is a production-plan style release table also included (H-017's direction, for the owner to decide)?

**Options.**
- A: a periodic piecewise-constant rate, generated by inverting the cumulative rate: the source's `arrival.schedule` (`period`, `segments: [{start, rate}]`, rate being the expected number of items per model time_unit, `process`: `poisson` or `deterministic`), mutually exclusive with `arrival.distribution`. Let Λ(t) = ∫₀ᵗ λ(s)ds, a₀ = 0; for the k-th item aₖ = aₖ₋₁ + Xₖ, Xₖ = 1 (deterministic) or −ln(1−U) (poisson, one draw from that source's arrival stream), time τₖ = min{t : Λ(t) ≥ aₖ}, quantized to a tick and at least 1 tick later than the previous item. Consequences: exactly one draw per item, and the k-th item of different scenarios uses the same draw (pairing kept); poisson is an exact non-homogeneous Poisson process, deterministic an exact takt; triangular/empirical interarrival is not supported.
- B: an explicit release table (`process: "table"`, `releases: [{at, quantity}]`, repeating every period). Consequences: closest to a production plan (for example releasing a batch at the start of each shift), no RNG; takt release over a long horizon needs many rows, so it is a third process alongside A, not a replacement for A.
- C: a separate interarrival distribution per time period, discarded at a segment boundary and redrawn at the start of the next segment. Consequences: supports any distribution; the boundary rule distorts non-exponential distributions; draw consumption depends on the number of boundary crossings, which breaks the pairing between scenarios; not adopted.

**Recommendation: A + B (three processes: poisson, deterministic, table).** Reason: planners usually describe release as "how many per hour", and A has exactly one draw per item and keeps the pairing; following H-017's direction, the agent recommends also including B: B costs little (no RNG, simple validation) and can express whole-batch release, so it is included too.

**Semantics.**
- Validation (`RELEASE_SCHEDULE_INVALID`): period ∈ (0, 365 days]. Rate type: the first segment's start = 0, starts strictly increasing and < period; rate finite and ≥ 0, at least one segment > 0, each segment's rate ≤ 1 item per tick; at most 1000 segments. Table type: `at` strictly increasing within [0, period), `quantity` an integer 1..10000, at most 1000 rows. `max_entities` still applies.
- **Numerical profile of the rate type (review L4)**: P = Λ(period) is summed in binary64 in segment order (each product explicitly rounded, as in D-038 (g)), recording each segment's starting cumulative cumStartⱼ and ending cumulative cumEndⱼ. k = ⌈a/P⌉−1, r = a−k·P; in binary64, r can fall outside (0, P] (example: P = 0.3, a = 502.5), so it is corrected once: when r ≤ 0, k decreases by 1 and r increases by P; when r > P, k increases by 1 and r decreases by P. Take the first segment j with rateⱼ > 0 and cumEndⱼ ≥ r; τ = k·period + startⱼ + (r−cumStartⱼ)/rateⱼ, then clamped to [k·period + startⱼ, k·period + endⱼ]. τ is converted into a tick by the sampler's quantization rule (one multiplication, round half up; beyond 365 days it saturates at 365 days + 1 tick and the event is not processed; `model.Ticks`, which reports an error, is not used), and then max(that tick, previous item + 1) is taken. ln uses the fixed `engine.ln`. The accumulator a keeps the unquantized value and is not derived back from the quantized tick, to avoid drift. The first item is at Λ⁻¹(X₁), consistent with the current "draw the first interarrival from t=0".
- **Table type**: one ARRIVAL event per row; on processing, the next row's ARRIVAL is scheduled first, then quantity entities are created in order, each routed by the current routing as soon as it is created (entity numbers consecutive); creation stops when `max_entities` is reached. Several releases in the same tick are finite (the quantity limit) and do not form the zero-time loop that D-033 forbids.

**Determinism and digests.** Only sources that use a schedule change; other sources' streams and events do not change. The table type uses no RNG.

**Golden vectors.** G-R1 deterministic: period 60 min, [0,30) rate 1/min, [30,60) rate 0: arrivals at minutes 1..30, 61..90, 121..150 (a = 30 falls at 30, not 60, which fixes the ⌈⌉ boundary). G-R2 poisson: the first N arrival ticks for a fixed seed are produced bit for bit by the Python reference. G-R3 a scenario that doubles one segment's rate: the k-th draw is the same as the baseline's. G-R4 neutral: the exactly representable single-segment rate above gives the same times as a constant interarrival of the same value. G-R5 high rate: ticks strictly increasing. G-R6 the correction step: an r that falls outside the bounds, such as with P = 0.3, a = 502.5, is corrected, and τ is bit for bit identical to the Python reference. G-R7 table: period 1440, [{at 360, quantity 50}, {at 840, quantity 50}]: 50 items each day at minutes 360 and 840, entity numbers consecutive, routed in creation order within the same tick.

**SimPy.** The rate type generates a non-homogeneous Poisson process with a different algorithm (Lewis–Shedler thinning, with Python's own RNG), and compares the mean and variance of the item counts per segment over many replications (tolerances fixed in advance); deterministic and table are compared value by value.

### D-054 Batch process (burn-in)

**Questions.** The lower and upper bounds of the batch size and the waiting limit; the IDs and trace of the items in a batch; the definitions of lead time and utilization.

**Options.**
- A: the process gets `batch: {min_size, max_size, max_wait}`. When the items waiting in the buffer reach max_size, or the oldest has waited max_wait and there are at least min_size items, the batch becomes "ready" and creates one batch request (one bundle, taking one FIFO position); at the grant, min(number waiting, max_size) items are taken in FIFO order; the whole batch has one service draw and starts and ends together; after completion, items are routed one by one in FIFO order; the bundle is released only after the whole batch has left (including blocked items). Consequences: matches a burn-in room; a batch request takes its FIFO position only when it is "ready" (an ordinary process takes it as each item enters); each batch process has at most one ungranted batch request at a time.
- B: fixed batch size only (starts only when max_size is filled, no max_wait). Consequences: simplest; in low-release periods (night shift) a batch may never fill, which is unrealistic.
- C: merge into one entity (assemble/separate). Consequences: needs merging and splitting and an ID mapping, with trace and lead time defined separately; not scheduled for P0 (panelization/depanelization also belong here, see Consequences).

**Recommendation: A.** Reason: the typical rule of a burn-in room is "start when the batch is full or has waited too long"; members keep their own IDs, so lead time, trace and 3D playback need no new entity concept.

**Semantics (A).**
- Validation (`BATCH_INVALID`): 1 ≤ min_size ≤ max_size ≤ 10000; when min_size < max_size there must be a max_wait (≥ 0); when the buffer is finite, capacity ≥ max_size.
- Readiness check: each time an entity enters the buffer, after each grant, and at BATCH_TIMEOUT (priority 15). When the oldest unbatched entity changes, a timeout event is scheduled (entry time + max_wait; if already expired, check immediately); an outdated timeout event is ignored when it fires. The check is repeated right after a grant, so several chambers can each start a batch in the same dispatch.
- Grant: one bundle (units counted per batch), one draw from the (process, service) stream; each member records ServiceStart in FIFO order with the batch ID `r<rep>/<process>/b<n>`, plus a BatchStart (batch size); the observation order is the bundle's ObsResource → BatchStart → each member's ServiceStart. Completion (one SERVICE_COMPLETE): first each member's route is resolved in FIFO order (routing draws in member order; members entering the same buffer take positions in order, and later members see the positions earlier members took). When no member is blocked: the bundle's ObsResource (once) → needDispatch → in FIFO order, each member's ServiceEnd, routing observation and entry into buffer/delay/sink. When a member is blocked (review L3): no release, and needDispatch is not called (unless a member enqueues); in FIFO order, each member records ServiceEnd and the routing observation, then the entry (unblocked members enqueue as usual, and enqueue schedules a dispatch) or Blocked. Afterwards, when a blocked member that is not the last is unblocked in a dispatch, only Unblocked and QueueEnter are recorded; when the last one is unblocked, the bundle's ObsResource is recorded first (release, pending failures satisfied first), then Unblocked and QueueEnter.
- Lead time and queue wait are counted per item (queue wait includes waiting for the batch to fill); the resource's utilization is the chamber being busy (not the slots); batch statistics (only for batch processes): the number of batches started, the mean batch size, the mean batch size/max_size.
- With blocking: when a member is blocked, the chamber is held, and the batch process is D-050's holder. With breakdowns and shift calendars: finish-first (the whole batch is completed).

**Determinism and digests.** One SERVICE_COMPLETE and one service draw per batch; BATCH_TIMEOUT and batch observations appear only in models with a batch process.

**Golden vectors.** G-T1: 1 chamber, min = max = 4, service 30, interarrival 10: batches start at 40, 80, 120…; members wait 30, 20, 10, 0 minutes, lead time 60, 50, 40, 30. G-T2: min 2, max 4, max_wait 25, service 30, interarrival 30: at 55 there is only 1 item, not ready; at 60 the second item arrives and the oldest has waited 30 ≥ 25 → (e1, e2) at 60–90; likewise (e3, e4) at 120–150. G-T3: 2 chambers, 9 items waiting, max 4: two batches start in the same dispatch, 1 item is left. G-T4: downstream full at completion: the chamber is held until the last member is unblocked. G-T5: the members' routing draws follow FIFO order.

**SimPy.** The buffer is a `simpy.Store`; a batcher process waits until the count ≥ max_size, or the count ≥ min_size and the oldest has waited max_wait (woken by a timeout event), then requests a chamber, takes out at most max_size items, timeout(service), and puts the items one by one into the next station. Deterministic cases are compared value by value, stochastic cases within tolerances fixed in advance.

### D-055 Changeover (setup/changeover, P0)

The owner's direction (H-017, 2026-10-19: 「時間還很久，盡量保留所有功能」 ("there is still plenty of time; keep as many features as possible"); H-017 lists changeover as a P0 proposal and does not approve the semantics): changeover is planned in P0; priority, preemption and advanced routing, which the PRD already lists as P1, stay P1. The semantics below were APPROVED on 2026-10-20 (H-018).

**Questions.** How are products represented; when does a changeover happen, how is its time determined, and on which unit does it happen; how does it interact with resource-wise FIFO, bundles, breakdowns, shift calendars and batches?

**Options.**
- A: resource-level sequence-dependent setup: the resource's optional `setups` (`initial`, `default`, `transitions: [{from, to, distribution}]`); product = the entity's `entity_type` (several products are expressed as several sources, one entity type per source, which the existing IR already supports); a resource with setups records each unit's setup state; at the grant a unit is chosen (preferring one whose state matches, otherwise the available unit with the smallest index); when the state differs, the setup time is drawn first and then the service, and the unit is in use during setup + service; dispatch is still FIFO. Consequences: covers each machine's own state and the changeover matrix; resource-wise FIFO and all-or-nothing do not change; under FIFO, interleaved products cause more changeovers (in practice reduced by grouping in scheduling; grouped dispatch belongs to the PRD's P1 priority/dispatch).
- B: process-level fixed setup: the process adds a setup segment when the entity_type differs from the previous item's. Consequences: simpler; when capacity > 1, "the previous item" can only be counted per process, which does not match each machine having its own state; cannot express a changeover matrix.
- C: A + dispatch grouped by product (campaigns, minimum-changeover sequencing). Consequences: closest to practical scheduling, but belongs to the PRD's P1 priority/dispatch rules and conflicts with resource-wise FIFO; P1.

**Recommendation: A.** Reason: each machine's own setup state and the changeover matrix are what engineers basically expect of changeovers; it only changes the "after the grant, before the service" step and the choice of unit, and the dispatch rules do not change.

**Semantics (A).**
- IR: the resource's optional `setups`: `initial` (an entity type, may be omitted), `default` (a distribution, may be omitted), `transitions` (from ≠ to, (from, to) unique, all existing entity types). The setup time takes the transition for (current state, product); when it is not listed, default is used; when there is no default either, 0; the same state means no changeover. When `initial` is omitted, each unit's first item has no changeover and sets the state to that product. Violations return `SETUP_INVALID`; an unknown entity type returns `UNKNOWN_REFERENCE`.
- P0 limits (violations return `SETUP_INVALID`): a resource with setups has units = 1 in every requires; a process needs at most one resource with setups; a batch process must not need a resource with setups (a batch may mix products).
- **Unit identity**: only for resources with setups, each unit's status (in use, down, idle) and setup state are recorded; the capacity rule is still a count (`inUse + units ≤ min(S, C−down)`, D-051, D-052). At the grant, among the available units, the one with the smallest index whose state matches the product is taken, otherwise the available unit with the smallest index. D-051's breakdown semantics do not change; only which unit is affected is now determined: an immediate down takes the idle unit with the smallest index; a pending failure is borne by the next unit released; going down does not change that unit's setup state.
- **Draws and events**: at the grant, if a changeover is needed, the setup time is first drawn from (resource ID, `setup/<u>`), then the service from (process, service) as now; the completion event is scheduled after setup + service, still a single SERVICE_COMPLETE, with no new event kind. At the grant a Setup observation (resource, unit, time) is recorded, then ServiceStart (as now); queue wait still counts up to the grant.
- **Statistics** (only for resources with setups): the number of changeovers started in the window, the fraction of unit time spent in setup ∫(units in setup)dt/(C·T) (the part that crosses W/H counted by overlap), the mean of complete setup times. The station states in ELECTRONICS_LINE §5 split "processing" into processing and setup.
- **With other features**: breakdowns and shift changes are finish-first (both the setup and the service are completed); when blocked, the unit is held per D-049. A scenario may modify the distributions in `setups` under D-057's rules (replace, risk at least medium); adding or deleting setups goes through draft→publish.
- **Event log**: inferring changeovers needs each serial's product (D-059's optional `product`).

**Determinism and digests.** Affects only resources with setups. A model with a single product and no `initial` never changes over and records no Setup observation, identical record by record to no setups (D-047's neutral setting); the choice of unit is a fixed rule and does not depend on map order. Implemented in T-050 (whose scope already includes "changeover, if included in P0").

**Golden vectors.** G-S1: 1 unit; `src_a` interarrival 10, `src_b` interarrival 20 (constant); service 2; A→B and B→A changeover 3: A1 at 10–12 (first item, no changeover, state A); at t=20 the arrival of B1 has a smaller seq (scheduled at t=0) and enters the buffer first, at 20–25 (changeover 3 + service 2), A2 at 25–30; A3 at t=30 has no changeover (30–32); at t=40 B2 comes before A4. G-S2: 2 units, with states A and B: B's item chooses unit 1, no changeover. G-S3: transitions take precedence over default, 0 when default is missing, with and without `initial`. G-S4: neutral (single product) identical record by record to no setups. G-S5: with capacity +1, the setup stream sequences of units 0..C−1 do not change. G-S6: a pending failure falls on a unit in changeover: it goes down only after the changeover and the service are done.

**SimPy.** Unit choice is a custom rule (SimPy's Store/FilterStore does not directly support "prefer a match, otherwise the smallest index"), so a dispatcher written in Python manages the unit states, together with SimPy's time advance; deterministic cases are compared value by value, stochastic cases compare the number of changeovers, the setup fraction and throughput (tolerances fixed in advance).

**Still P1.** Dispatch grouped by product and changeover-minimizing sequencing (PRD P1: priority/dispatch); interrupting a changeover (preemption).

### D-056 lognormal and Weibull (P0)

The owner's direction is the same as for D-055 (H-017 lists lognormal/Weibull as a P0 proposal): include them in P0. The semantics below were APPROVED on 2026-10-20 (H-018).

**Questions.** Repair times and times between failures are often described with lognormal and Weibull; how are the parameterization, the sampling algorithm and the numerical profile defined so as to keep "bit for bit identical across platforms, one draw per sample"?

**Options.**
- A: both by the inverse-transform method, one U per sample: Weibull x = scale·(−ln(1−U))^(1/shape), with the power computed as exp(ln(y)/shape); lognormal parameterized by mean and cv, σ² = ln(1 + cv²), μ = ln(mean)−σ²/2, x = exp(μ + σ·Φ⁻¹(U)), Φ⁻¹ with a fixed rational approximation (Wichura AS241). exp uses the pure-Go algorithm of Go's `math.exp`, with each product explicitly rounded (as D-038 (g) does for ln). Consequences: stream consumption is the same as the existing samplers' (one draw per sample); needs a fixed exp and AS241, an operation-by-operation Python port, vectors, an assembly check and a new engine_version.
- B: lognormal with the normal generated by Box–Muller. Consequences: two U per sample (or one has to be cached), stream consumption differs from the other samplers, and a fixed sin/cos is also needed; not adopted.
- C: add only one of them. Consequences: about half the work; the other common model is still missing.

**Recommendation: A.** Reason: the two are the most common parametric distributions for times between failures and repair times, and the owner asks to keep as many features as possible; the inverse-transform method keeps "one draw per sample" and the golden method unchanged; mean and cv are parameters engineers know better.

**Semantics (A).**
- IR: distribution adds `{"type": "lognormal", "mean", "cv"}` and `{"type": "weibull", "shape", "scale"}`, with parameters expressed in the model time_unit (cv and shape have no unit); `mean`, `scale` > 0; candidate ranges 0 < cv ≤ 10, 0.1 ≤ shape ≤ 20 (to be finalized after the vectors and an overflow analysis); usable in every distribution field (interarrival, service, delay, TTF, TTR, setup).
- D-033: the support of both is (0, ∞), treated as always > 0; a sample is at least 1 tick after quantization (as in D-038 (a)); beyond 365 days it is represented as 365 days + 1 tick (D-038 (b)). Validation: parameters finite, > 0 and within range, and `mean`/`scale` not exceeding 365 days after conversion (D-029); violations return `DISTRIBUTION_INVALID`.
- Numerical profile: the operation order and constants (bit patterns) of exp, ln, sqrt and AS241 are written into the vectors; the platform's `math.Exp`/`math.Pow` are not called; `make backend-numeric` checks them too. Changing any of them changes the engine_version. The implementation is merged into T-048 (breakdown parameters use them most).

**Determinism and digests.** Affects only models that use these two distributions; other samplers and streams do not change.

**Golden vectors.** As in T-020: each sampler's 12-draw vector and the SHA-256 of 10⁵ draws (including the binary64 values before quantization); the SHA-256 of 10⁶ exp inputs and boundary values (underflow, overflow, subnormals); the values of AS241 at U near 0, 0.5 and 1; the bit patterns of μ and σ converted from mean and cv.

**SimPy.** The Python reference is ported operation by operation to be bit for bit identical; in addition, distributions from independent implementations such as numpy/scipy are used for a KS test and a comparison of the first two moments on 10⁵ samples (tolerances fixed in advance), to confirm that the profile is statistically correct.

## Architectural approaches not adopted

- **Simulating with existing primitives in a domain pack**: a resource cannot be held across processes and capacity does not change over time, so it cannot be done; it also violates ADR-010 (a domain does not change the generic engine).
- **Switching to an external DES library or running SimPy in production**: violates ADR-006 (native Go DES) and AGENTS §7 (no arbitrary Python runtime); SimPy is only an independent reference.
- **A generalized "hold a resource across steps" or script hooks**: can express more (a rack debugged inside its test slot), but would change D-050's holder and blocking graph, with a large scope and validation cost; script hooks violate AGENTS §7. Holding across steps is recommended as a separate task after the core is complete (see the table below).
