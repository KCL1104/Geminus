# ADR-029 — Containers, migration step and S3-compatible object storage (T-039 hackathon slice)

Status: **PROPOSED** (2026-10-26, proposed and implemented by the T-039 agent; awaiting the owner and independent review). Basis: the scope of T-039, H-029 (3) (video + public URL: Docker + managed Postgres, synthetic data only, an Auth0 tenant created by the owner), the owner's cloud choice (H-030 first "railway + cloudflare", then H-031 changed it to 「純用 railway」 ("Railway only"): H-031 is the basis for Railway only), H-032 (the owner gives a Railway token to later sessions; the coordinator deploys with a non-interactive script), D-044 (the object storage interface; the production adapter gets its own ADR after the owner chooses a cloud), D-042 (provisioning login), ADR-017, ADR-018, ADR-024, ADR-028, AGENTS.md §2–§7. This ADR approves no PROPOSED decision and deploys nothing.

## Context

- The P0 deployment units are web, api, worker, managed PostgreSQL, object storage and an OTLP backend (ARCHITECTURE §8). The T-039 hackathon slice needs a public URL: Railway runs three Docker services and a managed PostgreSQL.
- Both the API and the worker read and write object storage (uploads, dataset snapshots, traces). The only adapter (`FS`) is for development/test only (D-044: `APP_ENV=production` refuses it), and a Railway volume belongs to a single service, so the API and the worker cannot share files. Railway offers S3-compatible Storage Buckets (private, Tigris, checked 2026-10-26, see the [deploy runbook](../runbooks/deploy.md) §7.4).
- There is no production migration tool: `scripts/run_db_tests.sh` only runs up/down against disposable `dt_test_*` databases.
- The API has no health endpoint that needs no token, and the platform (Railway's healthcheck) requires a 2xx.

## Decision

### Images (`Dockerfile.api`, `Dockerfile.worker`, `apps/web/Dockerfile`)

- Always built from the repository root; multi-stage; base images pinned by digest (the table in ADR-011); the runtime is non-root (Go: distroless static `nonroot`, uid 65532; web: Node's `node`, uid 1000); no `ARG` is declared (Railway passes into the build only the variables declared as `ARG`, see runbook §7); no credential goes into an image; `.dockerignore` excludes git, env files in any directory (`**/.env`, `**/.env.*`, with only `!**/.env.example` brought back; review round 1 L3), node_modules, build output, checks and sources.
- The API image also contains two operator commands, `geminus-migrate` and `geminus-provision-tenant` (each with its own login, which the API service never gets), and `/migrations/*.up.sql`.
- Web: Next's standalone server (only the image build sets `GEMINUS_NEXT_STANDALONE=1`; `make frontend-build` and the browser checks are unchanged); npm, corepack and yarn are removed from the runtime.
- Health checks: outside `/v1` the API serves `GET /healthz` (the process is alive) and `GET /readyz` (the database answers within 2 seconds); they need no token, return only `ok`/`ready`/`unavailable` and stay out of the access log; `geminus-api -probe` is the image's `HEALTHCHECK` (the image has no shell or HTTP client). They are not contract operations (every `/v1` operation runs in one organization, `scripts/check_contracts.py`), so they are not in `openapi/openapi.yaml`. The worker has no HTTP listener; the platform watches the process. Web is checked at `/`.
- Stopping: on SIGTERM the API stops accepting and finishes in-flight requests (20 seconds); the worker stops its handlers and records the attempt (ADR-024); Next's server exits on SIGTERM (no drain).

### Migration step (`cmd/migrate`, `internal/storage/migrations`)

- `geminus-migrate up|status` reads only `GEMINUS_MIGRATE_DATABASE_URL` (it never reads the runtime `DATABASE_URL`). The login must be able to act as twin_owner, must not be a member of twin_api/twin_worker/twin_provisioner, and must not have SUPERUSER, BYPASSRLS, CREATEROLE, CREATEDB or REPLICATION (a superuser is a member of every role, so it is refused too).
- Each migration and its record (`geminus_migrations.applied`: version, file name, the file's SHA-256, time, login; owner twin_owner, no privilege for PUBLIC) are in the same transaction; when the file itself has `BEGIN;…COMMIT;`, the record is inserted before its `COMMIT;`; when it does not (0003), the whole file is wrapped in one transaction; transaction statements anywhere else in a file are always refused. An advisory lock makes two concurrent runs take turns. When the records do not match this build's files (an applied file was changed, the database is newer than the build, there is a twin schema but no record), it refuses and does not repair. **Known gap (review round 1 L4, not fixed)**: transaction statements are detected by whole-line matching, so `END;`, `COMMIT WORK;`, `COMMIT AND CHAIN;`, `PREPARE TRANSACTION`, and a `COMMIT;` on the same line as another statement are not refused; until this is fixed, new migrations must not use these forms (none of the existing 16 do).
- Rule `migrations-only-in-their-command`: only `cmd/migrate` can link the runner (not the API, the worker or the storage probe).
- Creating the logins: `deploy/sql/create_logins.sql` (psql 15+, passwords only from environment variables via `\getenv`), run once by an administrator after `db/bootstrap_roles.sql`: `geminus_migrator` (twin_owner), `geminus_api`, `geminus_worker`, `geminus_provisioner` (NOINHERIT, D-042), and it gives twin_owner CREATE on that database.

### Object storage: S3-compatible adapter (`internal/storage/objects/s3.go`)

- `OBJECT_STORAGE_PROVIDER=s3` is accepted with any `APP_ENV`; `OBJECT_STORAGE_S3_ENDPOINT` (an https origin; plain http only on loopback), `_BUCKET` (a DNS label), `_REGION`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY` (a secret, printed as `[redacted]`), `_URL_STYLE` (`virtual-hosted`, the default, or `path`). The whole set or none: when the provider is not s3, any `OBJECT_STORAGE_S3_*` refuses startup.
- The same `Store` contract as FS: only server-generated keys are accepted (D-035); Put first buffers the bytes in `/tmp` (up to max; over it, nothing is sent), signs with SHA-256 (`x-amz-content-sha256`) and sends with `If-None-Match: *`, so an existing object is never replaced (412 → `ErrExists`; a HEAD comes first, so in the common case the bytes need not be sent); Get streams; Delete is for maintenance only. The bucket is private: every request is signed, no presigned URL is produced (D-044: stream after the API authorizes), redirects are not followed. Errors carry only the operation, the HTTP status and the service's error code.
- SigV4 is implemented in-house with the standard library (about 150 lines), with no SDK: the canonical request, string to sign and Authorization are verified against the test suite AWS publishes (15 vectors); an in-process fake S3 server (no network) verifies every request with the same signing, checks the payload hash and simulates the conditional PUT. All 17 mutants are caught by the tests.
- Whether the conditional PUT holds against a real bucket can only be confirmed by the owner running `TestLiveBucket` with the bucket's credentials (runbook §7.4); until it is confirmed, it must not hold any data that is not synthetic.

### Railway automation (`deploy/railway/deploy.sh`, H-032)

- `deploy.sh --apply`, with the pinned Railway CLI 5.64.2 (`--install-cli` checks the release archive's SHA-256; `CI=true` and `RAILWAY_NO_AUTO_UPDATE=1` keep it from updating itself), carries out runbook §7.1–§7.6: project and environment, PostgreSQL, bucket, the four services and each one's config-as-code file, public domains, the variables of `variables.json`, logins, migrate, seed, api/worker/web, verification; each step looks first and creates only what is missing, so it can be rerun. `--dry-run` does not touch the network; it checks the inputs, tools and deployment files and prints every command.
- The token is read only by the CLI from the environment (`RAILWAY_TOKEN`: a project token; `RAILWAY_API_TOKEN`: an account/workspace token); the script registers it as a secret to mask and removes it from the environment of every program other than the CLI (psql, `go run`, git); `deploy.sh` refuses (exit 2) before running any command when xtrace is on; before every call it checks that no argument holds a secret, any known secret in the output is always replaced by `[redacted]`, and CLI output that contains secrets (variable list, bucket credentials) is only parsed, never printed.
- Generated secrets (the passwords of the three logins, `SESSION_KEYS`) are generated locally with Python's `secrets`, set through `railway variable set KEY --stdin` and then sealed; Railway's `${{secret()}}` is not used: Railway's documentation describes it only as a function for template deployments and does not say that ordinary service variables can use it (runbook §7.7). The provisioning login's password is generated anew on every run and exists only in that run's seed environment. The owner's variables (`BFF_OIDC_CLIENT_SECRET`, the AI keys, `GEMINUS_AI_LIVE`) are not set by the script; verification only checks that the names of the required ones exist.
- The variable list (review round 1 M2): the only way to know whether a variable exists, `railway variable list --json`, returns every value that is not sealed (sealed ones are `null`). While it parses the JSON, the script keeps only the values it needs (the passwords it generated, Postgres's `DATABASE_PUBLIC_URL`) and registers each as a secret; every other value (all of the owner's included) is replaced by a "set/sealed" marker and never enters any state, output, error or exception. The owner should seal a variable right after adding it; verification lists by name the owner secrets not yet sealed. When a variable is not sealed, its value still passes briefly through the script's process: the literal gap with H-033's "only look at names, never read values" is for the owner to decide (runbook §7.3). Not every value received is registered as a secret, because Railway's own variables have values such as `railway`, `production` and `5432`, and once registered, the argument check would refuse the CLI's own calls; so values that are not needed are always discarded, which is more conservative than masking.
- The database bootstrap goes through Postgres's public TCP proxy (`sslmode=require`). The proxy opened in this run is removed at the end of steps 4–6, and also on failure, SIGTERM and SIGHUP (signals are turned into an exit); when `tcp-proxy delete` fails, the id and the removal command are written out and the run ends with exit 1; before every `--apply` ends, Postgres's TCP proxies are listed, and if any proxy is still open (including one that existed before the run and was reused rather than removed: the script cannot tell whether someone else opened it or an interrupted run left it) or they cannot be listed, it reports the id and the removal command and ends with exit 1; only with `GEMINUS_KEEP_DB_PROXY=1` set explicitly does an open proxy just give a warning (review round 1 M1). SIGKILL cannot be caught; the next run reports it. Migration does not use a pre-deploy command (that would hand the migration login to the API service); instead a separate `migrate` service is deployed, and api and worker are deployed only after the row count of `geminus_migrations.applied` equals the number of migrations in the checkout.
- `scripts/rehearse_railway_deploy.py` runs the full `--apply` offline with stand-ins for `railway`, `psql` and `go` (the author's 12 mutants and review round 1's mutants are in `checks/T-039_VALIDATION.md`); it does not prove that Railway accepts every call. Not checked: whether a reference to a sealed variable is expanded (the recovery in runbook §7.7: `GEMINUS_RAILWAY_SEAL=off`).

## Consequences

- D-044's "production adapter" now has an implementation, but the encryption keys, retention, region and backups are still the bucket provider's defaults, not decided by the owner: synthetic data only (SECURITY §6).
- Put needs scratch space: the API's uploads are at most 50 MB and the worker's canonical datasets at most 256 MiB, written to the container's `/tmp`.
- Railway's buckets are reachable only over the public network (Railway documentation); uploads from a service to the bucket count as service egress.
- The deployment order (migrate → api/worker → web) is guaranteed by `deploy.sh` or by the person deploying by hand; the platform does not enforce it.
- The CLI commands and JSON shapes in `deploy.sh` follow the source of CLI v5.64.2; before the CLI is upgraded, they must be checked again and the pin and the rehearsal's stand-ins updated.
- If the owner does not adopt it: remove `s3.go`, `sigv4.go`, the config's `s3` branch (back to not implemented), `cmd/migrate` and `internal/storage/migrations` (if another tool runs the migrations, it must likewise use the migration login, never the runtime login), the health probes and `deploy/`.

## For the owner to decide

1. Whether to accept this ADR (the S3 adapter, the in-house SigV4, the schema `geminus_migrations` of the migration records, health probes kept out of OpenAPI).
2. The BFF calls the API through the API's public domain (https); Railway's private network is plain http (WireGuard-encrypted), and the BFF currently accepts http only when every URL is loopback. Whether to allow the BFF to reach the API over http on the private network (this needs a change to the BFF's check and a separate review), or to keep the public domain.
3. The bucket's region (it cannot be changed after creation) and the data retention period.
4. Whether to accept secrets generated locally by `deploy.sh` and sealed (not `${{secret()}}`); if the first `--apply` finds that Railway does not expand a value that references a sealed variable, whether to accept `GEMINUS_RAILWAY_SEAL=off` (passwords visible in Railway's UI) or instead store the whole database URL as a sealed variable (needs changes to the script and the checks).
5. When the owner's variables are not sealed, the CLI's variable list hands their values to the script (discarded on receipt): whether to accept this, or the owner always adds them sealed (H-033).

## Addendum (T-057, 2026-10-26, PROPOSED): the Auth0 step of `deploy.sh` (H-034) and the judge account (H-035 (2))

Following H-034 (the owner chose 「裝置登入，由你設定」 ("device login, you set it up")) and H-035 (2) (the owner and one judge account, with access to the demo organization only), the following is added to this ADR's Railway automation; PROPOSED, awaiting independent review and the owner. Details and every setting are in the [deploy runbook](../runbooks/deploy.md) §7.8, the manual fallback in the [Auth0 runbook](../runbooks/auth0.md) §6, and the verification in `checks/T-057_AUTH0_VALIDATION.md`.

- **The CLI pin**: Auth0 CLI 1.37.0 (2026-09-30, MIT). `deploy.sh --install-auth0-cli DIR` checks the archive's SHA-256 (the release's `checksums.txt`) and then the SHA-256 of the binary in it, and installs only when both match; `railway_deploy.py` computes the SHA-256 of the binary on PATH before running the CLI and does not run it (not even `--version`) unless it is the pinned one. `check_deploy.py` checks that the two pins agree.
- **Step 2b** (`GEMINUS_AUTH0_SETUP=cli`, the default; skipped with `manual`, which is T-039's original manual flow by the owner): the CLI runs in agent mode (`--agent-mode --no-input --no-color`) in its own home (0700, deleted at the end; one left by an interrupted run is logged out and deleted first on the next run), with an environment of only PATH, locale, proxy and CA settings, `AUTH0_CLI_ANALYTICS=false`, `DBUS_SESSION_BUS_ADDRESS=disabled:` (the keyring is not touched; the CLI's session lives only in that home), and no Railway token. The owner approves the login in their own browser with a device code (only the URL and code the CLI prints are shown), and the tenant logged in must be the one of `GEMINUS_AUTH0_ISSUER`. After that, the API, the Regular Web Application, the database connection's sign-up, the connections enabled for the application and the judge account are each "compare if found, update only if different, create if missing", and every write is read back and compared; writes always go as JSON through stdin (`--data @-`), with the CLI's own commands (`apis`, `apps`, `connections`, `connections enabled-clients`, `users`), not `auth0 api` (the response of `auth0 api` in 1.37.0 does not mask `client_secret`). At the end (success, failure, SIGTERM, SIGHUP), `auth0 logout` ends every session and the home is deleted.
- **Client secret**: read with `auth0 apps show --reveal-secrets` only when this run created the application, the web does not have it, or the web's `BFF_OIDC_CLIENT_ID` is not this application; while the JSON is parsed, it is put into that one call's own list (every other credential field is replaced by a marker), handed only through stdin to `railway variable set BFF_OIDC_CLIENT_SECRET --stdin`, and sealed at once. Its `source` in `variables.json` changes from `owner` to `auth0` (only it may have that source; `check_deploy.py` checks this).
- **No secret in the deploy script's state**: the values to mask are now kept only as HMAC digests under a key new on every run (every substring of a text is compared by digest), `secret()` returns no value, and the Railway token is added only inside `run()` to the Railway CLI's own environment (the answer of `child_env` does not contain it); the judge's new password is kept only in `main()`'s own list and written to stderr once at the end of the run. The rehearsal scans the deploy script's attributes, results, and every method's return values and exceptions (the M2 approach of T-039); it found the original token in two places, in the state (the plaintext masking list) and in a return value (the `child_env` dict had the token added after it was returned); both are fixed.
- **The judge account's membership**: `cmd/provision-tenant organization` gains `-member-issuer`/`-member-subject`/`-member-role` (editor or viewer, all three together), which adds one member in the same transaction that creates the organization; the audit `organization.provision` gains `member_user_id` and `member_role` (new catalogue fields; D-091's "one event per business write" is unchanged). Migration 0004 is not loosened (provisioning can only add members to the organization it creates in the same transaction): when the demo organization was seeded earlier, the judge account is created only as a user, and verification fails and writes out how the owner adds it with the membership API (ADR-023). After the seed, an administrator lists the judge account's memberships, which must be only editor of the demo organization. Editor is the role chosen: proposing and approving AI proposals and running simulations need owner or editor (openapi's `x-required-roles`), which viewer cannot do; the extra things owner has, member management and the audit log, are not needed.
- **The application enables only the database connection**: H-035 (2) asks to turn off self-registration; a new tenant's default social connection (Google) would let anyone create a user in Auth0, so the Auth0 step disables the application on every other connection; before any write it first confirms that the owner's own user is in that database connection, and stops otherwise. This goes beyond the literal wording of H-034 and is listed as pending a decision.
