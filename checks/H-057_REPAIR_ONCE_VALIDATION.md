## 1. What changed

Before: when the server refused the model's first answer (live, photo proposals passed about 1 in 4: `ROUTING_INVALID` at an added node, `AI_OUTPUT_INVALID` at `/changes`; H-054), the proposal ended `invalid` at once.

After: an answer the server refused **for what it says** gets **one** repair inside the same job attempt. The model is asked once more with the same system prompt and context, its own previous answer as the assistant turn, and a user turn listing the server's issues (code, JSON Pointer path, the server's own fixed sentence). The second answer goes through exactly the same decode and checks; the proposal's state is whatever that review says (`ready`, `needs_input` or `invalid` with the second answer's issues). Never a third request.

## 7. Risks

1. **Meta's endpoint and the prior assistant turn are unverified live.** The request is the documented Anthropic-compatible Messages shape (user, assistant, user), but no live call ran. If Meta refuses it (for example a prior assistant turn without its reasoning blocks together with structured output), every repair fails: the proposal keeps the first answer's outcome (no worse than before this slice), `repair.outcome` is failed with the code, and the refused call is settled as any. That holds also when Meta answers but not with an answer the client can take (no text block, a stop reason this build does not know, another or a Contributor model): failed, `AI_INVALID_OUTPUT` (review round 1; before it, such a call was recorded as a reviewed `invalid` second answer). Item 2 of §5 checks it.
2. **Cost and time of a refused proposal roughly double.** A proposal the server refuses now makes a second call with a larger input (the first prompt, the prior answer and the follow-up; for a photo the image is counted again). Under the USD 20 organization day cap (H-050) fewer refused proposals fit in a day; a Muse Wonder or research repair is reserved at research's output bound. A photo proposal that used to end in about 30 to 140 s can take twice that; each call is still bounded at 300 s, and the page keeps polling and says the person may leave.
3. **A worker stop during the second call repeats both calls** on the job's next attempt (for a job with attempts left; research and slow-model jobs have one attempt and fail). The same as for the first call before; the spend ledger records both.
4. **The second answer can be worse elsewhere.** It is reviewed from the start like the first and the outcome is that review's; a person still approves. The repair cannot make a refused answer pass by itself.
5. **The model reads its own previous answer.** Whatever an image or a label steered into the first answer goes back to the model as its own turn (that text was already the model's output); it is never stored, logged or echoed by the server, and the server's follow-up quotes nothing of it.
6. **Larger audit events**: `audit.MaxFields` 40 → 56 (no database bound; the catalogue still checks every field's shape).
7. **Paths into the candidate.** `/nodes/45` is the candidate's index, which the model has to map to its own changes (the template explains; §5 item 3 would help).
