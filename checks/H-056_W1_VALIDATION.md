# H-056 W1: worker lanes, validation

Slice W1 of [docs/design/H-056_INVESTIGATIONS_ON_EINO.md](../docs/design/H-056_INVESTIGATIONS_ON_EINO.md) §9 ("Worker lanes"). Status: **PROPOSED**. It is built and tested on branch `worktree-wf_62a188fa-787-2` (base `e5ce6ee`). It is not merged, not deployed, and not reviewed. No live AI call was made, and no `.env` value or key was read.

## 1. What changed

- **`internal/config/worker.go`**: `WORKER_LANES` (`config.Lanes`).
  - Unset or `single` (the default) gives one loop. `split` gives two loops.
  - Any other value is `WORKER_LANES (invalid)`. The error never repeats the value. The check is case-sensitive, and spaces are not trimmed.
  - With `split`, `WORKER_ID` may be at most 123 characters. The lanes add `:sim` and `:rest`, and an actor reference is at most 128 characters (D-092).
  - Every problem is still reported together.
- **`cmd/worker/lanes.go`** (new):
  - `plan(mode, id, handlers)` splits the handlers the build made once into lanes.
    - Single: one lane under `WORKER_ID` with every handler, the same map as before.
    - Split: lane `<id>:sim` has `{simulation}`. Lane `<id>:rest` has every other type: `model_proposal`, `analysis`, `import_*`, and any type added later (such as an investigation's).
    - Split refuses a build that has no simulation handler, or nothing else.
  - `runLanes(ctx, log, lanes)` runs each lane's loop in a goroutine and returns only after every loop has returned. If a lane's loop panics outside a handler, or returns while the worker is still running:
    - it is logged at ERROR with `worker_id` = the lane, `code` `WORKER_LANE_PANICKED` or `WORKER_LANE_ENDED`, and for a panic the `panic` and `stack`. As in `internal/worker`, only a runtime error's message or the value's type is kept.
    - The other lanes are stopped, and their attempts are recorded as `WORKER_STOPPED`. runLanes then reports failure.
- **`cmd/worker/main.go`**: `run` builds one `worker.Worker` per lane before the database role check, on the same `workerscope` scope and pool, with the same policy and timing.
  - Single mode still calls the one loop directly. Its log lines are unchanged (`running` with `worker_id` = `WORKER_ID`, then `stopped`).
  - Split mode logs one `running` line per lane, then runs `runLanes`. A lane failure gives the new exit code **4** (`exitLane`), after the other lane has drained.
  - `jobs.Claim`, the lease fence `(locked_by, lease_token)`, the heartbeat, the reaper and the handlers are unchanged. Each lane is a worker in ADR-024's sense, under its own `locked_by`. The handlers are built once and shared by both lanes: one AI client, one spend meter, and the handlers' own audit events keep `WORKER_ID` as actor.
- **`deploy/railway/variables.json`**: the worker gets `WORKER_LANES` = `split`, with an `about` note. The replica count is unchanged.
- **Docs**:
  - `docs/runbooks/deploy.md` §4.3: a `WORKER_LANES` row, and the 123-character note on `WORKER_ID`.
  - `docs/adr/ADR-024-job-queue-and-worker.md`: a sentence marked "PROPOSED addition, not yet reviewed" after "A process runs one job at a time".
  - `.env.example`: the `WORKER_LANES=` line.
- **Regenerated by `make spec-check`**: `checks/deploy-check.json` (the worker has 26 variables, the runbook names 69, `WORKER_LANES` is among the code's variables) and `checks/docs-check.json` (this report).

No migration, schema, OpenAPI or prompt change. Nothing changed in `internal/worker`, `internal/storage/jobs` or any handler.

## 6. PROPOSED (for review or the owner)

- The whole slice is PROPOSED (design §9), as are the ADR-024 addition and `WORKER_LANES=split` in `variables.json`. Nothing is deployed. `variables.json` takes effect only at the next `deploy/railway/deploy.sh` run, with the owner's authorization.
- Exit code 4 for a lane failure. A crash used to exit 2 (Go's panic exit), which collided with `exitNotImplemented`.
- Lane audit actors: the loop's own events (reaps, `job.attempt_failed`) carry the lane's name. The handlers' events (`simulation.*`, `proposal.*`, …) keep `WORKER_ID`, because the handlers are built once. Either lane may reap another type's expired lease, as two processes would today.
- Reading of H-060's superseded §9 (§2 above).

## 7. Risks

- **Memory and CPU in one process.** Design §16: no GOMEMLIMIT or container limit is configured (SIMULATION_SPEC §8). A simulation (up to 300 s, 100,000 active entities) can now run at the same time as an AI job's prompt building, decoding and review in the same process. The AI side is mostly waiting on the network, but the memory headroom on Railway is unknown and not measured here. A simulation slowed by CPU contention counts against its own 300 s wall limit.
- **Database pool.** Both lanes share one pgx pool. With the default size (max(4, CPUs)), the peak is about five short transactions at once: two heartbeats, two handler transactions and the spend meter's. Transactions are short (ADR-024: a heartbeat at most), so the expected effect is brief waits, not lost leases. This is not measured, and the pool size is unchanged.
- **The rest lane still runs its own jobs one at a time.** An AI proposal still waits behind an analysis or another proposal. Only simulations got their own lane, as the design asks.
- **A lane failure stops the whole worker (exit 4).** Railway's restart policy (`ON_FAILURE`, at most 5 retries, in `deploy/railway/worker.railway.json`, unchanged) brings it back; this was not exercised here. A stop drains the two lanes in parallel, so Railway's 30 s `drainingSeconds` covers the slower lane's stop, not the sum of both. During the restart neither lane runs. The other lane's in-flight attempt is recorded as `WORKER_STOPPED`, which uses up an attempt, as at any stop (ADR-024).
- **A panic in a goroutine a handler starts itself** still crashes the process at once, in both modes. Nothing can recover that in-process; the leases expire and the reaper takes the jobs back.
- **Shared scratchpad.** At the start of this slice I overwrote a `pg.sh` that another session agent had left in the session scratchpad, and once tried to start that agent's old `pgdata`. The start failed before recovery (the socket path was too long), so that data directory was not changed. Everything of mine afterwards lived under `w1/`. Another agent's cluster on 127.0.0.1:55471 (pid 3756) was left alone.
