## 2. Findings and decisions taken in the slice

1. **H-061's text and the task differ (recorded, PROPOSED).** H-061 §9 and §18 (approved in H-063) keep "E1's Metered refusing tools" and put tool calling in a separate `einomodel.Planner` over `Client.PlanTurn` (A5, A6). The task asked E1's adapter to implement `ToolCallingChatModel` with tool calls. Both are kept where they agree: proposals and explanations through `Metered` refuse every tool, tool choice and extra message (H-061's invariant), and tool calls are a third call kind (`Call.Turn`) over a separate client method and backend interface, outside `LLMProvider` (H-061's `ToolTurner`, so the ~20 test fakes did not change). The investigator's policy (role `investigator`, exactly one `tool_use`, one attempt, the note's sanitizing, `tool_choice` any, Attribution target `investigation`) is not built: it is A5's and can be a layer over `Client.Turn`. Needs the coordinator's or the owner's confirmation that `Client.Turn` is the path A5 builds on (else the `Call.Turn` path moves to a `Planner` type unchanged), so that no second tool pipeline exists.
2. **No role may use tools yet.** No prompt role or approval names tool calls (A5 adds `investigator`); so the live Meta adapter answers every turn `policy_not_approved` before any I/O, the Claude adapter `tools_unsupported`, and only the fake (development and tests only) answers turns, for any known role. The tests use the `scenario` role as a stand-in.
3. **Eino's own parameter maps are refused.** `schema.NewParamsOneOfByParams` never sets `additionalProperties`, so such a tool is refused (`invalid_request`) by `WithTools`; Eino's `utils.InferTool` (its reflector closes every object) and `NewParamsOneOfByJSONSchema` with closed objects pass. A pointer field inferred by `InferTool` is not nullable: `null` is refused for it (seen while writing the test).
4. **Graph-level callbacks see content.** The adapter's own callbacks carry no messages (tested, inside a graph and standalone), but a handler attached to a compiled graph also gets the graph's own start and end, whose input is the message list and whose output is the answer message. The role graphs (E2+) must attach handlers that record node names and durations only, as the design says (§6.5), or filter on `RunInfo.Type`.
5. **Tool schemas sent to Meta use the output schemas' limits.** `SchemaViolations` (the structured-output limits and keyword list) is applied to each `input_schema`, so keywords such as `minLength` or `minimum` are refused before any I/O by the Meta adapter, although the client itself checks them. Whether tool schemas need a projection (bounds checked by the client only, as for outputs) is for A2/A5 once `schemas/investigator.schema.json` exists (PROPOSED).
6. **`make backend-test` hit Go's default 10-minute test timeout** in `scripts/check-architecture` (E0 recorded 575–589 s for that package; this run had a load average of about 32 from parallel agents). Every other package passed; the package passed alone with `-timeout 45m` (§3). Adding `-timeout` to the `backend-test` target, as `backend-race` has, is PROPOSED, not done.
7. **govulncheck is still NOT RUN** (ADR-031 asked E1 to run it): no binary is installed and the slice had no network but the module proxy.

## 6. Risks

- The tool path has never been sent live; Meta's custom tools, `tool_use` IDs and the multi-turn replay without reasoning blocks are documented, not observed (only the coordinator's one-turn probe of H-060).
- A tool turn's metadata has an empty `schema` and an input hash that is not the prompt's: audit consumers that assume a role's schema (none reads a turn's yet) must take it as it is.
- `contentBlock.ID` is read for every Meta answer now (as raw JSON, so nothing that decoded before fails); a malformed ID only fails a tool turn.
- The fake answers tool turns for every role in development deployments; no code path makes one.
- `scripts/check-architecture`'s test time is at Go's default timeout under load (finding 6).
