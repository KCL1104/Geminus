## 5. Deviations from the design, and why

1. **A cancelled investigation job does not follow to ai_failed.** §11 says a job that "fails or is cancelled while its investigation is running stops the investigation with ai_failed", but §13's stop cancels the queued agent job (step 1) before it stops the investigation as stopped_by_person (step 2): a follow on cancel would end it as ai_failed first and the stop would then meet an ended row. So `follow_investigation_job` follows **failed** only, and `investigation_job_completes_when_ended` (deferred) requires a job that is **completed or cancelled** to end with its investigation in the same transaction. The stop's order is kept, an operator who cancels a job must end the investigation with it, and every end still has its one cause.
2. **The worker's end is checked at once, not deferred.** "Only in the transaction that ends its own investigation job" is checked as "the investigation's job is no longer queued or running" when the worker updates the investigation; a running investigation's job is always queued or running except inside the transaction that ends it, so this is the same rule, and A6's Finish must end the job first (lock, finish call, complete or cancel, then `investigations.End`, then `investigation.end`).
3. **The observation is fenced by the job's lease, not by its token.** The UPDATE of an observation names no token (the row's `lease_token` is the one it was recorded under, and a resumed attempt observes rows an earlier attempt recorded), so the database requires the investigation's job running with an unexpired lease; the exact token fence is the worker's lease-fenced Checkpoint (A6). The design already frames the lease as a stale-attempt fence, not a security boundary.
4. **A duplicate seq is refused by the sequence rule** (55000) before the primary key; two racing inserts of one seq still meet the key (23505).
5. **Beyond §11, chosen here (each is stricter than the design, none weaker):** the API's insert also requires the requester's owner or editor membership in the database; the caps and the objective are stored exactly as H-060's (CHECKs); `intent` is null exactly for an analysis source, `baseline_name` exactly when scenario mode starts its own baseline; a done call names exactly what its tool makes (CHECK) and only what its investigation made (trigger); the error is `{code, path}` with the 15 codes; the deny triggers also cover the ledger's and the drafts' INSERT and DELETE and the proposals' DELETE; outside the scope a person's audit event may not carry the AI's mark (H-056 §8's rule); `RunOwners` refuses `ActingFor`; the index and slot a guard assigns overwrite any value given (the column is the database's, not the caller's).
6. **The arguments' size bound is 9216 bytes of jsonb text**, 8 KiB plus jsonb's own spacing: the decoder refuses more than 8 KiB of the model's JSON (A2), and jsonb prints `": "` and `", "`, so an exact 8 KiB bound could refuse what the decoder accepted.
7. **`constraints.sql` changed** (the design names roles.sql, invariants.sql and scenarios.sql as unchanged, and they are): its D-001 check fails on any ID column it has not classified, by design, so the new columns are classified (`investigation_id` inv_id, `source_analysis_id` and `analysis_id` ana_id, `job_id` job_id, `ai_edit_proposal_id` aip_id, the investigations table inv_id). No assertion was weakened.
8. **Files outside A3's list, each small:** the architecture rule `acting-for-only-in-the-executor` and its probes (A1's file; A3 adds the package, so it adds the fence with it), `provider.LimitInvestigation` (A5's package; one constant), `ai_spend.refuse`'s limit list, the log registry's `investigation_id`, `dbtest.NewModel`, the tenant scope package's `SetActing`.
9. **Test order, as it happened:** the SQL suite, the tenant, jobs, worker and aispend tests were run red before their code (§3); the actingfor tests were written before the package but not run before it; the `storage/investigations` code was written before its Go tests, and the audit refusal case after the catalogue change, so those have no red run; the ids test checks agreement with files that already existed.

## 9. Review round 1

Four Medium findings, all agreed and fixed. Tests came first: the final SQL suite fails 9 times on the 0019 under review, and the new Go test fails on it.

### Findings 1 and 2 (Medium, `migrations/0019_investigations.up.sql`): write_to_draft and `applied` did not read the investigation

**Finding.** In the acting-for scope, `guard_draft_ai_edit` and the ready → `applied` branch of `protect_proposal_content` never read the investigation. So the AI's draft write and `applied` were accepted after a person's stop (when no ledger resolve shared their transaction) and after the deadline (always). The resolve checked `running` but not the deadline, and no test exercised its `running` check. This broke H-061 §8 (usable only while running and before `deadline_at`; the database's own backstops), §12 (every labelled write needs `now() < deadline_at`) and §13 (after a stop the database refuses every labelled write).

**What changed** (0019 is not deployed anywhere, so it is fixed in place; 0001-0018 are untouched):
- `guard_draft_ai_edit`, acting-for branch: after the check that only the edit proposal changes, it reads the investigation FOR SHARE. This is §6.3's draft → investigation step, so the executor's lock order holds. It then requires, in order:
  - status `running` and `now() < deadline_at` (55000, the label guards' message);
  - `app.user_id` = the investigation's requester (42501, beside the existing updater and own-proposal checks);
  - the draft's `base_version_id` = the investigation's base (23514).
  Mode and model are already covered by the existing proposal check (`p.mode = 'edit'`, `p.model_id = NEW.model_id`, labelled with this investigation): the label guard binds a proposal's mode and model to its investigation's, and neither ever changes. A separate clause for them would be an equivalent mutant, so none was added.
