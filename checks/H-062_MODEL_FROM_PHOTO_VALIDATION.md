## 2. Why this IR

The smallest IR that passes the validator and the pack's rules is a source and a sink. It does not work for the photo path: `review.Photo` takes from a photo proposal only numbers the base already has (a resource's capacity may also count the boxes), and the photo prompt says "copy a station's service time"; with no process step a new station has no service time to copy, so every station would be refused, and the prompt answers `needs_input` when the photo shows no station the base lacks. The bare line has exactly the numbers a station of the demo floor plan copies (the SMT step's tri(0.9, 1, 1.4), capacity 1, probability 1) and is the base both ready live runs of H-054 §11 had (`aip_01M68N4VFT45G40D8NK871FNWD`, `aip_01M68N734BWHQYYRERFG98BF87`). Dropping its buffer would be smaller but untested live, and the demo answer's patch (`testdata/photos/electronics-line-demo.proposal.json`) tests `/flows/2/id` = `smt__shipped`; so the template is the bare line, node for node and flow for flow, and a test pins that.

The template's metadata (sent to the vision model within the IR, untrusted, under 2 KiB) differs from the bare line's: `source` is the template's "synthetic, for demonstration", and it has three assumptions (all descriptive, none an instruction). The live runs had the bare line's metadata; see §6.

## 6. PROPOSED and risks

- **Risk: metadata differs from the live-tested base.** The vision model sees the IR with its metadata (untrusted, at most 2 KiB). `photo_start`'s metadata says `template: photo_start`, the template's source and three descriptive assumptions; the bare line of the live runs had none of these. The IR (every node, flow, resource and number) is the same. PROPOSED: one live photo run on a model made from "Start from a photo or floor plan" on the deployment before the demo (about USD 0.07 to 0.3, inside H-050's cap), as H-054 did on the bare line.
- **Risk: a deployment without the photo path.** The option is offered whenever the domain's pack reads photos, as the model page's photo button is; on a deployment whose photo path is off (503 `AI_PROVIDER_NOT_CONFIGURED` / `AI_POLICY_NOT_APPROVED`), the model is created and the model page says the photo was not sent, with the API's refusal. Nothing is lost, but an empty model is left. The page cannot ask beforehand (no capability route); PROPOSED only if the owner wants it.
- **Risk: a lost answer.** If createImageProposal's response is lost (a network problem), the page says the photo was not sent although the server may have stored it; the model page's AI proposals list shows it if it was. The photo's key is not kept across pages, so sending it again from the model page can make a second proposal.
- **Risk: the default model choice.** The new-model page asks with the deployment's photo model (no `model` part), as the model page does by default; Muse Wonder 1.0 is not offered there (H-051).
- **Order of the options.** The photo option is the electronics group's second option, so the arrow keys pass it before the next group (the e2e and unit tests follow); the full template stays the first and the default.
- The fake API's photo route is test-only and does none of the server's work (no re-encoding, no SAM, no review); it is documented as such in `fake/servers.mjs`.
