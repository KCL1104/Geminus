## 2. Findings and decisions taken in the slice

1. **H-057 is absorbed as the unrolled branch (E4's shape).** H-057 merged into the old generator before this slice, and E3 deletes the old body, so the repair had to move with it or there would be two pipelines. It is three nodes over the reviewed `internal/ai/repair` code (`Plan`, `Settle`), not a copy: `Once` is the same two steps around a direct call (the photo path, E5's). What is left of E4: its own tests that the graph already makes true (no second repair, none after a provider failure; `TestExactlyOneRepair`, `TestNodeOrder`, `TestProviderFailures` cover them here) and the two-reservations ledger test through the graph (the generator's H-057 tests already pin the spend through the handler). PROPOSED: E4 reduces to that test.
2. **The order follows the code, not the design's sketch.** The design's §6.4 puts the repair between `review` and `bind`. In the merged H-057 the binding stage's refusal is repairable (the repair follows the whole `check`: review, then binding), so the graph binds before `repair_context`, and `review_2` runs both again. The design's order would have changed which answers are repaired.
3. **Cancellation is seen at node boundaries.** Eino checks the context before each step and ends the run (the graph then returns the client's cancelled error, so `errors.Is(err, context.Canceled)` and `provider.CodeOf(err) == cancelled`). The old body went on to its next step, which saw the cancellation itself (the snapshots' read, the binding stage's `Resolve`, the client's first `ctx.Err()`). What an attempt does is the same: no further call, nothing written, the worker's own state decides (`WORKER_STOPPED` or lease lost; a cancelled attempt's `Finish` never writes). Two observable differences, only while the worker stops or loses the lease: (a) a call the attempt never started is no longer logged as an `ai provider call ended … AI_CANCELLED` line with empty labels (and no `ProviderCall` metric point), and (b) in the live eval, a case whose call answered just before the operator's interrupt is now `failed` `AI_CANCELLED` instead of reviewed, and the run stops at that case rather than the next. No existing test pins either; both are recorded for the reviewer.
4. **A panic is raised again with its own value.** Eino recovers a node's panic into an error whose text holds the panic value and a stack. Each node keeps its own recovered value instead, and `Run` panics with it on the job's goroutine, so the worker's reviewed panic handling applies unchanged (`INTERNAL`, not retried, only a runtime error's message logged). The difference: the stack the worker logs ends at `Run`'s re-raise, not at the original frame. The design's §6.4 asks for "a typed INTERNAL error … its stack never reaches the logs raw"; that would have changed the worker's handling of a bug (a `proposal.attempt_failed` audit row, a different log line), so the behaviour-preserving option was taken (PROPOSED for the reviewer).
5. **The adapter had to hand back the refused answer.** E1's `Metered` returned only the metadata with an error, so through it an `invalid_output` answer could not be repaired (the client hands the answer back only then). `CallError.Prior` is the one addition; `TestARefusedProposalKeepsTheAnswerForItsRepair` pins it against a direct call.
6. **The binaries.** `cmd/worker` (through the generator) and `cmd/ai-eval-live` (through `internal/aievals`) now link Eino: 23 `github.com/cloudwego/eino` packages each by `go list -deps`; `cmd/api`, `cmd/migrate`, `cmd/provision-tenant`: 0. So H-064's one sonic stderr line now appears once at the start of the worker and of the live eval (accepted by the owner; no script parses the worker's stderr as JSON: searched). `internal/api`'s closed-loop tests link Eino through the generator, as E0 anticipated (`no-eino-in-the-api-tests` covers `cmd/api` only).
7. **No telemetry of node names or durations was added.** The design mentions callbacks recording them; that would be new behaviour, and `internal/aigraph` may not import observability. Callbacks are only attached per run in tests. PROPOSED, if wanted: a handler in the generator that records node names and durations only (E1 finding 4: graph-level callbacks see the run's state).
8. **Unreachable mappings are pinned directly.** A review or binding stage that cannot run after an answer, and a follow-up that cannot be built, are the server's own faults that the context builder keeps unreachable (tried: a pool that overlaps the base is refused by `aicontext` first). `TestWhatEndsAnAttempt` pins `ended` for every typed error against the old body's return paths (21 cases).
9. **Two E0 architecture probes no longer loaded once the graph was real (fixed in their fixtures; for the reviewer).** The first `scripts/check-architecture` run alone failed `TestEinoPlacement`'s "the engine links Eino through a role graph" and "a pack links Eino through a role graph" with `internal/ai/repair [internal/ai/aicontext.test]: import cycle not allowed in test`. E0 wrote these probes while no role graph existed ("each probe adds them through a go build overlay"): the overlay made `internal/aigraph/proposal` a package importing only Eino, and the engine or the electronics pack import it. The real graph imports the context builder, and `internal/ai/aicontext`'s own (internal) tests import the electronics pack and the engine, so the probe tree is now an import cycle that Go refuses before the checker reads any rule (a real placement like this could not be built either). The fix restores the probe's premise and nothing else: the overlay also stands the probe's synthetic graph in for the real `proposal.go`; each case still requires `no-eino-in-kernel-packs-transport` on the same package, ending at `github.com/cloudwego/eino/compose`, via `./internal/aigraph/proposal`. The graph's own test closure reaches neither the pack nor the engine (`go list -deps -test`), so it adds no cycle of its own. E2 and E5 will meet the same when their graphs become real (the probe "the context builder links the photo graph" uses `internal/aigraph/photo`).
