## 2. Findings and decisions taken in the slice (PROPOSED)

1. **No `internal/ai/photostep`; the graph takes the steps as an interface.** The design (§6.4) moves the node bodies into a new pure `internal/ai/photostep` that the graph imports, and makes `photopipeline` a facade of type aliases. With that layout the graph depends on `aicontext` (through the steps), and E0's existing probe "the context builder links the photo graph" (`TestEinoPlacement`, an overlay in which `aicontext` imports `internal/aigraph/photo`) becomes an import cycle. The test then fails to load: `github.com/kcl1104/geminus/internal/aigraph/photo (/ cgo=): import cycle not allowed in test`. I checked this by adding a temporary `import _ ".../internal/ai/aicontext"` to the graph package and removing it afterwards. Editing E0's test was not allowed. So `internal/aigraph/photo` depends only on Eino, `einomodel` and `provider`, and it takes the bodies as `photo.Steps`. The bodies stay in `photopipeline` (the reviewed code, where it was), so no aliases and no new package are needed. The architecture rules are unchanged and pass (104 packages, 40 rules).
2. **Eino ends a run between nodes when its context is done.** `compose`'s runner checks `ctx.Done()` before every step (`graph_run.go`: "context has been canceled"). The steps would then no longer meet a cancellation where the pipeline did: the client's cancelled call with its observer line and settlement, and `repair.Prepare` refusing the repair once the attempt is stopping. So `Run` invokes the graph on `context.WithoutCancel(ctx)`, and each node hands its step a context (`within`) with Eino's values over the caller's, and the caller's deadline, cancellation and `context.Cause`. `Value` asks the node's context first, then the caller's. The node's context is beneath `WithoutCancel`, so only the caller's answers for its cancel context. That makes a context a client derives for each attempt end at once with the caller's, as before. A first version that asked only the node's context propagated cancellation through a goroutine instead: three parity cases failed (a call made right after the cancellation still went out), and `TestTheCallersContext` now pins it.
   - **The pre-E5 tests do not see this.** With the graph run on the caller's context directly (the naive refactor), seven cancellation cases of the new parity test change behaviour. Yet every pre-E5 test still passes: photopipeline's three, the generator's (`photo_test.go`, `photo_repair_test.go`, `boxes_test.go`, …) and the live eval's (§3, mutation rows). E1's `TestErrorsThroughAGraph` comment "Cancellation reaches the client" holds only for its `errors.Is(err, context.Canceled)`: in a graph, Eino's own check ends the run before the client is asked. **E2 and E3 meet the same trap** (PROPOSED: the same approach, or a parity test that proves the difference does not matter there).
3. **A panic in a step is re-panicked by `Run` with the same value.** The design says "a recovered panic becomes a typed INTERNAL error". But Eino's recovered panic is an error (`internal/safe.panicErr`) whose `Error()` holds the stack. `generatePhoto` would pass it to the worker as an ordinary error (`providerFailure` returns it unchanged), and the worker retries those as INTERNAL. Before, the panic reached the worker's `handle`, which records it as `panicked` and never retries it (a bug). To keep that, each node recovers its step's panic before Eino does, the run ends, and `Run` panics again with the value. The panic's value, type and message are the same (parity test cases). The stack the worker logs now starts at `photo.Run` rather than in the step, so the step's own frames are lost.
4. **`einomodel.CallError` gains `Prior`.** On `invalid_output`, the client returns `ProposalResult{Metadata, Prior}` with the error, and the photo path's repair follows that answer (H-057: "refused by the client for what it says"). E1's adapter dropped it. The field is added to the error, and the adapter's own callbacks get a copy without it (tested; a mutant that hands them the full error fails). A handler on a compiled graph still gets the node's returned error (E1 finding 4). The photo graph returns no error from a node and attaches no handler, so no handler sees it. E3 needs the same field for the text path; this is a merge point with E3.
5. **`repair.Once` split into `Prepare` and `Settle`.** The photo graph makes the second call through `Metered`, so the repair's rules are reached as two pure steps. `Once` is now their composition over the client, used unchanged by the generator's text path, so one implementation of the rules remains. `TestOnceIsPrepareCallAndSettle` shows the three steps equal `Once` in eight cases.
6. **First production binaries linking Eino.** `cmd/worker` and `cmd/ai-eval-live` link 23 Eino packages each (`go list -deps`), so H-064's sonic line is printed once at their start (accepted). `cmd/api`, `cmd/migrate` and `cmd/provision-tenant` link none. `go.mod` is unchanged; `go mod tidy -diff` would only add dependencies' test-module checksums to `go.sum`, as E1 recorded (not applied).
7. **E6's seal (design §6.6)** would flag `repair.Once` and `internal/proposals/generator` (direct `GenerateModelProposal` calls). Those belong to the text path (E3, E4). The photo path makes no direct call any more.
8. `make ai-eval` does not exercise the photo path (its corpus is context, review and analyst). The photo path's parity is the new parity test, and the generator's and the live eval's photo tests, all in `make backend-test`.

## 5. PROPOSED (for the coordinator or the owner)

- Findings 1–3: the graph's steps as an interface (no `photostep`), the graph on `WithoutCancel` with the caller's cancellation in each step, and a step's panic re-panicked rather than typed. Each departs from the design's text in order to keep H-059's "no behaviour change" and E0's tests.
- Finding 2 for E2 and E3: their graphs need the same context handling, or a parity test that shows the difference does not matter for them.
- Finding 4: `CallError.Prior`, shared with E3.
- Finding 5: `repair.Prepare` and `repair.Settle` as the repair's steps for every graph (E4 can use them for the text path's branch).

## 6. Risks

- **Merge contention with E2/E3/E4.** `einomodel/metered.go` (`CallError.Prior`) and `internal/ai/repair/repair.go` are likely touched by E3/E4 too. E0's shared rule and probe files are not touched here.
- The parity test's reference (`before`) is a copy of the pipeline as it was, in a test file. It is no production path, but E6's AST seal must skip test files (it does by design: "non-test code"), or the copy has to go once E5 has been reviewed.
- The `within` context type: anything that type-asserts a context's concrete type, or relies on `context.AfterFunc` being cheap, sees a wrapper. Nothing in the photo path does today: the client derives children with `WithTimeout`, which now attach to the caller's cancel context directly (tested).
- A panic's logged stack starts at `photo.Run` (finding 3).
- The worker and the live eval now print the sonic line at start (H-064 accepted it). A log pipeline that parses every line as JSON sees it.
- The fake vision model does not exercise the live adapters' streaming, timeouts or the provider's real refusals through the graph. Those go through the same client calls (E1's goldens), but no live call through the graph has been made.
