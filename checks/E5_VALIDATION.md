## 2. Findings and decisions taken in the slice (PROPOSED)

1. **No `internal/ai/photostep`; the graph takes the steps as an interface.** The design (§6.4) moves the node bodies into a new pure `internal/ai/photostep` that the graph imports, and makes `photopipeline` a facade of type aliases. With that layout the graph depends on `aicontext` (through the steps), and E0's existing probe "the context builder links the photo graph" (`TestEinoPlacement`, an overlay in which `aicontext` imports `internal/aigraph/photo`) becomes an import cycle. The test then fails to load: `github.com/kcl1104/geminus/internal/aigraph/photo (/ cgo=): import cycle not allowed in test`. I checked this by adding a temporary `import _ ".../internal/ai/aicontext"` to the graph package and removing it afterwards. Editing E0's test was not allowed. So `internal/aigraph/photo` depends only on Eino, `einomodel` and `provider`, and it takes the bodies as `photo.Steps`. The bodies stay in `photopipeline` (the reviewed code, where it was), so no aliases and no new package are needed. The architecture rules are unchanged and pass (104 packages, 40 rules).
2. **Eino ends a run between nodes when its context is done.** `compose`'s runner checks `ctx.Done()` before every step (`graph_run.go`: "context has been canceled"). The steps would then no longer meet a cancellation where the pipeline did: the client's cancelled call with its observer line and settlement, and `repair.Prepare` refusing the repair once the attempt is stopping. So `Run` invokes the graph on `context.WithoutCancel(ctx)`, and each node hands its step a context (`within`) with Eino's values over the caller's, and the caller's deadline, cancellation and `context.Cause`. `Value` asks the node's context first, then the caller's. The node's context is beneath `WithoutCancel`, so only the caller's answers for its cancel context. That makes a context a client derives for each attempt end at once with the caller's, as before. A first version that asked only the node's context propagated cancellation through a goroutine instead: three parity cases failed (a call made right after the cancellation still went out), and `TestTheCallersContext` now pins it.
   - **The pre-E5 tests do not see this.** With the graph run on the caller's context directly (the naive refactor), seven cancellation cases of the new parity test change behaviour. Yet every pre-E5 test still passes: photopipeline's three, the generator's (`photo_test.go`, `photo_repair_test.go`, `boxes_test.go`, …) and the live eval's (§3, mutation rows). E1's `TestErrorsThroughAGraph` comment "Cancellation reaches the client" holds only for its `errors.Is(err, context.Canceled)`: in a graph, Eino's own check ends the run before the client is asked. **E2 and E3 meet the same trap** (PROPOSED: the same approach, or a parity test that proves the difference does not matter there).
3. **A panic in a step is re-panicked by `Run` with the same value.** The design says "a recovered panic becomes a typed INTERNAL error". But Eino's recovered panic is an error (`internal/safe.panicErr`) whose `Error()` holds the stack. `generatePhoto` would pass it to the worker as an ordinary error (`providerFailure` returns it unchanged), and the worker retries those as INTERNAL. Before, the panic reached the worker's `handle`, which records it as `panicked` and never retries it (a bug). To keep that, each node recovers its step's panic before Eino does, the run ends, and `Run` panics again with the value. The panic's value, type and message are the same (parity test cases). The stack the worker logs now starts at `photo.Run` rather than in the step, so the step's own frames are lost. (Fixed in review round 1: the steps run on the caller's goroutine, and the stack shows the step again.)
4. **`einomodel.CallError` gains `Prior`.** On `invalid_output`, the client returns `ProposalResult{Metadata, Prior}` with the error, and the photo path's repair follows that answer (H-057: "refused by the client for what it says"). E1's adapter dropped it. The field is added to the error, and the adapter's own callbacks get a copy without it (tested; a mutant that hands them the full error fails). A handler on a compiled graph still gets the node's returned error (E1 finding 4). The photo graph returns no error from a node and attaches no handler, so no handler sees it. E3 needs the same field for the text path; this is a merge point with E3.
5. **`repair.Once` split into `Prepare` and `Settle`.** The photo graph makes the second call through `Metered`, so the repair's rules are reached as two pure steps. `Once` is now their composition over the client, used unchanged by the generator's text path, so one implementation of the rules remains. `TestOnceIsPrepareCallAndSettle` shows the three steps equal `Once` in eight cases. (Review round 1: that compared the code with itself; the test now holds both to `Once` as it was, in 13 cases.)
6. **First production binaries linking Eino.** `cmd/worker` and `cmd/ai-eval-live` link 23 Eino packages each (`go list -deps`), so H-064's sonic line is printed once at their start (accepted). `cmd/api`, `cmd/migrate` and `cmd/provision-tenant` link none. `go.mod` is unchanged; `go mod tidy -diff` would only add dependencies' test-module checksums to `go.sum`, as E1 recorded (not applied).
7. **E6's seal (design §6.6)** would flag `repair.Once` and `internal/proposals/generator` (direct `GenerateModelProposal` calls). Those belong to the text path (E3, E4). The photo path makes no direct call any more.
8. `make ai-eval` does not exercise the photo path (its corpus is context, review and analyst). The photo path's parity is the new parity test, and the generator's and the live eval's photo tests, all in `make backend-test`.

### M1: no test showed that the vision calls go through `einomodel.Metered`

- **Problem.** `TestTheCallsAreTheClients` compares results, errors and requests, and those are the same when the call skips the adapter. The reviewer's mutant returned `vision.GenerateModelProposal(ctx, *pc)` before `einomodel.New` in `photo.go`'s `call`, and every test of `./internal/aigraph/...`, `./internal/ai/photopipeline/`, `./internal/proposals/generator/` and `./internal/aievals/` still passed.
- **Fix** (tests only, `internal/aigraph/photo/metered_test.go`). Two checks:
  - `TestNoCallAroundTheMeteredChatModel` brings design §6.6's E6 seal forward for this package. It is a go/ast test: no non-test file of `internal/aigraph/photo` may name `GenerateModelProposal`, `AnalyzeSimulation`, `ProposeImportMapping` or `Turn` (any selector, so a method value counts too). The parse must find at least one file, one `einomodel.New` and one `Generate`, so the check cannot pass with nothing to check.
  - `TestTheCallsGoThroughTheMeteredChatModel` runs the graph with a handler attached for this run only (`callbacks.InitCallbacks` on the caller's context: "callbacks attached per run", design §6.4). Each client call must carry the mark the adapter's `OnStart` put on its context, so the call is made inside the adapter's call. The test also wants exactly one `GeminusMetered` start and end per call (start and error when the calls fail).
- **The Low the reviewer cross-refers to.** The Medium's second option says it is "valid only while the graph still inherits the caller's handlers (see the Low below)". That Low was not in this round's list, so nothing was changed for it. If the graph ever stops passing the caller's handlers on, the callbacks test has to attach its handler some other way, and the source seal still holds.

### L1: the repair parity tests compared the new code with itself

- **Problem.** After E5, `Once` is exactly `Prepare`, the call and `Settle`. So `TestOnceIsPrepareCallAndSettle` compared the code with itself, and the photo parity reference `before` called the post-E5 `repair.Once`. The reviewer's mutant dropped `&& res.Prior.Present()` from `Settle`'s invalid_output branch. Only the pre-E5 `TestASecondCallRefusedWithoutAnAnswerIsAFailedRepair` caught it, and neither new parity test did. My report's finding 5 also claimed more than the test showed.

### L2: a step's panic lost the frames that locate it in the worker's log

- **Problem.** The node recovered the panic and `Run` raised it again, so the stack the worker takes at its recover (`internal/worker` `handle`, logged as `stack` in "job handler panicked") started at `photo.Run`. The panic's value, type, message and no-retry handling were unchanged.
- **Fix** (`internal/aigraph/photo/photo.go`). No step runs inside Eino any more, so nothing recovers its panic on the way:
  - Each node hands its body to `Run` over a channel and waits.
  - `Run` runs the body on the caller's goroutine (the one the step ran on before E5), while Eino's `Invoke` runs on a goroutine of its own, which only orders the nodes.
  - A body that panics tells its node it did not return. The run ends there (`f.stopped`, as `f.panicked` did), and `Run`'s deferred wait lets the panic go on only once Eino's run has ended. So no goroutine of the run outlives `Run`.
  - A panic of Eino's own outside every body (none has been seen) is passed to the caller with the same value.
  - The worker is unchanged, and so are the panic's value and type.
  - The stack now reads, from the top: `panic`, the step (`(*steps).rec`, `(*steps).Repaired` in the probe), the node's closure, `body.exec`, `photo.Run`, the caller.
- **Side effect.** A step that calls `runtime.Goexit` (a test's `t.FailNow`) now ends its goroutine without hanging the run, because the node is told as for a panic.
- **Tests (written first).**
  - `TestAPanicKeepsItsStack` (`photo_test.go`) recovers each of the eight steps' panics, and the vision client's, the way the worker does, then reads the stack's first non-runtime frame below `panic(`. Before the fix it was `photo.Run` in all nine. After the fix it is the step's frame and the step's own method.
  - The photo parity test now compares that frame with `before`'s in its three panic cases: the segmenter, the vision backend, and the binding stage on the repair (the reviewer's scenario).
  - `TestAPanicWaitsForTheRunToEnd` slows the graph's own end callback by 50 ms. When the caller recovers, the run must have ended exactly once.
