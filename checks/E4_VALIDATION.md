## 2. Findings and decisions taken in the slice

1. **E4's branch was already built (E3 absorbed it).** H-057 merged into the old generator before E3, and E3 deleted the old body, so E3 moved the repair onto the graph with it (its finding 1: "E4 reduces to a ledger test"). E4 therefore adds E4's own tests and the compile hook for the shape test, and changes no behaviour. The slice's "port it with its tests unchanged" holds: every H-057 test (`internal/ai/repair`, `internal/proposals/generator` `repair_test.go`, `repair_loop_test.go`, `photo_repair_test.go`) passes with its expectations unchanged.
2. **No `classify_2` node (PROPOSED to keep as built).** The design's sketch has four repair nodes; the graph has three, because `review_2` is `repair.Settle`, which classifies the second call's end (the attempt stopping, a refusal for what the answer says, any other failure) before it reviews and binds, exactly as `repair.Once` does around a direct call (the photo path). A `classify_2` node of its own would split the reviewed `Settle` and add a Lambda node to every repaired run, which changes the node order E3's `TestNodeOrder` pins (`... repair_context, generate_2, review_2`); the task forbids editing an existing test's expectations. The behaviour the sketch asks for is pinned instead: `TestNoThirdCall` (every way a second answer can be refused ends there), `TestTheRepairOfResearchAndASlowModel` (a failed repair keeps the first outcome), E3's `TestExactlyOneRepair`.
3. **The order is review → bind → repair, not the sketch's "review_2 → bind or END".** As E3 found (its finding 2), the merged H-057 repairs a ready candidate the binding stage refuses, so the binding stage runs before `repair_context` and again inside `review_2`. Kept: the sketch's order would change which answers are repaired.
4. **H-057's row excludes neither research nor a slow model.** The slice asked for "no repair where H-057's rule excludes it (research, slow model)" pending the row. The row says "every proposal path (edit, scenario, research mode without a second search, photo without a second SAM call)" and names no model, and H-065 gives a slow model its own bounds "on every path ... and its H-057 repair". So the negative test became a positive one: research is repaired without a second search (no web search on the repair's request, the research output bound and the budget's retries, no search reserved, the first call's sources kept), Muse Wonder under its own bounds (both calls at 128,000 output tokens and 900 s, reserved at its price), and a failed repair of either is the first outcome, not a final job failure (`TestTheRepairOfResearchAndASlowModel`).
5. **"Reserved and settled like the first" is pinned as parity with a direct repair.** `TestTheRepairIsMeteredAsADirectRepair` runs the graph and, on a fresh client and ledger, the direct path (`GenerateModelProposal`, the review, `repair.Once`): the backend's requests (reservation IDs included), the ledger's charges and settlements, both calls' metadata (but latency) and the repair's record are equal, for an edit, a scenario, research, Muse Wonder and Muse Wonder with research. The first run of this test failed on a test-side fault: the fixtures are JSON of a Go map, which `encoding/json/v2` orders anew on every marshal, so the two sides' answers differed in member order; the answers are now marshalled once for both (§4).
6. **The shape test reads Eino's `GraphInfo`.** `compose.WithGraphCompileCallbacks` reports the compiled graph's edges and branches; `TestOneRepairByConstruction` walks every way from START to END (it fails on a cycle), and requires the graph's nodes to be exactly the eleven known ones (no way repeats a node, so the model is asked at most twice on each), `generate_2` only after `generate` and directly after `repair_context`, only `END` after `review_2`, and both a way with the repair and one without. This needed `compile` (§1); `New`'s behaviour is the same.
7. **No `repair.go` (the slice list's file; PROPOSED to keep the branch in `proposal.go`).** The branch's three node bodies were first moved, unchanged, to a new `internal/aigraph/proposal/repair.go`. `make backend-test` then failed in `scripts/check-architecture`: `TestEinoPlacement`'s "a pack links Eino through a role graph" and "the engine links Eino through a role graph" with `internal/ai/repair [internal/ai/aicontext.test]: import cycle not allowed in test`. These are E0's probes whose fixtures E3 adapted (E3's finding 9): the overlay stands a synthetic graph in for `proposal.go` only, so a second non-test file in the package that imports `internal/ai/repair` and the context builder brings the cycle back. Making the move work needs another fixture edit to an existing test (the overlay standing in for `repair.go` too), which this task forbids, so the move was undone (the bodies put back byte for byte where they were) and the probes pass again (§4). If the reviewer wants the file, the probe's overlay must name it as well (a fixture-only change, as E3's). E2's and E5's graphs meet the same constraint: their probes stand in for one file each.

## 7. Risks

- `TestOneRepairByConstruction` reads `GraphInfo`, Eino's introspection struct (v0.9.21: `Edges`, `DataEdges`, `Branches[...].GetEndNode()`). A later Eino that reports branches or edges differently would fail the test loudly (a node leading nowhere, or no way with the repair), not pass it silently.
- E0's placement probes stand a synthetic graph in for one file of each role graph package: a second non-test file that imports the context builder brings back the import cycle of E3's finding 9 (finding 7). E2 and E5 should keep each graph in one file or extend the probe's overlay.
- E5 (the photo graph) will call `repair.Plan` and `Settle` too, or keep `Once`; the photo path's repair is untouched here (`photo_repair_test.go` unchanged and passing).
- The parity test compares against `repair.Once` over the same client, so a fault shared by both paths (in the client or in `internal/ai/repair`) is not visible to it; the provider's, the repair package's and the generator's own tests cover those, and the research and slow-model test checks the requests' bounds and reservations against fixed expectations (M4, M5).
